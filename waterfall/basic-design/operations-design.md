# 運用・移行設計レシピ — ウォーターフォール基本設計

> **レイヤー**: 第2層レシピ（手法別具体指針）
> **原則参照**: [`../../principles/granularity-axis.md`](../../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。
> **責務対照**: [`../../principles/responsibility-map.md`](../../principles/responsibility-map.md) の**「基本設計：運用/移行設計」行**を参照。

---

## 目的とスコープ

このレシピが対象とする**運用・移行設計の工程範囲**を明確にする。運用・移行設計は、運用フロー（監視・バックアップ・障害対応の**方針**）と移行**方針**（切替戦略・ロールバック条件）を**方針レベル**で確定する工程である。運用側（どう運用し続けるか）と移行側（どう新システムへ切り替えるか）の両面を、外から見た意思決定の基準として固める。

これに対し、具体的な運用作業の段取り書・移行を実行するための実装コード・インフラ構成の詳細値は「どう実行するか（How）」であり、詳細設計／後続工程の対象である。本レシピではこれらの実行手段を扱わない。

| 工程 | 本レシピでの扱い |
|---|---|
| **基本設計（運用・移行設計）** | 対象。監視・バックアップ・障害対応の方針、移行方式・切替戦略・ロールバック条件をここで確定する |
| **詳細設計／構築（後続工程）** | 対象外。具体的な運用作業の段取り書・移行を実行する実装コード・インフラ構成の詳細値は実行手段に属し、詳細設計レシピ [`../detailed-design/`](../detailed-design/) ／後続工程の対象である |

責務対照表（responsibility-map.md の「基本設計：運用/移行設計」行）は「運用フロー（監視・バックアップ・障害対応方針）・移行方針・切替戦略・ロールバック条件」を含む範囲、「詳細な段取り書・移行を実行する実装コード・インフラ構成詳細」を含まない範囲と定める。運用方針は詳細設計へ、移行条件は受入テスト設計へ渡す。本レシピはこの境界を各節に具体化する。

**境界を越えた記述の扱い**（詳細は末尾の越境節）:
- 運用作業の段取り書・移行を実行する実装コード・インフラ構成の詳細値が混入していたら、詳細設計 [`../detailed-design/`](../detailed-design/) ／後続工程へ移す（P2: 運用・移行設計は方針・条件までに限る）。

## 運用方針

システムを稼働させ続けるための運用フローを**方針レベル**で確定する。監視・バックアップ・障害対応の3観点で、「何を・どの方針で行うか」を外から見た意思決定の基準として固める。

**含む**: 監視（何をどの方針で監視するか）・バックアップ（取得方針・世代方針・復旧目標 RPO/RTO の方針）・障害対応（検知から対応への流れの方針・エスカレーションの方針）。

**含まない**: 具体的な運用作業の段取り書・監視ツールの設定値・バックアップ取得コマンドの具体記述。
> これらは運用の実行手段であり、外から見た運用の意思決定基準ではない。詳細設計／後続工程へ委ねる（P2: 運用・移行設計は方針までに留める）。

**該当の薄い項目の扱い**: 監視・バックアップ・障害対応のうち該当の薄いもの（例: ステートレスな表示専用システムにおけるバックアップ）は、空節にせず「該当なし＋理由」を明記する。空節は「検討漏れ」と「対象外」を区別できないため禁止する（external-design / nonfunctional-design と同方針・gold plating 回避）。

### 例（最小限・テンプレート用）

```
監視:
  方針 : 稼働・リソース・主要業務トランザクションの成否を常時監視する
  対象 : サービス死活、CPU/メモリ使用率、受注登録の失敗率

バックアップ:
  方針 : 日次フルバックアップ＋世代管理
  世代 : 直近7世代を保持
  復旧目標: RPO 24 時間 / RTO 4 時間（方針値）

障害対応:
  方針 : 監視アラート検知 → 一次切り分け → エスカレーションの流れで対応する
  エスカレーション: 一次対応で復旧不能なら30分以内に運用責任者へ上申する
```

## 移行方針

旧システム（または旧状態）から新システムへ切り替えるための移行を**方針レベル**で確定する。移行方式・切替戦略・ロールバック条件・移行対象データの範囲方針を、外から見た意思決定の基準として固める。

**含む**: 移行方式（一括／段階）・切替戦略（カットオーバー／並行稼働）・ロールバック条件（どの観測可能な条件で旧へ戻すか）・移行対象データの範囲方針。

**含まない**: 移行を実行するためのデータ変換クエリ本文・移行作業の段取り書のステップ詳細・移行を回す実装コード。
> これらは移行の実行手段であり、外から見た移行の意思決定基準ではない。詳細設計／後続工程へ委ねる（P2: 運用・移行設計は方針・条件までに留める）。

**該当の薄い項目の扱い**: 移行が発生しない場合（例: 新規構築で移行元が存在しない）は、空節にせず「該当なし＋理由」を明記する。検討漏れと対象外を区別するためである。

### 例（最小限・テンプレート用）

```
移行方式 : 段階移行（マスタ → トランザクションの順で投入）
切替戦略 : 並行稼働を2週間設けた後にカットオーバー
ロールバック条件:
  - カットオーバー後24時間以内に受注登録の失敗率が5%を超えたら旧へ戻す
  - 並行稼働期間中、新旧の受注件数差が観測可能な許容範囲を超えたら切替を延期する
移行対象データの範囲方針:
  - 過去3年分の受注・顧客マスタを移行対象とする（それ以前はアーカイブ＝移行対象外）
```

## トレーサビリティ

各運用方針・移行方針を **要件 ID／NFR ID** に紐付ける。孤立方針（要件に出どころのない運用・移行の取り決め）を作らない。
> P4: 設計は要件へ全要素トレース可能でなければならない。孤立した方針はスコープクリープの検出点になる。

**表の書き方**:
- 「対応要件 ID／NFR ID」列に、SRS（`waterfall/requirements/srs.md`）の機能要件 ID ／ `NFR-{カテゴリ略}-NN`（可用性・運用保守性・移行性等）を記載する。
- 1つの方針が複数の上位要求に対応する場合はカンマ区切りで列挙する。
- 運用方針には運用保守性・可用性系の NFR、移行方針には移行性系の NFR を対応づけるのが自然である（その意味的妥当性は rubric が見る）。

| 本書の方針 | 対応要件 ID／NFR ID | 備考 |
|---|---|---|
| 監視（死活・リソース・業務成否） | NFR-OPS-01 | 運用保守性 |
| バックアップ RPO 24h/RTO 4h | NFR-AVAIL-02 | 復旧目標 |
| 段階移行＋並行稼働切替 | NFR-MIG-01 | 移行性 |
| ロールバック条件（失敗率5%超） | NFR-MIG-02 | 切替判定 |

**逸脱の判定基準**:
- 「対応要件 ID／NFR ID」が空の方針が存在する → 孤立方針（スコープクリープ候補）。要件への追記または方針の削除を検討する。
- 運用方針に移行性 NFR、移行方針に無関係な機能要件 ID が付くような意味的ミスマッチがある → トレーサビリティの質の問題（機械では空セルのみ検出・意味的妥当性は rubric が見る）。
- 要件に存在しない運用・移行目標を本書が立てている → 要件定義工程へのフィードバックが必要。

## 境界を越えた記述の扱い

運用・移行設計に以下の**下流実行先取りマーカー**が現れたら、外から見た方針・条件ではなく実行手段の先取り＝詳細設計／後続工程への混入である。該当工程へ移送する。これらの厳密な語はフェンスブロック内に列挙する（語彙チェッカーはフェンス内を検査対象外とする。地の文では言い換える）。

```
運用・移行設計に書いてはいけない下流実行先取りマーカー（出たら詳細設計／後続工程へ移送）:

  手順書          → 詳細設計／後続工程（具体的な作業の段取り＝実行手段）へ
  移行スクリプト  → 詳細設計／後続工程（移行を実行する実装コード）へ
```

- **具体的な作業の段取り書**（運用・移行の作業を逐次実行するための成果物）が混入したら → 詳細設計／後続工程へ（P2: 運用・移行設計は方針までに限る）。
- **移行を実行する実装コード**（移行を回す実装・データ変換のコード本体）が混入したら → 詳細設計／後続工程へ（P2: 本書は移行の方針・条件までに留める）。
- **インフラ構成の詳細値**（サーバ台数・スペック・ネットワーク設定の具体値）が混入したら → 詳細設計／後続工程へ（P5: 厳密値は下流工程のマーカーである）。

> **機械判定の限界（P2 訂正・cycle-4 srs / cycle-7 external-design / cycle-8 architecture-design / cycle-9 nonfunctional-design と同方針）**: 技術スタック名・製品名・プロトコル名は運用・移行設計でも**正当な記述**である（監視対象の製品名・移行元/先の環境記述として現れる）。これらを機械 vocab で一律に弾くと正当な記述を誤爆する。**特に `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する**（cycle-8 で実機検出）。よって技術名・`SQL` は機械 vocab の禁止語に入れず、`rubric/operations-design.md` の質的観点で判定する。
>
> また**「手順」単独**のような汎用語も、部分一致では正当な文脈（「運用手順の方針」「移行手順の方針」等の方針記述）と区別できず誤爆するため、機械 vocab では弾かない。機械 vocab が禁止するのは技術名・汎用語と誤爆しにくい下流実行先取りマーカー（前掲フェンス内の2語＝具体的な成果物名・実装名）に限り、移行を実行するデータ変換クエリ本文の全文混入・「方針」でなく逐次手順の粒度での記述は rubric の質的観点で見る。

# 外部設計レシピ — ウォーターフォール基本設計

> **レイヤー**: 第2層レシピ（手法別具体指針）
> **原則参照**: [`../../principles/granularity-axis.md`](../../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。
> **責務対照**: [`../../principles/responsibility-map.md`](../../principles/responsibility-map.md) の**「基本設計：外部設計」行**を参照。

---

## 目的とスコープ

このレシピが対象とする**外部設計の工程範囲**を明確にする。外部設計は**外部から観測可能な仕様**（画面・帳票・外部 IF）に限る。クラス構造・内部処理フロー・アルゴリズム・DB 物理設計・DB 操作文などの**内部実装**は外部から観測できないため、外部設計の対象ではなく詳細設計の対象である。本レシピでは内部実装を扱わない。

| 工程 | 本レシピでの扱い |
|---|---|
| **基本設計（外部設計）** | 対象。画面（レイアウト・入出力項目・遷移）・帳票・外部公開 IF/API 仕様・CRUD 図・外部から見たシステム構成をここで確定する |
| **詳細設計（内部）** | 対象外。内部構造図・内部処理フロー図・処理アルゴリズム・DB 物理設計・DB 操作文・エラーハンドリング詳細・UI コンポーネント内部仕様は内部実装に属し、詳細設計レシピ [`../detailed-design/`](../detailed-design/) で確定する |

責務対照表（responsibility-map.md の「基本設計：外部設計」行）は「システム構成図・画面設計・帳票・外部 IF/API 仕様・CRUD 図」を含む範囲、内部構造図・内部処理フロー図・処理アルゴリズム詳細・DB 物理設計・DB 操作文を含まない範囲と定める。外部仕様は詳細設計へ、IF 契約は結合テスト設計へ渡す。本レシピはこの境界を各節に具体化する。

**境界を越えた記述の扱い**:
- 外部から観測できない内部実装（内部構造図・内部処理フロー図・DB 操作文・物理 index）が混入していたら、詳細設計レシピ [`../detailed-design/`](../detailed-design/) へ移す（P2: 外部設計は外部観測仕様に限る）。
- ピクセル・hex カラーの厳密値が画面設計に混入していたら、詳細設計の UI コンポーネント仕様へ移す（P5: 厳密値は詳細設計工程のマーカーである）。

## 画面設計

**含む**: 画面レイアウト（配置・領域構成）・入出力項目（項目名・必須/任意・入力種別）・画面遷移図（画面間の遷移とトリガ）・帳票レイアウト（出力項目・集計単位）。

**含まない**: UI コンポーネントの内部仕様・イベントハンドラの実装・ピクセル単位の厳密値や hex カラー指定。
> これらは外部から観測する「画面の振る舞いと項目」ではなく内部の作り込みであるため、詳細設計の UI コンポーネント仕様へ委ねる（P5: 厳密値は詳細設計工程のマーカーである）。

**該当なし（API 専用システム等）の扱い**: 画面を持たないシステム（バックエンド API 専用・バッチ専用等）では、この節を空にせず「該当なし」と明記し、なぜ画面を持たないか（例: クライアントは別チームが開発する外部 IF 経由のみ）を1行添える。空節は「検討漏れ」と「対象外」を区別できないため禁止する。

### 例（最小限・テンプレート用）

```
画面: 受注登録画面

レイアウト:
  ヘッダ領域（顧客選択・受注日）
  明細領域（商品・数量・単価の繰り返し行）
  フッタ領域（合計金額・登録ボタン・キャンセルボタン）

入出力項目:
  顧客       入力（必須・顧客マスタから選択）
  受注日     入力（必須・日付）
  商品       入力（必須・商品マスタから選択）
  数量       入力（必須・1以上の整数）
  合計金額   出力（自動計算・編集不可）

画面遷移:
  受注一覧画面 ──[新規ボタン]──> 受注登録画面
  受注登録画面 ──[登録成功]────> 受注一覧画面（完了メッセージ表示）
  受注登録画面 ──[キャンセル]──> 受注一覧画面

帳票: 受注控え（受注単位・明細行＋合計を印字）
```

## 外部インターフェース

**含む**: 外部公開 API 仕様（Swagger / OpenAPI 等の契約定義）・IF の入出力契約（リクエスト/レスポンスの項目と意味）・エラーコード/ステータス一覧・CRUD 図（外部 IF とエンティティの操作対応）。

**含まない**: 内部処理アルゴリズム・DB 操作文・認証実装の詳細・内部処理フロー図。
> これらは IF を「どう実装するか」であり外部から観測する契約ではないため、詳細設計へ委ねる（P2: 外部設計は外部観測仕様に限る）。認証は「どのエンドポイントが認証を要するか」までは外部契約だが、トークン検証ロジックや署名アルゴリズムは詳細設計に属する。

**該当なし（スタンドアロン）の扱い**: 外部 IF を一切公開しないスタンドアロンシステムでは、この節を空にせず「該当なし」と明記し、その理由（例: 単一プロセスで完結し外部システムとの連携を持たない）を1行添える。空節にしない。

### 例（最小限・テンプレート用）

```
外部公開API: 受注登録 API（OpenAPI で定義）

エンドポイント: POST /orders

入出力契約:
  リクエスト  customerId（必須）, items[]（商品ID・数量）
  レスポンス  orderId, totalAmount, status

エラーコード/ステータス一覧:
  201 Created          受注登録成功
  400 Bad Request      入力項目の不足・形式不正（errorCode=E-VALIDATION）
  404 Not Found        顧客または商品が存在しない（errorCode=E-NOTFOUND）
  409 Conflict         在庫不足（errorCode=E-STOCK）

CRUD図（IF × エンティティ）:
  POST /orders         受注=C, 受注明細=C, 在庫=U
  GET  /orders/{id}    受注=R, 受注明細=R
```

## トレーサビリティ

各画面・各外部 IF を要件 ID に紐付ける。孤立した外部仕様（要件の根拠のない画面・IF）を作らない。外部から観測可能な仕様（画面名・IF 名）を主語にしてトレースする。
> P4: 設計は要件へ全要素トレース可能でなければならない。孤立した設計要素はスコープクリープの検出点になる。

**表の書き方**:
- 要件 ID は SRS の章番号・ユースケース番号・機能要件 ID のいずれかを統一して使う。
- 1つの画面/IF が複数要件に対応する場合はカンマ区切りで列挙する。
- 要件に直接紐付かない横断的な画面/IF（共通エラー画面・ヘルスチェック IF 等）は「横断」と記載し、対応する NFR の ID を付ける。

| 外部仕様（画面名/IF 名） | 対応要件 ID | 備考 |
|---|---|---|
| 受注登録画面 | UC-02, FR-05 | 受注登録要件 |
| 受注一覧画面 | UC-02, FR-06 | 受注検索・一覧要件 |
| 受注登録 API（POST /orders） | UC-02, FR-05 | 外部システムからの受注連携 |
| 受注控え（帳票） | FR-07 | 受注控え出力要件 |
| 共通エラー画面 | NFR-USE-01 | 横断的なユーザビリティ要件（エラー表示方針） |

**逸脱の判定基準**:
- 「対応要件 ID」が空の画面/IF が存在する → 孤立設計要素（スコープクリープ候補）。要件への追記または削除を検討する。
- 画面/IF が要件に存在しない機能を実現している → 要件定義工程へのフィードバックが必要。

## システム構成図（任意・推奨）

外部から見たシステムの配置（公開エンドポイント・連携する外部システム・利用者の接続経路）を示す。クライアント・外部システムとの境界を一望できるため推奨するが、画面も外部 IF も持たない最小構成では省略してよい。

> **越境 note（方式設計との境界）**: 内部アーキテクチャの詳細（コンポーネント分割・レイヤ構成・技術選定根拠）は外部設計ではなく**方式（アーキ）設計**の責務である。responsibility-map.md 上で外部設計と方式設計は「システム構成図」で一部重複しうるため、本節は**外部から観測可能な配置（誰がどこに繋がるか）に限り**、内部構成は方式設計レシピ（将来整備）へ委ねる。両者の重複を避けるための境界線である。

## 境界を越えた記述の扱い

外部設計に以下の**内部実装マーカー**が現れたら、外部から観測できない内部仕様の先取り＝詳細設計への混入である。該当工程へ移送する。これらの厳密な語はフェンスブロック内に列挙する（語彙チェッカーはフェンス内を検査対象外とする。地の文では言い換える）。

```
外部設計に書いてはいけない内部実装マーカー（出たら詳細設計へ移送）:

  クラス図          → 詳細設計（内部構造設計）へ
  シーケンス図      → 詳細設計（内部処理フロー）へ
  インデックス      → 詳細設計（物理データ設計）へ
  テーブル定義      → 詳細設計（物理データ設計）へ
```
（注: SQL クエリ／DB 操作文も外部設計には書かないが、`SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列で機械 vocab が誤爆するため、機械の禁止語には入れず後述の rubric で見る。）

- **内部構造図**（部品間の構造・相互作用の図）が外部設計に出たら → 詳細設計（内部設計）へ。
- **内部処理フロー図**（処理の時系列・呼び出し順序の図）が出たら → 詳細設計へ。
- **DB 操作文・索引・物理テーブル設計**（問い合わせ文・物理データ構造）が出たら → 詳細設計（物理データ設計）へ。
- **ピクセル/hex の厳密値**: 画面設計に `16px` や `#3366FF` のような厳密値が現れたら → 詳細設計の UI コンポーネント仕様へ（P5: 厳密値・物理精度は詳細設計工程のマーカーである）。

> **機械判定の限界（P2 訂正・cycle-4 srs / cycle-8 architecture-design と同方針）**: API 語・技術スタック名・ピクセル/hex の厳密値は、外部設計では**正当な記述**になりうる（外部公開 API の仕様、外部から観測する画面項目、帳票の出力位置など）。これらを機械 vocab で一律に弾くと正当な外部設計記述を誤爆するため、機械 vocab では禁止語として扱わず、`rubric/external-design.md` の質的観点（「内部実装に踏み込んでいないか」「厳密値が外部契約として必要か単なる詳細先取りか」）で判定する。**特に `SQL` は製品名 PostgreSQL・NoSQL・MySQL・SQLite 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する**（cycle-8 で実機検出）。よって `SQL`（DB 操作文／クエリ）も機械 vocab の禁止語から外し、SQL クエリ/DB 操作文の混入は `rubric/external-design.md` の質的観点（内部仕様 leak）で判定する。機械 vocab が禁止するのは技術名と誤爆しない内部実装マーカー（前掲フェンス内の4語）に限る。

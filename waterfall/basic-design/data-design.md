# データ設計レシピ — ウォーターフォール基本設計

> **レイヤー**: 第2層レシピ（手法別具体指針）
> **原則参照**: [`../../principles/granularity-axis.md`](../../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。
> **責務対照**: [`../../principles/responsibility-map.md`](../../principles/responsibility-map.md) のデータ設計行を参照。

---

## 目的とスコープ

このレシピが対象とする**データ設計の工程範囲**を明確にする。基本設計のデータ設計は**論理**に限る。物理設計（型/NULL/PK/FK/index）は詳細設計の対象であり、本レシピでは扱わない。

| 工程 | 本レシピでの扱い |
|---|---|
| **基本設計（論理）** | 対象。エンティティ・関連・正規化レベル・テーブル一覧・主要ビジネスルールの論理モデルをここで確定する |
| **詳細設計（物理）** | 対象外。型・NULL・PK・FK・代表 index 等の物理制約は物理設計に属し、詳細設計レシピ [`../detailed-design/data-design.md`](../detailed-design/data-design.md) で確定する |

責務対照表（responsibility-map.md のデータ設計行）は「論理 ER 図・テーブル一覧・主要ビジネスルール」を基本設計の含む範囲、「DB 物理設計（型/NULL/FK/index）・DML・データ移行 SQL」を含まない範囲と定める。本レシピはこの境界を各節に具体化する。

**境界を越えた記述の扱い**:
- 論理 ER に物理（型・index・物理テーブル名）が先取りされていたら、詳細設計レシピ [`../detailed-design/data-design.md`](../detailed-design/data-design.md) へ移す（P5: 厳密値・物理精度は詳細設計工程のマーカーである）。

## 論理ER

**含む**: エンティティ・関連（多重度・方向）・属性（論理名）・正規化レベルの明示・テーブル一覧（論理名）・主要ビジネスルール（関連の制約条件）。

**含まない**: index 種別・ストレージエンジン・型（varchar/int 等）・NULL 許可・物理テーブル名のプレフィックス・PK/FK の物理定義。
> 物理的な詳細は詳細設計レシピへ委ねる（P5: 厳密値は詳細設計工程のマーカーである）。

**正規化レベルの明示**: 「3NF」「BCNF」など到達レベルを明記する。理由のある非正規化は根拠を付記する。

### 例（最小限・テンプレート用）

```
エンティティ: 受注、顧客、商品、受注明細
正規化レベル: 3NF（顧客住所は顧客エンティティへ分離済み）

関連:
  顧客  1 ──< 受注        (1人の顧客は複数の受注を持つ)
  受注  1 ──< 受注明細    (1件の受注は1件以上の明細を持つ)
  商品  1 ──< 受注明細    (1つの商品は複数の明細に現れうる)

テーブル一覧（論理名）: 顧客、受注、受注明細、商品

主要ビジネスルール:
  - 受注明細の数量は1以上（業務ルール）
  - 顧客は退会後も受注履歴を保持する（論理削除方針）
```

## トレーサビリティ

各エンティティを要件 ID に紐付ける。孤立したエンティティ（要件の根拠のない設計要素）を作らない。論理レベルでのトレースであり、物理テーブルではなくエンティティ（論理名）を主語にする。
> P4: 設計は要件へ全要素トレース可能でなければならない。孤立した設計要素はスコープクリープの検出点になる。

**表の書き方**:
- 要件 ID は SRS の章番号・ユースケース番号・機能要件 ID のいずれかを統一して使う。
- 1エンティティが複数要件に対応する場合はカンマ区切りで列挙する。
- 要件に紐付かないエンティティ（ログ・監査等の横断的なもの）は「横断」と記載し、対応する NFR の ID を付ける。

| エンティティ（論理名） | 対応要件 ID | 備考 |
|---|---|---|
| 顧客 | UC-01, FR-03 | 顧客登録・検索要件 |
| 受注 | UC-02, FR-05, FR-06 | 受注登録・ステータス管理要件 |
| 受注明細 | UC-02, FR-05 | 受注明細の数量・金額要件 |
| 商品 | UC-03, FR-08 | 商品マスタ管理要件 |
| 監査ログ | NFR-SEC-02 | 横断的なセキュリティ要件（操作ログ） |

**逸脱の判定基準**:
- 「対応要件 ID」が空のエンティティが存在する → 孤立設計要素（スコープクリープ候補）。要件への追記または削除を検討する。
- エンティティが要件に存在しない機能を実現している → 要件定義工程へのフィードバックが必要。

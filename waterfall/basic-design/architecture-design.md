# 方式設計レシピ — ウォーターフォール基本設計

> **レイヤー**: 第2層レシピ（手法別具体指針）
> **原則参照**: [`../../principles/granularity-axis.md`](../../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。
> **責務対照**: [`../../principles/responsibility-map.md`](../../principles/responsibility-map.md) の**「基本設計：方式（アーキ）設計」行**を参照。

## 目的とスコープ

このレシピが対象とする**方式設計の工程範囲**を明確にする。方式設計は**システム全体のアーキテクチャ方式・技術選定・横断的な設計方針**を決める工程である。アーキテクチャスタイル、外から見たコンポーネント分割、採用技術とその根拠、複数コンポーネントを横断する設計方針（ログ・認証・エラー処理）を、外から観測できる粒度で確定する。

これに対し、コンポーネント**内部**の作り込み（内部構造図・メソッド単位の内部仕様・内部処理フロー図・アルゴリズム）は外から観測できる方式ではないため詳細設計の対象であり、DB 物理（型・index・物理テーブル・DB 操作文）はデータ設計／詳細設計の対象である。本レシピではこれらの内部実装・DB 物理を扱わない。

| 工程 | 本レシピでの扱い |
|---|---|
| **基本設計（方式設計）** | 対象。アーキテクチャスタイル・主要コンポーネント構成（外から見た責務分割）・デプロイトポロジ・技術選定根拠・ADR へのリンク・横断懸念（ログ/認証/エラー処理方針）をここで確定する |
| **詳細設計（内部）** | 対象外。内部構造図・メソッド単位の内部仕様・内部処理フロー図・コンポーネント内部のアルゴリズム・DB 物理設計・DB 操作文は内部実装に属し、詳細設計レシピ [`../detailed-design/`](../detailed-design/) で確定する |

責務対照表（responsibility-map.md の「基本設計：方式（アーキ）設計」行）は「アーキテクチャスタイル・主要コンポーネント構成・技術選定根拠・ADR へのリンク・横断懸念・デプロイトポロジ」を含む範囲、内部構造図・メソッド単位の内部仕様・モジュール内部実装・DB 操作文の全文を含まない範囲と定める。アーキ決定は詳細設計へ、設計判断記録は ADR スキルへ（採番・生成は委譲）渡す。本レシピはこの境界を各節に具体化する。

**境界を越えた記述の扱い**:
- 外から観測できない内部実装（内部構造図・内部処理フロー図・メソッド単位の内部仕様・DB 操作文）が混入していたら、詳細設計レシピ [`../detailed-design/`](../detailed-design/) へ移す（P2: 方式設計は外から観測できるアーキ方式に限る）。
- DB 物理（型・index・物理テーブル）が混入していたら、データ設計レシピ [`./data-design.md`](./data-design.md) または詳細設計へ移す（P5: 厳密値・物理精度は下流工程のマーカーである）。

## アーキテクチャ方式

**含む**: アーキテクチャスタイル（レイヤード・イベント駆動・マイクロサービス・モジュラモノリス等）・主要コンポーネント構成（外から見た責務分割と、コンポーネント間の依存・連携方向）・デプロイトポロジ（どのコンポーネントがどの実行単位/ノードに載るか）。

**含まない**: コンポーネント内部のクラス階層・メソッドレベルの内部実装・コンポーネント内部のアルゴリズム。
> これらは「外から見た方式」ではなくコンポーネント内部の作り込みであるため、詳細設計の内部構造設計へ委ねる（P2: 方式設計は外から観測できる範囲に限る）。

**選定スタイルの根拠**: 採用したアーキテクチャスタイルには、なぜそのスタイルかの根拠（NFR との対応・将来の拡張性・チーム構成との適合等）を1行添える。根拠なきスタイル選択は孤立したアーキ判断であり、トレーサビリティ節で要件 ID へ紐付ける（P4）。

### 例（最小限・テンプレート用）

```
アーキテクチャスタイル: モジュラモノリス
  根拠: 初期リリースは単一チーム・単一デプロイで運用負荷を抑える。
        将来のサービス分割に備えモジュール境界は明確に保つ（NFR-MNT-01）。

主要コンポーネント構成（外から見た責務分割）:
  受注モジュール   ── 受注の受付・状態遷移を担う
  在庫モジュール   ── 在庫の引当・補充を担う
  通知モジュール   ── 受注確定イベントを購読しメール送信

  依存方向:
    受注モジュール ──(在庫引当を要求)──> 在庫モジュール
    受注モジュール ──(受注確定イベント発行)──> 通知モジュール（疎結合・非同期）

デプロイトポロジ:
  アプリケーション実行単位 1（受注・在庫・通知の3モジュールを同居）
  リバースプロキシ 1（外部公開エンドポイントを集約）
  RDB 1（永続化層・物理設計は詳細設計／データ設計で確定）
```

## 技術選定

**含む**: 採用技術（言語・フレームワーク・ミドルウェア・プロトコル等）・**選定根拠**（なぜそれを選んだか）・**却下した代替**（比較した他案と却下理由）・**ADR へのリンク**（採番された ADR への参照）。

**含まない**: 実装手順・設定ファイル全文・チューニングパラメータの詳細値。
> これらは技術を「どう使うか」であり方式設計の粒度を越える。詳細設計または運用設計へ委ねる（P5: 厳密値・手順は下流工程のマーカーである）。

> **技術スタック名・製品名・プロトコル名は方式設計では正当な記述である。** 技術選定は方式設計の核であり、技術名そのものを禁止語として弾くと正当な選定記述を誤爆する。技術名が**正当な選定**（根拠付きの比較・決定）か、根拠のない**解の先取り**（要件段階に書くべきでないものの混入）かは、`rubric/architecture-design.md` の質的観点で判定する（機械 vocab では禁止語にしない）。

**該当なし（既定指定）の扱い**: 上位要求・契約で技術が既定指定されている場合は、選定の余地がない旨と既定の根拠（契約条項・既存資産との互換等）を明記する。空節にしない。

### 例（最小限・テンプレート用）

```
採用技術: メッセージング基盤に Apache Kafka
  選定根拠: 受注確定イベントを複数コンシューマへ配信する要件（FR-12）に対し、
            イベントの再処理・順序保証・スケールアウトの観点で適合する。
  却下した代替: RabbitMQ — 順序保証とログ再生（replay）の運用要件で劣ると判断。
  ADR リンク: [ADR-0001](../../docs/adr/0001-messaging-platform.md)

採用技術: 永続化に PostgreSQL
  選定根拠: トランザクション整合性（NFR-DATA-01）と既存運用ノウハウ。
  却下した代替: NoSQL（ドキュメント型）— 受注の強整合要件に対し過剰なトレードオフ。
  ADR リンク: [ADR-0002](../../docs/adr/0002-database-engine.md)
```

> ADR リンク先の採番・生成は本書ではなく ADR スキルが行う（後述「ADR 委譲」節）。本書は採番された番号とリンクを**参照**するだけである。

## 横断懸念

**含む**: 複数コンポーネントを横断する設計方針 — ログ方針（出力レベル・相関 ID の通し方の方針）・認証/認可方針（どの境界で認証するか・認可モデルの方針）・エラー処理方針（例外の扱い・障害時のフォールバック方針）・トランザクション方針（境界・整合性レベルの方針）。

**含まない**: 各方針の実装コード・詳細手順・ライブラリ固有の設定値。
> これらは方針を「どう実装するか」であり詳細設計／運用設計の粒度である。本節は「方針」の粒度に留める（P2: 方式設計は方針レベルの How に限り、実装の How は下流へ）。

**薄い項目の扱い**: 横断懸念のうち該当の薄い項目（例: 認証不要の社内バッチ専用システムにおける認証方針）は、空にせず「該当なし＋理由」を明示する。空節は「検討漏れ」と「対象外」を区別できないため禁止する。

### 例（最小限・テンプレート用）

```
ログ方針:
  全コンポーネントで構造化ログを採用し、リクエスト単位の相関 ID を伝播させる。
  個人情報はマスクして出力する（NFR-SEC-03）。

認証/認可方針:
  認証はリバースプロキシ境界で一元化する。
  認可はモジュール側でロールベースに判定する（認可モデルの詳細は詳細設計）。

エラー処理方針:
  外部公開境界では共通エラー応答形式に正規化する。
  在庫引当失敗は補償処理でロールバックする（トランザクション方針と整合）。

トランザクション方針:
  受注確定はモジュール内ローカルトランザクション。
  モジュール間（在庫引当）は結果整合とし、失敗時は補償イベントで巻き戻す。
```

## トレーサビリティ

各**アーキ判断・技術選定・横断方針**を要件 ID／NFR ID に紐付ける。孤立したアーキ判断（要件・NFR の根拠のない方式決定）を作らない。
> P4: 設計は要件へ全要素トレース可能でなければならない。孤立した設計要素はスコープクリープの検出点になる。あわせて design rationale（選定根拠・却下案）は必須であり、その記録は ADR スキルへ委譲する（後述）。

**表の書き方**:
- 要件 ID は SRS の機能要件 ID／ユースケース番号を、NFR ID は基本設計（非機能設計）の NFR ID を統一して使う。
- 1つの判断が複数要件・NFR に対応する場合はカンマ区切りで列挙する。
- 機能要件に直接紐付かない横断方針（ログ・監査等）は、対応する NFR の ID を付ける。
- ADR で根拠を記録した判断は備考に ADR 番号を併記する（リンク本体は技術選定節）。

| アーキ判断/技術選定/横断方針 | 対応要件・NFR ID | 備考 |
|---|---|---|
| モジュラモノリス採用 | NFR-MNT-01 | 保守性・将来分割への布石 |
| Kafka 採用（イベント配信） | FR-12 | ADR-0001 |
| PostgreSQL 採用 | NFR-DATA-01 | ADR-0002 |
| 認証をプロキシ境界で一元化 | NFR-SEC-01 | 横断方針 |
| 構造化ログ＋相関 ID | NFR-SEC-03, NFR-OPS-02 | 横断方針（監査・運用） |

**逸脱の判定基準**:
- 「対応要件・NFR ID」が空のアーキ判断/技術選定が存在する → 孤立設計要素（スコープクリープ候補）。要件/NFR への追記または判断の削除を検討する。
- 重要な技術選定に ADR リンクがない → 決定根拠が不明（responsibility-map の逸脱基準「ADR リンクなし」に該当）。ADR を作成しリンクする。
- 判断が要件・NFR に存在しない機能/品質を実現している → 要件定義・非機能設計工程へのフィードバックが必要。

## ADR 委譲（設計判断の記録）

**設計判断の記録（ADR の採番・生成）は [`architecture-decision-records`](../../principles/responsibility-map.md#3-既存スキル委譲表) スキルに委譲する。** 本書は ADR を生成しない。技術選定・アーキ判断の根拠は ADR 側に記録し、方式設計書からはリンク＋採番（`[ADR-0001](...)`）で**参照**するだけである。

この委譲は responsibility-map.md の[既存スキル委譲表](../../principles/responsibility-map.md#3-既存スキル委譲表)（S5: 設計判断の記録は `architecture-decision-records` が所有・採番・生成、doc-standards は参照・リンク・存在チェックのみ）に基づく。doc-standards 側でADR の番号体系・記録フォーマットを二重定義しない（S3 と整合: 委譲先が source of truth）。

**doc-standards 側の関与（rubric 観点）**:
- 重要なアーキ判断・技術選定に**ADR リンクが存在し採番されているか**を確認する（リンク切れ・番号欠落の検出）。
- ADR の**内容の良し悪し**（却下案が妥当か等）は評価しない。それは ADR スキルおよびレビュースキル（`review-handoff` / `santa-method`）の責務である。

## 境界を越えた記述の扱い

方式設計に以下の**内部実装マーカー**が現れたら、外から観測できる方式ではなくコンポーネント内部の先取り＝詳細設計への混入である。該当工程へ移送する。これらの厳密な語はフェンスブロック内に列挙する（語彙チェッカーはフェンス内を検査対象外とする。地の文では言い換える）。

```
方式設計に書いてはいけない内部実装マーカー（出たら詳細設計へ移送）:

  クラス図        → 詳細設計（内部構造設計）へ
  メソッド仕様    → 詳細設計（メソッド単位の引数/戻り値/処理）へ
  シーケンス図    → 詳細設計（内部処理フロー）へ
```
（注: SQL クエリ／DB 操作文も方式設計には書かないが、`SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列で機械 vocab が誤爆するため、機械の禁止語には入れず後述の rubric で見る。）

- **内部実装**（内部構造図・メソッド単位の内部仕様・内部処理フロー図・コンポーネント内部のアルゴリズム）が混入したら → 詳細設計へ（P2: 方式設計は外から観測できるアーキ方式に限る）。
- **DB 物理**（型・index・物理テーブル・DB 操作文）が混入したら → データ設計 [`./data-design.md`](./data-design.md) または詳細設計へ（P5: 厳密値・物理精度は下流工程のマーカーである）。
- **ADR リンクなし**で根拠不明な重要判断が混入したら → ADR を採番・記録（ADR スキルへ委譲）し、本書からリンクする。

> **機械判定の限界（P2 訂正・cycle-4 srs / cycle-7 external-design と同方針）**: 技術スタック名・製品名・プロトコル名は方式設計では**正当な記述**である（技術選定の核）。これらを機械 vocab で一律に弾くと正当な選定記述を誤爆する。**特に `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する**（cycle-8 で実機検出）。よって `SQL`（DB 操作文／クエリ）も機械 vocab の禁止語に入れず、技術名・SQL とも `rubric/architecture-design.md` の質的観点（「技術名が根拠付きの正当な選定か、根拠なき解の先取りか」「方針レベルに留まり実装詳細／DB 操作文に踏み込んでいないか」「重要判断に ADR リンクがあるか」）で判定する。機械 vocab が禁止するのは技術名と誤爆しない内部実装マーカー（前掲フェンス内の3語）に限る。

# 非機能設計レシピ — ウォーターフォール基本設計

> **レイヤー**: 第2層レシピ（手法別具体指針）
> **原則参照**: [`../../principles/granularity-axis.md`](../../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。
> **責務対照**: [`../../principles/responsibility-map.md`](../../principles/responsibility-map.md) の**「基本設計：非機能設計」行**を参照。

---

## 目的とスコープ

このレシピが対象とする**非機能設計の工程範囲**を明確にする。非機能設計は、SRS で What＋具体グレード値・**測定方法の方向性/観点**まで合意された品質要求を受け取り、**具体グレード値（定量化された目標）・測定方法の確定（SRS の方向性を受けて測定手段・測定条件・測定タイミングを具体化する）・合意済みターゲット**を設計として確定する工程である。IPA 非機能要求グレードの **6 カテゴリ**（可用性／性能・拡張性／運用・保守性／移行性／セキュリティ／システム環境）で網羅性を点検する。

> **SRS との境界（F4 決着＝スタンスα・2026-06-05）**: 測定方法は工程で粒度分割する——SRS（要件定義 [`../requirements/srs.md`](../requirements/srs.md)）が「測定方法の方向性/観点」を、本工程（非機能設計）が「測定方法の確定（測定手段・条件・タイミングの具体化）」を持つ。これにより責務対照表の要件定義行・非機能設計行で `測定方法` が二重所有されていた食い違いを粒度差で解消する（F1〔論理/物理を工程で割る〕を測定方法という軸へ一般化した同型の決着）。本工程は SRS の方向性を**単純転記せず**、測定方法を確定させることが設計の付加価値である。

これに対し、その品質要求を**アーキテクチャでどう実現するか**の詳細・測定を自動化する実装コード・性能を引き上げるための調整手順は「どう実現するか（How）」であり、詳細設計／運用設計の対象である。本レシピではこれらの実現手段を扱わない。

| 工程 | 本レシピでの扱い |
|---|---|
| **基本設計（非機能設計）** | 対象。IPA 6 カテゴリの NFR 具体グレード値・測定方法（測定手段／条件／タイミング）・合意済みターゲットをここで確定する |
| **詳細設計／運用設計** | 対象外。NFR をアーキテクチャでどう実現するかの詳細・測定の自動化実装・性能の調整手順は実現手段に属し、詳細設計レシピ [`../detailed-design/`](../detailed-design/) ／運用設計の対象である |

責務対照表（responsibility-map.md の「基本設計：非機能設計」行）は「NFR 具体グレード値・測定方法・合意済みターゲット（IPA 6 カテゴリ）・測定タイミング」を含む範囲、「アーキ実現方法の詳細・測定の自動化実装・性能の調整手順」を含まない範囲と定める。NFR ターゲットは非機能テスト設計へ、セキュリティ要件は詳細設計へ渡す。本レシピはこの境界を各節に具体化する。

**境界を越えた記述の扱い**（詳細は末尾の越境節）:
- 品質要求を実現する手段（アーキ実現詳細・測定の自動化実装・性能の調整手順）が混入していたら、詳細設計 [`../detailed-design/`](../detailed-design/) ／運用設計へ移す（P2: 非機能設計はターゲット値と測定方法までに限る）。

## 非機能要件

IPA 6 カテゴリでカテゴリ別にターゲット（具体グレード値）を確定する。SRS から受け取った What＋方向性を、設計として測定可能なグレード値へ落とす。

**含む**: カテゴリ別の要求項目・**定量化されたグレード値**（具体的な目標値）・合意済みターゲット。

**含まない**: それを**どう実現するか**（アーキテクチャでの実現方法・性能の調整手順）。
> これらは品質要求の実現手段であり、外から見たターゲットではない。詳細設計／運用設計へ委ねる（P2: 非機能設計はターゲット値までに留める）。

**verifiable（P6）**: 「速い」「安定している」「十分な」のような定量化されていない表現は検証不能であり、本節では使わない。各 NFR は**測定可能なグレード値**で書き、その測り方は次の「測定方法」節に紐づける。値があっても測れる方法が無い NFR は検証可能性を満たさない。

**該当の薄いカテゴリの扱い**: 6 カテゴリのうち該当の薄いもの（例: オンプレ閉域システムにおける移行性）は、空節にせず「該当なし＋理由」を明記する。空節は「検討漏れ」と「対象外」を区別できないため禁止する（external-design / architecture-design と同方針・gold plating 回避）。

### 例（最小限・テンプレート用）

```
可用性:
  要求 : サービス稼働率
  グレード値: 月間稼働率 99.5% 以上（計画停止を除く）

性能・拡張性:
  要求 : 受注照会のレスポンス
  グレード値: 通常負荷時、応答が3秒以内（p95）

運用・保守性:
  要求 : 障害一次切り分けの着手時間
  グレード値: 検知から30分以内に切り分けを開始できる運用体制

移行性:
  該当なし（理由: 新規構築で移行元データが存在しない）

セキュリティ:
  要求 : 操作履歴の保全
  グレード値: 全更新操作の操作者・日時を記録、保持期間1年

システム環境:
  要求 : 同時利用者数の収容
  グレード値: 想定ピーク同時利用者数 500 を収容
```

## 測定方法

各 NFR を**どう測るか**を確定する。verifiable の核＝グレード値に対して実際に測れる方法（測定手段・測定条件・測定タイミング）が紐づくことを保証する。

**含む**: 各 NFR の測定手段（何で測るか）・測定条件（どの負荷・どの環境で）・測定タイミング（いつ測るか）。

**含まない**: 測定を自動化する実装コード・性能を引き上げる調整手順。
> これらは「どう測るかの実装」「どう実現するか」であり詳細設計／運用設計の粒度である。本節は測定の**方針**に留める（P2）。

各グレード値に対し、対応する測定方法を1対1で対応づける。グレード値はあるが測定方法が無い NFR は verifiable 違反である（「非機能要件」節の値と本節の測定方法が同数で対応していることを点検する）。測定タイミングは V 字の検証工程（性能試験・受入テスト等）に対応させ、非機能テスト設計へ渡せる粒度にする。

### 例（最小限・テンプレート用）

```
可用性（月間稼働率 99.5% 以上）:
  測定手段 : 監視ツールの稼働ログ集計
  測定条件 : 計画停止を除外して算出
  測定タイミング: 毎月末（運用フェーズ・月次）

性能・拡張性（応答3秒以内 p95）:
  測定手段 : 想定ピーク同時利用者数で受注照会を反復実行し応答時間分布を計測
  測定条件 : 通常負荷時・p95 を採る
  測定タイミング: 結合テスト後の性能試験

セキュリティ（操作履歴1年保持）:
  測定手段 : 監査ログの抽出件数と更新操作件数の突合
  測定条件 : 全更新操作を対象
  測定タイミング: 受入テスト
```

## トレーサビリティ

各 NFR を **SRS の NFR ID／要件 ID** に紐付ける。孤立 NFR（SRS に出どころのない品質目標）を作らない。
> P4: 設計は要件へ全要素トレース可能でなければならない。孤立した NFR はスコープクリープの検出点になる。

**表の書き方**:
- 「対応 SRS NFR ID／要件 ID」列に、SRS（`waterfall/requirements/srs.md`）の `NFR-{カテゴリ略}-NN` ／機能要件 ID を記載する。
- 1つの NFR が複数の上位要求に対応する場合はカンマ区切りで列挙する。
- SRS の NFR を**単純転記しない**——基本設計として測定方法・測定タイミング・合意済みターゲットが設計として足されていること（その質的妥当性は rubric が見る）。

| 本書の NFR | 対応 SRS NFR ID／要件 ID | 備考 |
|---|---|---|
| 可用性 99.5% | NFR-AVAIL-01 | 稼働率合意 |
| 応答3秒以内（p95） | NFR-PERF-01 | 受注照会の応答性能 |
| 操作履歴1年保持 | NFR-SEC-01 | 監査・操作履歴 |

**逸脱の判定基準**:
- 「対応 SRS NFR ID／要件 ID」が空の NFR が存在する → 孤立 NFR（スコープクリープ候補）。SRS への追記または NFR の削除を検討する。
- グレード値だけで測定方法が紐づかない NFR がある → verifiable 違反（「測定方法」節の欠落は機械が、値はあるが測れないケースは rubric が見る）。
- SRS に存在しない品質目標を本書が立てている → 要件定義工程へのフィードバックが必要。

## 境界を越えた記述の扱い

非機能設計に以下の**下流実装先取りマーカー**が現れたら、外から見たターゲット・測定方針ではなく実現手段の先取り＝詳細設計／運用設計への混入である。該当工程へ移送する。これらの厳密な語はフェンスブロック内に列挙する（語彙チェッカーはフェンス内を検査対象外とする。地の文では言い換える）。

```
非機能設計に書いてはいけない下流実装先取りマーカー（出たら詳細設計／運用設計へ移送）:

  チューニング手順    → 詳細設計／運用設計（性能の実現手段）へ
  計測スクリプト      → 詳細設計／運用設計（測定の自動化実装）へ
```

- **アーキ実現方法の詳細**（品質要求をアーキテクチャでどう実現するか）が混入したら → 詳細設計／運用設計へ（P2: 非機能設計はターゲット値と測定方法までに限る）。
- **測定の自動化実装**（測定を回す実装コード）が混入したら → 詳細設計／運用設計へ（P2: 本書は測定の方針までに留める）。
- **性能の調整手順**（設定値の具体調整・パラメータ列挙）が混入したら → 詳細設計／運用設計へ（P5: 厳密値・手順は下流工程のマーカーである）。

> **機械判定の限界（P2 訂正・cycle-4 srs / cycle-7 external-design / cycle-8 architecture-design と同方針）**: 技術スタック名・製品名・プロトコル名は非機能設計でも**正当な記述**である（測定対象の環境・監視製品名として現れる）。これらを機械 vocab で一律に弾くと正当な記述を誤爆する。**特に `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する**（cycle-8 で実機検出）。よって技術名・`SQL` は機械 vocab の禁止語に入れず、`rubric/nonfunctional-design.md` の質的観点で判定する。
>
> また**定量化されていない曖昧表現**（「高速に」「安定して」「十分な」等）も、部分一致では正当な文脈（説明文・対比のための引用）と区別できず誤爆するため、機械 vocab では弾かず rubric の質的観点（グレード値の定量化）で見る。機械 vocab が禁止するのは技術名・曖昧表現と誤爆しない下流実装先取りマーカー（前掲フェンス内の2語）に限る。

## 位置づけ

このレシピが対象とする**詳細設計（処理）の工程範囲**を明確にする。詳細設計は方式設計（基本設計・[`../basic-design/architecture-design.md`](../basic-design/architecture-design.md)）が「クラス図・メソッド仕様・処理アルゴリズム詳細は詳細設計へ」と渡した受け皿である。本レシピが担うのは**処理の内部設計**——クラス・モジュールの静的構造、メソッド仕様（引数/戻り値/エラー処理）、処理ロジック・IPO——を、実装可能な設計レベルで確定する層に限る。

これは WF 詳細設計の**2本目**であり、**データ詳細**（[`./data-design.md`](./data-design.md)＝物理データ設計）と**対**をなす。データ詳細が「どう保持するか」（テーブル・カラム・型・制約）を確定するのに対し、**処理詳細は「どう動くか」**（クラスの責務分割・メソッドの入出力とロジック・エラー処理）を確定する。両者は同じ詳細設計工程の二側面である。

| 工程 | 本レシピでの扱い |
|---|---|
| **基本設計（方式設計）** | 前提（入力・上流）。アーキテクチャスタイル・主要コンポーネント構成・技術選定・横断方針は方式設計（[`../basic-design/architecture-design.md`](../basic-design/architecture-design.md)）で確定済みとする。本レシピでは機能スコープ・UI レイアウトを再記述しない（基本設計既出は ID 参照） |
| **詳細設計（処理）** | 対象。クラス・モジュールの静的構造（責務分割・依存方向）・メソッド仕様（引数/戻り値/エラー処理）・処理ロジック・IPO をここで確定する |
| **詳細設計（データ）** | 隣接（対）。物理テーブル・カラム・型・制約・index・DDL はデータ詳細（[`./data-design.md`](./data-design.md)）が確定する。処理詳細はデータ詳細を参照し、テーブル定義を再記述しない |
| **実装（コード）** | 対象外（下流）。変数宣言・SQL 全文・boilerplate の逐語はコードの領分。詳細設計がコード同等まで降りると ghost document 化する（後述・両端逸脱の一端） |

責務対照表（responsibility-map.md の詳細設計行）は「クラス図・シーケンス図・アクティビティ図・モジュール構造図・IPO・メソッド仕様〔引数/戻り値/エラー処理〕・厳密数値（3600ms@p99 等）」を含む範囲、「SQL 全文・言語文法・単純 CRUD 全ステップ・業務理由〔要件既出〕・機能スコープ再記述〔基本設計既出〕・UI レイアウト〔基本設計確定済〕」を含まない範囲と定める。本レシピはこの境界を処理詳細レベルへ具体化する。

### 上端境界＝基本設計（抽象）↔ 詳細設計（具体）の F1 同型境界（このスライスの肝・上側）

本レシピの上端の肝は **基本設計（方式設計・外部設計）↔ 詳細設計の境界**である。基本設計は「クラス図・メソッド仕様・処理アルゴリズム詳細」を詳細設計へ渡す＝**基本設計↔詳細設計は F1（論理 ER↔物理 ER）と同型の抽象↔具体境界**である（外部設計↔詳細設計・方式設計↔詳細設計とも同型問題＝responsibility-map で確定済み）。基本設計が外から観測できる方式・コンポーネント構成（抽象）を、詳細設計が内部の作り込み（具体）を担う。**機能スコープの再記述・UI レイアウト（基本設計確定済）の重複は上流の越境**であり、ID 参照に置換する（後述の越境 note）。

### 下端境界＝詳細設計特有の両端逸脱（このスライスの肝・下側）

詳細設計には**両端の逸脱**がある。これが詳細設計工程に特有の痛みである。

- **① ghost document（厚すぎ・コードへ降りすぎ）**: メソッド仕様・処理ロジックがコード逐語（変数宣言・SQL 全文・boilerplate の逐語）にまで降りると、設計書が「逐語のコード」と化す。これはコード（実装）の越境であり、詳細設計の役目は「実装に必要な設計判断を確定する」ことであってコードを書き写すことではない。
- **② 実質空（薄すぎ・分岐/エラー条件/性能制約が未記述）**: 逆に、メソッド名と一行説明だけで、分岐条件・エラー条件・性能制約が書かれていないと、開発者が実装判断できず詳細設計の体をなさない。

> **両端とも構造・量の判定ゆえ機械語彙でなく rubric・越境 note で見る**: 「厚すぎ（コード逐語）」「薄すぎ（分岐/エラー条件 未記述）」は**特定の禁止語では弾けない構造・量の問題**であり、機械（[`../../scripts/check_vocabulary.py`](../../scripts/check_vocabulary.py)）では厚薄を測れない。とりわけ `SQL` は製品名 PostgreSQL・MySQL の部分文字列で誤爆する（cycle-8 で実機検出）ため機械の禁止語に入れず、SQL 全文の混入（ghost document）は [`../../rubric/detailed-design-process.md`](../../rubric/detailed-design-process.md) の質的判定（観点3）へ委ねる。実質空（薄すぎ）も同 rubric（観点4）へ委ねる。

### 必須は絞る／残りは推奨（このスライス固有の設計理由）

**必須節**: `クラス・モジュール構造`（静的構造＝クラス/モジュール構成・責務分割・依存方向）／`処理仕様`（動的＝メソッド仕様〔引数/戻り値/エラー処理〕・処理ロジック・IPO）／`トレーサビリティ`（対応 基本設計〔方式/外部〕・要件へ）。

- **`処理仕様` を独立必須にするのが肝**＝処理詳細の核は「メソッドがどう動くか」（引数/戻り値/エラー処理・処理ロジック・IPO）であり、それを欠いて静的構造（クラス一覧）だけ並べても処理詳細の体をなさない。処理仕様節の欠落を見出し欠落で機械検出する（データ詳細の「テーブル定義」必須化・nonfunctional の「測定方法」必須化・test-design-spec の「網羅方針」必須化と同型）。

> **なぜ「導入見出し」を `位置づけ` にするか（機械表現の罠回避）**: 機械判定（[`../../scripts/check_headings.py`](../../scripts/check_headings.py)）は見出しの**部分一致**で必須を見る。スキーマ（[`../../scripts/schema/detailed-design-process.json`](../../scripts/schema/detailed-design-process.json)）の `required_headings` は `["モジュール構造", "処理仕様", "トレーサビリティ"]` の3語で、`モジュール構造` は実見出し `## クラス・モジュール構造` に部分一致する。`クラス` を required に使うと本文の「クラス図」言及や推奨節で誤爆しやすいため、**デコイ低リスクな後半語 `モジュール構造` で機械表現する**（cycle-14 の Goals/Non-Goals・cycle-18 のテストレベル・test-procedure-spec の `前提・セットアップ`→`前提` と同型＝「部分一致しやすく誤爆しにくい語を選ぶ」技法）。
>
> **デコイ厳禁（cycle-15/16/17/18 教訓）**: `モジュール構造`／`処理仕様`／`トレーサビリティ` の各必須語を、導入見出し（`位置づけ`）・推奨節見出しに**部分一致で紛れ込ませない**。推奨節 `例外・エラー処理詳細` は `処理` を含むが `処理仕様` を含まないため安全、`シーケンス図`／`アクティビティ図`／`状態遷移` は必須3語のいずれも部分一致しないため安全。各必須語が**実見出しに1つだけ部分一致**するように見出しを設計する（専用節を削った版が確実に deviation になることを保証する）。

**推奨節（必須にしない・必須語を見出しに含めない）**: `シーケンス図`（動的な相互作用の時系列）／`アクティビティ図`（処理フロー）／`状態遷移`（オブジェクトの状態変化）／`例外・エラー処理詳細`（例外設計の掘り下げ）等。**必須にすると小さい処理詳細でも全節を埋めさせる過剰テンプレ化（gold plating）を招くため、必須にしない**（data-design がテーブルごと全節を強制しない・test-plan が IEEE 829 多セクションを全強制しない・test-design-spec/test-procedure-spec/test-strategy が推奨節を置いたのと同じ判断）。推奨節の見出しに必須語〔`モジュール構造`／`処理仕様`／`トレーサビリティ`〕を部分一致で含めない（デコイ回避）。

**境界を越えた記述の扱い**（詳細は末尾の越境 note）:
- メソッド仕様・処理ロジックがコード逐語（SQL 全文・変数宣言・boilerplate）まで降りていたら → コード（実装）へ。詳細設計は設計レベルに留め、コードを書き写さない（ghost document＝厚すぎの一端・rubric で見る）。
- 逆に分岐条件・エラー条件・性能制約が未記述で実質空なら → 書き足す（薄すぎの他端・rubric で見る）。
- 機能スコープ・UI レイアウト（基本設計既出）が再記述されていたら → 基本設計（[`../basic-design/`](../basic-design/)）を ID 参照し、本書では再記述しない（上端の越境）。
- 業務上の理由（要件で既出の Why）が処理仕様に混入していたら → 要件（SRS）を参照し、業務理由転記マーカー（上位 Why の定型字面）を転記しない（P2）。

## クラス・モジュール構造

処理を担う**クラス・モジュールの静的構造**（責務分割・依存方向）を設計レベルで定める。これは「どう動くか」の前提となる「何が・どこに居るか」の構造である。

**含む**: クラス・モジュールの構成（名前・責務の1〜2行）・クラス間/モジュール間の依存方向・抽象境界（ポート/インターフェース）・モジュール構造図（パッケージ/レイヤの構成）。

**含まない**: コード逐語（変数宣言・boilerplate）・各メソッドの内部実装の全行・基本設計で確定済みの機能スコープの再記述。
> 静的構造はクラス/モジュールの「責務と関係」までであり、メソッド内部の逐語ロジックは処理仕様節（設計レベル）で、コード全行は実装で扱う。

### 例（最小限・テンプレート用）

```
クラス・モジュール構成（責務分割）:
  OrderConfirmationService（受注確定サービス） ── 受注確定のユースケースを統括
  InventoryReservation（在庫引当）             ── 在庫の引当・解放を担う
  NotificationPort（通知発行ポート）           ── 受注確定イベントを外部通知基盤へ渡す抽象境界

依存方向:
  受注確定サービス ──(同期呼び出し)──> 在庫引当
  受注確定サービス ──(イベント発行・疎結合)──> 通知発行ポート
  循環依存は持たせない
```

## 処理仕様

各メソッドの**入出力（IPO）・処理ロジック・エラー処理**を設計レベルで定める。処理詳細の核であり、開発者が追加の設計判断なしに実装に着手できる粒度を狙う。

**含む**: メソッド仕様（引数・戻り値・例外/エラー処理）・処理ロジック（分岐条件・繰り返し条件・前後条件）・IPO（入力→処理→出力）・性能制約（厳密数値＝p95 800ms 等は詳細設計工程のマーカー・P5）。

**含まない**: SQL 全文・言語文法・単純 CRUD の全ステップ（コード逐語＝ghost document）・業務上の理由（要件で既出の Why は転記しない・P2）。
> 処理ロジックは「分岐・エラー条件・性能制約」の設計判断までであり、それをコード逐語（`for` ループの全行・`SELECT ... FROM ...` の全文）に展開すると ghost document 化する（rubric 観点3）。逆に分岐・エラー条件・性能制約を書かないと実質空（rubric 観点4）。

> **SQL 全文・boilerplate はここに書かない**（ghost document 化の主因）。DB アクセスが必要な場合はデータ詳細（[`./data-design.md`](./data-design.md)）のテーブル定義を ID 参照し、処理仕様では「どのテーブルに何を要求するか」の設計レベルに留める。`SQL` という語自体は製品名（PostgreSQL/MySQL）の部分文字列で機械が誤爆するため禁止語にせず、**SQL 全文の混入は rubric で見る**（後述 vocab の説明・cycle-8 と同方針）。

### 例（最小限・テンプレート用）

```
メソッド: OrderConfirmationService.confirm(orderId)
  入力(Input):  orderId（受注 ID・必須・正整数）
  出力(Output): 確定結果（確定済み受注の状態と確定日時）
  処理(Process): 受注を取得 → 在庫引当を要求 → 引当成功なら受注を確定状態へ遷移 → 通知イベントを発行
  エラー処理:
    - 受注が存在しない        → OrderNotFound を返す
    - 在庫引当に失敗          → 確定せず InventoryShortage を返す（状態遷移・通知の副作用を行わない）
  処理ロジック（分岐・エラー条件・性能制約）:
    - 受注ステータスが cancelled の場合は確定不可（分岐条件）
    - 在庫引当は受注確定と同一トランザクション境界・失敗時はロールバック（エラー条件）
    - 確定処理の応答は p95 で 800ms 以内（性能制約・厳密数値は詳細設計のマーカー）
```

## 推奨節（必須にしない・処理の複雑度に応じて書く）

以下は処理の複雑度・チームの規約に応じて記述する。**必須にすると小さい処理詳細でも全節を埋めさせる過剰テンプレ化（gold plating）を招くため、必須にしない**（data-design/test-plan/test-design-spec/test-procedure-spec/test-strategy が推奨節を置いたのと同じ）。**推奨節の見出しに必須語〔`モジュール構造`／`処理仕様`／`トレーサビリティ`〕を部分一致で含めない**（デコイ回避＝cycle-15/16/17/18 教訓）。

- `シーケンス図`: 複数クラスにまたがる相互作用の時系列（メッセージの往復・順序）。
- `アクティビティ図`: 分岐・並行を含む処理フローの俯瞰。
- `状態遷移`: オブジェクト（受注など）の状態変化と遷移条件。
- `例外・エラー処理詳細`: 例外の分類・回復戦略・補償処理の掘り下げ（処理仕様の概要を超える詳細）。

## トレーサビリティ

各**クラス・処理**を、対応する**基本設計（方式/外部設計）・要件 ID** へ紐付ける。孤立した設計要素（要件・基本設計の根拠のない処理）を作らない（P4: 全要素トレース可能）。詳細設計は基本設計を具体化したものであり、基本設計のコンポーネント→詳細設計のクラス/処理の対応を明示する。要件文・基本設計の文言は転記せず **ID 参照**にとどめる（P2/P6）。

**表の書き方（クラス/処理 → 基本設計/要件 ID）**:
- ID 列のヘッダに「**対応**」を含める（例: `対応 基本設計/要件 ID`）。第1列はクラス/処理名（主語）であり、機械の [`../../scripts/check_traceability.py`](../../scripts/check_traceability.py) は第1列を主語として除外し、「対応」を含む列を ID 列とみなす。
- 全セルを埋める。対応列が空・ダッシュ（`-`）のクラス/処理は孤立設計要素（スコープクリープ候補）であり、機械が検出する逸脱になる。
- 基本設計 ID（方式 ARC-xx／外部 EXT-xx 等）と要件 ID（UC-xx／FR-xx）の両方向を、運用に応じて統一して使う。
- 機能要件に直接紐付かない横断的処理（ログ・監査等）は「横断」と記載し、対応する NFR の ID を付ける。

| 設計要素（クラス/処理） | 対応 基本設計/要件 ID | 備考 |
|---|---|---|
| OrderConfirmationService | 方式: ARC-02, 要件: UC-02, FR-05 | 受注確定のユースケース統括 |
| InventoryReservation | 方式: ARC-03, 要件: FR-06 | 在庫引当・解放 |
| confirm() のエラー処理 | 要件: FR-07（在庫不足時の挙動） | 在庫不足時は確定しない |
| 通知イベント発行 | 方式: ARC-04, 要件: FR-12 | 受注確定イベントの配信 |

**逸脱の判定基準**:
- 「対応 基本設計/要件 ID」が空（またはダッシュ）のクラス/処理が存在する → 孤立設計要素（スコープクリープ候補）。要件/基本設計への紐付け補完または削除を検討する（**空セルそのものの検出は機械の [`../../scripts/check_traceability.py`](../../scripts/check_traceability.py) の担当**。rubric は過大主張しない＝cycle-12/F5 の教訓）。
- 対応が形式上は埋まっているが、その基本設計/要件と処理が意味的に食い違う → 紐付けの質の問題であり、[`../../rubric/detailed-design-process.md`](../../rubric/detailed-design-process.md) の質的判定で見る。
- 処理が要件・基本設計に存在しない機能を実現している → 要件定義・基本設計工程へのフィードバックが必要。

## 越境 note（粒度・帰属のズレ検出）

処理詳細に以下が現れたら、詳細設計（処理）レベルを越境している。該当工程へ移送する。**詳細設計は両端を持つ**（上流＝基本設計既出の重複・業務理由／下流＝コード逐語）点が特徴であり、データ詳細（[`./data-design.md`](./data-design.md)）とは**対**（同じ詳細設計の処理側）である。

- **ghost document（コード逐語＝SQL 全文・変数宣言・boilerplate）** が処理仕様に出たら → コード（実装）へ。詳細設計は「実装に必要な設計判断」までで、コードを書き写さない（**厚すぎ＝両端の一端**・厚薄は機械で測れず [`../../rubric/detailed-design-process.md`](../../rubric/detailed-design-process.md) 観点3 で見る）。
- **実質空（分岐・エラー条件・性能制約が未記述）** なら → 書き足す（**薄すぎ＝両端の他端**・量は機械で測れず rubric 観点4 で見る）。
- **基本設計既出（機能スコープ・UI レイアウト）の再記述** が出たら → 基本設計（[`../basic-design/`](../basic-design/)）を **ID 参照に置換**する。基本設計↔詳細設計は F1（論理/物理）と同型の抽象↔具体境界であり、抽象側（基本設計）の重複は同期リスク（上端の越境・rubric/上流レシピで見る）。
- **業務理由（要件で既出の Why）** が処理仕様に出たら → 要件（SRS）を参照し、業務理由転記マーカー（上位 Why の定型字面・下のフェンス内に列挙）を**転記しない**（P2）。機械が検出するのは**この定型字面マーカーのみ**（唯一の機械語彙・後述）であり、言い換え・別表記で混入した業務 Why は機械では拾えず [`../../rubric/detailed-design-process.md`](../../rubric/detailed-design-process.md) の質的判定が横断的に見る（データ詳細 [`./data-design.md`](./data-design.md) rubric と同じ分担）。

> 詳細設計（処理）のコード越境マーカー・業務理由転記マーカーはフェンスブロック内に列挙する（語彙チェッカーはフェンス内を検査対象外とする。地の文では字面を書かず言い換える）。

```
処理詳細に書いてはいけないマーカー（出たら該当工程へ）:

  なぜなら業務〜（業務上の Why の転記）   → 要件（SRS）を ID 参照・転記しない（唯一の機械禁止語）
  SQL 全文（SELECT ... FROM ... の本文）  → 実装／データ詳細のテーブル定義を ID 参照（rubric）
  変数宣言・boilerplate の逐語            → 実装（rubric）
  単純 CRUD の全ステップ                  → 実装（設計レベルでは「どのテーブルに何を要求するか」まで・rubric）
```
（注: `SQL` は製品名 PostgreSQL・MySQL 等の部分文字列で機械 vocab が誤爆するため、機械の禁止語には入れず後述の rubric で見る。技術名・製品名・メソッド名は処理仕様で正当に出るため非禁止。）

## vocab の説明（detailed-design-data 踏襲＝同じ詳細設計工程・経験検証で出番あり∧誤爆なし）

**本 doc_type（detailed-design-process）の機械語彙（vocab）は業務理由転記マーカー（上位 Why の定型字面・前掲フェンス内に列挙）1語のみ**（[`../../scripts/vocab/detailed-design-process.json`](../../scripts/vocab/detailed-design-process.json)）であり、これは**対をなすデータ詳細（[`./data-design.md`](./data-design.md)＝detailed-design-data）から踏襲**したものである。

**vocab の有無は『その doc_type の逸脱が機械で綺麗に拾えるか』で決まる——agile か WF かの別でも、データ詳細か処理詳細かの別でもない**（[`../../agile/design-doc.md`](../../agile/design-doc.md) で確立し、WF テスト工程5本〔[`../test/test-strategy.md`](../test/test-strategy.md) の vocab 説明〕で実証した原則）。詳細設計（処理）は detailed-design-data と同じ詳細設計工程であり、責務対照表の「含まない」に**業務理由（要件既出）**を持つ。よって業務理由転記マーカー（上位 Why の定型字面）の転記を禁止語にできるかを**経験検証**した:

- **(a) 出番がある（綺麗に拾える）**: 業務上の理由（要件で既出の Why）を処理詳細に転記する逸脱は実際に起こり、「このクラスを設ける。〜という業務上の都合で…」のように上位 Why の定型字面で出る（実機で violation fixture が deviation を返すことを確認）。これは詳細設計の「含まない＝業務理由」の主たる字面であり、データ詳細と同じ主戦場を処理詳細も持つ。
- **(b) 誤爆しない**: 処理詳細の正当な地の文（メソッド仕様・処理ロジック・クラス構造・例外処理の散文。技術名 PostgreSQL・メソッド名 `confirm()`・例外名を含む）にこのマーカーは誤爆しない（実機で good fixture が pass を確認）。

(a)（出番あり）∧(b)（誤爆なし）ゆえ**踏襲した**（既定＝迷ったら空だが、本語は綺麗に拾えるため非空）。これはデータ詳細との**対称**（同じ詳細設計工程の二側面が同じ業務理由マーカーを持つ）であり、「同一工程だから持つ」のではなく「**処理詳細でも業務理由転記が機械で綺麗に拾える**から持つ」のが正確な理由である。

**機械で弾かないもの（誤爆回避・rubric へ委ねる）**:

- **ghost document（コード逐語＝SQL 全文・変数宣言・boilerplate）** と **実質空（分岐・エラー条件・性能制約 未記述）** は**構造・量の判定**であり、特定の禁止語では弾けない。機械は厚薄を測れないため [`../../rubric/detailed-design-process.md`](../../rubric/detailed-design-process.md)（観点3・観点4＝詳細設計特有の両端）へ委ねる。
- **`SQL`** は製品名 PostgreSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出）。よって機械 vocab に入れず、SQL 全文混入（ghost document）は rubric 観点3 で見る。
- **技術名・製品名・言語名・メソッド名** は処理仕様で正当に現れる（メソッド仕様の核）ため禁止語にしない。

禁止語を採用したため、悪い例（業務理由転記マーカーの字面）は地の文に置かずコードフェンス内に隔離して列挙する（語彙チェッカーはフェンス内を検査対象外とする＝前掲の越境マーカー欄と同じ扱い）。本レシピ自身も `check_vocabulary detailed-design-process` で pass する（地の文にこのマーカーの字面を持たない）。

# 要件定義レシピ — ウォーターフォール要件定義（SRS）

> **レイヤー**: 第2層レシピ（手法別具体指針・要件定義）
> **原則参照**: [`../../principles/granularity-axis.md`](../../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。
> **責務対照**: [`../../principles/responsibility-map.md`](../../principles/responsibility-map.md) の要件定義（SRS）行を参照（業務目的・スコープ・機能要件・NFR・トレーサビリティ）。

## 目的とスコープ

このレシピが対象とする**要件定義（SRS）の工程範囲**を明確にする。要件定義は「何を（What）・なぜ（Why）」を確定する工程であり、「どう作るか（How）＝設計構造」は原則として後続工程（基本設計・詳細設計）に委ねる。当初の痛み「要件で詰めすぎ／設計の先取り」を防ぐことが本レシピの主眼である。

| 工程 | 本レシピでの扱い |
|---|---|
| **要件定義（SRS）** | 対象。業務目的・スコープ・機能要件（What/Why）・非機能要件（グレード値＋測定方法の方向性/概要）・トレーサビリティをここで確定する |
| **基本設計（外部・方式・データ・非機能・運用）** | 対象外。画面レイアウト詳細・システム構成・論理 ER・アーキ選定等は基本設計の対象であり、要件には先取りしない |
| **詳細設計（内部）** | 対象外。物理データ構造・処理アルゴリズム・部品分解・索引設計等は詳細設計の対象であり、要件には先取りしない |

責務対照表（responsibility-map.md の要件定義行）は「業務目的・背景・スコープ・機能要件一覧・NFR（具体グレード値＋測定方法の方向性/観点）・ステークホルダー・ユースケース・受入基準の方向性」を含む範囲、「画面レイアウト詳細・物理データ構造・処理アルゴリズム・部品への分解・API 設計・内部構造図・色/ピクセル値」を含まない範囲と定める。本レシピはこの境界を各節に具体化する。なお NFR の**測定方法の確定**（測定手段・条件・タイミングの具体化）は基本設計（非機能設計）の責務であり、要件段階では測定方法の方向性/観点（どういう条件・観点で検証するか）までを扱う（F4 決着＝スタンスα・2026-06-05）。

**必須セクションと推奨セクション**:
- **必須**: `機能要件一覧`・`非機能要件`・`トレーサビリティ`（後続タスクで schema 化）。必須見出しは `機能要件一覧` とする（`機能要件` だと部分一致チェッカー上で `非機能要件` の部分文字列になり、機能要件節が欠落しても誤って pass しうるため＝`機能要件一覧` ⊄ `非機能要件` で包含を解消する）。
- **推奨（必須にしない）**: `ステークホルダー`・`ユースケース`。要件の過剰テンプレ化（全項目埋め強制による gold plating）を避けるため、これらは必要なときに記載する。
- `目的とスコープ` は導入であり必須ではない。

**境界を越えた記述の扱い**:
- 要件に設計構造（内部構造図・物理データ構造・部品への分解・索引設計）が先取りされていたら、基本設計レシピ（[`../basic-design/data-design.md`](../basic-design/data-design.md) 等）または詳細設計レシピ（[`../detailed-design/data-design.md`](../detailed-design/data-design.md)）へ移す。要件に書いてはいけない設計構造マーカーの厳密な例は、各節および末尾の越境 note のフェンスブロックに列挙する。
- 要件は設計の解空間を不当に狭めない（P3: StRS→SyRS→SRS の三層で抽象度が降下する。解を先取りすると解空間が狭まる）。

## ステークホルダー

> **推奨セクション**（必須ではない）。利害関係者とその関心事を整理し、後続の要件・受入基準の出どころを明示する。

**含む**: 利害関係者の役割（発注者・利用者区分・運用者・外部連携先等）・各々の主要な関心事（達成したい業務目的）・要件の出どころとしての位置づけ。

**含まない**: 個人名・連絡先などの運用情報・利用者ごとの画面権限の詳細（後者は外部設計の対象）。

### 例（最小限・テンプレート用）

```
| ステークホルダー | 役割 | 主要な関心事 |
|---|---|---|
| 営業部門 | 受注業務の主利用者 | 受注入力の手間削減・入力ミスの防止 |
| 管理部門 | 売上集計・監査 | 正確な集計・操作履歴の追跡 |
| 顧客 | 外部利用者 | 注文状況の確認 |
```

## 機能要件一覧

システムが提供すべき機能を **What（何を）／Why（なぜ）** で一覧化する。**How（設計・実装の構造）は書かない**——内部構造の分解・物理データ構造・処理アルゴリズム・索引設計といった解は後続工程に委ねる（P2: 要件は What/Why、How は原則排除）。

**含む**: 機能の一覧（機能 ID 付き）・各機能が満たす業務目的（Why）・観測可能な振る舞い（What）・入力と出力の概要（業務語彙で）・受入基準の方向性。

**含まない**: 主語が「システム内部／部品」になった内部仕様・処理手順の分岐ロジック（if-then の実装ロジック）・物理データ構造・画面の色やピクセル値・特定実装手段への固定（正当な制約を除く。下記参照）。

> 主語ヒューリスティック（P1・検出補助）: 主語が「利用者／業務」なら要件、「システム／コンポーネント」なら基本設計、「部品／メソッド／物理データ」なら詳細設計。要件節で主語がシステム内部に降りていたら粒度ズレを疑う。

### 正当な制約は根拠付きで例外許容（P2 訂正版）

How を原則排除する一方で、**上位要求や外部条件に由来する正当な制約**は、その**根拠を明示したうえで例外として許容する**。これは絶対禁止ではない。例外として許容される代表例:

- **セキュリティ要件・セーフティ要件**に由来する制約（例: 法令・社内規程が暗号化方式を指定している）。
- **契約・上位要求で指定されたプロトコルやベンダー**（例: 連携先が通信規格を固定している）。
- **既定の業界標準・規格適合**が上位から課されている場合。

これらは「根拠（なぜその制約が課されるか）」とセットで書く。根拠のない技術選択（単なる開発者の好みによる実装手段の固定）は許容しない。なお、根拠付きの制約として技術手段を書くこと自体は要件逸脱ではない（質的判定はルーブリックに委ねる）。

### 例（最小限・テンプレート用）

```
FR-01 受注登録
  Why : 営業担当が受注を漏れなく記録し、後工程（出荷・請求）へ連携するため
  What: 利用者は顧客・商品・数量を指定して受注を登録できる。
        登録時に在庫数を超える数量は受け付けない（業務ルール）。
  受入の方向性: 在庫超過の数量で登録を試みると業務エラーが返ること

FR-02 受注状況の照会
  Why : 顧客が自身の注文の進捗を自己解決で確認できるようにするため
  What: 顧客は注文番号で受注の現在ステータスを照会できる。

FR-03 操作の暗号化通信（正当な制約・例外許容の例）
  Why : 個人情報保護方針および契約上、外部公開経路の通信暗号化が義務付けられているため
  What: 外部利用者との通信は暗号化された経路で行う。
  制約根拠: 上位の情報セキュリティ規程 SEC-POL-01 で必須化（根拠を明示した正当な制約）
```

## 非機能要件

非機能要件（NFR）は機能要件と**並行して要件段階で検討・合意する**。後工程への先送りを禁止する（P9: NFR は要件段階で並行検討・後回し禁止）。IPA 非機能要求グレードの **6 カテゴリ**（可用性／性能・拡張性／運用・保守性／移行性／セキュリティ／システム環境）で網羅性を点検する。

**含む**: 6 カテゴリごとの要求項目・**グレード値（具体的な目標値）＋測定方法の方向性/概要**（どういう条件・観点で検証するかの方向性）・測定タイミングの方向性・合意済みターゲットの方向性。

**含まない**: その NFR をアーキテクチャでどう実現するかの詳細・計測スクリプト・チューニング手順（実現方法は基本設計／詳細設計の対象）。**測定方法の確定**（測定手段・測定条件・測定タイミングの具体化）も含まない——これは基本設計（非機能設計）の責務であり、要件段階では測定の方向性/観点までを扱う（F4 決着＝スタンスα・2026-06-05）。

> **verifiable（P6）**: 「速い」「安定している」のような曖昧表現は検証不能。各 NFR は**測定可能な値**と**どう測るかの方向性**（どういう条件・観点で検証するか）をセットで書く。値が無い、または測定の方向性が無い NFR は検証可能性を満たさない。要件段階では測定方法を**方向性/概要レベル**で示せばよく、測定手段・条件・タイミングの確定は基本設計（非機能設計）へ渡す。
>
> **境界（測定方法の確定は基本設計へ渡す）**: NFR の**測定方法の確定**（具体的な測定手段・条件・タイミングの確定）は基本設計（非機能設計 [`../basic-design/nonfunctional-design.md`](../basic-design/nonfunctional-design.md)）の責務である。SRS は測定の方向性/観点までに留め、確定は越境させずに非機能設計へ渡す（F4 決着＝スタンスα・2026-06-05。F1〔論理/物理〕を測定方法という軸へ一般化した同型の工程粒度分割）。
>
> **具体値の置き場について**: NFR の具体グレード値を SRS に置くか基本設計（非機能設計）に置くかは規格・実務で割れる（責務対照表に判断を委ねる）。本レシピが主眼とするのは「要件段階で**並行検討・後回し禁止**」であり、置き場の最終決定は責務対照表とプロジェクト方針に従う。少なくとも要件段階で**検討・合意が始まっている**ことを満たす。

### 例（最小限・テンプレート用）

```
NFR-PERF-01 性能・拡張性
  要求 : 受注照会のレスポンス
  グレード値: 通常負荷時、応答が約3秒以内（p95）
  測定方法の方向性 : 性能は本番相当の負荷条件で応答時間を検証する方針
                     （具体的な測定手段・条件・タイミングの確定は基本設計＝非機能設計）

NFR-AVAIL-01 可用性
  要求 : サービス稼働率
  グレード値: 月間稼働率 99.5% 以上（計画停止を除く）
  測定方法の方向性 : 稼働率は運用フェーズの稼働実績で検証する方針
                     （計測手段・集計周期の確定は基本設計＝非機能設計）

NFR-SEC-01 セキュリティ
  要求 : 操作履歴の保全
  グレード値: 全更新操作の操作者・日時を記録、保持期間1年
  測定方法の方向性 : 操作履歴の網羅性を監査観点で検証する方針
                     （突合手段・対象範囲の確定は基本設計＝非機能設計）
```

> 上記の値は概算粒度（P5: 概算値は上流、厳密値は詳細工程のマーカー）。要件段階では「約3秒（p95）」のような合意可能な粒度でよく、`3600ms@p99` のような厳密値の確定は後続工程に属する。

## ユースケース

> **推奨セクション**（必須ではない）。アクターとシステムの相互作用を、主成功シナリオと代替シナリオで記述し、機能要件の文脈を補強する。

**含む**: アクター（利用者区分）・事前条件・主成功シナリオ（業務の流れ）・代替／例外シナリオ・事後条件。

**含まない**: 画面の具体的なレイアウト・内部の処理手順（分岐ロジックの実装）・物理データの読み書き手順（これらは設計工程の対象）。

### 例（最小限・テンプレート用）

```
UC-01 受注を登録する
  アクター  : 営業担当
  事前条件  : 顧客・商品マスタが登録済み
  主成功シナリオ:
    1. 営業担当が顧客を選択する
    2. 商品と数量を指定する
    3. システムが受注内容を確認し、受注番号を発行する
  代替シナリオ:
    2a. 数量が在庫を超える → 業務エラーを表示し登録を中止する
  事後条件  : 受注が登録され、後工程へ連携可能な状態になる
```

## トレーサビリティ

各機能要件・非機能要件を **上位の業務要求（StRS／業務要求 ID）** へ紐付け、要件 ID 体系を確立する。上位要求に紐付かない孤立要件を作らない（P4: 設計は要件へ全要素トレース可能。要件自身も上位要求へトレース可能であるべきで、孤立要件はスコープクリープの検出点になる）。

**要件 ID 体系**:
- 機能要件: `FR-NN`（例: FR-01）。
- 非機能要件: `NFR-{カテゴリ略}-NN`（例: NFR-PERF-01・NFR-SEC-01）。カテゴリ略は IPA 6 カテゴリに対応させる。
- ユースケース: `UC-NN`（例: UC-01）。

**表の書き方**:
- 「上位要求 ID」列に業務要求／StRS の ID を記載し、各要件がどの業務目的から来たかを示す。
- 1要件が複数の上位要求に対応する場合はカンマ区切りで列挙する。
- 横断的な要件（監査・ログ等、特定の業務機能に属さないもの）は「横断」と記載し、由来する方針 ID を付ける。

| 要件 ID | 要件種別 | 上位要求 ID | 備考 |
|---|---|---|---|
| FR-01 | 機能 | BR-01 | 受注業務の効率化（業務要求） |
| FR-02 | 機能 | BR-02 | 顧客の自己解決（問い合わせ削減） |
| FR-03 | 機能（制約） | SEC-POL-01 | 通信暗号化（正当な制約・根拠付き） |
| NFR-PERF-01 | 非機能 | BR-01 | 受注照会の応答性能 |
| NFR-AVAIL-01 | 非機能 | BR-03 | サービス稼働率の合意 |
| NFR-SEC-01 | 非機能 | 横断 | 監査・操作履歴（SEC-POL-01 由来） |

**逸脱の判定基準**:
- 「上位要求 ID」が空の要件が存在する → 孤立要件（スコープクリープ候補）。上位要求の補完または要件削除を検討する。
- 上位要求に存在しない機能を要件が実現している → 業務要求工程へのフィードバックが必要。
- 機能要件に設計構造（後述の越境マーカー）が混入している → 後続設計工程へ移送する。

## 越境 note（設計の先取り検出）

要件定義に以下の**設計構造マーカー**が現れたら、要件で詰めすぎ＝設計の先取り（当初の痛み#1）である。該当工程へ移送する。これらの厳密な語はフェンスブロック内に列挙する（語彙チェッカーはフェンス内を検査対象外とする。地の文では言い換える）。

```
要件に書いてはいけない設計構造マーカー（出たら後続工程へ移送）:

  クラス図          → 詳細設計（内部構造設計）へ
  テーブル定義      → 基本設計（論理 ER）／詳細設計（物理）へ
  モジュール分割    → 基本設計（方式設計）／詳細設計へ
  インデックス      → 詳細設計（物理データ設計）へ
```

- **内部構造図**（部品間の構造・相互作用の図）が要件に出たら → 詳細設計（内部設計）へ。
- **物理データ構造**（型・NULL 可否・主キー／外部キーの物理定義・物理名）が要件に出たら → 詳細設計（物理データ設計）へ。
- **部品への分解**（システム内部の構成要素への割り当て）が要件に出たら → 基本設計（方式設計）／詳細設計へ。
- **索引設計**（検索高速化のための物理構造）が要件に出たら → 詳細設計（物理データ設計）へ。
- **論理データモデル**（エンティティ・関連）が要件で詳細化されていたら → 基本設計（データ設計）へ。概念レベルの関連図までは要件で許容するが、正規化レベルや論理属性の確定は基本設計に委ねる。

> 対比に注意: **上記4語（設計構造マーカー）は禁止語**（要件に出たら設計の先取り）だが、**技術手段の名称そのもの**（通信規格名・基盤製品名等）は**禁止語ではない**。技術名は正当な制約（P2 訂正版）として根拠付きで現れることがあり、その場合は逸脱でない。技術名が設計の先取りかどうかは「根拠ある制約か／単なる解の先取りか」の質的判定であり、ルーブリックに委ねる。

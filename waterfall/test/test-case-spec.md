# テストケース仕様レシピ — ウォーターフォール テスト（ケース仕様）

> **レイヤー**: 第2層レシピ（手法別具体指針・テスト）
> **原則参照**: [`../../principles/granularity-axis.md`](../../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。
> **責務対照**: [`../../principles/responsibility-map.md`](../../principles/responsibility-map.md) のテスト仕様行を参照（テスト戦略・計画・設計仕様・ケース仕様・手順仕様のうち、本レシピは**ケース仕様**＝テスト条件＋具体値を担う）。

---

## 目的とスコープ

このレシピが対象とする**テスト工程の範囲**を明確にする。テスト文書は抽象度で階層化される（計画 → 設計仕様 → ケース仕様 → 手順仕様。P7）。本レシピが担うのは**ケース仕様レベル**——テスト条件に対して**具体値（事前条件・入力・操作・期待結果）を確定**した層——に限る。計画レベル（戦略・体制・スケジュール）、設計仕様レベルの高レベルテスト条件のみの記述、手順仕様レベルの実行順の詳細は本レシピでは扱わない。

このレシピは V 字（要件 ↔ 設計 ↔ テスト）の背骨を通す位置にある。要件定義（SRS）で確定した要件 ID を、テスト文書側で「何をすべきか」から「どう確認するか」へ**変換**して書き、要件はテスト文書から **ID で参照**する（P6: テスト文書は要件を ID 参照する・要件文を転記しない）。

| 工程 | 本レシピでの扱い |
|---|---|
| **テスト戦略・計画** | 対象外。組織方針・体制・スケジュール・対象範囲（スコープ／対象外＋理由）は計画レベルに属し、別工程（計画仕様）で確定する。本レシピにケース具体値とともに混在させない |
| **テスト設計仕様** | 隣接（入力）。テスト観点＝高レベルのテスト条件はここで導出される。本レシピは観点を**推奨セクション**として受け、具体値の確定（ケース仕様）へ展開する |
| **テストケース仕様** | 対象。1ケースの事前条件・入力・操作・**測定可能／観測可能な期待結果**・対応要件 ID をここで確定する |
| **テスト手順仕様** | 対象外。実行の前後関係・反復順序・環境セットアップの逐次手順は手順仕様レベルに属し、別工程で確定する。本レシピのケースは「1件として観測可能」な粒度にとどめる |

責務対照表（responsibility-map.md のテスト仕様行）は「テスト戦略・計画・設計仕様・ケース仕様・手順仕様」を含む範囲、「計画へのテストケース具体値の記載・設計仕様への低レベルケースの混入・要件文の転記」を含まない範囲と定める。本レシピはこの境界をケース仕様レベルへ具体化する。

**必須セクションと推奨セクション**:
- **必須**: `テストケース`・`トレーサビリティ`（後続タスクで schema 化）。
- **推奨（必須にしない）**: `テスト観点`。観点をすべて埋めることを強制すると過剰テンプレ化（gold plating）を招くため、設計仕様から自然に導かれる範囲で記載する。
- `目的とスコープ` は導入であり必須ではない。

**境界を越えた記述の扱い**:
- 計画事項（戦略・体制・スケジュール・スコープ宣言）がケース仕様に紛れ込んでいたら、計画仕様へ移す（計画へのケース具体値の混入も逆向きの逸脱であり、両者を分離する。P7／P8）。
- 実行の逐次手順（環境構築の手順・反復順序の詳細）がケースに紛れ込んでいたら、手順仕様へ移す。
- 要件の理由（Why）や要件文そのものがケース／トレーサビリティに転記されていたら、SRS（[`../requirements/srs.md`](../requirements/srs.md)）へ一元化し、テスト文書側は **ID 参照に置換**する（P6: 転記は二重管理と矛盾の温床）。

## テスト観点

> **推奨セクション**（必須ではない）。設計仕様レベルの**高レベルのテスト条件**——「何を確認するか」——を整理する。ここでは観点（テスト条件）までを書き、具体値は次節（テストケース）へ降ろす（P7: 設計仕様＝テスト条件＋高レベルケース／具体値なし、ケース仕様＝具体値）。

**含む**: 確認すべき観点の一覧（正常系・異常系・境界値・業務ルールの検証点など）・各観点が対応する要件 ID・観点ごとに想定するケースの数の見立て（高レベル）。

**含まない**: 具体的な入力値・期待される具体的な出力値（これらはケース仕様＝次節の対象）。テスト体制・スケジュール・対象範囲の宣言（計画レベル）。実行の逐次手順（手順仕様レベル）。

### 例（最小限・テンプレート用）

```
観点 V-01 受注登録の正常系       対応要件: FR-01    （高レベル: 在庫内数量で登録が成立するか）
観点 V-02 在庫超過の業務エラー   対応要件: FR-01    （境界: 在庫数 ちょうど／+1 の振る舞い）
観点 V-03 受注照会の応答性能     対応要件: NFR-PERF-01（負荷条件下の応答時間分布）
```

> 観点は「テスト条件」止まりにする。たとえば「在庫超過で登録できないこと」までが観点であり、「在庫 10 に対し数量 11 を入力したら業務エラー E-STOCK が返る」は具体値であるため次節へ書く。

## テストケース

各テストケースを **1ケース＝事前条件・入力・操作・期待結果・対応要件 ID** の5要素で記述する（ケース仕様＝具体値の層。P7）。

**期待結果は測定可能／観測可能な状態で書く**。検証不能な期待結果——たとえば「ただしく表示される」「てきせつに処理される」のような**測定できない表現**——は書かない（P6: 検証可能性は工程を貫く不変量）。期待結果は「どの値になるか」「どの状態・コード・件数が観測されるか」で書く。本レシピで避けるべき曖昧表現の厳密な文字列例は、末尾の越境 note のフェンスブロックに列挙する。

**含む**: ケース ID・事前条件（テスト開始前に成立している状態・データ）・入力（具体値）・操作（利用者またはシステムへの単一の働きかけ）・**測定可能/観測可能な期待結果**（具体値・状態・コード・件数・しきい値との比較）・対応要件 ID。

**含まない**: テスト体制・スケジュール・対象範囲の宣言（計画レベル）。環境構築や複数ケースの実行順といった逐次手順の詳細（手順仕様レベル）。要件文の逐語転記・要件の Why（SRS へ一元化し ID 参照に置換）。1件として観測しきれない過大な粒度のシナリオ（複数ケースへ分割する）。

> **要件は転記せず ID 参照**（P6）。各ケースの「対応要件 ID」に SRS の要件 ID（FR-NN／NFR-{カテゴリ略}-NN／UC-NN）を書き、要件文そのものはケースに写さない。要件の文言が必要なら SRS を参照する。

> **粒度の目安**（P5・検出補助）: 期待結果はケース仕様にふさわしい具体値で書く。性能系では「応答が 3 秒以内（p95）」のような合意粒度ではなくケース確定値（例: `p95 ≤ 3000ms`）を期待結果に置く。1ケースが観測単位を超えて肥大していたら分割する。

### 例（最小限・テンプレート用）

正常系・異常系・境界値・性能の各タイプを、期待結果を測定可能にして書く例を示す。

```
TC-01 受注登録（正常系）
  対応要件 : FR-01
  事前条件 : 商品 P-100 の在庫が 10、顧客 C-001 が登録済み
  入力     : 顧客=C-001, 商品=P-100, 数量=3
  操作     : 受注登録を1回実行する
  期待結果 : 受注が1件作成され、レスポンスに受注番号（数値・採番済）が含まれる。
             在庫 P-100 が 10 → 7 に減少している（DB 上の在庫値=7）。

TC-02 在庫超過（異常系）
  対応要件 : FR-01
  事前条件 : 商品 P-100 の在庫が 10
  入力     : 顧客=C-001, 商品=P-100, 数量=11
  操作     : 受注登録を1回実行する
  期待結果 : 受注は作成されない（受注テーブルの該当件数=0）。
             業務エラーコード E-STOCK が返る。在庫 P-100 は 10 のまま変化しない。

TC-03 在庫境界（境界値）
  対応要件 : FR-01
  事前条件 : 商品 P-100 の在庫が 10
  入力     : 顧客=C-001, 商品=P-100, 数量=10
  操作     : 受注登録を1回実行する
  期待結果 : 受注が1件作成される（在庫ちょうどは登録成立）。在庫 P-100 が 10 → 0 になる。

TC-04 受注照会の応答性能（NFR ケース）
  対応要件 : NFR-PERF-01
  事前条件 : 受注データが 10,000 件投入済み、同時利用者 50 で照会を反復
  入力     : 既存の受注番号で照会
  操作     : 受注照会を 1,000 回実行する
  期待結果 : 応答時間の p95 が 3000ms 以下（p95 ≤ 3000ms）。HTTP ステータスは全件 200。
```

> 期待結果は「観測できる値」で書く。上記はいずれも件数・在庫値・エラーコード・しきい値比較で判定でき、合否が一意に決まる。判定者の主観に依存する書き方は避ける。

## トレーサビリティ

各テストケースを **要件 ID** へ紐付ける。要件文は転記せず **ID 参照**にとどめる（P6）。あわせて**要件 → ケースの逆引き**を行い、各要件が最低1ケースでカバーされているかを点検する（P4: 全要素トレース可能。カバーされない要件はテスト漏れの検出点になる）。

**表の書き方（ケース → 要件）**:
- 「対応要件 ID」列に SRS の要件 ID（FR-NN／NFR-{カテゴリ略}-NN／UC-NN）を記載する。
- 1ケースが複数要件を検証する場合はカンマ区切りで列挙する。
- 要件文（What の文言・Why の説明）は写さない。必要なら SRS を ID で参照する。
- 「観点 ID」列は**テスト観点節を設けた場合のみ**埋める（テスト観点は推奨・非必須のため、省略時は空欄でよい。必須は「対応要件 ID」列）。

| ケース ID | 対応要件 ID | 観点 ID | 備考 |
|---|---|---|---|
| TC-01 | FR-01 | V-01 | 受注登録の正常系 |
| TC-02 | FR-01 | V-02 | 在庫超過の業務エラー |
| TC-03 | FR-01 | V-02 | 在庫ちょうどの境界 |
| TC-04 | NFR-PERF-01 | V-03 | 照会の応答時間分布 |

**逆引き表（要件 → ケース／カバレッジ点検）**:
- 各要件 ID に対し、検証するケース ID を列挙する。
- ケースが0件の要件はテスト漏れ（カバレッジ欠落）の候補として明示する。

| 要件 ID | 検証するケース ID | カバレッジ |
|---|---|---|
| FR-01 | TC-01, TC-02, TC-03 | 充足（正常・異常・境界） |
| NFR-PERF-01 | TC-04 | 充足 |
| FR-02 | （なし） | **未充足**（ケース未作成・要追加） |

**逸脱の判定基準**:
- 「対応要件 ID」が空のケースが存在する → 孤立ケース（根拠のないテスト）。対応要件の補完またはケース削除を検討する。
- 逆引きでケース0件の要件が存在する → テスト漏れ。ケースを追加する。
- トレーサビリティ表やケースに要件文が逐語転記されている → ID 参照へ置換し、文言は SRS へ一元化する（P6）。

## 越境 note（粒度・帰属のズレ検出）

ケース仕様に以下が現れたら、ケース仕様レベルを越境している。該当工程へ移送する。曖昧表現の厳密な語はフェンスブロック内に列挙する（語彙チェッカーはフェンス内を検査対象外とする。地の文では言い換える）。

```
期待結果に書いてはいけない曖昧表現マーカー（出たら測定可能な記述へ書き換える）:

  正しく表示    → 「画面に件数 N が表示される」等、観測できる値・状態へ
  正しく動作    → 「ステータスが confirmed になる」「HTTP 200 が返る」等、観測できる結果へ
  適切に処理    → 「在庫が 10 → 7 に減る」「エラーコード E-STOCK が返る」等、観測できる状態変化へ
```

- **計画事項**（戦略・体制・スケジュール・スコープ／対象外宣言）がケース仕様に出たら → 計画仕様（テスト計画レベル）へ。計画にケース具体値を逆流させることも避ける（P7／P8: 階層を飛び越えない）。
- **実行の逐次手順**（環境構築の手順・複数ケースの実行順・反復順序の詳細）がケースに出たら → テスト手順仕様へ。本レシピのケースは「1件として観測可能」な粒度にとどめる。
- **要件文の逐語転記・要件の Why** がケース／トレーサビリティに出たら → SRS（[`../requirements/srs.md`](../requirements/srs.md)）へ一元化し、テスト文書側は **ID 参照に置換**する（P6）。
- **設計仕様レベルの高レベルテスト条件のみ**（具体値を欠いた観点だけ）がテストケース節に出たら → 観点はテスト観点節へ置き、テストケース節には具体値を補う（P7: ケース仕様＝具体値）。

> 対比に注意: 「測定できない期待結果（曖昧表現）」はケース仕様の禁止対象（後続 vocab 化）だが、**要件文の転記**は特定語ではなく**構造の問題**であり、機械語彙では弾かず質的判定（後続ルーブリック）に委ねる。

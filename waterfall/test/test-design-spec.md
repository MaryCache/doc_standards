## 位置づけ

このレシピが対象とする**テスト工程の範囲**を明確にする。テスト文書は抽象度で階層化される（計画 → **設計仕様** → ケース仕様 → 手順仕様の4層。テスト戦略は組織横断の方針層として計画の直上に分離する〔戦略/計画の二分は厳密な規格境界ではない＝P7 注〕。P7）。本レシピが担うのは**設計仕様（Test Design Specification）レベル**——SRS／設計から導いた**抽象的なテスト項目（テスト条件＝高レベルケース）**と、それを**どう網羅するか（テスト技法・カバレッジ方針）**を確定する層——に限る。

これは WF テスト工程の**3本目**のレシピである（1本目＝[`./test-case-spec.md`](./test-case-spec.md)＝ケース仕様・2本目＝[`./test-plan.md`](./test-plan.md)＝計画）。本レシピは階層上**ケース仕様の直上**に位置し、計画が確定したテストレベル／タイプの枠組みを受けて、テスト条件を導き網羅の方針を立てる。**設計仕様は「テスト条件＝抽象的なテスト項目・高レベルケース」までで、個々のケースの具体的入力値・期待結果（低レベルケース）は書かない**（それはケース仕様）。

| 工程 | 本レシピでの扱い |
|---|---|
| **テスト計画** | 隣接（上位）。プロジェクトのテスト対象・対象外＋理由・終了基準・テストレベル/タイプの枠組みは計画（[`./test-plan.md`](./test-plan.md)）で確定する。本レシピは枠組みを受け、テスト条件の網羅を導く（計画の方針を転記しない） |
| **テスト設計仕様** | 対象。SRS／設計から導いた抽象的なテスト項目（テスト条件＝高レベルケース）・それをどう網羅するか（テスト技法＝同値分割/境界値分析等＋カバレッジ方針）・対応要件/設計へのトレーサビリティをここで確定する |
| **テストケース仕様** | 隣接（下位）。1ケースの事前条件・入力・操作・**具体的な期待結果（低レベルケース）**はケース仕様（[`./test-case-spec.md`](./test-case-spec.md)）の担当。**設計仕様にケース具体値を書かない**（P7／P8: 階層を飛び越えない） |

責務対照表（responsibility-map.md のテスト仕様行）は「テスト戦略・計画・設計仕様・ケース仕様・手順仕様」を含む範囲、「**設計仕様への低レベルケースの混入**」を含まない範囲と定める。本レシピはこの境界を設計仕様レベルへ具体化する。

### F1 同型の隣接境界（設計仕様＝抽象 ↔ ケース仕様＝具体値）

本レシピの肝は **設計仕様（テスト条件＝抽象）とケース仕様（具体値）の境界**である。設計仕様は「テスト条件＝抽象的なテスト項目・高レベルケース」までを書き、個々のケースの具体的入力値・期待結果（低レベルケース）はケース仕様へ降ろす。これは **F1（基本設計＝論理 ER ↔ 詳細設計＝物理 ER。[`../basic-design/data-design.md`](../basic-design/data-design.md) ↔ [`../detailed-design/data-design.md`](../detailed-design/data-design.md)）と同型**の隣接境界——抽象 vs 具体を工程で割る——である。論理 ER がエンティティ・関連（抽象）までで型/NULL/index（物理＝具体）を書かないのと同じく、テスト設計仕様はテスト条件（抽象）までで具体的入力値・期待結果（具体）を書かない。

> **低レベルケース（具体値）の混入は構造判定ゆえ機械語彙でなく rubric で見る**: 「在庫超過で登録できないこと」は設計仕様のテスト条件（抽象）だが、「在庫 10 に対し数量 11 で E-STOCK が返る」は具体値であり、特定の禁止語では弾けない**構造の問題**である。機械（[`../../scripts/check_vocabulary.py`](../../scripts/check_vocabulary.py)）では拾えないため [`../../rubric/test-design-spec.md`](../../rubric/test-design-spec.md) の質的判定（観点3＝F1 同型境界）へ委ねる。

### 必須は絞る／残りは推奨（このスライス固有の設計理由）

**必須節**: `テスト条件`（SRS／設計から導いた**抽象的なテスト項目・高レベルケース**＝具体値でない）／`網羅方針`（同値分割・境界値分析等の**テスト技法**とカバレッジ方針＝どう網羅するか）／`トレーサビリティ`（対応要件/設計へ）。

- **`網羅方針` を独立必須にするのが肝**。設計仕様の核は「テスト条件を**どう網羅するか**（テスト技法・カバレッジ）」である。テスト条件だけ並べて網羅の根拠が無い設計仕様＝設計仕様の体をなさない。`網羅方針` を独立必須見出しにして欠落を機械検出する（[`../../scripts/check_headings.py`](../../scripts/check_headings.py)）。これは非機能設計が `測定方法` を独立必須にして「値はあるが測定方法なし」を機械検出するのと同型である。
- **`テスト条件` は抽象（高レベルケース）に留める**。具体値（低レベルケース）はケース仕様へ降ろす（上記 F1 同型）。

**推奨節（必須にしない）**: `テスト観点`（性能/セキュリティ/使用性等のテストタイプの枠組み・ただしテストレベル/タイプ自体は計画と重なるので「観点の網羅をここで導く」位置づけ）／`前提・制約`。**必須にすると小さい設計仕様でも全節を埋めさせる過剰テンプレ化（gold plating）を招くため、必須にしない**（test-plan が IEEE 829 の多セクションを全強制しない・Design Doc が arc42 全12セクション埋めを強制しないのと同じ判断）。

> **なぜ「導入見出し」を `位置づけ` にするか（機械表現の罠回避）**: 機械判定（[`../../scripts/check_headings.py`](../../scripts/check_headings.py)）は見出しの**部分一致**で必須を見る。スキーマ（[`../../scripts/schema/test-design-spec.json`](../../scripts/schema/test-design-spec.json)）の `required_headings` は `["テスト条件", "網羅方針", "トレーサビリティ"]` の3語で、いずれもスラッシュ等の罠がなく実見出しに素直に部分一致する。導入見出しを `スコープ` 等にすると別の罠になりうるが、本スライスの必須3語に部分一致する導入語は無いため `位置づけ` を導入見出しに用いる（必須語を導入見出しに紛れ込ませると、専用節を削っても誤 pass する＝cycle-15 のデコイ教訓を回避）。

**境界を越えた記述の扱い**（詳細は末尾の越境 note）:
- 個々のテストケースの具体的入力値・期待結果（低レベルケース）が設計仕様に紛れ込んでいたら、ケース仕様（[`./test-case-spec.md`](./test-case-spec.md)）へ移す（F1〔論理/物理〕と同型の隣接境界＝抽象/具体を割る）。
- 要件文そのものが設計仕様やトレーサビリティに転記されていたら、SRS（[`../requirements/srs.md`](../requirements/srs.md)）へ一元化し、設計仕様側は **ID 参照に置換**する（P6）。
- 計画事項（テスト対象・対象外宣言・終了基準・テストレベル/タイプの枠組み）が設計仕様に逆流していたら、計画（[`./test-plan.md`](./test-plan.md)）へ戻す（階層を飛び越えない）。

## テスト条件

SRS／設計から導いた**抽象的なテスト項目（高レベルケース）**を識別する。ここでは「何を確認するか」までを書き、具体的な入力値・期待結果（低レベルケース）はケース仕様へ降ろす（F1 同型＝抽象/具体を工程で割る）。

**含む**: 確認すべきテスト条件の一覧（正常系・異常系・境界値・業務ルールの検証点など、抽象的なテスト項目）・各条件が対応する要件/設計 ID・条件ごとに想定するケース数の見立て（高レベル）。

**含まない**: 具体的な入力値・期待される具体的な出力値（これらはケース仕様＝[`./test-case-spec.md`](./test-case-spec.md) の対象。F1 同型）。テスト対象・対象外の宣言・終了基準（計画レベル）。実行の逐次手順（手順仕様レベル）。

> **テスト条件も観測可能に書く（P6・高レベルでも）**: テスト条件は抽象だが、「機能が（測定不能マーカー）することを確認する」のような非観測の動詞句で逃げない。抽象のままでも「在庫超過で登録できないことを確認する」のように観測へ降ろせる方向で書く。本レシピで避けるべき非観測の定型句（厳密な3語）は末尾の越境 note のフェンスブロックに列挙する（語彙チェッカーはフェンス内を検査対象外とする）。

### 例（最小限・テンプレート用）

```
TCD-01 受注登録の正常系     対応要件: FR-01    （高レベル: 在庫内数量で登録が成立するか）
TCD-02 在庫超過の業務エラー  対応要件: FR-01    （境界: 在庫数ちょうど／+1 の振る舞い）
TCD-03 受注照会の応答性能    対応要件: NFR-PERF-01（負荷条件下の応答時間分布が合意水準に収まるか）
```

> テスト条件は「抽象」止まりにする。たとえば「在庫超過で登録できないこと」までがテスト条件であり、「在庫 10 に対し数量 11 を入力したら業務エラー E-STOCK が返る」は具体値であるためケース仕様へ書く（F1 同型）。

## 網羅方針

テスト条件を**どう網羅するか**——**テスト技法とカバレッジ方針**——を確定する。これが設計仕様の核である。テスト条件だけ並べて網羅の根拠が無い設計仕様は設計仕様の体をなさない。

**含む**: テスト技法（同値分割・境界値分析・デシジョンテーブル・状態遷移・組み合わせ等）の選択と、各テスト条件への適用方針・カバレッジ方針（機能カバレッジ・分岐網羅 C1 等の**測定可能な目標**）・性能等の NFR では網羅の前提（負荷条件・分位点）。

**含まない**: 個々のケースの具体的入力値・期待結果（ケース仕様の対象）・チューニング手順や計測スクリプト等の実現手段（非機能設計／運用設計／後続工程の対象）。

> **カバレッジ方針は測定可能に書く（P6）**: 「網羅的に確認する」「十分にカバーする」のような測定不能な方針では網羅の達成を一意に判定できない。機能カバレッジ 95% 以上・分岐網羅（C1）100% 目標・有効/無効同値類の全網羅のような**観測可能・判定可能**な目標で書く。

### 例（最小限・テンプレート用）

```
技法:
  - 正常系・異常系  : 同値分割（有効同値類・無効同値類を識別）
  - 在庫数の境界    : 境界値分析（在庫ちょうど／+1）
  - 業務ルール分岐  : デシジョンテーブル

カバレッジ方針:
  - 機能カバレッジ（要件 ID 数に対する検証済み ID 数）95% 以上
  - 主要業務ロジックの分岐網羅（C1）100% 目標
  - 性能テスト条件は負荷条件（同時利用者 50・データ 10,000 件）と p95 を網羅の前提に明記
```

## テスト観点

> **推奨セクション**（必須ではない）。性能・セキュリティ・使用性等の**テストタイプの枠組み**を整理し、観点の網羅をテスト条件へ橋渡しする。

**含む**: テストタイプ（性能・セキュリティ・使用性・互換性等）の枠組みと、各タイプで導出すべきテスト条件の方向性。

**含まない**: テストレベル/タイプの組織方針そのもの（計画レベル＝[`./test-plan.md`](./test-plan.md) の担当。ここは「観点の網羅をテスト条件へ降ろす」位置づけに留める）・具体的入力値・期待結果（ケース仕様）。

> テスト観点は計画の「テストレベル/タイプ」と重なる。重複転記でなく、計画の枠組みを受けて**観点ごとのテスト条件の網羅をここで導く**（同期負債を避ける＝計画の方針は転記せず参照する）。

## 前提・制約

> **推奨セクション**（必須ではない）。本設計仕様が前提とするテストレベル・環境前提・適用範囲の制約を記す。プロジェクト規模に応じて省略してよい。

**含む**: 対象とするテストレベル（結合・システム等）・テストデータの前提・本設計仕様の適用範囲の制約。

**含まない**: 終了基準・テスト対象/対象外の宣言（計画レベル）・具体的なケースデータ（ケース仕様）。

## トレーサビリティ

各**テスト条件**を、対応する**要件 ID／設計要素**へ紐付ける。要件文は転記せず **ID 参照**にとどめる（P6）。対応の無い孤立テスト条件（根拠のないテスト）を作らない（P4: 全要素トレース可能）。

**表の書き方（テスト条件 → 要件/設計）**:
- ID 列のヘッダに「**対応**」を含める（例: `対応要件/設計 ID`）。第1列はテスト条件名（主語）であり、機械の [`../../scripts/check_traceability.py`](../../scripts/check_traceability.py) は第1列を主語として除外し、「対応」を含む列を ID 列とみなす。
- 全セルを埋める。対応列が空・ダッシュ（`-`）のテスト条件は孤立テスト条件であり、機械が検出する逸脱になる。
- 要件文（What の文言・Why の説明）は写さない。必要なら SRS を ID で参照する。

| テスト条件 | 対応要件/設計 ID | 備考 |
|---|---|---|
| TCD-01 受注登録の正常系 | FR-01/UC-02 | 在庫内数量での登録成立 |
| TCD-02 在庫超過の業務エラー | FR-01 | 在庫境界の振る舞い |
| TCD-03 受注照会の応答性能 | NFR-PERF-01 | 応答時間分布 |

**逸脱の判定基準**:
- 「対応要件/設計 ID」が空（またはダッシュ）のテスト条件が存在する → 孤立テスト条件（根拠のないテスト）。対応の補完またはテスト条件の削除を検討する（**空セルそのものの検出は機械の [`../../scripts/check_traceability.py`](../../scripts/check_traceability.py) の担当**）。
- 対応が形式上は埋まっているが、その要件/設計とテスト条件が意味的に食い違う → 紐付けの質の問題であり、[`../../rubric/test-design-spec.md`](../../rubric/test-design-spec.md) の質的判定で見る。
- トレーサビリティ表やテスト条件に要件文が逐語転記されている → ID 参照へ置換し、文言は SRS へ一元化する（P6）。

## 越境 note（粒度・帰属のズレ検出）

設計仕様に以下が現れたら、設計仕様レベルを越境している。該当工程へ移送する。曖昧表現の厳密な語はフェンスブロック内に列挙する（語彙チェッカーはフェンス内を検査対象外とする。地の文では言い換える）。

```
テスト条件に書いてはいけない非観測マーカー（出たら観測可能なテスト条件へ書き換える）:

  正しく表示  → 「件数 N が画面に出る」等、観測できる値・状態を導くテスト条件へ
  正しく動作  → 「ステータスが confirmed になる」「HTTP 200 が返る」等、観測できる結果を導くテスト条件へ
  適切に処理  → 「在庫が 10 → 7 に減る」「エラーコード E-STOCK が返る」等、観測できる状態変化を導くテスト条件へ
```

- **低レベルケース（具体的入力値・期待結果）の混入**が設計仕様に出たら → ケース仕様（[`./test-case-spec.md`](./test-case-spec.md)）へ。設計仕様は「テスト条件＝抽象・どう網羅するか」までに留め、具体値（事前条件・入力値・操作・観測値）はケース仕様へ降ろす（**F1〔論理/物理〕と同型の隣接境界＝抽象/具体を割る**）。
- **計画事項**（テスト対象・対象外宣言・終了基準・テストレベル/タイプの組織方針）が設計仕様に逆流したら → 計画（[`./test-plan.md`](./test-plan.md)）へ。階層を飛び越えない（P7／P8）。
- **要件文の逐語転記・要件の Why** が設計仕様／トレーサビリティに出たら → SRS（[`../requirements/srs.md`](../requirements/srs.md)）へ一元化し、設計仕様側は **ID 参照に置換**する（P6）。
- **網羅方針の測定不能な曖昧表現**（上記3語の定型句のほか「十分に」「網羅的に」等の言い換え）が出たら → 観測可能・判定可能なカバレッジ方針へ書き換える（P6）。

> 対比に注意: 上記3語の定型句（非観測マーカー）はテスト条件の禁止対象（[`../../scripts/vocab/test-design-spec.json`](../../scripts/vocab/test-design-spec.json) の forbidden で機械検出）だが、**低レベルケース（具体値）の混入**は特定語ではなく**構造の問題**であり、機械語彙では弾かず質的判定（[`../../rubric/test-design-spec.md`](../../rubric/test-design-spec.md)）に委ねる。

## vocab の説明（test-case-spec/test-plan の3語を踏襲＝WF だが「綺麗に拾えるか」で決めた）

**本 doc_type（test-design-spec）の機械語彙チェック（vocab）は test-case-spec／test-plan の曖昧期待結果3語を踏襲して非空である**（[`../../scripts/vocab/test-design-spec.json`](../../scripts/vocab/test-design-spec.json) の forbidden に3語）。厳密な3語は上の越境 note のフェンスブロックに列挙してある（語彙チェッカーはフェンス内を検査対象外とするため、本レシピは禁止語を語りつつ自己 pass を保てる）。

**vocab の有無は『その doc_type の逸脱が機械で綺麗に拾えるか』で決まる——agile か WF かの別ではない**（[`../../agile/design-doc.md`](../../agile/design-doc.md) で確立した原則の延長。[`./test-plan.md`](./test-plan.md) が WF 側で実証）。test-design-spec は WF だが、それだけで vocab を持つと決めたのではない。**経験的に**次を確認して踏襲を決めた:

- test-design-spec は抽象（テスト条件・網羅方針）が主眼で具体的期待結果を書かないため、3語の**出番は test-plan より薄い可能性があった**。しかし実機検証で、設計仕様の高レベルケース（テスト条件）に「受注登録機能が（非観測マーカー）することを確認する観点を設ける」のような非観測条件が紛れる逸脱が実在し、3語とも **deviation を返す出番がある**ことを確認した（テスト条件も P6＝観測可能を担保すべきため）。
- これら3語は test-design-spec の**正当な地の文**（テスト条件の境界識別・網羅方針の同値分割/境界値/分岐網羅 C1 100%・テスト観点の性能/セキュリティ/使用性・トレーサビリティ・PostgreSQL を含む散文）に対し**誤爆しない**（実機で pass を確認）。

両者が満たされる＝「逸脱が機械で綺麗に拾える」ため踏襲した。**出番が乏しければ空にしていた**（user-story / Design Doc が agile でも vocab を空にしたのと同じ判断軸）。これが「**WF でも vocab の有無は逸脱が綺麗に拾えるかで決まる**」ことの、同じ WF テスト工程内での再実証である（test-case-spec／test-plan は踏襲・本スライスも経験検証して踏襲）。

> **機械で弾かないもの（誤爆回避・非対称継続）**: 技術スタック名・製品名・`SQL`・ツール名（JUnit 等）は test-design-spec のテスト条件の対象環境・網羅方針の技法記述で正当に現れるため禁止語にしない。とりわけ `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出・WF 既存スライスと同方針）。また**低レベルケース（具体値）の混入**・**網羅方針の3語以外の曖昧表現の言い換え**（「十分に」「網羅的に」等）は構造・文脈の判定であり、機械では拾えないため [`../../rubric/test-design-spec.md`](../../rubric/test-design-spec.md) の質的判定へ委ねる。

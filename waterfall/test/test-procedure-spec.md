> **レイヤー**: 第2層レシピ（手法別具体指針・テスト）
> **原則参照**: [`../../principles/granularity-axis.md`](../../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。
> **責務対照**: [`../../principles/responsibility-map.md`](../../principles/responsibility-map.md) のテスト仕様行〔手順仕様レベル〕を参照（テスト戦略・計画・設計仕様・ケース仕様・手順仕様のうち、本レシピは**手順仕様**＝実行のしかた〔実行手順・ステップ順〕を担う。**各操作の期待結果の合否判定〔What to expect〕は含まない**＝それはケース仕様＝[`./test-case-spec.md`](./test-case-spec.md)）。

## 位置づけ

このレシピが対象とする**テスト工程の範囲**を明確にする。テスト文書は抽象度・段階で階層化される（計画 → 設計仕様 → ケース仕様 → **手順仕様**の4層。テスト戦略は組織横断の方針層として計画の直上に分離する〔戦略/計画の二分は厳密な規格境界ではない＝P7 注〕。P7）。本レシピが担うのは**手順仕様（Test Procedure Specification）レベル**——確定したテストケースを**どの開始状態・環境から、どのステップ順で実行するか（How to run）**を定める層——に限り、階層上**最下位＝ケース仕様の直下**に位置する。

これは WF テスト工程の**4本目**のレシピである（1本目＝[`./test-case-spec.md`](./test-case-spec.md)＝ケース仕様・2本目＝[`./test-plan.md`](./test-plan.md)＝計画・3本目＝[`./test-design-spec.md`](./test-design-spec.md)＝設計仕様）。ケース仕様が「1ケースの事前条件・入力・操作・**期待結果（What to expect）**」を確定するのに対し、**手順仕様は『どう実行するか』＝開始状態・環境の前提とステップ順の操作のみを書き、各操作の期待結果の合否判定は書かない**（それはケース仕様）。

| 工程 | 本レシピでの扱い |
|---|---|
| **テスト設計仕様** | 上流（隣接ではない）。テスト条件＝抽象（高レベルケース）・どう網羅するか（技法・カバレッジ）は設計仕様（[`./test-design-spec.md`](./test-design-spec.md)）で確定する。設計意図・テスト条件を手順仕様に逆流させない |
| **テストケース仕様** | 隣接（上位）。1ケースの事前条件・入力・操作・**期待結果（合否＝What to expect）**はケース仕様（[`./test-case-spec.md`](./test-case-spec.md)）が確定する。手順仕様は**そのケースを実行する手順**を定め、判定基準はケース仕様へ ID 参照する |
| **テスト手順仕様** | 対象。実行を始める**前提・セットアップ**（開始状態・環境）と、ケースを実行する**ステップ順の操作（実行手順）**・対応ケース ID へのトレーサビリティをここで確定する。**期待結果の合否判定は書かない**（ケース仕様の領分） |

責務対照表（responsibility-map.md のテスト仕様行）は「テスト戦略・計画・設計仕様・ケース仕様・手順仕様」を含む範囲、「設計仕様への低レベルケースの混入・要件文の転記」等を含まない範囲と定める。本レシピはこの境界を手順仕様レベルへ具体化する。

### 隣接境界＝実行（How to run）↔ 判定（What to expect）（このスライスの肝）

本レシピの肝は **手順仕様（実行＝How to run）とケース仕様（判定＝What to expect）の境界**である。手順仕様は「実行手順＝ステップ順・操作」と「その前提＝開始状態・環境」を書き、**各操作の期待結果の合否判定（What to expect）は書かない**。ケース仕様を挟んで、上が設計仕様（抽象・テスト条件＝F1 同型の抽象/具体境界）、下が手順仕様（実行）であり、手順仕様↔ケース仕様の境界は **「実行のしかた vs 期待結果の判定」の分離**である。

> **判定基準の混入は構造判定ゆえ機械語彙でなく rubric・越境 note で見る**: 「登録ボタンを押す」は手順仕様の操作（実行）だが、「登録すると受注番号が（判定基準）されることを確認する」は期待結果の合否判定（What to expect＝ケース仕様）であり、判定基準の混入の多く（観測可能な合否判定の言い換え等）は特定の禁止語では弾けない**構造の問題**である。機械（[`../../scripts/check_vocabulary.py`](../../scripts/check_vocabulary.py)）の対象は曖昧期待結果3語の単純な出現のみであり、3語に当たらない判定基準の混入・設計意図/テスト条件（設計仕様）の逆流は [`../../rubric/test-procedure-spec.md`](../../rubric/test-procedure-spec.md) の質的判定（観点3＝隣接境界）へ委ねる。

### 必須は絞る／残りは推奨（このスライス固有の設計理由）

**必須節**: `前提・セットアップ`（どの開始状態・環境から実行を始めるか＝再現性の前提）／`実行手順`（ステップ順・操作）／`トレーサビリティ`（対応ケース ID へ）。

- **`前提・セットアップ` を独立必須にするのが肝**。手順だけあって開始状態・環境（投入データ・初期値・認証状態・対象バージョン）が不明なら、その手順は**再現できない**。前提節の欠落を機械検出する（[`../../scripts/check_headings.py`](../../scripts/check_headings.py)）。これは非機能設計が `測定方法` を独立必須にして「値はあるが測定方法なし」を機械検出し、test-design-spec が `網羅方針` を独立必須にして「条件は並ぶが網羅根拠なし」を機械検出するのと**同型**である。
- **`実行手順` は操作（実行）に留める**。各操作の期待結果の合否判定（What to expect）はケース仕様へ ID 参照する（上記の実行↔判定の分離）。

> **なぜ「導入見出し」を `位置づけ` にするか（機械表現の罠回避）**: 機械判定（[`../../scripts/check_headings.py`](../../scripts/check_headings.py)）は見出しの**部分一致**で必須を見る。スキーマ（[`../../scripts/schema/test-procedure-spec.json`](../../scripts/schema/test-procedure-spec.json)）の `required_headings` は `["前提", "実行手順", "トレーサビリティ"]` の3語で、実見出し `## 前提・セットアップ` に `前提` が素直に部分一致する（中黒込みの `前提・セットアップ` を required にすると完全一致依存の罠になりうるため `前提` で機械表現する）。導入見出しを `スコープ` 等にすると別の罠になりうるが、本スライスの必須3語に部分一致する導入語は無いため `位置づけ` を導入見出しに用いる（必須語を導入見出しに紛れ込ませると、専用節を削っても誤 pass する＝cycle-15/16 のデコイ教訓を回避）。
>
> **デコイ厳禁（cycle-15/16 教訓）**: `前提`／`実行手順`／`トレーサビリティ` の各必須語を、導入見出し・推奨節見出しに**部分一致で紛れ込ませない**。とくに `前提` が必須語であるため、推奨節に「前提・制約」のような `前提` を含む見出しは置けない（test-design-spec は推奨節に「前提・制約」を使ったが、本スライスでは使えない＝推奨節は別名にする）。各必須語が**実見出しに1つだけ部分一致**するように見出しを設計する（専用節を削った版が確実に deviation になることを保証する）。

**推奨節（必須にしない・必須語を見出しに含めない）**: `事後処理`（テスト後のクリーンアップ）／`実行環境`（前提に含めず分けたい場合）等。**必須にすると小さい手順仕様でも全節を埋めさせる過剰テンプレ化（gold plating）を招くため、必須にしない**（test-plan が IEEE 829 の多セクションを全強制しない・Design Doc が arc42 全12セクション埋めを強制しない・test-design-spec が前提制約等を推奨にしたのと同じ判断）。推奨節の見出しに必須語〔`前提`／`実行手順`／`トレーサビリティ`〕を部分一致で含めない（デコイ回避）。

**境界を越えた記述の扱い**（詳細は末尾の越境 note）:
- 各操作の期待結果の合否判定（What to expect＝合否基準）が手順に紛れ込んでいたら、ケース仕様（[`./test-case-spec.md`](./test-case-spec.md)）へ移す（実行↔判定の隣接境界）。
- 設計意図・テスト条件（抽象・どう網羅するか）が手順仕様に逆流していたら、設計仕様（[`./test-design-spec.md`](./test-design-spec.md)）へ戻す（階層を飛び越えない＝P7／P8）。
- ケース内容（事前条件・入力値・期待結果）を逐語転記していたら、ケース ID 参照に置換する（P6 同型＝転記は二重管理の温床）。

## 前提・セットアップ

実行を始める前に**成立していなければならない開始状態・環境**を定める。前提が曖昧だと、誰が実行しても同じ初期条件から始められず、手順を**再現できない**（再現性は手順仕様の核）。

**含む**: 対象環境（テスト環境・対象バージョン・依存ミドルウェア＝製品名/ツール名は環境記述として正当に書ける）・開始状態（初期データ・初期値・在庫等の状態）・認証/セッションの前提・投入データ（フィクスチャ・シードデータ）。

**含まない**: 各操作の期待結果の合否判定（What to expect＝ケース仕様の対象）・テスト条件＝抽象/網羅方針（設計仕様の対象）・テスト対象/対象外宣言・終了基準（計画の対象）。

> **前提を「特になし」で逃げない**: 手順仕様で前提が本当に空であることは稀である。投入データ・初期値・認証状態・対象バージョンのいずれかは必ず実行の前提になる。前提節の中身の質（再現可能な具体性があるか・"特になし" で逃げていないか）は [`../../rubric/test-procedure-spec.md`](../../rubric/test-procedure-spec.md) の質的判定で見る（見出しの有無は機械・中身の質は rubric の分担）。

### 例（最小限・テンプレート用）

```
対象環境 : テスト環境（アプリ v2.3.0 デプロイ済み・DB は本番同等スキーマ投入済み）
開始状態 : 商品 P-100 の在庫=10、顧客 C-001 登録済み、受注テーブルは空
認証     : テストユーザー tester01 でログイン済みの状態から開始
投入データ: フィクスチャ orders-seed をロード
```

## 実行手順

確定したテストケース（ケース仕様で期待結果まで定めたケース）を実行する**ステップ順の操作**を定める。各ステップは**操作（働きかけ）**であり、観測した結果の合否判定は**対応ケース ID のケース仕様に従う**（本書には判定基準を書かない＝実行↔判定の分離）。

**含む**: 番号付き等で順序が一意に決まる操作のステップ（画面遷移・入力・押下・送信・反復実行など）・反復回数や順序依存（先に X を実行してから Y）・各ステップが対応するケース ID（参照）。

**含まない**: 各操作の**期待結果の合否判定**（What to expect＝「…されることを確認」型の判定基準・観測値の合否＝ケース仕様の対象）・設計意図/テスト条件（設計仕様の対象）・ケース内容の逐語転記（ケース ID 参照に置換）。

> **操作のみを書き、判定基準を書かない（実行↔判定の分離）**: 「登録ボタンを押す」は操作（実行）であり手順仕様に書く。「登録すると受注番号が表示されることを確認する」は期待結果の合否判定（What to expect）であり**ケース仕様**に書く（手順仕様には書かず、対応ケース ID を参照する）。手順に判定基準が混じるのは期待結果の逆流（越境）である。曖昧表現の厳密な語（判定基準混入の典型）は末尾の越境 note のフェンスブロックに列挙する（語彙チェッカーはフェンス内を検査対象外とする）。

> **粒度の目安（P5・検出補助）**: ステップは「再現可能な単一の働きかけ」を1つの粒度にする。1ステップに複数の独立操作を詰めて順序が曖昧になる（過大）／逆に自明な所作まで刻みすぎる（過小）のを避ける。粒度の境界は [`../../rubric/test-procedure-spec.md`](../../rubric/test-procedure-spec.md) の質的判定で見る。

### 例（最小限・テンプレート用）

```
1. 受注登録画面を開き、顧客=C-001・商品=P-100・数量=3 を入力する。
2. 登録ボタンを押す。
3. 数量欄を 11 に変更し、再度登録ボタンを押す（在庫超過ケースの操作）。
4. 数量欄を 10 に変更し、登録ボタンを押す（在庫境界ケースの操作）。
5. 受注照会画面へ遷移し、既存の受注番号で照会を 1,000 回反復実行する（性能ケースの操作）。

→ 各ステップの観測結果の合否判定は対応ケース ID（TC-01〜TC-04）のケース仕様に従う。
   本書は操作の順序と働きかけのみを定める（期待結果＝判定基準は書かない）。
```

## 事後処理（推奨・必須にしない）

> **推奨セクション**（必須ではない）。テスト実行後のクリーンアップ・環境の原状回復を定める。プロジェクト規模に応じて省略してよい（必須にすると小さい手順仕様でも全節を埋めさせる gold plating を招くため、必須にしない）。

**含む**: テストデータの削除・初期化（truncate・初期値への復元）・セッションのログアウト・一時生成物の片付け。

**含まない**: 各操作の期待結果の合否判定（ケース仕様）・終了基準（計画）。

> `実行環境` を前提・セットアップから分けて書きたい場合も推奨節として扱う。**推奨節の見出しに必須語〔`前提`／`実行手順`／`トレーサビリティ`〕を部分一致で含めない**（デコイ回避＝cycle-15/16 教訓。とくに `前提` は必須語のため「前提・制約」のような見出しは使わない）。

## トレーサビリティ

各**実行手順**を、対応する**ケース仕様の ID**へ紐付ける。ケース内容（期待結果・入力値）は転記せず **ID 参照**にとどめる。対応の無い孤立手順（根拠のない実行）を作らない（P4: 全要素トレース可能）。

**表の書き方（実行手順 → ケース）**:
- ID 列のヘッダに「**対応**」を含める（例: `対応ケース ID`）。第1列は実行手順名（主語）であり、機械の [`../../scripts/check_traceability.py`](../../scripts/check_traceability.py) は第1列を主語として除外し、「対応」を含む列を ID 列とみなす。
- 全セルを埋める。対応列が空・ダッシュ（`-`）の手順は孤立手順であり、機械が検出する逸脱になる。
- ケース内容（期待結果の文言・入力値）は写さない。必要ならケース仕様を ID で参照する。

| 実行手順 | 対応ケース ID | 備考 |
|---|---|---|
| 手順1-2 受注登録の操作 | TC-01 | 在庫内数量での登録操作 |
| 手順3 在庫超過の操作 | TC-02 | 在庫超過数量での登録操作 |
| 手順4 在庫境界の操作 | TC-03 | 在庫ちょうどでの登録操作 |
| 手順5 受注照会の反復操作 | TC-04 | 負荷条件下の照会操作 |

**逸脱の判定基準**:
- 「対応ケース ID」が空（またはダッシュ）の手順が存在する → 孤立手順（根拠のない実行）。対応の補完または手順の削除を検討する（**空セルそのものの検出は機械の [`../../scripts/check_traceability.py`](../../scripts/check_traceability.py) の担当**。rubric は過大主張しない＝cycle-12/F5 の教訓）。
- 対応が形式上は埋まっているが、その手順が実行するケースと意味的に食い違う → 紐付けの質の問題であり、[`../../rubric/test-procedure-spec.md`](../../rubric/test-procedure-spec.md) の質的判定で見る。
- トレーサビリティ表や手順にケース内容（期待結果・入力値）が逐語転記されている → ID 参照へ置換し、文言はケース仕様へ一元化する。

## 越境 note（粒度・帰属のズレ検出）

手順仕様に以下が現れたら、手順仕様レベルを越境している。該当工程へ移送する。曖昧表現の厳密な語はフェンスブロック内に列挙する（語彙チェッカーはフェンス内を検査対象外とする。地の文では言い換える）。

```
手順に書いてはいけない判定基準マーカー（出たら期待結果＝ケース仕様 test-case-spec へ移す）:

  正しく表示  → 「…が正しく表示されることを確認」型の合否判定は手順に書かずケース仕様へ
  正しく動作  → 「…が正しく動作することを確認」型の合否判定は手順に書かずケース仕様へ
  適切に処理  → 「…が適切に処理されることを確認」型の合否判定は手順に書かずケース仕様へ
```

- **各操作の期待結果の合否判定**（What to expect＝「…されることを確認」型の判定基準・観測値の合否）が手順に出たら → ケース仕様（[`./test-case-spec.md`](./test-case-spec.md)）へ。手順仕様は「どう実行するか（操作・ステップ順）」と「その前提」までに留め、判定基準は書かない（**実行↔判定の隣接境界**＝このスライスの肝）。
- **設計意図・テスト条件**（抽象・どう網羅するか）が手順仕様に逆流したら → 設計仕様（[`./test-design-spec.md`](./test-design-spec.md)）へ。階層を飛び越えない（P7／P8）。
- **ケース内容の逐語転記**（期待結果の文言・入力値）が手順／トレーサビリティに出たら → ケース仕様へ一元化し、手順仕様側は **ケース ID 参照に置換**する（P6 同型＝転記は二重管理の温床）。
- **手順の粒度過大／過小**（複数の独立操作を1ステップに詰めて順序が曖昧／自明な所作まで刻みすぎ）は構造・文脈の判定であり、機械では拾えないため [`../../rubric/test-procedure-spec.md`](../../rubric/test-procedure-spec.md) の質的判定へ委ねる。

> 対比に注意: 上記3語の定型句（判定基準混入マーカー）は手順仕様の禁止対象（[`../../scripts/vocab/test-procedure-spec.json`](../../scripts/vocab/test-procedure-spec.json) の forbidden で機械検出）だが、**3語に当たらない判定基準の混入**・**設計意図/テスト条件の逆流**・**ケース内容の逐語転記**・**手順の粒度過大/過小**は特定語ではなく**構造の問題**であり、機械語彙では弾かず質的判定（[`../../rubric/test-procedure-spec.md`](../../rubric/test-procedure-spec.md)）に委ねる。

## vocab の説明（test-case-spec/test-plan/test-design-spec の3語を踏襲＝WF だが「綺麗に拾えるか」で決めた）

**本 doc_type（test-procedure-spec）の機械語彙チェック（vocab）は test-case-spec／test-plan／test-design-spec の曖昧期待結果3語を踏襲して非空である**（[`../../scripts/vocab/test-procedure-spec.json`](../../scripts/vocab/test-procedure-spec.json) の forbidden に3語）。厳密な3語は上の越境 note のフェンスブロックに列挙してある（語彙チェッカーはフェンス内を検査対象外とするため、本レシピは禁止語を語りつつ自己 pass を保てる）。

**vocab の有無は『その doc_type の逸脱が機械で綺麗に拾えるか』で決まる——agile か WF かの別ではない**（[`../../agile/design-doc.md`](../../agile/design-doc.md) で確立した原則の延長。[`./test-plan.md`](./test-plan.md)／[`./test-design-spec.md`](./test-design-spec.md) が WF テスト工程で実証）。test-procedure-spec は WF だが、それだけで vocab を持つと決めたのではない。**経験的に**次を確認して踏襲を決めた:

- 手順仕様は**操作（実行手順）のみを書き、各操作の期待結果の合否判定（What to expect）はケース仕様の領分**である（実行↔判定の隣接境界）。よって3語が手順に出る＝「…が（厳密な3語はフェンス内）されることを確認」のように**期待結果の判定基準が手順へ混入したサイン**であり、3語とも実機で **deviation を返す出番がある**ことを確認した（手順に判定基準が逆流する逸脱が実在する）。
- これら3語は test-procedure-spec の**正当な地の文**（前提・セットアップの状態/環境記述・実行手順の操作〔「ボタンを押す」「データを入力する」〕・トレーサビリティ・PostgreSQL/MySQL を含む散文）に対し**誤爆しない**（実機で pass を確認）。

両者が満たされる＝「逸脱が機械で綺麗に拾える」ため踏襲した。**出番が乏しければ空にしていた**（user-story / Design Doc が agile でも vocab を空にしたのと同じ判断軸）。これが「**WF でも vocab の有無は逸脱が綺麗に拾えるかで決まる**」ことの、WF テスト工程内での再々実証である（test-case-spec／test-plan／test-design-spec は踏襲・本スライスも経験検証して踏襲）。

> **機械で弾かないもの（誤爆回避・非対称継続）**: 技術スタック名・製品名・`SQL`・ツール名（JUnit 等）は test-procedure-spec の前提・セットアップ／実行環境で正当に現れるため禁止語にしない。とりわけ `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出・WF 既存スライスと同方針）。また**3語に当たらない判定基準の混入**・**設計意図/テスト条件の逆流**・**ケース内容の逐語転記**・**手順の粒度過大/過小**は構造・文脈の判定であり、機械では拾えないため [`../../rubric/test-procedure-spec.md`](../../rubric/test-procedure-spec.md) の質的判定へ委ねる。

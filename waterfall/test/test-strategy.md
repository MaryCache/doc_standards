> **原則参照**: [`../../principles/granularity-axis.md`](../../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。

## 位置づけ

このレシピが対象とする**テスト工程の範囲**を明確にする。テスト文書は抽象度で階層化される（計画 → 設計仕様 → ケース仕様 → 手順仕様の4層。**テスト戦略**は組織横断の方針層として計画の直上に分離する〔戦略/計画の二分は厳密な規格境界ではない＝P7 注〕。P7）。本レシピが担うのは**戦略（Test Strategy）レベル**——**組織横断**で、品質目標・全体アプローチ・テストレベル/タイプの標準・自動化/環境の方針を**方針レベル**で定める層——に限り、階層上**最上位＝計画の直上**に位置する。

これは WF テスト工程の**5本目＝最上位**のレシピであり、これで**テスト工程5レベル（戦略・計画・設計仕様・ケース仕様・手順仕様）が完備**する（1本目＝[`./test-case-spec.md`](./test-case-spec.md)＝ケース仕様・2本目＝[`./test-plan.md`](./test-plan.md)＝計画・3本目＝[`./test-design-spec.md`](./test-design-spec.md)＝設計仕様・4本目＝[`./test-procedure-spec.md`](./test-procedure-spec.md)＝手順仕様）。計画が「**プロジェクト単位**で何をテストするか／いつ完了とするか」を確定するのに対し、**戦略は『組織として』どんな品質目標・アプローチ・レベル/タイプの標準を持つかを書き、プロジェクト固有の具体は書かない**（それは計画）。

| 工程 | 本レシピでの扱い |
|---|---|
| **テスト戦略** | 対象。組織横断のテスト方針（品質目標・全体アプローチ）・テストレベル/タイプの組織標準・品質目標/上位標準/事業目標へのトレーサビリティをここで確定する。**プロジェクト固有詳細は書かない**（計画の領分） |
| **テスト計画** | 隣接（下位）。プロジェクト単位の**具体的なスコープ/対象外・終了基準の具体値・スケジュール・個別ケース**は計画（[`./test-plan.md`](./test-plan.md)）が確定する。戦略は組織標準を定め、その具体化（どこまでやるか）は計画へ降ろす |
| **テスト設計仕様** | 下流（隣接ではない）。テスト観点＝高レベルのテスト条件・どう網羅するかは設計仕様（[`./test-design-spec.md`](./test-design-spec.md)）が確定する。戦略はテストレベル/タイプの**標準の枠組み**までに留め、観点の網羅は設計仕様へ降ろす |
| **テストケース仕様** | 対象外。1ケースの事前条件・入力・操作・**具体的な期待結果**はケース仕様（[`./test-case-spec.md`](./test-case-spec.md)）の担当。戦略にケース具体値を書かない（P7／P8: 階層を飛び越えない） |

責務対照表（responsibility-map.md のテスト仕様行）は「テスト戦略・計画・設計仕様・ケース仕様・手順仕様」を含む範囲、「計画へのテストケース具体値の記載／設計仕様への低レベルケースの混入／要件文の転記」等を含まない範囲と定める。本レシピはこの境界を戦略レベルへ具体化する。

### 隣接境界＝戦略（組織横断・方針）↔ 計画（プロジェクト単位）（このスライスの肝）

本レシピの肝は **戦略（組織横断）と計画（プロジェクト単位）の境界**である。これは「組織 vs プロジェクト」の**抽象度境界**であり、手順仕様↔ケース仕様が「実行 vs 判定」を割ったのとは別軸である。戦略は**組織横断のテスト方針**（品質目標・全体アプローチ・テストレベル/タイプの標準・自動化/環境の方針）を書き、**プロジェクト固有詳細（具体スケジュール・個別ケース・プロジェクトのスコープ/対象外・終了基準の具体値）は書かない**。後者は計画（[`./test-plan.md`](./test-plan.md)）の領分である。

> **プロジェクト固有詳細の混入は構造判定ゆえ機械語彙でなく rubric・越境 note で見る**: 「組織標準として機能・性能・セキュリティのテストタイプを定義する」は戦略の方針（組織横断）だが、「本リリースでは受注照会機能の性能テストを 3/15 までに実施し、p95 ≤ 3000ms を終了基準とする」はプロジェクト固有の具体（スケジュール・対象機能・終了基準の具体値＝計画）である。**プロジェクト固有詳細の混入は特定の禁止語では弾けない構造の問題**であり、機械（[`../../scripts/check_vocabulary.py`](../../scripts/check_vocabulary.py)）では拾えないため [`../../rubric/test-strategy.md`](../../rubric/test-strategy.md) の質的判定（観点3＝隣接境界）へ委ねる。

### 必須は絞る／残りは推奨（このスライス固有の設計理由）

**必須節**: `テスト方針`（組織の品質目標・全体アプローチ）／`テストレベル/タイプ`（テストレベル/タイプの組織標準＝どのレベル・タイプを組織標準とするか）／`トレーサビリティ`（品質目標/上位標準/事業目標へ）。

- **`テスト方針` に組織横断の「測定可能な品質目標」と「全体アプローチ」を書く**。"高品質を目指す" のような測定不能な抽象論で逃げると、戦略が方向性を持たない（その質は rubric の領分。後述）。
- **`テストレベル/タイプ` を独立必須にするのが肝**＝戦略の核は「組織として標準とするテストレベル・テストタイプの枠組み」であり、それを欠くと各プロジェクトが拠り所無く独自にレベルを決めることになる。**ただし V 字（要件 ↔ 設計 ↔ テスト）の1対1対応を機械的に固定で強制しない**。テストレベルとテスト対象の対応関係は古典的 V 字では1対1で語られるが、ISTQB v4 はテストレベルを固定せず状況に応じた適応を許す（memory 帰納調査の訂正＝V字1:1 は古典的・規格はレベルを固定しない）。本レシピは「組織標準として何を用意するか」までを定め、固定的な対応関係の強制はしない。

> **なぜ「導入見出し」を `位置づけ` にするか（機械表現の罠回避）**: 機械判定（[`../../scripts/check_headings.py`](../../scripts/check_headings.py)）は見出しの**部分一致**で必須を見る。スキーマ（[`../../scripts/schema/test-strategy.json`](../../scripts/schema/test-strategy.json)）の `required_headings` は `["テスト方針", "テストレベル", "トレーサビリティ"]` の3語で、`テストレベル` は実見出し `## テストレベル/タイプ` に素直に部分一致する（中黒/スラッシュ込みの `テストレベル/タイプ` を required にすると完全一致依存の罠になりうるため `テストレベル` で機械表現する＝cycle-14 の Goals/Non-Goals 教訓・test-procedure-spec の `前提・セットアップ`→`前提` と同型）。導入見出しを `テスト方針` 等にすると必須語の重複（デコイ）になるが、本スライスの必須3語に部分一致する導入語は無いため `位置づけ` を導入見出しに用いる。
>
> **デコイ厳禁（cycle-15/16/17 教訓）**: `テスト方針`／`テストレベル`／`トレーサビリティ` の各必須語を、導入見出し・推奨節見出しに**部分一致で紛れ込ませない**。推奨節 `自動化方針` は `方針` を含むが `テスト方針` を含まないため安全、`テスト環境標準` は `テスト` を含むが必須3語のいずれも部分一致しないため安全。各必須語が**実見出しに1つだけ部分一致**するように見出しを設計する（専用節を削った版が確実に deviation になることを保証する）。

**推奨節（必須にしない・必須語を見出しに含めない）**: `自動化方針`（自動化の組織方針）／`テスト環境標準`（テスト環境の組織標準）／`組織体制・役割`（テストの役割分担・責任）等。**必須にすると小さい戦略でも全節を埋めさせる過剰テンプレ化（gold plating）を招くため、必須にしない**（test-plan が IEEE 829 の多セクションを全強制しない・Design Doc が arc42 全12セクション埋めを強制しない・test-design-spec/test-procedure-spec が推奨節を置いたのと同じ判断）。推奨節の見出しに必須語〔`テスト方針`／`テストレベル`／`トレーサビリティ`〕を部分一致で含めない（デコイ回避）。

**境界を越えた記述の扱い**（詳細は末尾の越境 note）:
- プロジェクト固有詳細（具体スケジュール・個別ケース・プロジェクトのスコープ/対象外・終了基準の具体値）が戦略に紛れ込んでいたら、計画（[`./test-plan.md`](./test-plan.md)）へ移す（組織↔プロジェクトの抽象度境界＝このスライスの肝）。
- 要件文そのものが戦略やトレーサビリティに転記されていたら、SRS（[`../requirements/srs.md`](../requirements/srs.md)）へ一元化し、戦略側は **ID 参照に置換**する（P6）。
- 品質目標が測定不能な曖昧表現（"高品質"・"安定" 等）で書かれていたら、観測可能・判定可能な目標へ書き換える（P6）。

## テスト方針

組織横断で共通する**品質目標**と**全体アプローチ**を方針レベルで確定する。これは個別プロジェクトでなく**組織として**の方向性であり、各プロジェクトの計画はこの方針を拠り所に具体化する。

**含む**: 組織共通の品質目標（**測定可能**な目標値＝重大欠陥流出件数・自動回帰カバレッジ率・MTTR 等、観測できる値・率・時間で書いた目標）・全体アプローチ（シフトレフト／リスクベース等の組織標準とする考え方）・投資配分の原則（リスクに応じた工数配分の方針）。

**含まない**: プロジェクト固有の具体（特定リリースのスコープ/対象外・終了基準の具体値・スケジュール＝計画の対象）・個々のテストケースの具体値（ケース仕様の対象）・要件文そのものの転記（SRS を ID 参照する）。

> **測定不能な抽象論で逃げない**: 「高品質を目指す」「安定したシステムにする」のような副詞・形容の品質目標は、組織として何を達成すれば良いかを定義していない。組織共通の品質目標は**観測できる値・率・時間**（例: 重大欠陥流出 0 件・自動回帰カバレッジ 80% 以上・MTTR 30 分以内）で書く（P6）。曖昧表現の質的判定は [`../../rubric/test-strategy.md`](../../rubric/test-strategy.md) で見る（測定可能性は P6・3語以外の言い換えも含むため rubric の領分）。

### 例（最小限・テンプレート用）

```
品質目標（組織共通・測定可能）:
  - 本番への重大欠陥（Severity 1）流出を年間 0 件に保つ
  - 主要機能の自動回帰カバレッジを 80% 以上に維持する
  - 本番障害の検出から復旧までの平均時間（MTTR）を 30 分以内に抑える

全体アプローチ:
  - シフトレフト（設計レビュー段階から品質を作り込む）を組織標準とする
  - リスクベースで投資配分を決める（高リスク領域へ重点配分）
```

## テストレベル/タイプ

組織標準として採用する**テストレベル**と**テストタイプ**の枠組みを確定する。各プロダクトはこの標準から選択し、プロジェクト単位の計画へ降ろす。戦略は「**組織として何を標準に用意するか**」までを定め、各レベル/タイプをどこまで実施するかの具体は計画が決める。

**含む**: 組織標準のテストレベル（単体・結合・システム・受入等）・組織標準のテストタイプ（機能・性能・セキュリティ・使用性等）・各レベル/タイプの位置づけ（何のために用意する標準か）。

**含まない**: 特定プロジェクトでどのレベル/タイプをどこまで実施するかの具体（計画の対象）・テスト観点＝高レベルのテスト条件（設計仕様の対象）・個々のケースの具体値（ケース仕様の対象）。

> **V 字の1対1対応を機械的に固定で強制しない**: テストレベルとテスト対象（要件・設計）の対応は古典的 V 字モデルでは1対1で語られるが、これは古典的な整理であって絶対の制約ではない。ISTQB v4 はテストレベルを固定せず、プロジェクトの状況に応じた適応を許す（memory 帰納調査の訂正）。本レシピは「組織標準としてどのレベル/タイプを用意するか」を定めるが、特定の固定的な対応関係を一律に強制しない（状況適応を許す）。固定対応の妥当性そのものは [`../../rubric/test-strategy.md`](../../rubric/test-strategy.md) の質的判定で見る。

### 例（最小限・テンプレート用）

```
標準テストレベル:
  - 単体・結合・システム・受入の4段を組織標準とする
  - 各レベルがどの開発成果物にどう対応するかはプロジェクトの状況に応じて適応してよい
    （V 字の1対1対応を組織として一律固定しない）

標準テストタイプ:
  - 機能・性能・セキュリティ・使用性を標準タイプとして定義する
  - 各プロダクトは該当タイプを選択して計画へ降ろす
```

## 推奨節（必須にしない・組織の状況に応じて書く）

以下は組織の規模・成熟度に応じて記述する。**必須にすると小さい戦略でも全節を埋めさせる過剰テンプレ化（gold plating）を招くため、必須にしない**（test-plan が IEEE 829 の多セクションを全強制しない・test-design-spec/test-procedure-spec が推奨節を置いたのと同じ）。**推奨節の見出しに必須語〔`テスト方針`／`テストレベル`／`トレーサビリティ`〕を部分一致で含めない**（デコイ回避＝cycle-15/16/17 教訓）。

- `自動化方針`: 自動化の組織方針（回帰の自動化既定・標準スタック・CI 実行）。**技術名・製品名・ツール名（JUnit／Playwright／PostgreSQL 等）はここで正当に書ける**。
- `テスト環境標準`: テスト環境の組織標準（本番同等構成・データマスキング・IaC 再現）。製品名・ツール名はここでも正当に書ける。
- `組織体制・役割`: テストの役割分担・責任（QA 組織・トリアージ責任の方針）。

## トレーサビリティ

各**テスト方針／テストレベル**を、対応する**品質目標・上位標準・事業目標**へ紐付ける。戦略は最上位ゆえトレースの方向に注意する——戦略は「下位（計画）に降ろす」と同時に「**上位（品質目標・上位標準・事業目標）に根拠を持つ**」。トレース表は各方針/レベルを**対応する品質目標/NFR カテゴリ/上位標準 ID** へ紐付け、**根拠の無い孤立した方針（拠り所のない方針）を作らない**（P4: 全要素トレース可能）。要件文・上位標準の文言は転記せず **ID 参照**にとどめる（P6）。

**表の書き方（テスト方針/レベル → 品質目標/上位標準/事業目標）**:
- ID 列のヘッダに「**対応**」を含める（例: `対応する品質目標/上位標準/事業目標`）。第1列はテスト方針/レベル名（主語）であり、機械の [`../../scripts/check_traceability.py`](../../scripts/check_traceability.py) は第1列を主語として除外し、「対応」を含む列を ID 列とみなす。
- 全セルを埋める。対応列が空・ダッシュ（`-`）の方針は孤立した方針（拠り所のない方針）であり、機械が検出する逸脱になる。
- 品質目標・上位標準の文言（What の文言・Why の説明）は写さない。必要なら ID で参照する。

| テスト方針/レベル | 対応する品質目標/上位標準/事業目標 | 備考 |
|---|---|---|
| シフトレフト方針 | 品質目標: 重大欠陥流出 0 件 | 設計段階での作り込み |
| リスクベース投資配分 | 事業目標: BIZ-GOAL-02（重点領域の信頼性確保） | 高リスク領域への重点配分 |
| 自動回帰の標準化 | 品質目標: 自動回帰カバレッジ 80% 以上 | CI 実行 |
| セキュリティテスト標準 | 上位標準: 情報セキュリティ規程 SEC-STD-01 | 全プロダクト適用 |

**逸脱の判定基準**:
- 「対応する品質目標/上位標準/事業目標」が空（またはダッシュ）の方針が存在する → 孤立した方針（拠り所のない方針）。根拠の補完または方針の削除を検討する（**空セルそのものの検出は機械の [`../../scripts/check_traceability.py`](../../scripts/check_traceability.py) の担当**。rubric は過大主張しない＝cycle-12/F5 の教訓）。
- 対応が形式上は埋まっているが、その品質目標/上位標準と方針が意味的に食い違う → 紐付けの質の問題であり、[`../../rubric/test-strategy.md`](../../rubric/test-strategy.md) の質的判定で見る。
- トレーサビリティ表や方針に要件文・上位標準が逐語転記されている → ID 参照へ置換し、文言は SRS／上位標準へ一元化する（P6）。

## 越境 note（粒度・帰属のズレ検出）

戦略に以下が現れたら、戦略レベルを越境している。該当工程へ移送する。

- **プロジェクト固有詳細**（具体スケジュール・個別ケース・プロジェクトのスコープ/対象外・終了基準の具体値）が戦略に出たら → 計画（[`./test-plan.md`](./test-plan.md)）へ。戦略は「組織として何を標準・方針とするか」までに留め、プロジェクト単位の具体は書かない（**組織↔プロジェクトの抽象度境界**＝このスライスの肝）。
- **要件文の逐語転記・要件の Why** が戦略／トレーサビリティに出たら → SRS（[`../requirements/srs.md`](../requirements/srs.md)）へ一元化し、戦略側は **ID 参照に置換**する（P6）。
- **品質目標の測定不能な曖昧表現**（"高品質"・"安定"・"十分" 等の副詞・形容）が出たら → 観測可能・判定可能な目標へ書き換える（P6）。曖昧表現は無数の言い換えがあり特定語で機械検出できないため、本越境はフェンスブロックの禁止語列挙を**持たない**（vocab 空＝後述）。

> 対比に注意: 本レシピは**機械語彙（vocab）を持たない**（[`../../scripts/vocab/test-strategy.json`](../../scripts/vocab/test-strategy.json) の forbidden は空）。WF テスト工程の他4本（ケース仕様・計画・設計仕様・手順仕様）が曖昧期待結果3語を持つのに対し、戦略だけが空である。理由は次節で述べる。戦略の主たる逸脱（プロジェクト固有詳細の混入・測定不能な曖昧品質目標）はいずれも構造・文脈の判定であり、機械語彙では弾かず質的判定（[`../../rubric/test-strategy.md`](../../rubric/test-strategy.md)）に委ねる。

## vocab の説明（WF テスト5本中4踏襲1空＝工程でなく「綺麗に拾えるか」で決まる実証）

**本 doc_type（test-strategy）の機械語彙チェック（vocab）は意図的に空である**（[`../../scripts/vocab/test-strategy.json`](../../scripts/vocab/test-strategy.json) の forbidden は `[]`）。これは WF テスト工程5本（ケース仕様・計画・設計仕様・手順仕様・戦略）のうち**唯一 vocab を持たない** doc_type である。

**vocab の有無は『その doc_type の逸脱が機械で綺麗に拾えるか』で決まる——agile か WF かの別でも、テスト工程か否かの別でもない**（[`../../agile/design-doc.md`](../../agile/design-doc.md) で確立した原則）。test-case-spec／test-plan／test-design-spec／test-procedure-spec は曖昧期待結果3語（厳密な語は安全のためここでは列挙しない・フェンス不要）を**踏襲して非空**だが、それは WF だからではなく、それらが「期待結果・完了条件・テスト条件・合否判定」を書く層であり、3語がその**主たる逸脱として出番がある**（経験検証で出番あり∧誤爆なしを確認した）からである。

戦略を**経験検証**して、次の理由で**空**にした:

- **(a) 出番が乏しい（綺麗に拾えない）**: 曖昧期待結果3語は「期待結果・完了条件・テスト条件・合否判定の定型句」である。だが**テスト戦略は組織横断のテスト方針（品質目標・全体アプローチ・テストレベル/タイプの標準）を書く最上位層であり、期待結果・完了条件・テスト条件・合否判定を書かない**＝3語の主戦場（出番がある文脈）が戦略レベルには存在しない。3語は技術的には「主要機能が正しく動作することを品質目標とする」のように出現しうる（実機で deviation を返すことは確認した）が、それは「**測定不能な品質目標**（"高品質を目指す"・"安定"・"十分" 等の副詞・曖昧目標）」という広い逸脱の**狭い字面サブセット**にすぎない。その広い測定可能性問題は P6・誤爆性ゆえ本来 rubric の領分である（nonfunctional-design の曖昧表現を rubric にした前例と同型）。無数の曖昧表現のうち3語だけを機械で切り出すと「機械で綺麗に拾えている」偽の安心を与えつつ、残り大半の曖昧目標は結局 rubric へ逃げる＝逸脱が機械で**綺麗には拾えない**。
- **(b) 誤爆はしない**: 戦略の正当な地の文（品質目標の指標値・全体アプローチ・テストレベル/タイプの標準・自動化方針・テスト環境標準・組織体制）に3語は誤爆しない（実機で good fixture が pass を確認）。

(b) は満たすが **(a) を満たさない（綺麗に拾えない）ため空にした**（既定＝迷ったら空）。**もし出番が十分あれば踏襲していた**（user-story／Design Doc が agile でも vocab を空にしたのと同じ判断軸）。これが「**vocab の有無は工程でなく『逸脱が機械で綺麗に拾えるか』で決まる**」ことの**最強の実証**である——同じ WF テスト工程5本のうち、case/plan/design-spec/procedure-spec は3語踏襲・**strategy だけ空（WF テスト5本中4踏襲1空・同一ファミリで逆の帰結）**。同じテスト工程でも、3語の主戦場（期待結果・完了条件・テスト条件・合否判定）を持つ層は踏襲し、それを持たない最上位の戦略層は空になる。

> **機械で弾かないもの（誤爆回避・rubric へ委ねる）**: 技術スタック名・製品名・`SQL`・ツール名（JUnit 等）は戦略の `自動化方針`／`テスト環境標準` で正当に現れるため、仮に vocab を持つとしても禁止語にしない（部分一致誤爆回避・WF 既存スライスと同方針。とりわけ `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列で誤爆する）。本スライスは vocab 自体を空にするため、**プロジェクト固有詳細の混入**（組織↔プロジェクトの抽象度境界・構造判定）・**測定不能な曖昧品質目標**（"高品質" 等の副詞・無数の言い換え）・**V 字1対1の固定強制**（状況判定）はすべて [`../../rubric/test-strategy.md`](../../rubric/test-strategy.md) の質的判定へ委ねる。

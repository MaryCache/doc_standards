# テスト計画（Test Plan）レシピ — ウォーターフォール テスト計画

> **レイヤー**: 第2層レシピ（手法別具体指針・テスト）
> **原則参照**: [`../../principles/granularity-axis.md`](../../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。
> **責務対照**: [`../../principles/responsibility-map.md`](../../principles/responsibility-map.md) のテスト仕様行〔計画レベル〕を参照（テスト戦略・計画・設計仕様・ケース仕様・手順仕様のうち、本レシピは**計画**＝プロジェクトのテスト対象・対象外+理由・終了基準を担う。**計画へのテストケース具体値の記載は含まない**＝それはケース仕様＝[`./test-case-spec.md`](./test-case-spec.md)）。

## 位置づけ

このレシピが対象とする**テスト工程の範囲**を明確にする。テスト文書は抽象度で階層化される（**計画** → 設計仕様 → ケース仕様 → 手順仕様の4層。テスト戦略は組織横断の方針層として計画の直上に分離する〔戦略/計画の二分は厳密な規格境界ではない＝P7 注〕。P7）。本レシピが担うのは**計画（Test Plan・IEEE 829 系）レベル**——プロジェクト単位で**何をテストするか／何をテストしないか（対象外+理由）／いつテストを完了・合格とみなすか（終了基準）**を方針レベルで確定する層——に限る。

これは WF テスト工程の**2本目**のレシピである（1本目＝[`./test-case-spec.md`](./test-case-spec.md)＝ケース仕様）。ケース仕様が「1ケースの具体的入力値・期待結果」を確定するのに対し、**計画は個々のケースの具体値を書かない**。計画は V 字（要件 ↔ 設計 ↔ テスト）のテスト側の骨格を、プロジェクトの意思決定基準として先に固める位置にある。

| 工程 | 本レシピでの扱い |
|---|---|
| **テスト戦略** | 隣接（上位）。組織横断のテスト方針・標準は戦略レベルに属する。本レシピはプロジェクト単位の計画を扱い、組織戦略は転記しない |
| **テスト計画** | 対象。テスト対象・対象外+理由（スコープ）・終了基準（測定可能な完了/合格条件）・対応要件/テストレベルへのトレーサビリティをここで確定する |
| **テスト設計仕様** | 隣接（下位）。テスト観点＝高レベルのテスト条件は設計仕様で導出する。計画はテストレベル/タイプの枠組みまでに留め、観点の網羅は設計仕様へ降ろす |
| **テストケース仕様** | 対象外。1ケースの事前条件・入力・操作・**具体的な期待結果**はケース仕様（[`./test-case-spec.md`](./test-case-spec.md)）の担当。**計画にケース具体値を書かない**（P7／P8: 階層を飛び越えない） |

責務対照表（responsibility-map.md のテスト仕様行）は「テスト戦略・計画・設計仕様・ケース仕様・手順仕様」を含む範囲、「**計画へのテストケース具体値の記載**」を含まない範囲と定める。本レシピはこの境界を計画レベルへ具体化する。

### 必須は絞る／残りは推奨（このスライス固有の設計理由）

**必須節**: `スコープ`（テスト対象・**対象外+理由**）／`終了基準`（テスト完了/合格の測定可能な判定条件）／`トレーサビリティ`（対応要件/テストレベルへ）。

- **`スコープ` に「対象外+理由」を必ず含める**。テスト対象（Goals 側）だけ書いて対象外（やらないテスト範囲）を欠くと、テスト範囲が無限に広がる（スコープクリープ）。これは Design Doc の Non-Goals（[`../../agile/design-doc.md`](../../agile/design-doc.md)）と**同型**——スコープ否定側の欠落こそスコープクリープの主因であり、対象外を「特になし」で逃げない。
- **`終了基準` は P6（測定可能）を担保する**。「十分にテストできたら」「網羅的に確認できたら」のような測定不能な完了条件では、誰が見ても同じ完了判定に到達できない。カバレッジ X%・重大バグ 0 件・全 P1 ケース pass・p95 ≤ しきい値 のような**観測可能・判定可能な条件**で書く。`終了基準` を独立必須見出しにして欠落を機械検出する（[`../../scripts/check_headings.py`](../../scripts/check_headings.py)）。

**推奨節（必須にしない）**: `テスト体制`／`スケジュール・マイルストーン`／`リソース・環境`／`リスクと対策`／`テストレベル/タイプ`。これらはプロジェクト規模で可変であり、必須にすると小さい計画でも全節を埋めさせる過剰テンプレ化（gold plating）を招く。IEEE 829 は多セクションを挙げるが、本レシピはそれを全強制しない（ISTQB v4 もテスト計画のレベル/粒度を固定しない＝プロジェクトに合わせて取捨する。memory 帰納調査の訂正＝規格の節を全強制しないと整合）。**この「必須は絞る／残りは推奨」は Design Doc が arc42 全12セクション埋めを強制しないのと同じ判断**である。

> **なぜ Non-Goals 型の「対象外」を必須スコープに含めるのか（機械表現の肝）**: 機械判定（[`../../scripts/check_headings.py`](../../scripts/check_headings.py)）は見出しの**部分一致**で必須を見る。スキーマ（[`../../scripts/schema/test-plan.json`](../../scripts/schema/test-plan.json)）の `required_headings` は `["スコープ", "終了基準", "トレーサビリティ"]` の3語で、いずれもスラッシュ等の罠がなく実見出しに素直に部分一致する。`スコープ` 見出しの**中身**に「対象外+理由」を必ず書かせ、その質（"特になし" で逃げていないか）は [`../../rubric/test-plan.md`](../../rubric/test-plan.md) の質的判定で見る（見出しの有無は機械・中身の質は rubric の分担）。

**境界を越えた記述の扱い**（詳細は末尾の越境 note）:
- 個々のテストケースの具体的入力値・期待結果が計画に紛れ込んでいたら、ケース仕様（[`./test-case-spec.md`](./test-case-spec.md)）へ移す（F1〔論理/物理〕と同型の隣接境界。計画 vs ケース仕様）。
- 要件文そのものが計画やトレーサビリティに転記されていたら、SRS（[`../requirements/srs.md`](../requirements/srs.md)）へ一元化し、計画側は **ID 参照に置換**する（P6）。
- 終了基準が測定不能な曖昧表現で書かれていたら、観測可能・判定可能な条件へ書き換える（P6）。

## スコープ

本テスト計画が対象とする**テスト範囲**と、あえて**対象外とする範囲＋その理由**を確定する。対象外を明示することがスコープクリープ防止の要である（やらないテスト範囲を曖昧にしない）。

**含む**: テスト対象（テストするフィーチャ／機能・テストレベル）・**対象外＋理由**（今回テストしないフィーチャ／機能とその理由）。

**含まない**: 個々のテストケースの具体的入力値・期待結果（ケース仕様の対象）・要件文そのものの転記（SRS を ID 参照する）。

**"特になし" で逃げない**: 対象外を「特になし」で埋めるのは、スコープ否定を放棄しているのと同じである。境界が本当に無いテスト計画は稀であり、「今回テストしないこと」を理由とともに具体的に1つ以上挙げる（Design Doc の Non-Goals と同型）。

### 例（最小限・テンプレート用）

```
対象:
  - 受注登録・受注照会の機能テスト（結合・システムテストレベル）
  - 受注照会の性能テスト（負荷条件下の応答時間）

対象外（＋理由）:
  - 顧客マスタ管理機能: 前リリースで変更が無く、回帰は自動回帰スイートで担保済みのため
  - 帳票出力機能: 今回のリリーススコープ外（次フェーズで別計画として扱う）
  - 単体テスト: 開発工程の単体テスト計画で別途確定するため
```

## 終了基準

テストを**完了・合格と判定する条件**を、第三者が同じ結論に到達できる**測定可能・判定可能**な形で確定する（P6: 検証可能性は工程を貫く不変量）。終了基準が曖昧だと、いつテストを止めてよいか・リリース可否を誰も一意に判断できない。

**含む**: 測定可能な完了条件（カバレッジしきい値・残存バグ件数の上限・優先度別ケースの pass 条件・性能ケースのしきい値比較など、観測できる値・件数・率・状態で書いた合否条件）。

**含まない**: 「十分にテストできたら」「網羅的に確認できたら」「品質が安定したら」のような測定不能な表現（観測可能・判定可能な条件へ書き換える）・個々のケースの具体的期待結果（ケース仕様の対象）。

### 例（最小限・テンプレート用）

```
以下をすべて満たしたとき本テストを完了・合格とする:
  - 計画した全 P1（最優先）テストケースが pass している
  - 機能カバレッジ（要件 ID 数に対する検証済み ID 数）が 95% 以上である
  - 未解決の重大バグ（Severity 1）が 0 件、Severity 2 が 3 件以下である
  - 性能ケースの応答時間 p95 が 3000ms 以下である
```

> 終了基準は「観測できる条件」で書く。上記はいずれもカバレッジ%・件数・しきい値比較で判定でき、合否が一意に決まる。判定者の主観に依存する書き方（「十分に」「網羅的に」等）は避ける。曖昧表現の厳密な語は末尾の越境 note のフェンスブロックに列挙する。

## 推奨節（必須にしない・プロジェクトに応じて書く）

以下はプロジェクト規模に応じて記述する。**必須にすると小さい計画でも全節を埋めさせる過剰テンプレ化（gold plating）を招くため、必須にしない**（IEEE 829 の多セクションを全強制しない＝ISTQB v4 もレベルを固定しない）。該当が薄い節は無理に埋めず省略してよい（Design Doc が arc42 全12セクション埋めを強制しないのと同じ）。

- `テスト体制`: テストの役割分担・トリアージの進め方の方針。
- `スケジュール・マイルストーン`: フェーズ区切りとマイルストーン（各フェーズ末の終了基準判定など）。
- `リソース・環境`: テスト環境（製品名・ツール名は環境記述として正当に書ける）・必要なデータ。
- `リスクと対策`: テスト遂行上のリスクと緩和策。
- `テストレベル/タイプ`: 結合・システム・性能等のレベルとタイプの枠組み（観点の網羅は設計仕様へ降ろす）。

## トレーサビリティ

各**テスト対象（テスト項目）**を、対応する**要件 ID と検証するテストレベル**へ紐付ける。要件文は転記せず **ID 参照**にとどめる（P6）。対応の無い孤立テスト項目（根拠のないテスト）を作らない（P4: 全要素トレース可能）。

**表の書き方（テスト項目 → 要件/テストレベル）**:
- ID 列のヘッダに「**対応**」を含める（例: `対応要件/テストレベル`）。第1列はテスト項目名（主語）であり、機械の [`../../scripts/check_traceability.py`](../../scripts/check_traceability.py) は第1列を主語として除外し、「対応」を含む列を ID 列とみなす。
- 全セルを埋める。対応列が空・ダッシュ（`-`）のテスト項目は孤立テスト項目であり、機械が検出する逸脱になる。
- 要件文（What の文言・Why の説明）は写さない。必要なら SRS を ID で参照する。

| テスト項目 | 対応要件/テストレベル | 備考 |
|---|---|---|
| 受注登録の機能テスト | FR-01/結合・システム | 正常・異常・境界を含む |
| 受注照会の機能テスト | FR-02/システム | 照会条件の網羅 |
| 受注照会の性能テスト | NFR-PERF-01/性能 | p95 応答時間の確認 |

**逸脱の判定基準**:
- 「対応要件/テストレベル」が空（またはダッシュ）のテスト項目が存在する → 孤立テスト項目（根拠のないテスト）。対応の補完またはテスト項目の削除を検討する（**空セルそのものの検出は機械の [`../../scripts/check_traceability.py`](../../scripts/check_traceability.py) の担当**）。
- 対応が形式上は埋まっているが、その要件/テストレベルとテスト項目が意味的に食い違う → 紐付けの質の問題であり、[`../../rubric/test-plan.md`](../../rubric/test-plan.md) の質的判定で見る。
- トレーサビリティ表やスコープに要件文が逐語転記されている → ID 参照へ置換し、文言は SRS へ一元化する（P6）。

## 越境 note（粒度・帰属のズレ検出）

計画に以下が現れたら、計画レベルを越境している。該当工程へ移送する。曖昧表現の厳密な語はフェンスブロック内に列挙する（語彙チェッカーはフェンス内を検査対象外とする。地の文では言い換える）。

```
終了基準に書いてはいけない測定不能マーカー（出たら測定可能な完了条件へ書き換える）:

  正しく表示  → 「カバレッジ X% 以上」「表示崩れの未修正バグ 0 件」等、観測できる完了条件へ
  正しく動作  → 「全 P1 ケースが pass」「重大バグ 0 件」等、観測できる完了条件へ
  適切に処理  → 「例外処理の網羅率 100%」等、観測できる完了条件へ
```

- **個々のテストケースの具体値**（事前条件・入力値・期待結果）が計画に出たら → ケース仕様（[`./test-case-spec.md`](./test-case-spec.md)）へ。計画は「何を・どこまでテストするか／いつ完了とするか」の方針までに留め、ケースの具体値は書かない（F1〔論理/物理〕と同型の隣接境界）。
- **要件文の逐語転記・要件の Why** が計画／トレーサビリティに出たら → SRS（[`../requirements/srs.md`](../requirements/srs.md)）へ一元化し、計画側は **ID 参照に置換**する（P6）。
- **終了基準の測定不能な曖昧表現**（上記3語の定型句のほか「十分に」「網羅的に」「適切にカバー」等の言い換え）が出たら → 観測可能・判定可能な条件へ書き換える（P6）。

> 対比に注意: 上記3語の定型句（測定不能マーカー）は終了基準の禁止対象（[`../../scripts/vocab/test-plan.json`](../../scripts/vocab/test-plan.json) の forbidden で機械検出）だが、**計画へのケース具体値の混入**は特定語ではなく**構造の問題**であり、機械語彙では弾かず質的判定（[`../../rubric/test-plan.md`](../../rubric/test-plan.md)）に委ねる。

## vocab の説明（test-case-spec の3語を踏襲＝WF だが「綺麗に拾えるか」で決めた）

**本 doc_type（test-plan）の機械語彙チェック（vocab）は test-case-spec の曖昧期待結果3語を踏襲して非空である**（[`../../scripts/vocab/test-plan.json`](../../scripts/vocab/test-plan.json) の forbidden に3語）。厳密な3語は上の越境 note のフェンスブロックに列挙してある（語彙チェッカーはフェンス内を検査対象外とするため、本レシピは禁止語を語りつつ自己 pass を保てる）。

**vocab の有無は『その doc_type の逸脱が機械で綺麗に拾えるか』で決まる——agile か WF かの別ではない**（[`../../agile/design-doc.md`](../../agile/design-doc.md) で確立した原則の WF 側適用）。Test Plan は WF だが、それだけで vocab を持つと決めたのではない。**経験的に**次を確認して踏襲を決めた:

- Test Plan の**終了基準は P6（測定可能）を担保する必要があり**、上の越境 note のフェンス内に列挙した定型句（「すべての画面が（測定不能マーカー1）されること」のような非測定の完了条件）は終了基準の**主たる逸脱として出番がある**（実機で deviation を確認）。
- これら3語は Test Plan の**正当な地の文**（スコープの対象外記述・終了基準のカバレッジ%／pass 率／件数／しきい値・リソース環境の製品名）に対し**誤爆しない**（実機で pass を確認）。

両者が満たされる＝「逸脱が機械で綺麗に拾える」ため踏襲した。これが**「WF でも vocab の有無は逸脱が綺麗に拾えるかで決まる」**ことの WF 側実証である（user-story / Design Doc が agile でも vocab を空にしたのと対をなす）。

> **機械で弾かないもの（誤爆回避・非対称継続）**: 技術スタック名・製品名・`SQL`・ツール名（JUnit 等）は Test Plan の `リソース・環境` 等で正当に現れるため禁止語にしない。とりわけ `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出・WF 既存スライス〔external-design / architecture-design / nonfunctional-design / operations-design〕と同方針）。また**計画へのテストケース具体値の混入**・**終了基準の3語以外の曖昧表現の言い換え**（「十分に」「網羅的に」等）は構造・文脈の判定であり、機械では拾えないため [`../../rubric/test-plan.md`](../../rubric/test-plan.md) の質的判定へ委ねる。

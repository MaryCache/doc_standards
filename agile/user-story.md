> **原則参照**: [`../principles/granularity-axis.md`](../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。

## このレシピの位置づけ（agile 第2層の最初のスライス）

これは doc-standards で**初の agile レシピ**である。これまでの第2層は WF（ウォーターフォール）スライスのみで、いずれも**工程フェーズ軸**（要件定義→基本設計→詳細設計→テスト、と工程を時間順に区切る軸）で整理されてきた。これに対し agile の第2層は**成果物ライフサイクル軸**（living docs として継続的に育ち、必要になった時点で詳細を確定する JIT 詳細化の軸）で整理する。同じ第2層でも軸が異なる——これが**非対称設計の原則（S4）**である。両者を同じ「工程フェーズ」軸で対称に並べると、アジャイルの「いつ何を確定するか（JIT 詳細化）」が表現できなくなるため、軸を意図的にずらす。

ただし**原則層（第1層）は手法非依存で共通**である。What/Why と How の分離（P2）・検証可能性（P6）・トレーサビリティ（P4）・主語ヒューリスティック（P1）は WF でも agile でも変わらない不変量であり、本レシピもそれらを再定義せず参照するだけである（S3）。

**必須セクションと推奨セクション**:
- **必須**: `ユーザーストーリー`・`受入基準`（後続タスクで schema 化）。
- **推奨（必須にしない）**: `INVEST チェック`。自己点検の補助であり、全項目を埋めることを強制すると過剰テンプレ化（gold plating）を招くため必須にしない。
- `このレシピの位置づけ` は導入であり必須ではない。

**境界を越えた記述の扱い**:
- ストーリーに実装作業（"configure / upgrade / migrate" 等の実装動詞で表される開発タスク）が混入していたら、それは開発タスク（スプリントバックログのタスク）または設計の領域である。ストーリーから外し、タスク／設計へ移す。
- 技術選択（どの基盤・どのプロトコル・どのライブラリで実現するか）がストーリーや受入基準に書かれていたら、方式設計（アーキ設計）の領域へ移す。User Story は WHO/WHAT/WHY にとどめる。
- まだ確定していない詳細は無理に書き切らない。スプリント中の会話で必要になった時点で確定する（JIT・living doc）。書き切ろうとすること自体が WF 的な前倒しであり、agile の趣旨に反する。

## ユーザーストーリー

ユーザーストーリーは **WHO（誰が）／WHAT（何をしたい）／WHY（なぜ＝どんな価値があるか）** を一文で表す。定型は「**＜役割＞として、＜目的＞したい、なぜなら＜価値＞**」である。

**主語は利用者であり、システムではない**（P1: 主語ヒューリスティック・検出補助）。「システムが〜する」と書き始めた時点でそれは要件・仕様の言い回しであり、ユーザーストーリーではない。ユーザーストーリーの主語は常に価値を受け取る人（役割）である。

**so that（価値）を必ず書く**。「＜役割＞として＜目的＞したい」で止め、「なぜなら＜価値＞」を欠落させてはならない。価値が書けないストーリーは「なぜ作るのか」が定義できていないストーリーであり、優先順位づけも受入の合意もできない。価値の欠落は逸脱である。

**含む**: 役割（WHO・価値を受け取る利用者区分）・目的（WHAT・利用者がしたいこと＝観測可能なゴール）・価値（WHY・その目的が達成されると利用者／事業にどんな良いことがあるか）・INVEST に沿った1ストーリー1価値の単位。

**含まない**: 実装タスク（実装作業を表す動詞——たとえば設定作業・バージョン更新・データ移行といった開発手順——をストーリーの本体にすること）・技術選択（どの技術・基盤・ライブラリで作るか）・受入条件への実装機構の記述（内部の仕組みをストーリーに書き込むこと）・主語をシステム／コンポーネントにした仕様文。

> **逸脱の例**（いずれもストーリーとして書き直すか、別の置き場へ移す）:
> - 主語がシステム: 「システムは受注を在庫数で検証する」→ 仕様文。利用者主語の価値文へ書き直す。
> - 価値（so that）の欠落: 「営業担当として受注を登録したい」（なぜなら…が無い）→ 価値を補う。
> - 実装作業化: 「管理者として認証基盤をアップグレードしたい」→ これは開発タスク。ストーリーは利用者の価値で表す。

### 例（最小限・テンプレート用）

```
US-01 受注をまとめて登録する
  営業担当として、複数の受注を一度に登録したい、
  なぜなら 1件ずつの入力では繁忙期に処理が追いつかず、受注漏れが起きるから。

US-02 注文状況を自分で確認する
  顧客として、注文番号で自分の注文の進捗を確認したい、
  なぜなら 進捗を問い合わせる手間なく自己解決でき、安心して待てるから。
```

> 上の2例はいずれも主語が利用者（営業担当・顧客）であり、so that（価値）が明示されている。価値は「業務上・利用者体験上の良いこと」であって、実装手段の説明ではない点に注意する。

## 受入基準

受入基準（Acceptance Criteria・AC）は、そのストーリーが「完成した」と合意できる**観測可能な振る舞い**を定義する。定型は **Given-When-Then**（前提／きっかけの操作／観測できる結果）である。

**AC には実装機構を書かない**。前提・操作・結果はすべて**外から観測できる振る舞い**で書き、内部の仕組み——たとえば検索の内部挙動や内部状態の遷移といった「どう実現しているか」——は書かない。実装機構は方式設計・詳細設計・コードの領域であり、AC が見るのは「利用者から何が観測できるか」だけである（P2: What/Why と How の分離・P6: 検証可能性）。

**AC が肥大したらストーリー分割のサイン**。1ストーリーの AC が増えすぎる（目安として **5 件を超える**）と、そのストーリーは複数の価値を抱え込んでいる（INVEST の Small / Independent を満たしていない）疑いがある。AC を削るのではなく、ストーリーを小さく割って各ストーリーに AC を再配分する。

**含む**: Given（前提＝確認開始前に成立している状態・データ）・When（きっかけ＝利用者またはシステムへの単一の働きかけ）・Then（結果＝外から観測できる状態・表示・件数・エラー等）・各 AC が対応するストーリー。

**含まない**: 実装機構の記述（内部の検索方式・キャッシュ・索引・内部状態遷移など「どう実現するか」）・技術選択・テスト体制やスケジュール・1件として観測しきれない過大なシナリオ（分割する）。

> **観測可能で書く**（P6）。Then は「どの値・どの状態・どの件数・どのメッセージが観測されるか」で書く。「正しく処理される」「適切に表示される」のような測定できない表現は、合否が一意に決まらないため使わない。
>
> **実装機構を AC に書かない例**: 「Then: 索引を走査して該当件数を返す」は内部挙動の記述であり AC として不適切。「Then: 検索結果に該当する 3 件が一覧表示される」と、観測できる結果だけで書く。

### 例（最小限・テンプレート用）

```
US-01（受注をまとめて登録する）の受入基準

  AC-1
    Given 在庫が十分にある商品が複数選択されている
    When  利用者が「一括登録」を1回実行する
    Then  選択した全件が受注として作成され、作成件数が画面に表示される

  AC-2
    Given 選択した商品の中に在庫を超える数量のものが1件含まれている
    When  利用者が「一括登録」を1回実行する
    Then  在庫超過の1件は登録されず、業務エラーとして「どの行が登録できなかったか」が表示される。
          在庫内の他の件は登録が成立する（部分成立の振る舞いが観測できる）

  AC-3
    Given 選択された商品が0件である
    When  利用者が「一括登録」を実行しようとする
    Then  登録は実行されず、「対象が選択されていない」旨が表示される
```

> 上の3例はいずれも Given-When-Then で、Then が観測可能（件数表示・部分成立・メッセージ）で書かれている。AC は 3 件で、目安の 5 件以内に収まっている。これ以上振る舞いが増えるなら、ストーリーを分割する。

## INVEST チェック

> **推奨セクション**（必須ではない）。ストーリーが良い粒度かを自己点検する補助である。全項目を機械的に埋めることが目的ではなく、引っかかった項目があればストーリーの書き直し・分割の入口として使う。

ストーリーを次の6観点で自己点検する。

- **Independent（独立）**: 他のストーリーへの順序依存なく着手・リリースできるか。強い依存があるなら分割・統合を検討する。
- **Negotiable（交渉可能）**: 実装の細部まで固めず、How はスプリント中の会話で詰める余地を残しているか（JIT・living doc）。AC に実装機構を書き込んでいないか。
- **Valuable（価値がある）**: so that（価値）が利用者／事業の言葉で書けているか。価値が書けないなら作る理由が不明である。
- **Estimable（見積り可能）**: 規模を見積もれるだけ意図が明確か。見積れないほど曖昧なら情報が不足している。
- **Small（小さい）**: 1スプリントに収まる単位か。AC が肥大（目安 5 件超）していたら分割のサイン。
- **Testable（テスト可能）**: AC が観測可能な振る舞いで書けているか。測定できない受入条件は Testable を満たさない。

> 各項目は二者択一の合否ではなく「引っかかりの検出点」である。複数項目で引っかかるストーリーは、たいてい「大きすぎる」か「価値が曖昧」のどちらかに帰着する。

## vocab が空である旨（機械判定は AC 節の有無のみ／質的判定は rubric 主導）

**本 doc_type（user-story）の機械語彙チェック（vocab）は空である**。これは設計上の判断であり、欠落ではない。

User Story の逸脱（主語が System になっている／so that の欠落／実装動詞でストーリーを書いている／AC が 5 件を超えて肥大している／INVEST 違反）は、いずれも**構造・件数・文脈の判定**であって、特定の禁止トークンの部分一致では原理的に拾えない。とりわけ実装動詞（設定・更新・移行といった作業）は、正当な利用者ゴールと**同一のトークン**になりうる（同じ動詞が「利用者が達成したい価値」を表すことも「開発の実装作業」を表すこともある）。これを vocab の部分一致で弾くと、正当なストーリーを誤って弾く（false positive）一方、言い換えられた逸脱は取り逃す（低再現率）。英語動詞を部分一致で見ると、無関係な語に巻き込まれる誤爆も起きる。

したがって**機械層は必須見出し（`ユーザーストーリー`／`受入基準` 節）の有無のみを見る**（とりわけ AC＝受入基準節の欠落が主な機械検出点）。それ以外の逸脱判定——主語・価値の有無・実装動詞かどうか・AC 件数・INVEST——はすべて [`../rubric/user-story.md`](../rubric/user-story.md) の**質的判定に委ねる**。実装動詞は「正当なユーザー目標と同一トークンになりうる」ため、機械の vocab には入れず、rubric が**意図**（その動詞が利用者の価値を表しているか、開発作業を表しているか）を見て判断する。

これは agile が **rubric 主導**であることの現れであり、機械判定中心の WF スライスとの非対称（S4）の正しい帰結である。WF（要件・テスト等）は「禁止トークンの混入」が機械で拾える逸脱を多く含むため vocab を持つが、User Story の逸脱は質的判定が本質であるため vocab を空にする。

## 越境 note（粒度・帰属のズレ検出）

ユーザーストーリー／受入基準に以下が現れたら、User Story の責務を越境している。該当する置き場へ移す。

- **実装タスク（実装作業化）**がストーリー本体になっていたら → 開発タスク（スプリントバックログのタスク）または設計へ。「利用者がしたいこと（価値）」ではなく「開発者がする作業」になっていないかを見る。
- **技術選択**（どの基盤・プロトコル・ライブラリで実現するか）がストーリーや AC に書かれていたら → 方式設計（アーキ設計）へ。User Story は WHO/WHAT/WHY にとどめる。
- **受入条件への実装機構の記述**（内部の検索方式・索引・内部状態遷移など「どう実現するか」）が AC に出たら → 観測可能な振る舞いへ書き換え、内部の仕組みは設計・コードの領域に残す。
- **まだ確定していない詳細**を無理に書き切ろうとしていたら → スプリント中の会話で必要になった時点で確定する（JIT・living doc）。書き切ろうとすること自体が WF 的な前倒しで、agile の趣旨に反する。

> 対比に注意: User Story の逸脱は**特定の禁止トークン**ではなく**構造・件数・文脈**の問題である（主語／so that 欠落／実装動詞か否か／AC 件数／INVEST）。よって機械語彙では弾かず（vocab は空）、質的判定（後続 rubric）に委ねる。実装動詞は正当なユーザー目標と同一トークンになりうるため、トークンではなく意図で見る。

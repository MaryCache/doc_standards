## 位置づけ（agile 第2層の 5 本目のスライス）

これは doc-standards で**5 本目の agile レシピ**である（1 本目＝[`./user-story.md`](./user-story.md)・2 本目＝[`./acceptance-criteria.md`](./acceptance-criteria.md)・3 本目＝[`./design-doc.md`](./design-doc.md)・4 本目＝[`./adr.md`](./adr.md)）。User Story が WHO/WHAT/WHY を、Acceptance Criteria がその価値の観測可能な合否を、Design Doc が「どう作るか」の設計合意を、ADR が決まった1判断の永続記録を担うのに対し、**RFC（Request for Comments）は『まだ決めていない』提案をチームへ開いてコメントを募る探索文書**である。

### RFC と ADR の時間軸連鎖（このスライス固有の肝・生きた代替 vs 葬った代替）

RFC と ADR は**同じ設計判断を時間軸で前後に分担する対**である。

| | RFC（本レシピ・**決定前**） | ADR（[`./adr.md`](./adr.md)・**決定後**） |
|---|---|---|
| 位置づけ | 提案を開いてコメントを募る探索文書 | 1 判断を永続記録する確定文書 |
| 代替の扱い | **代替案＝まだ生きている選択肢**（どれも採りうる） | **却下案＝葬った選択肢**（採らないと決めた） |
| 中核節 | **未解決の論点**（まだ決まっていない問い） | Decision（決めた内容）／Consequences（帰結） |
| 状態 | 未決を正直に開く | 承認を経て決定済み |

連鎖は **RFC → コメント収集 → 決定 → ADR** の向きで流れる。RFC で**生きていた代替**のうち採らなかったものは、決定の瞬間に ADR の**却下案（葬った選択肢）**へ移る。逆に言えば、RFC の代替案を「もう却下済み」のように書いたら、それは RFC でなく ADR を前倒しした**未決を装った既決**であり逸脱である（後述）。本レシピは RFC の**決定前**の粒度を定義し、決定後の記録の粒度は ADR レシピが定義する——両者で時間軸を割って二重定義を避ける。

agile の第2層は**成果物ライフサイクル軸**（living docs として育ち、必要になった時点で詳細を確定する JIT 詳細化）で整理する。WF の**工程フェーズ軸**とは軸が異なる——これが**非対称設計の原則（S4）**である。ただし**原則層（第1層）は手法非依存で共通**であり、What/Why と How の分離（P2）・トレーサビリティ（P4）・設計根拠の必須（P4: design rationale）は WF でも agile でも変わらない不変量である。本レシピもそれらを再定義せず参照するだけである（S3）。

### 必須は絞る／動機・影響範囲は推奨（このスライス固有の設計理由）

RFC の核は **提案内容・まだ生きている代替・未解決の論点・トレース**である。これらを必須にし、それ以外（動機・影響範囲・Prior art 等）は推奨にとどめる。必須を増やすほど小さい提案にまで全節を埋めさせる過剰テンプレ化（gold plating）を招くため、design-doc / adr / test 系と同じく必須は絞る。

- **必須節**: `提案内容`（何を提案するか・たたき台レベル）／`代替案`（まだ生きている選択肢とそのトレードオフ）／`未解決の論点`（まだ決まっていない問い）／`トレーサビリティ`（各提案・論点→対応要求への紐付け）。
- **推奨節（必須にしない）**: `動機`（Motivation・なぜ今この提案を開くか）／`影響範囲`／`Prior art（先行事例）`等。必須にすると過剰テンプレ化を招く。
- `位置づけ` は導入であり必須ではない。末尾の `vocab の説明` も必須見出しではない。

> **なぜ `未解決の論点` が必須なのか（機械表現の肝・RFC の核）**: 提案と代替だけ書いて**未決の問い（未解決の論点）を欠く**と、その文書は「もう全部決まっている＝提案を装った既決」と区別がつかなくなる。RFC は**決定前**の文書であり、まだ決まっていない問いを正直に開くことが体をなす条件である。**未決を装った既決＝RFC の体をなさない**を、未解決の論点の見出し欠落で機械検出する。これは [`./adr.md`](./adr.md) の `却下案` 独立必須（Why の片側欠落の検出）・[`./design-doc.md`](./design-doc.md) の `Non-Goals` 必須（スコープ否定側の検出）・WF nonfunctional の `測定方法` 必須化と**同型**の「欠けると体をなさない側を独立必須にして機械検出する」設計である。機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）は見出しの**部分一致**で必須を見るため、スキーマ（[`../scripts/schema/rfc.json`](../scripts/schema/rfc.json)）の `required_headings` に `未解決の論点` を入れ、本レシピの実見出しを `## 未解決の論点` としている。

> **なぜ `提案内容`（複合語）を required にするのか**: 「提案」単独を required にすると、本文の地の文「〜を提案する」「本提案では」等に部分一致で誤爆し、提案見出しが無くても誤って pass する。これを避けるため discriminating な複合語 `提案内容` を required にし、実見出しを `## 提案内容` にする。**推奨節・本文見出しに「提案」を含む見出し（例 `## 提案の背景`）を置かない**（デコイ回避・後述）。

> **デコイの罠（最重要・破壊テストで検証済み）**: required 各語（`提案内容`/`代替案`/`未解決の論点`/`トレーサビリティ`）は**レシピ実見出しに「1つだけ」部分一致**しなければならない。H1・導入見出し（`位置づけ`）・推奨節・本文の他見出しに required 4語の**いずれも含めない**。本レシピの H1 は `# RFC（コメント要求）レシピ — アジャイル RFC`（「提案内容」「代替案」「未解決の論点」「トレーサビリティ」を一切含まない・「RFC」「コメント要求」は可）。`代替案` の実見出しは `## 代替案`（推奨節・本文見出しに「代替」を含めない）。とりわけ missing-headings fixture は、欠落させる `未解決の論点` を H1 や他見出しに残さない decoy-clean なものにする（cycle-16/cycle-20 で実装者が踏んだ罠＝missing fixture の H1 に required 語が残り偽 pass する罠を避ける）。required 各語を1見出しだけに部分一致させる設計を守る（cycle-14 Goals/Non-Goals・cycle-18 テストレベル・cycle-19 処理仕様・cycle-20 ADR デコイ回避と同型）。

**境界を越えた記述の扱い**:
- **決定済みの記録**（もう決まった判断）を RFC に書いていたら、それは ADR の領分である（責務対照表「含まない」）。RFC は決定前で、決まったら ADR へ落とす。
- **未決を装った既決**（代替を「却下済み」のように書く・未解決の論点が無い）は逸脱である。代替は**まだ生きている選択肢**として、未決の問いは正直に開く。
- **straw man 代替**（見せかけの弱い代替を並べ採用本命を引き立てる事後正当化）を避ける。各代替のトレードオフを正直に書く。
- **実装詳細の先取り**（コード・詳細設計レベルの作り込み）は書かない。RFC は提案レベル＝方向への合意を先に得る。
- **trivial な提案**（可逆で影響小・わざわざコメントを募るまでもない）は RFC 化しない。

## 提案内容

何を提案するか（たたき台レベルの方向）を書く。1つの RFC は1つの提案を開く（1 提案 1 RFC）。

**含む**: 提案する方向・たたき台としての方式（確定でなく、コメントで磨く前提のもの）。

**含まない**: コード・詳細設計レベルの作り込み（実装詳細の先取り）・決定済みであるかのような断定（それは ADR）・代替の比較（それは `代替案`）。

提案内容は「方向への合意を先に得る」ためのものである。クラス構成・ロック粒度・API シグネチャといった**実装詳細を先取りしない**——それらは決定後の詳細設計／コードの領域である。

### 例（最小限・テンプレート用）

```
提案内容:
  受注の一括登録（US-01）に行単位の部分成立を導入することを提案する。在庫内の行は成立、
  在庫超過の行のみ業務エラーで弾く方向をたたき台として示す。ロック粒度・クラス構成は
  ここで確定せず、方向への合意を先に得る（実装詳細は決定後の詳細設計へ）。
```

## 代替案

検討している代替を、**まだ生きている選択肢**として書く。ADR の `却下案`（葬った選択肢）とは時間軸で対であり、ここでは「採らないと決めた」ものではなく「どれも採りうる」ものを並べる。

**含む**: 比較している代替案・各案のトレードオフ（長所と短所の両面）。提案本命にも長所短所を書く（本命だけ良く書かない）。

**含まない**: 「もう却下済み」のような断定（それは未決を装った既決＝ADR の前倒し）・見せかけの弱い代替（straw man）。

代替案は**straw man にしない**。採用本命を引き立てるために弱い代替をわざと並べるのは事後正当化であり、RFC の体をなさない。各代替に正直なトレードオフ（採りうる長所も）を書く。代替がまだ思いついていないなら、その旨を正直に書く（捏造しない）。

### 例（最小限・テンプレート用）

```
案A: 全行一括の強整合（1行でも超過なら全件失敗）。
  長所: 整合が単純で呼び出し側は「全部成功/全部失敗」だけ考えればよい。
  短所: 繁忙期に1行の不足で全件やり直しになり、受注漏れ防止の価値(US-01)を損なう。
案B: 行単位の部分成立（提案本命）。
  長所: 落ちた行だけ提示でき受注漏れを減らせる。
  短所: 在庫の一時的不整合ウィンドウが生じ、ロック戦略の検討が要る。
```

## 未解決の論点

まだ決着していない問いを正直に列挙する。**RFC の核**であり、欠けると「提案を装った既決」になる（前述・機械表現の肝）。

**含む**: 本当にまだ決まっていない問い・コメントで決めたい論点・判断材料が不足している箇所。

**含まない**: 決まったかのように書いた問い（既決を装った未決＝形だけの論点）・実装詳細レベルの瑣末な疑問。

未解決の論点は**本当に未決**のものを書く。「決まったかのように見えて実は議論したい」を曖昧にせず、決着していないことを明示する。論点が1つも無いなら、それは RFC を要しない（もう決まっている＝ADR へ）兆候である。

### 例（最小限・テンプレート用）

```
未解決の論点:
  - 案B のロックは悲観/楽観どちらにするか（性能影響の実測がまだ無い）。
  - 部分成立の内訳を呼び出し側へどの粒度で返すか（行単位エラーの API 形）。
  - 案C を採るなら別スプリントへ切るか（期限との兼ね合いが未決）。
```

## 推奨節（動機・影響範囲・Prior art）

> **推奨節（必須ではない）**。必須にすると小さい RFC でも全節を埋めさせる過剰テンプレ化（gold plating）を招くため必須にしない。推奨節の見出しには必須語（`提案内容`/`代替案`/`未解決の論点`/`トレーサビリティ`）を**含めない**（デコイ回避＝「提案の背景」「検討した代替」のような見出しを置かない）。

- **動機（Motivation）**: なぜ今この提案を開くか・解こうとしている課題・きっかけになった要求。
- **影響範囲**: この提案が及びうる範囲（呼び出し側・関連サービス・運用）。決定前なので方針レベルにとどめる。
- **Prior art（先行事例）**: 社内外の類似事例・参考にした設計。

## トレーサビリティ

各**提案・論点**を対応する要求／user-story へ紐付ける。孤立した提案（対応要求を持たない提案＝スコープクリープ候補・P4 違反）を作らない（P4: 全要素トレース可能）。

> **独立トレース節を持つ理由（ADR との非対称）**: ADR はトレースを Context 内に書き独立節を設けなかった（採番・記録フォーマットを [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルが所有し、その形式と衝突させないため）。これに対し **RFC は doc-standards 固有の doc_type で外部スキル所有フォーマットと衝突しない**ので、独立トレーサビリティ節を持ち機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) を**有効化**する。これは [`./acceptance-criteria.md`](./acceptance-criteria.md) / [`./design-doc.md`](./design-doc.md) と同型であり、[`./adr.md`](./adr.md) / [`./user-story.md`](./user-story.md) とは非対称である。

**表の書き方（提案・論点 → 対応要求）**:
- ID 列のヘッダに「**対応**」を含める（例: `対応要求`）。第1列は提案・論点名（主語）であり、機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) は第1列を主語として除外し、「対応」を含む列を ID 列とみなす（[`./design-doc.md`](./design-doc.md) の対応 user-story 列と同方式）。
- 全セルを埋める。対応列が空・ダッシュ（`-`）の提案・論点は孤立提案（根拠のない提案＝スコープクリープ候補）であり、機械が検出する逸脱になる。
- 機能要件に直接紐付かない論点（性能・運用等）は、対応する NFR の ID を付ける。

| 提案・論点 | 対応要求 | 備考 |
|---|---|---|
| 行単位の部分成立を提案 | US-01 | 受注漏れ防止の中核 |
| ロック方式の未決論点 | NFR-PERF-02 | 性能要求に紐付く |
| 部分成立内訳の返却粒度 | US-01 | 利用者への提示要求 |

**逸脱の判定基準**:
- 「対応要求」が空（またはダッシュ）の提案・論点が存在する → 孤立提案。対応を補うか、提案を削除する（**空セルそのものの検出は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当**）。
- 対応要求が形式上は埋まっているが、その価値と提案が食い違う → 紐付けの質の問題であり、[`../rubric/rfc.md`](../rubric/rfc.md) の質的判定で見る。

## 決定後は ADR へ落とす（委譲分担の明示・S5・二重定義回避）

**doc-standards は RFC の「粒度境界」だけを定義する。** すなわち (a) 必須4節（提案内容 / 代替案 / 未解決の論点 / トレーサビリティ）の存在・(b) 代替案がまだ生きている選択肢として書かれているか・(c) 未解決の論点が本当に未決か・(d) 実装詳細を先取りしていないか、である。

RFC は**決定前**の文書であり、コメントを収集して**決定したら ADR へ落とす**（時間軸連鎖）。その決定の記録の採番（ADR-NNNN）・記録フォーマット・内容評価は [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルが所有する（S5）。RFC で生きていた代替のうち採らなかったものは、ADR の却下案（葬った選択肢）へ移る。

| 関心事 | 所有 | 内容 |
|---|---|---|
| RFC の**粒度境界** | doc-standards（本レシピ・[`../rubric/rfc.md`](../rubric/rfc.md)） | 必須4節の存在・代替が生きている選択肢・未決が本当に未決・実装詳細を先取りしない |
| 決定後の **ADR の採番・生成・内容評価** | `architecture-decision-records` スキル | ADR-NNNN 採番・記録フォーマット・決定や却下案の技術的妥当性 |

doc-standards 側で ADR の番号体系・記録フォーマットを**二重定義しない**（S3 と整合: 委譲先が source of truth）。RFC の提案・代替・論点の**内容の正否**（提案が技術的に妥当か・どの代替を採るべきか）は本レシピも rubric も評価しない——それはレビュースキル（`review-handoff` / `santa-method`）および決定時の ADR スキルの責務である。

## vocab の説明（RFC は vocab を空にする／逸脱は rubric 主導）

**本 doc_type（rfc）の機械語彙チェック（vocab）は空である**（[`../scripts/vocab/rfc.json`](../scripts/vocab/rfc.json) の forbidden は `[]`）。これは設計上の判断であり、欠落ではない。

**経験検証（3語の出番を確かめた）**: agile の [`./acceptance-criteria.md`](./acceptance-criteria.md) は曖昧期待結果3語（`正しく表示`/`正しく動作`/`適切に処理`）を vocab に持つ。これらが誤爆なく拾えたのは、AC が**観測可能な合否（Then の期待結果）**を書く doc_type だからである。だが **RFC は『決定前の提案/探索文書』であり、期待結果・完了条件・テスト合否を書かない**——3語の**主戦場が構造的に無い**。出番が無いので置いても検出に寄与せず、むしろ RFC が将来の振る舞いを地の文で語る正当な未決表明（例「提案する仕組みが**正しく動作**するかは未解決の論点で検討する」——これは逸脱でなく未決の表明）に部分一致で**誤爆**しうる。よって3語は採らず、vocab を空にする。

RFC の逸脱（**実装詳細の先取り**・**未決を装った既決**・**straw man 代替**）は、いずれも**構造・文脈の判定**であって、特定の禁止トークンの部分一致では原理的に拾えない。「代替案なし」「未解決の論点なし」（提案を装った既決）は必須見出し `代替案` / `未解決の論点` の欠落として [`../scripts/check_headings.py`](../scripts/check_headings.py) が機械検出し、孤立提案（対応要求 ID 空セル）は独立トレース節の空セルとして [`../scripts/check_traceability.py`](../scripts/check_traceability.py) が機械検出する。機械で綺麗に拾える逸脱はそちらに委ね、残る質的逸脱（実装詳細先取り・未決を装った既決・straw man）には明確な定型句マーカーが無いため vocab を空にする。

> **vocab の有無は『その doc_type の逸脱が機械で綺麗に拾えるか』で決まる**——agile か WF かの別ではない。[`./acceptance-criteria.md`](./acceptance-criteria.md) は Then の曖昧期待結果3語が部分一致誤爆なく拾えたから vocab を持ち、[`./user-story.md`](./user-story.md) / [`./design-doc.md`](./design-doc.md) / [`./adr.md`](./adr.md) と本 RFC は拾えないから vocab を空にする（design-doc/adr 同型で構造・文脈ゆえ空＝5例目の空）。技術名・製品名・`SQL` は禁止しない（RFC は技術選定の探索で技術名が正当に頻出するため誤爆を避ける・既存方針踏襲・S4 非対称）。これが agile の **rubric 主導**の正しい現れであり、機械で綺麗に拾える逸脱だけ機械に任せ（＝必須見出し欠落・トレース空セル）、それ以外（実装詳細先取り・未決を装った既決・straw man・提案/論点の質・委譲境界）は [`../rubric/rfc.md`](../rubric/rfc.md) の質的判定へ委ねる。

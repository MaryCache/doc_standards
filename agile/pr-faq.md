## 位置づけ（agile 第2層の 6 本目のスライス）

これは doc-standards で**6 本目の agile レシピ**である（1 本目＝[`./user-story.md`](./user-story.md)・2 本目＝[`./acceptance-criteria.md`](./acceptance-criteria.md)・3 本目＝[`./design-doc.md`](./design-doc.md)・4 本目＝[`./adr.md`](./adr.md)・5 本目＝[`./rfc.md`](./rfc.md)）。User Story が WHO/WHAT/WHY を、Acceptance Criteria がその価値の観測可能な合否を、Design Doc が「どう作るか」の設計合意を、ADR が決まった1判断の永続記録を、RFC が「まだ決めていない」提案のコメント募集を担うのに対し、**PR-FAQ（Amazon Working Backwards）は『顧客視点の未来プレスリリース＋想定問答（FAQ）で企画そのものを逆算する最上流の提案文書**である。社内の機能リストからではなく、「顧客にとって何が良くなるか」という到達点（プレスリリース）から逆向きに（Working Backwards）企画の是非を判断する。

### Working Backwards（逆算）の起点とは何か（このスライス固有の肝）

PR-FAQ の核は **顧客の便益から逆算する**ことである。普通の企画は「作れる機能」を起点に積み上げる（プロダクトアウト）。Working Backwards はこれを反転し、**まだ作る前に「顧客に向けた未来の記者発表（プレスリリース）」を書いてしまう**——その発表が顧客にとって魅力的でなければ、その企画は作る価値が無いと早期に判断する。

| | プロダクトアウト（避ける） | Working Backwards（PR-FAQ の起点） |
|---|---|---|
| 起点 | 作れる機能・技術 | 顧客の課題と便益（到達点） |
| 書く順 | 機能 → （あれば）顧客価値 | 顧客便益（PR）→ 逆算して機能 |
| プレスリリースの中身 | 内部機能の羅列 | 顧客にとって何が良くなるか |
| 判断 | 作れるか | 顧客が喜ぶか・どうなれば成功か |

この向き（顧客便益 → 機能）が崩れ、プレスリリースが**内部機能の羅列**になった瞬間、PR-FAQ は Working Backwards の体をなさなくなる（後述・最大の逸脱）。

agile の第2層は**成果物ライフサイクル軸**（living docs として育ち、必要になった時点で詳細を確定する JIT 詳細化）で整理する。WF の**工程フェーズ軸**とは軸が異なる——これが**非対称設計の原則（S4）**である。ただし**原則層（第1層）は手法非依存で共通**であり、What/Why と How の分離（P2）・トレーサビリティ（P4）・設計根拠の必須（P4）は WF でも agile でも変わらない不変量である。本レシピもそれらを再定義せず参照するだけである（S3）。

### 必須は絞る／顧客の課題・社内向けの補足は推奨（このスライス固有の設計理由）

PR-FAQ の核は **プレスリリース（未来の顧客発表・1p）・想定問答（FAQ・5p）・成功指標・トレース**である。これらを必須にし、それ以外（顧客の課題・社内向けの補足・利用開始方法等）は推奨にとどめる。必須を増やすほど小さい企画にまで全節を埋めさせる過剰テンプレ化（gold plating）を招くため、design-doc / adr / rfc / test 系と同じく必須は絞る。

- **必須節**: `プレスリリース`（未来の記者発表・顧客視点・1ページ）／`想定問答`（FAQ・顧客向けの想定問答）／`成功指標`（どうなれば成功か・測定可能な数値）／`トレーサビリティ`（各主張・指標→対応する顧客課題／事業目標への紐付け）。
- **推奨節（必須にしない）**: `顧客の課題`（Working Backwards 起点・なぜこの企画か）／`社内向けの補足`（Internal FAQ＝難所・コスト・リスク）／`利用開始方法`等。必須にすると過剰テンプレ化を招く。
- `位置づけ` は導入であり必須ではない。末尾の `vocab の説明` も必須見出しではない。

> **なぜ `成功指標` が必須なのか（機械表現の肝・PR-FAQ の核）**: 魅力的なプレスリリースと想定問答だけ書いて**「どうなれば成功か（成功指標）」を欠く**と、その企画は「夢は語るが達成の判定基準が無い＝絵に描いた餅」と区別がつかなくなる。Working Backwards は到達点から逆算する手法であり、**到達点（成功条件）を測定可能に定めることが体をなす条件**である。**測定可能な成功条件の欠落＝絵に描いた餅**を、成功指標の見出し欠落で機械検出する。これは [`./adr.md`](./adr.md) の `却下案` 独立必須（Why の片側欠落の検出）・[`./design-doc.md`](./design-doc.md) の `Non-Goals` 必須（スコープ否定側の検出）・[`./rfc.md`](./rfc.md) の `未解決の論点` 必須（未決を装った既決の検出）・WF nonfunctional の `測定方法` 必須化と**同型**の「核の否定／欠落側を独立必須にして機械検出する」設計である。機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）は見出しの**部分一致**で必須を見るため、スキーマ（[`../scripts/schema/pr-faq.json`](../scripts/schema/pr-faq.json)）の `required_headings` に `成功指標` を入れ、本レシピの実見出しを `## 成功指標` としている。

> **なぜ `想定問答`（複合語）を required にし `FAQ` を使わないのか（PR-FAQ 固有のデコイ最難関）**: PR-FAQ の "FAQ" を required にすると、`FAQ`（3文字）が **H1 や doc_type 名「PR-FAQ」に部分一致してデコイ化する**（`"FAQ" in "PR-FAQ"` は真）——`## 想定問答` 節を削っても doc_type 名のせいで誤って pass する。これを避けるため discriminating な日本語複合語 `想定問答` を required にし、実見出しを `## 想定問答（FAQ）` にする（"想定問答" は H1「PR-FAQ」に含まれないので安全）。Internal FAQ の推奨節は `## 社内向けの補足` のように**「想定問答」を含めない**見出しにする（`## 想定問答（社内向け）` のように2見出しに「想定問答」を入れると、想定問答節を削っても誤 pass するデコイになる）。

> **デコイの罠（最重要・破壊テストで検証済み）**: required 各語（`プレスリリース`/`想定問答`/`成功指標`/`トレーサビリティ`）は**レシピ実見出しに「1つだけ」部分一致**しなければならない。H1・導入見出し（`位置づけ`）・推奨節・本文の他見出しに required 4語の**いずれも含めない**。本レシピの H1 は `# PR-FAQ レシピ — アジャイル（Working Backwards）`（required 4語を一切含まない・"PR-FAQ" の "FAQ" は required `想定問答` と一致しないので安全・"Working Backwards" も可）。`プレスリリース` の実見出しは `## プレスリリース`（H1・推奨節・本文見出しに「プレスリリース」を含めない）。`成功指標` の実見出しは `## 成功指標`。とりわけ missing-headings fixture は、欠落させる `成功指標` を H1 や他見出しに残さない decoy-clean なものにする（cycle-16/cycle-20 で実装者が踏んだ罠＝missing fixture の H1 に required 語が残り偽 pass する罠を避ける）。required 各語を1見出しだけに部分一致させる設計を守る（cycle-14 Goals/Non-Goals・cycle-18 テストレベル・cycle-19 処理仕様・cycle-20 ADR・cycle-21 RFC デコイ回避と同型だが、PR-FAQ は doc_type 名「PR-FAQ」に "FAQ" を含む点で ADR の "Decision" と並ぶ最難関）。

**境界を越えた記述の扱い**:
- **PR の内部機能リスト化**（顧客便益でなく内部機能を羅列）は PR-FAQ 最大の逸脱である。プレスリリースは顧客にとって何が良くなるかで書く（プロダクトアウトの反転＝Working Backwards）。
- **楽観バイアス**（FAQ が難所・コスト・リスクに不正直）を避ける。とりわけ社内向けの補足（Internal FAQ）で、都合の悪い難所・コスト・リスクに正直に答える。
- **成功指標の曖昧表現**（「大幅に改善」「高い満足度」等・測定不能な形容詞/副詞）を避ける。成功指標は測定可能な数値で書く（節の有無は機械、中身の測定可能性は [`../rubric/pr-faq.md`](../rubric/pr-faq.md) の質的判定）。
- **スコープ肥大**（15p の機能リスト・スライド化）を避ける。PR-FAQ は PR 1p＋FAQ 5p 程度の量に収める。書き切ろうとして機能を網羅し始めたら、それは Working Backwards でなく機能リストへ堕している。
  - 注（出典・2026-10-11）: 「PR 1p＋FAQ 5p」は Bryar & Carr『Working Backwards』（2021）の抜き書きを引いた二次の記述でしか確認できていない。元の Werner Vogels「Working Backwards」（2006・https://www.allthingsdistributed.com/2006/11/working_backwards.html）にも、二人の公式サイト（https://workingbackwards.com/resources/working-backwards-pr-faq/）にも、ページ数の記述は無い。量の目安として扱い、規格のようには扱わない。
  - 注（出典・2026-10-11 追い）: PR の長さには元の言い方がある。Amazon の Ian McAllister の Quora 回答（2010・https://www.quora.com/What-is-Amazons-approach-to-product-development-and-product-management）に「1ページ半を超えたら、たぶん長すぎ。段落はたいてい3〜4文」とある。FAQ のページ数は書いていない。事業や実行の問いは FAQ に回して、PR は顧客が得るものに集中させる、という扱い。McAllister の PR の骨組み（見出し・副見出し・要約・課題・解決・社内の人の言葉・始め方・顧客の言葉・締め）は、本レシピの推奨節（顧客の課題・利用開始方法）と向きが合う。
  - 注（範囲）: Vogels 2006 の Working Backwards は、プレスリリース → FAQ → 顧客体験の定義 → 利用者マニュアルの4段を書く手順である。本レシピが扱うのは最初の2段（PR と FAQ）で、顧客体験と利用者マニュアルは後続の文書（外部設計・利用者向け文書）に委ねる。
- **決まった設計判断**（もう確定した方式）を PR-FAQ に書いていたら、それは ADR の領分である（隣接）。観測可能な合否の細目は acceptance-criteria へ落とす（隣接）。

## プレスリリース

未来の記者発表（顧客視点・1ページ）を、まだ作る前に書く。**顧客にとって何が良くなるか**を、内部機能ではなく顧客の言葉で語る。

**含む**: 見出し（顧客便益の一言）・課題と解決の物語・顧客や現場の声（引用）・顧客が得る具体的な体験。顧客視点の便益で書く。

**含まない**: 内部機能の羅列（PR の内部機能リスト化＝最大の逸脱）・実装方式やアーキの説明（それは Design Doc / ADR）・確定していない数値の断定。

プレスリリースは**顧客便益から逆算**して書く（Working Backwards）。「この機能を作りました」ではなく「顧客はこれができるようになりました」で書く。機能の羅列に堕したら、それはプロダクトアウトであり Working Backwards の体をなさない。

### 例（最小限・テンプレート用）

```
プレスリリース（未来の記者発表・顧客視点・1p）:
  見出し:「受注をまとめて一度に登録できるようになりました」
  本日、当社は受注管理に一括登録を追加した。繁忙期に1件ずつ手入力していた現場担当者は、
  複数の受注を一度の操作で登録でき、在庫内は即成立、超過分だけが即提示される。
  「どれが通りどれが在庫待ちか一目で分かり、受注漏れを心配せず接客に集中できる」と店長は語る。
  （内部のロック方式・クラス構成は書かない＝それは決定後の設計の領域）
```

## 想定問答（FAQ）

顧客・利用者が抱くであろう問いに、未来の発表に添える形で答える（External FAQ）。プレスリリースの便益が「本当に成り立つのか」という疑問に正面から答える。

**含む**: 顧客が実際に抱く問い・その率直な答え・便益の裏で気になる点（上限・既存機能との関係・移行）。

**含まない**: 内部実装の詳細な Q&A（それは Design Doc）・難所/コスト/リスクを隠した都合のよい問答だけ（楽観バイアス・社内向けの補足で正直に補う）。

想定問答は**楽観バイアスにしない**。便益だけを並べた都合のよい問答にせず、顧客が当然抱く不安（上限・既存運用への影響）に率直に答える。都合の悪い難所・コスト・リスクは推奨節 `社内向けの補足`（Internal FAQ）で正直に開く。

### 例（最小限・テンプレート用）

```
想定問答（FAQ・顧客向け）:
  Q: 在庫を超えた受注はどうなる？  A: その行だけがエラー提示され、在庫内は成立する（全件やり直しにならない）。
  Q: 既存の1件ずつの登録は使えなくなる？  A: いいえ。単件登録は残り、一括は追加の選択肢。
```

## 成功指標

**どうなれば成功か**を測定可能な数値で定める。**PR-FAQ の核**であり、欠けると「夢は語るが達成基準の無い絵に描いた餅」になる（前述・機械表現の肝）。

**含む**: 測定可能な成功条件（数値・期限つき）・現状値との対比・誰がどう測るか。

**含まない**: 測定不能な曖昧表現（「大幅に改善」「高い満足度」等の形容詞/副詞）・実装の進捗指標（成功は顧客成果で測る）。

成功指標は**測定可能な数値**で書く。「大幅に改善」「高い満足度」のような曖昧表現は、達成したか誰も判定できず成功指標の体をなさない。Working Backwards の到達点（プレスリリースで約束した便益）が、数値でどうなれば実現したと言えるかを定める。

### 例（最小限・テンプレート用）

```
成功指標（どうなれば成功か・測定可能に）:
  - 繁忙期の受注漏れ件数を、リリース後3か月で月20件未満に減らす（現状は月80件前後）。
  - 一括登録の1操作あたり処理時間を、500行で5秒以内に収める。
  - 対象店舗での繁忙期の利用率を70%以上にする。
  （「大幅に改善」「高い満足度」のような測定不能な曖昧表現は避ける＝rubric の質的判定で見る中身）
```

## 推奨節（顧客の課題・社内向けの補足・利用開始方法）

> **推奨節（必須ではない）**。必須にすると小さい PR-FAQ でも全節を埋めさせる過剰テンプレ化（gold plating）を招くため必須にしない。推奨節の見出しには必須語（`プレスリリース`/`想定問答`/`成功指標`/`トレーサビリティ`）を**含めない**（デコイ回避＝Internal FAQ を `## 社内向けの補足` にして「想定問答」を含めない・「成功指標」を含む見出しを別に置かない）。

- **顧客の課題（Working Backwards 起点）**: なぜ今この企画を開くか・顧客が抱える課題・きっかけになった要求。Working Backwards の出発点。
- **社内向けの補足（Internal FAQ）**: 顧客向けの想定問答（External）では出しにくい**難所・コスト・リスク**に正直に答える。楽観バイアスを避ける最後の砦であり、ここで都合の悪い点を隠さない。
- **利用開始方法**: 顧客がどう使い始めるか（オンボーディング）。

## トレーサビリティ

各**主張・成功指標**を、対応する**顧客課題／事業目標**へ紐付ける。顧客課題に紐付かない機能・主張（プロダクトアウト＝Working Backwards 違反）を作らない（P4: 全要素トレース可能）。

> **トレース先が「対応する顧客課題／事業目標」である理由（PR-FAQ 固有・最上流ゆえ）**: PR-FAQ は要件定義の**入口（最上流）**であり、対応すべき要求 ID（FR/NFR）がまだ確定していない段階で書かれる。そのため他の doc_type のように「対応要求」へ向けるのではなく、**「対応する顧客課題」または「対応事業目標」**へ向ける（[`../waterfall/test/test-strategy.md`](../waterfall/test/test-strategy.md) がトレースを上位＝事業目標へ向けた前例と同型）。これにより、PR-FAQ にとって意味的に最も強い逸脱——**顧客課題に紐付かない機能/主張＝Working Backwards 違反＝プロダクトアウト**——の空セルを機械検出できる。「作れるから書いた」だけの主張は対応する顧客課題を埋められず、孤立要素として [`../scripts/check_traceability.py`](../scripts/check_traceability.py) が検出する。

> **独立トレース節を持つ理由（ADR との非対称）**: ADR はトレースを Context 内に書き独立節を設けなかった（採番・記録フォーマットを [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルが所有し、その形式と衝突させないため）。これに対し **PR-FAQ は doc-standards 固有の doc_type で外部スキル所有フォーマットと衝突しない**ので、独立トレーサビリティ節を持ち機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) を**有効化**する。これは [`./acceptance-criteria.md`](./acceptance-criteria.md) / [`./design-doc.md`](./design-doc.md) / [`./rfc.md`](./rfc.md) と同型であり、[`./adr.md`](./adr.md) / [`./user-story.md`](./user-story.md) とは非対称である。

**表の書き方（主張・指標 → 対応する顧客課題／事業目標）**:
- ID 列のヘッダに「**対応**」を含める（例: `対応する顧客課題`）。第1列は主張・指標名（主語）であり、機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) は第1列を主語として除外し、「対応」を含む列を ID 列とみなす（[`./design-doc.md`](./design-doc.md) / [`./rfc.md`](./rfc.md) の対応列と同方式）。
- 全セルを埋める。対応列が空・ダッシュ（`-`）の主張・指標は、顧客課題に紐付かない機能/主張（プロダクトアウト＝Working Backwards 違反）であり、機械が検出する逸脱になる。
- 顧客課題に直接紐付かない指標（性能・運用等）は、対応する事業目標や NFR の ID を付ける。

| 主張・指標 | 対応する顧客課題 | 備考 |
|---|---|---|
| 行単位の部分成立で受注漏れを防ぐ | US-01 | 繁忙期の機会損失の解消 |
| 受注漏れ件数 月20件未満 | US-01 | 課題の解消度を測る成功指標 |
| 500行5秒以内の処理時間 | NFR-PERF-02 | 現場運用に耐える性能 |

**逸脱の判定基準**:
- 「対応する顧客課題」が空（またはダッシュ）の主張・指標が存在する → 顧客課題に紐付かない機能/主張（プロダクトアウト）。対応を補うか、主張を削除する（**空セルそのものの検出は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当**）。
- 対応する顧客課題が形式上は埋まっているが、その課題と主張が食い違う → 紐付けの質の問題であり、[`../rubric/pr-faq.md`](../rubric/pr-faq.md) の質的判定で見る。

## 決定後は ADR／acceptance-criteria へ落とす（委譲分担の明示・S5・二重定義回避）

**doc-standards は PR-FAQ の「粒度境界」だけを定義する。** すなわち (a) 必須4節（プレスリリース / 想定問答 / 成功指標 / トレーサビリティ）の存在・(b) プレスリリースが顧客便益で書かれているか（内部機能リスト化していないか）・(c) 想定問答が楽観バイアスでないか・(d) 成功指標が測定可能か・(e) スコープが肥大していないか、である。

PR-FAQ は**最上流**の文書であり、企画が承認されたら下流へ落とす。**確定した設計判断は ADR へ**（採番・記録フォーマット・内容評価は [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルが所有・S5）、**観測可能な合否の細目は [`./acceptance-criteria.md`](./acceptance-criteria.md) へ**落とす。PR-FAQ で語った成功指標は、AC で観測可能な合否（Then の期待結果）へブレークダウンされうる——両者で時間軸と抽象度を割って二重定義を避ける。

| 関心事 | 所有 | 内容 |
|---|---|---|
| PR-FAQ の**粒度境界** | doc-standards（本レシピ・[`../rubric/pr-faq.md`](../rubric/pr-faq.md)） | 必須4節の存在・顧客便益で書く・楽観バイアスでない・成功指標が測定可能・スコープが肥大しない |
| 確定した **設計判断の記録（ADR）** | `architecture-decision-records` スキル | ADR-NNNN 採番・記録フォーマット・決定の技術的妥当性 |
| 観測可能な**合否の細目** | [`./acceptance-criteria.md`](./acceptance-criteria.md) | Then の期待結果・受け入れ条件の粒度 |

doc-standards 側で ADR の番号体系・記録フォーマットを**二重定義しない**（S3 と整合: 委譲先が source of truth）。PR-FAQ の主張・指標の**内容の正否**（企画が事業的に妥当か・指標が適切か）は本レシピも rubric も評価しない——それはレビュースキル（`review-handoff` / `santa-method`）の責務である。

## vocab の説明（PR-FAQ は vocab を空にする／逸脱は rubric 主導）

**本 doc_type（pr-faq）の機械語彙チェック（vocab）は空である**（[`../scripts/vocab/pr-faq.json`](../scripts/vocab/pr-faq.json) の forbidden は `[]`）。これは設計上の判断であり、欠落ではない。

**経験検証（3語の出番を確かめた）**: agile の [`./acceptance-criteria.md`](./acceptance-criteria.md) は曖昧期待結果3語（`正しく表示`/`正しく動作`/`適切に処理`）を vocab に持つ。これらが誤爆なく拾えたのは、AC が**観測可能な合否（Then の期待結果）**を書く doc_type だからである。だが **PR-FAQ は『顧客視点の未来発表＋想定問答で企画を逆算する提案文書』であり、期待結果・完了条件・テスト合否を書かない**——3語の**主戦場が構造的に無い**。出番が無いので置いても検出に寄与せず、むしろ PR-FAQ が将来の顧客体験を便益として地の文で語る正当な文（例「在庫超過行が**正しく表示**されるようになる」——これは PR の顧客便益記述であり逸脱でない）に部分一致で**誤爆**しうる。よって3語は採らず、vocab を空にする（[`./rfc.md`](./rfc.md) / [`./design-doc.md`](./design-doc.md) / [`./adr.md`](./adr.md) / [`./user-story.md`](./user-story.md) / WF `test-strategy` に続く**6例目の空**）。

PR-FAQ の真の逸脱（**PR の内部機能リスト化**・**楽観バイアス**・**成功指標の曖昧表現**・**スコープ肥大／スライド化**）は、いずれも**構造・量・文脈の判定**であって、特定の禁止トークンの部分一致では原理的に拾えない。とりわけ**成功指標の曖昧表現**（「大幅に改善」「高い満足度」）は副詞・形容詞であり、WF nonfunctional の「高速に」等と同じく**部分一致では正当な記述（例「大幅に」を含む正当な文脈）と切り分けられず誤爆**するため rubric の領分である。「プレスリリースなし」「想定問答なし」「成功指標なし」は必須見出し `プレスリリース`/`想定問答`/`成功指標` の欠落として [`../scripts/check_headings.py`](../scripts/check_headings.py) が機械検出し、顧客課題に紐付かない機能/主張（対応する顧客課題 ID 空セル＝Working Backwards 違反）は独立トレース節の空セルとして [`../scripts/check_traceability.py`](../scripts/check_traceability.py) が機械検出する。機械で綺麗に拾える逸脱はそちらに委ね、残る質的逸脱（内部機能リスト化・楽観バイアス・成功指標の曖昧表現・スコープ肥大）には明確な定型句マーカーが無いため vocab を空にする。

> **vocab の有無は『その doc_type の逸脱が機械で綺麗に拾えるか』で決まる**——agile か WF かの別ではない。[`./acceptance-criteria.md`](./acceptance-criteria.md) は Then の曖昧期待結果3語が部分一致誤爆なく拾えたから vocab を持ち、[`./user-story.md`](./user-story.md) / [`./design-doc.md`](./design-doc.md) / [`./adr.md`](./adr.md) / [`./rfc.md`](./rfc.md) と本 PR-FAQ は拾えないから vocab を空にする（design-doc/adr/rfc 同型で構造・量・文脈ゆえ空＝6例目の空）。技術名・製品名・`SQL` は禁止しない（PR-FAQ は顧客便益を語るが、機能名・製品名が顧客向けの説明として正当に出るため誤爆を避ける・既存方針踏襲・S4 非対称）。これが agile の **rubric 主導**の正しい現れであり、機械で綺麗に拾える逸脱だけ機械に任せ（＝必須見出し欠落・トレース空セル）、それ以外（内部機能リスト化・楽観バイアス・成功指標の曖昧表現・スコープ肥大・紐付けの質・委譲境界）は [`../rubric/pr-faq.md`](../rubric/pr-faq.md) の質的判定へ委ねる。

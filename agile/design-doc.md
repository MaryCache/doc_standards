## 目的とスコープ（agile 第2層の 3 本目のスライス）

これは doc-standards で**3 本目の agile レシピ**である（1 本目＝[`./user-story.md`](./user-story.md)・2 本目＝[`./acceptance-criteria.md`](./acceptance-criteria.md)）。User Story が WHO/WHAT/WHY（価値）を、Acceptance Criteria がその価値の観測可能な合否を定めるのに対し、**Design Doc は「どう作るか」の設計合意をチームで形成する living doc** である（Google Style / arc42 / C4 系）。≒ WF の基本設計の合意形成版であり、スプリントのインクリメントに合わせて育てる。

agile の第2層は**成果物ライフサイクル軸**（living docs として育ち、必要になった時点で詳細を確定する JIT 詳細化）で整理する。WF の**工程フェーズ軸**とは軸が異なる——これが**非対称設計の原則（S4）**である。ただし**原則層（第1層）は手法非依存で共通**であり、What/Why と How の分離（P2）・トレーサビリティ（P4）・設計根拠の必須（P4）は WF でも agile でも変わらない不変量である。本レシピもそれらを再定義せず参照するだけである（S3）。

### 必須は絞る／代替・横断は推奨（このスライス固有の設計理由）

他の doc_type は「必須見出しを増やして欠落を機械検出する」方向で整備してきた。**だが Design Doc はこの方向を取らない。** 責務対照表（Design Doc 行）が**「全セクション強制記入＝逸脱」「arc42 全12セクション埋め強制＝含まない」**と定めるため、必須見出しを増やすほど Design Doc 自身の哲学（必要な節だけ書く・JIT 詳細化）に反する。だから必須は最小限に絞り、残りは推奨にする。

- **必須節**: `Context`（背景・なぜこの設計が必要か）／`Goals / Non-Goals`（達成すること・**やらないこと＝スコープ否定**）／`トレーサビリティ`（対応 user-story／要求へ紐付け）。
- **推奨節（必須にしない）**: `検討した代替案`（代替と却下理由・重要判断は ADR リンク委譲）／`横断懸念`（ログ・認証・エラー処理など）。これらを必須にすると、小さい設計でも全節を埋めさせる過剰テンプレ化（gold plating）を招くため、必須にしない。
- `目的とスコープ`（位置づけ）は導入であり必須ではない。末尾の `vocab の説明` も必須見出しではない。

> **なぜ Non-Goals が必須なのか（機械表現の肝）**: 達成すること（Goals）だけ書いて**やらないこと（Non-Goals）を欠く**と、スコープが無限に広がる（スコープクリープ）。スコープ否定側の欠落こそスコープクリープの主因であり、意味的にも Non-Goals 必須が正しい。機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）は見出しの**部分一致**で必須を見るため、スキーマ（[`../scripts/schema/design-doc.json`](../scripts/schema/design-doc.json)）の `required_headings` に `Non-Goals` を入れ、本レシピの実見出しを `Goals / Non-Goals`（Goals と Non-Goals を1節に併記）として、`Non-Goals` がその見出しの部分文字列になるようにしている。`Goals/Non-Goals`（スラッシュ込み）を required に書くと、スペース込みの実見出し `Goals / Non-Goals` に部分一致せず誤って欠落判定になる罠（cycle-13 で H1 部分一致の罠を踏んだのと同種）があるため、`Non-Goals` で機械表現する。

**境界を越えた記述の扱い**:
- 自明な実装・バグ修正を Design Doc 化していたら、それは過剰文書化である（責務対照表「含まない」）。Design Doc は非自明な設計判断・横断懸念のある変更に限る。
- 抽象度を上げすぎず下げすぎず、**arc42 は必要なセクションのみ**・**C4 は L1-L2（システム文脈・コンテナ）を優先**し、**L4（クラス図レベル）を最初から全描画しない**。L4 相当のコンポーネント内部の作り込みは詳細設計／コードの領域である。
- まだ確定していない詳細は無理に書き切らない。スプリント中の会話で必要になった時点で確定する（JIT・living doc）。書き切ろうとすること自体が WF 的な前倒しで、agile の趣旨に反する。

## Context（背景・なぜこの設計が必要か）

**含む**: この設計をいま作る理由——解こうとしている課題・現状の痛み・きっかけになった要求や user-story。設計合意の出発点として、読み手が「なぜこの判断が要るのか」を理解できる背景。

**含まない**: 設計の答えそのもの（それは Goals／代替案で書く）・自明な実装やバグ修正の冗長な背景説明（そもそも Design Doc 化しない）。

Context は「なぜ作るか」を書く節である。自明な実装・バグ修正にまで Design Doc を起こすのは過剰文書化であり、Context が薄くなる（書くべき非自明な背景が無い）兆候でもある。Context が書けないなら、その変更は Design Doc を要しない可能性が高い。

### 例（最小限・テンプレート用）

```
Context（背景・課題）:
  繁忙期に受注を1件ずつ登録する運用では処理が追いつかず、受注漏れが発生している（US-01）。
  複数受注をまとめて登録できる仕組みが必要だが、在庫引当との整合という非自明な設計判断を
  含むため、チームで設計合意を形成する目的で本書を書く。
```

## Goals / Non-Goals

達成すること（Goals）と、**あえてやらないこと（Non-Goals＝スコープ否定）**を明示する。Goals だけ書いて Non-Goals を欠くとスコープが無限に広がる（スコープクリープ）。Non-Goals は本スライスの**必須**であり、機械判定も `Non-Goals` の見出しを必須として見る（前述の機械表現の肝）。

**含む**: Goals（この設計で達成する範囲・成功条件）・Non-Goals（今回はやらないこと・対象外とする範囲とその理由）。

**含まない**: Goals/Non-Goals に紛れ込ませた実装手順・L4 相当のクラス内部設計。

**"特になし" で逃げない**: Non-Goals を「特になし」で埋めるのは、スコープ否定を放棄しているのと同じである。境界が本当に無い設計は稀であり、「今回やらないこと」を具体的に1つ以上挙げる。

### 例（最小限・テンプレート用）

```
Goals:
  - 複数受注を1操作でまとめて登録できる。
  - 在庫超過の行は弾き、在庫内の行は登録が成立する（部分成立の振る舞い）。

Non-Goals:
  - 受注のキャンセル・修正フローは本書の対象外とする。
  - 在庫補充の自動発注は今回はやらない（別スプリントで扱う）。
```

## 検討した代替案

> **推奨節（必須ではない）**。代替を比較・却下した記録を残す。**重要な設計判断は ADR にリンク委譲**し、本文に詳細展開しない（後述「ADR 委譲」節・S5・二重定義回避）。

**含む**: 比較した代替案・各案の却下理由（トレードオフ）・採用案。重要なものは [ADR-0001](../../docs/adr/0001-...) 形式で ADR へリンク。

**含まない**: ADR 本体の詳細（Context/Decision/Consequences の全文）——それは ADR 側に書く。本書は採番された ADR を参照するだけである。

代替検討は**事後正当化にしない**。「採用案ありき」で都合のよい却下理由を後付けするのではなく、実際に比較したトレードオフを書く。代替が思いつかない／検討していないなら、その旨を正直に書く（無理に捏造しない）。

### 例（最小限・テンプレート用）

```
案A: 1件ずつの逐次登録 API を呼ぶバッチ。
  却下理由: 部分成立の合意形成が呼び出し側に漏れ、整合が崩れる。
案B: 一括登録の専用ユースケースを設ける（採用）。
  在庫引当の整合方針は ADR に記録: [ADR-0007](../../docs/adr/0007-bulk-order-stock.md)
```

## 横断懸念

> **推奨節（必須ではない）**。複数コンポーネントを横断する設計方針（ログ・認証/認可・エラー処理・トランザクション等）のうち、本設計に関係するものだけを書く。

**含む**: 本設計に関係する横断方針（どの境界で・どの方式で・どう正規化するかの**方針レベル**）。**arc42 は必要な節のみ**・**C4 は L1-L2 を優先**し、**L4（クラス図レベル）を最初から全描画しない**。

**含まない**: 各方針の実装コード・詳細手順・ライブラリ固有の設定値（実装の How は詳細設計／運用設計へ）・コンポーネント内部の作り込み（L4 相当）。

横断懸念は**該当するものだけ**書く。関係の薄い懸念まで全項目テンプレで埋めるのは、arc42 全12セクション埋め強制と同じ過剰テンプレ化（gold plating）であり、Design Doc の逸脱である。

### 例（最小限・テンプレート用）

```
ログ: 一括登録の単位で相関 ID を通し、部分成立の内訳を構造化ログに残す（方針レベル）。
エラー処理: 在庫超過行は業務エラーとして利用者に提示し、在庫内の行は登録を成立させる。
```

## トレーサビリティ

各**設計判断**を対応する user-story／要求へ紐付ける。孤立した設計判断（対応 user-story／要求を持たない判断）を作らない（P4: 全要素トレース可能）。

**表の書き方（設計判断 → user-story／要求）**:
- ID 列のヘッダに「**対応**」を含める（例: `対応 user-story`）。第1列は設計要素名（設計判断）であり、機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) は第1列を主語として除外し、「対応」を含む列を ID 列とみなす。
- 全セルを埋める。対応列が空・ダッシュ（`-`）の設計判断は孤立判断（根拠のない判断）であり、機械が検出する逸脱になる。
- 機能要件に直接紐付かない横断方針（ログ・監査等）は、対応する NFR の ID を「横断 NFR-…」の形で付ける。

| 設計判断 | 対応 user-story | 備考 |
|---|---|---|
| 一括登録専用ユースケース | US-01 | 受注漏れ防止の中核 |
| 部分成立の振る舞い | US-01 | 在庫超過行の扱い |
| 相関 ID 付き構造化ログ | 横断 NFR-OPS-02 | 運用・監査の横断方針 |

**逸脱の判定基準**:
- 「対応 user-story」が空（またはダッシュ）の設計判断が存在する → 孤立判断。対応を補うか、判断を削除する（**空セルそのものの検出は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当**）。
- 対応 user-story が形式上は埋まっているが、その価値と設計判断が食い違う → 紐付けの質の問題であり、[`../rubric/design-doc.md`](../rubric/design-doc.md) の質的判定で見る。

## ADR 委譲（設計判断の記録）

**設計判断の記録（ADR の採番・生成）は [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルに委譲する（S5）。** 本書は ADR を生成しない。重要な設計判断（採用したアーキ方針・技術選定の根拠・却下した代替）は ADR 側に記録し、Design Doc からは `[ADR-0001](...)` の形でリンク＋採番を**参照**するだけである。doc-standards 側で ADR の番号体系・記録フォーマットを二重定義しない（S3 と整合: 委譲先が source of truth・[`./acceptance-criteria.md`](./acceptance-criteria.md) 隣接の architecture-design と同じ S5）。

**ADR リンクは必須にしない**: 小さい Design Doc では ADR が不要なこともある。リンクの**存在**を機械強制せず、重要判断が本文に詳細展開されず ADR に委譲されているか・あれば事後正当化でないかは [`../rubric/design-doc.md`](../rubric/design-doc.md) の質的判定で見る。

## vocab の説明（Design Doc は vocab を空に戻す／逸脱は rubric 主導）

**本 doc_type（design-doc）の機械語彙チェック（vocab）は空である**（[`../scripts/vocab/design-doc.json`](../scripts/vocab/design-doc.json) の forbidden は `[]`）。これは設計上の判断であり、欠落ではない。

注意すべきは、**同じ agile でも [`./acceptance-criteria.md`](./acceptance-criteria.md) は vocab を持つ**（Then の曖昧期待結果3語）ことである。AC が vocab を持てたのは、その逸脱（Then の観測可能性違反）が test-case-spec で**部分一致の誤爆なく機械検出できると実証済み**の定型句だったからである。これに対し **Design Doc の逸脱（全セクション強制記入・arc42 全12セクション埋め・C4 の L4 クラス図を最初から全描画・自明な実装やバグ修正の過剰文書化・gold plating）は、いずれも構造・量・文脈の判定**であって、特定の禁止トークンの部分一致では原理的に拾えない。とりわけ「クラス図」を禁止語にすると、Design Doc が C4／詳細設計へ**正当に委譲を語る文**（「L4 のクラス図レベルは詳細設計へ委譲する」等）で誤爆する。

> **vocab の有無は『その doc_type の逸脱が機械で綺麗に拾えるか』で決まる**——agile か WF かの別ではない。AC は拾えたから vocab を持ち、user-story と Design Doc は拾えないから vocab を空にする。これが agile の **rubric 主導**の正しい現れであり、機械で綺麗に拾える逸脱だけ機械に任せ、それ以外（L4 先取り・gold plating・自明文書化・代替の事後正当化・トレース紐付けの質）は [`../rubric/design-doc.md`](../rubric/design-doc.md) の質的判定へ委ねる。

> **予防的ガイド（将来 vocab を足す場合）**: 本 doc_type は forbidden が空なので現状は何も禁止していないが、仮に将来 vocab を持たせたくなっても、Design Doc 固有の頻出語「クラス図」「C4」「arc42」は禁止語にしてはならない——正当な設計記述・委譲記述（「L4 のクラス図レベルは詳細設計へ委譲する」等）と同一トークンになり部分一致が誤爆するためである（技術名・製品名・`SQL` も同様で、WF/srs・architecture-design の「技術名は機械 vocab で弾かず質的判定へ」と同方針・S4 非対称）。これらの逸脱は rubric の質的判定で見る。

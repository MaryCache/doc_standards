# Acceptance Criteria（受入基準）レシピ — アジャイル 受入基準（Acceptance Criteria）

> **レイヤー**: 第2層レシピ（手法別具体指針・**agile**・受入基準）
> **原則参照**: [`../principles/granularity-axis.md`](../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。
> **元の出典（2026-10-11 原文照合）**: Given/When/Then のシナリオ形式は Dan North「Introducing BDD」（https://dannorth.net/introducing-bdd/）。「Given some initial context (the givens), When an event occurs, Then ensure some outcomes.」
> **責務対照**: [`../principles/responsibility-map.md`](../principles/responsibility-map.md) の**アジャイル責務対照表の Acceptance Criteria 行**を参照（観測可能な振る舞い〔precondition / event / observable outcome〕・CI 実行可能な形式を含む／実装詳細〔index scan 等の内部挙動〕・内部状態遷移の記述を含まない）。

## 目的とスコープ（agile 第2層の 2 本目のスライス）

これは doc-standards で**2 本目の agile レシピ**である（1 本目＝[`./user-story.md`](./user-story.md)）。User Story が WHO/WHAT/WHY（価値）を定めるのに対し、Acceptance Criteria（受入基準・AC）は、そのストーリーが「完成した」と合意できる**観測可能な振る舞い**を Given-When-Then で定める。AC は User Story の各価値に紐付き、テスト仕様の**実行可能版**（CI で自動実行できる形式）として機能する。

> **「受入基準」という語のねじれに注意（user-story の `受入基準` 節 ↔ 本 doc_type）**: [`./user-story.md`](./user-story.md) は story と同居する**インラインの軽量 AC**を `受入基準` 節として持つ（vocab 空・件数の目安は 5 件＝story 分割サイン・living doc の萌芽）。本 doc_type `acceptance-criteria` は、その AC が**育って独立した実行可能仕様**（CI 実行可能・vocab あり・トレース有効・件数の目安は 20 件＝AC 仕様分割サイン）である。同じ「受入基準」でも**ライフサイクル上の段階が違う**（story 内の萌芽 ↔ 分離した living doc）。本レシピの機械必須見出しを `受入シナリオ` と名付けたのは、story 内節名 `受入基準` との混同を避けるためでもある。

agile の第2層は**成果物ライフサイクル軸**（living docs として育ち、必要になった時点で詳細を確定する JIT 詳細化）で整理する。WF の**工程フェーズ軸**とは軸が異なる——これが**非対称設計の原則（S4）**である。ただし**原則層（第1層）は手法非依存で共通**であり、What/Why と How の分離（P2）・検証可能性（P6）・トレーサビリティ（P4）は WF でも agile でも変わらない不変量である。本レシピもそれらを再定義せず参照するだけである（S3）。

**必須セクション**:
- **必須**: `受入シナリオ`・`トレーサビリティ`。
- `目的とスコープ`（位置づけ）は導入であり必須ではない。末尾の `越境 note`・`vocab の説明` も必須見出しではない。

**境界を越えた記述の扱い**:
- AC の Then に内部実装（「どう実現するか」＝索引走査・キャッシュ・内部状態遷移など）が混入していたら、それは方式設計・詳細設計・コードの領域である。Then から外し、観測可能な振る舞いへ書き換える。
- 技術選択（どの基盤・どのプロトコル・どのライブラリで実現するか）が AC に書かれていたら、方式設計（アーキ設計）へ移す。AC は「利用者から何が観測できるか」にとどめる。
- まだ確定していない詳細は無理に書き切らない。スプリント中の会話で必要になった時点で確定する（JIT・living doc）。

## 受入シナリオ

各受入シナリオを **Given-When-Then**（前提／きっかけの操作／観測できる結果）で書く。Given は確認開始前に成立している状態・データ、When は利用者またはシステムへの**単一**の働きかけ、Then はそこから**外から観測できる結果**（値・件数・状態・表示・メッセージ・エラー等）である。

**Then は観測可能な振る舞いのみで書く**（P6）。Then は「どの値・どの件数・どの状態・どのメッセージが観測されるか」で書く。測定できない表現は、合否が一意に決まらないため使わない（避けるべき定型句の厳密な文字列は末尾の vocab の説明にフェンスで列挙する）。

**Then に内部実装を書かない**（P2/P6）。索引走査・キャッシュ・内部状態遷移といった「どう実現しているか」は AC に書かない。実装機構は方式設計・詳細設計・コードの領域であり、AC が見るのは「利用者から何が観測できるか」だけである。

**シナリオが 20 件を超えたら AC 仕様の分割サイン**（責務対照表の Acceptance Criteria 行準拠）。1 つの AC 仕様（実行可能シナリオ群）が膨らみすぎたら、AC 仕様を分割する。これは User Story 側の「AC が 5 件超ならストーリーを割るサイン」（[`./user-story.md`](./user-story.md) の受入基準節）とは**別レベル**である——前者は AC 仕様の粒度（20 件超）、後者は story の粒度（5 件超）を指す。取り違えてはならない。

**含む**: Given（前提＝確認開始前に成立している状態・データ）・When（きっかけ＝単一の働きかけ）・Then（結果＝外から観測できる値・件数・状態・表示・メッセージ・エラー）・各シナリオが対応する user-story。

**含まない**: Then への実装機構の記述（内部の検索方式・キャッシュ・索引・内部状態遷移など「どう実現するか」）・技術選択・テスト体制やスケジュール・1 件として観測しきれない過大なシナリオ（分割する）。

> **観測可能で書く**（P6）。Then は観測できる結果で書き、第三者が同じ判定に到達できるようにする。合否が判定者の主観に依存する書き方（測定基準を持たない受入条件）は使わない。
>
> **実装機構を Then に書かない例**: 「Then: 索引を走査して該当件数を返す」は内部挙動の記述であり AC として不適切。「Then: 検索結果に該当する 3 件が一覧表示される」と、観測できる結果だけで書く。

### 例（最小限・テンプレート用）

User Story（[`./user-story.md`](./user-story.md) の US-01「受注をまとめて登録する」）に対する受入基準を、Given-When-Then で、Then を観測可能にして書く例を示す。

```
US-01（受注をまとめて登録する）の受入基準

  AC-1 全件登録できる
    Given 在庫が十分にある商品が複数選択されている
    When  利用者が「一括登録」を1回実行する
    Then  選択した全件が受注として作成され、作成件数が画面に表示される

  AC-2 在庫超過の1件は弾かれ部分成立する
    Given 選択した商品の中に在庫を超える数量のものが1件含まれている
    When  利用者が「一括登録」を1回実行する
    Then  在庫超過の1件は登録されず、どの行が登録できなかったかが業務エラーとして表示される。
          在庫内の他の件は登録が成立する（部分成立の振る舞いが観測できる）

  AC-3 対象0件では実行されない
    Given 選択された商品が0件である
    When  利用者が「一括登録」を実行しようとする
    Then  登録は実行されず、対象が選択されていない旨が表示される
```

> 上の3例はいずれも Given-When-Then で、Then が観測可能（件数表示・部分成立・メッセージ）に書かれている。これは [`./user-story.md`](./user-story.md) の AC 例と整合する。シナリオは3件で、分割サイン（20 件超）には遠い。

## トレーサビリティ

各受入シナリオを**対応する user-story** に紐付ける。孤立したシナリオ（対応 user-story を持たないシナリオ）を作らない（P4: 全要素トレース可能）。

**表の書き方（シナリオ → user-story）**:
- ID 列のヘッダに「**対応**」を含める（例: `対応 user-story`）。第1列は設計要素名（シナリオ ID）であり、機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) は第1列を主語として除外し、「対応」を含む列を ID 列とみなす。
- 全セルを埋める。対応 user-story 列が空・ダッシュ（`-`）のシナリオは孤立シナリオ（根拠のないシナリオ）であり、機械が検出する逸脱になる。
- 1 シナリオが複数の user-story を検証することは通常ない（AC は 1 価値に紐付く）。複数価値にまたがるなら、シナリオまたはストーリーの粒度を見直す。

| シナリオ ID | 対応 user-story | 備考 |
|---|---|---|
| AC-1 | US-01 | 全件登録の正常系 |
| AC-2 | US-01 | 在庫超過の部分成立 |
| AC-3 | US-01 | 対象0件の防御 |

**逸脱の判定基準**:
- 「対応 user-story」が空（またはダッシュ）のシナリオが存在する → 孤立シナリオ。対応 user-story を補うか、シナリオを削除する（**空セルそのものの検出は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当**）。
- 対応 user-story が形式上は埋まっているが、そのストーリーの価値とシナリオが検証する内容が食い違う → 紐付けの質の問題であり、[`../rubric/acceptance-criteria.md`](../rubric/acceptance-criteria.md) の質的判定で見る。

## 越境 note（粒度・帰属のズレ検出）

受入シナリオ／トレーサビリティに以下が現れたら、Acceptance Criteria の責務を越境している。該当する置き場へ移す。

- **Then に実装機構**（内部の検索方式・索引走査・キャッシュ・内部状態遷移など「どう実現するか」）が出たら → 観測可能な振る舞いへ書き換え、内部の仕組みは方式設計・詳細設計・コードの領域に残す。
- **技術選択**（どの基盤・プロトコル・ライブラリで実現するか）が AC に書かれていたら → 方式設計（アーキ設計）へ移す。AC は観測可能な振る舞いにとどめる。
- **シナリオが 20 件を超えた**ら → AC 仕様の分割サイン。1 つの AC 仕様（実行可能シナリオ群）が膨らみすぎている。AC 仕様を分割する（story を割る 5 件の話とは別レベル）。
- **まだ確定していない詳細**を無理に書き切ろうとしていたら → スプリント中の会話で必要になった時点で確定する（JIT・living doc）。書き切ろうとすること自体が WF 的な前倒しで、agile の趣旨に反する。

## vocab の説明（AC は agile だが vocab を持つ／構造・件数・トレース質は rubric 主導）

**本 doc_type（acceptance-criteria）は agile だが、機械語彙チェック（vocab）を持つ**。これは [`./user-story.md`](./user-story.md)（vocab が空）との違いであり、設計上の判断である。

理由は、AC の Then の**観測可能性は test-case-spec の期待結果と同じ P6 の要請**だからである。期待結果の曖昧な定型句——観測できる値・件数・状態を示さず合否が一意に決まらない言い回し——は、[`../waterfall/test/test-case-spec.md`](../waterfall/test/test-case-spec.md) の vocab で**部分一致の誤爆なく機械検出できると実証済み**である。AC の Then も同じ観測可能性を要請するため、test-case-spec の定型句 3 語をそのまま踏襲する。具体的な禁止語は、地の文で書くと本レシピ自身が自分の vocab に引っかかるため、次のフェンス内に隔離して列挙する（語彙チェッカーはフェンス内を検査対象外にする）。

```
Then に書いてはいけない曖昧表現マーカー（出たら観測できる値・件数・状態へ書き換える）:

  正しく表示    → 「画面に件数 N が表示される」等、観測できる表示内容・件数へ
  正しく動作    → 「ステータスが confirmed になる」「HTTP 200 が返る」等、観測できる結果へ
  適切に処理    → 「在庫が 10 → 7 に減る」「エラーコード E-STOCK が返る」等、観測できる状態変化へ
```

一方、**機械語彙で拾えない逸脱は [`../rubric/acceptance-criteria.md`](../rubric/acceptance-criteria.md) の質的判定（rubric 主導）に委ねる**。次のものは構造・文脈・件数の判定であり、特定の禁止トークンの部分一致では原理的に拾えない:

- **GWT 構造の質**（Given/When/Then が揃っているか・When が単一のきっかけか）＝構造判定。
- **Then への内部実装の混入**（索引走査・キャッシュ・内部状態遷移など「どう実現するか」）＝文脈判定。これは上の 3 定型句では拾えない内部実装の記述である。
- **観測可能性のうち 3 定型句以外の測定不能表現**（「使いやすい」「十分速い」「自然な」など別語に化けた曖昧さ）＝文脈判定。
- **シナリオ件数**（20 件超＝分割サイン）＝件数/構造判定。
- **トレーサビリティの質**（各シナリオが実在 user-story に正しく紐付くか・粒度）＝文脈判定。**空セルそのものの検出は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当**であり、rubric は紐付けの妥当性・粒度を見る。

これが agile の **rubric 主導**の現れである——「機械で綺麗に拾える逸脱だけ機械、それ以外は rubric」。技術名・製品名・`SQL`・GWT キーワード（Given/When/Then）は、正当な記述・キーワードと同一トークンになり部分一致が誤爆するため、機械 vocab では禁止しない（WF/srs の「技術名は機械 vocab で弾かず質的判定へ」と同方針・S4 非対称）。

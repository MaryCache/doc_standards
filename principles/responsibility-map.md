### 基本設計の細分（M3）について

基本設計を単一バケットに畳むと「方式設計が無い」「非機能がどこにも無い」という**欠落**を検出できない。そのため本表では基本設計を 5 サブ成果物（外部設計・方式/アーキ設計・データ設計・非機能設計・運用/移行設計）に細分する。詳細設計は基本設計の子ではなく独立した工程フェーズとして扱う。

> **M3 実装完成（cycle-10 時点）**: この5細分はすべて機械判定＋rubric 稼働の `doc_type` として整備済み——データ設計（cycle-2）・外部設計（cycle-7）・方式設計（cycle-8）・非機能設計（cycle-9）・運用/移行設計（cycle-10）。基本設計が「単一バケット」でなく「5成果物の集合」として回ることを5本で完結させ、**基本設計 M3 が完成に到達した**。各細分の整備済み注は下表の各行「逸脱の判定基準」列に記す。なお原則層（`granularity-axis.md`）の不変量はこの5細分を載せても一切変えていない（S3 維持）。

### V字対応関係

各設計成果物と対応するテストレベルの推奨マッピングを示す。

| 設計成果物 | 対応テストレベル | テストベース |
|---|---|---|
| 要件定義（SRS） | 受入テスト | 要件仕様書（業務要件・受入基準） |
| 基本設計（アーキ・外部 IF） | 結合テスト（システム結合） | アーキ設計・IF 仕様 |
| システム設計（全体） | システムテスト | 性能・セキュリティ・**使用性（usability）**・互換性 |
| 詳細設計 | 単体テスト（コンポーネントテスト） | 詳細設計仕様 |

> **訂正（裏取り済）**: システムテストが検証する非機能項目は「性能・セキュリティ・**使用性（usability）**・互換性」である。「可用性（availability）」への言い換えは誤りであるため採用しない。
>
> **留意**: ISTQB Foundation v4.0 はテストレベルを開発工程に固定した 1:1 の V 字定義を明示採用しておらず、「コンポーネント/コンポーネント結合・システム結合」へ改称・分割している。反復型（アジャイル等）では上記 1:1 対応が崩れる。本表の対応関係は**推奨設計であり、反復型では柔軟に解釈する**。

## 2. アジャイル責務対照表（成果物ライフサイクル別）

### 非対称設計の原則（S4）

WF の第2層は「工程フェーズ」軸、アジャイルの第2層は「成果物ライフサイクル（living docs）」軸で整理する。両者を同じ軸で対称配置すると、アジャイルの JIT 詳細化（いつ何を確定するか）が表現できない。

| 成果物 | 含む | 含まない | 隣接/WF 対応 | 逸脱の判定基準 |
|---|---|---|---|---|
| **User Story** | WHO/WHAT/WHY（価値）・INVEST 準拠（Independent/Negotiable/Valuable/Estimable/Small/Testable） | 実装タスク（configure/upgrade/migrate）・技術選択・受入条件への実装機構の記述 | ≒ SRS の価値対話版。詳細はスプリント中の会話で JIT 確定 | 主語が「System（システム主語ストーリー）」／so that 欠落／実装動詞（configure/upgrade/migrate）／AC が 5 件超（肥大・gold plating＝**ここで言う AC は story 内インライン受入基準＝story 粒度を割るサイン。独立 doc_type `acceptance-criteria` の「シナリオ20件超＝AC 仕様粒度を割るサイン」とは別レベル。取り違えない**）（**user-story スライス整備済み＝cycle-6・初の agile スライス**: レシピ `agile/user-story.md`・機械判定〔必須見出し `ユーザーストーリー`/`受入基準`・**vocab は空＝実装動詞は同一トークン/部分一致誤爆ゆえ rubric へ**〕・rubric〔**agile は rubric 主導**〕） |
| **Acceptance Criteria（Given-When-Then）** | 観測可能な振る舞い（precondition / event / observable outcome）・CI 実行可能な形式 | 実装詳細（index scan 等の内部挙動）・内部状態遷移の記述 | ≒ テスト仕様の実行可能版。CI で自動実行 | Then に内部実装の記述／シナリオが 20 件超（分割不足）（**acceptance-criteria スライス整備済み＝cycle-13・agile 2本目**: レシピ `agile/acceptance-criteria.md`・機械判定〔必須見出し `受入シナリオ`/`トレーサビリティ`・**agile で初めて check_traceability が有効になるスライス**＝シナリオ→対応 user-story の空セル〔孤立シナリオ〕を機械検出・vocab は test-case-spec の曖昧期待結果3語〔正しく表示/正しく動作/適切に処理〕を踏襲＝Then 観測可能性が test-case-spec 期待結果と同性質の P6〕・rubric〔**agile は rubric 主導**・5観点〕。**user-story は vocab 空だが AC は vocab を持つ非対称**＝機械で綺麗に拾える逸脱だけ機械。GWT 構造/Then 内部実装混入/件数/トレース紐付けの質は rubric） |
| **ADR（Architecture Decision Record）** | 1 判断につき 1 ADR・Context/Decision/Status/Consequences・却下案の明示（Nygard 5節〔Title は H1〕＋却下案） | trivial な決定（Prettier 等・可逆で影響小）・決定済みの再宣言 | ≒ SAD（Software Architecture Document）の意思決定層。**採番・生成は `architecture-decision-records` スキルに委譲** | 事後正当化（承認なし accepted）／trivial な決定の ADR 化／Why の記述なし（**adr スライス整備済み＝cycle-20・agile 4本目**: レシピ `agile/adr.md`・機械判定〔必須見出し Context/Decision/Status/却下案/Consequences＝**必須は絞る**・**却下案を独立必須にして「Why 片側欠落＝事後正当化の主因」を機械検出**・vocab 空〔逸脱は構造/文脈ゆえ design-doc 同型〕・トレースは Context 内＝check_traceability skipped〔user-story 同型〕・H1 に英語 Decision を書かずデコイ回避〕・rubric〔agile 主導〕。**委譲二重定義の S5 試金石＝doc-standards は ADR の粒度境界〔必須節の存在・却下案明示・trivial/事後正当化でない〕を定義／本スキル architecture-decision-records は採番・生成・内容評価〔却下案の技術的妥当性・決定の正否〕を所有**＝粒度 vs 内容 vs 採番生成の三分で重ならない。architecture-design/design-doc が ADR を**リンク委譲する側**であったのと**対**〔こちらは ADR の粒度を定義する側〕） |
| **RFC（Request for Comments）** | 決定前の探索・合意形成（チーム境界越え）・代替案比較 | 決定済み内容の一方的な宣言 | RFC 探索 → 採択 → ADR 記録、の時間軸で連鎖 | 既決事項を RFC 化／広い合意が必要な変更を ADR だけで一方的に記録（**rfc スライス整備済み＝cycle-21・agile 5本目**: レシピ `agile/rfc.md`・機械判定〔必須見出し 提案内容/代替案/未解決の論点/トレーサビリティ＝**必須は絞る**・**`未解決の論点` を独立必須にして「未決を装った既決＝RFC の体をなさない」を機械検出**〔ADR 却下案・design-doc Non-Goals と同型〕・vocab 空〔提案文書で期待結果・完了条件を書かず3語の主戦場が無い＝design-doc/adr/test-strategy 型・5例目〕・**独立トレース有効**〕・rubric〔agile 主導・5観点〕。**ADR と時間軸で対**＝RFC の代替案は**生きた選択肢**〔どれも採りうる〕／ADR の却下案は**葬った選択肢**〔採らないと決めた〕・RFC で生きていた代替のうち採らなかったものは決定の瞬間に ADR 却下案へ移る。トレースは ADR〔外部スキル所有形式と衝突回避で Context 内・skipped〕と**非対称**＝RFC は doc-standards 固有で衝突せず独立トレース節を持ち check_traceability 有効） |
| **Design Doc（Google Style / arc42 / C4）** | Context・Goals/Non-Goals・代替検討・横断懸念。arc42 は必要なセクションのみ記載。C4 は L1-L2 を優先 | 自明な実装・バグ修正の Design Doc 化／arc42 全 12 セクション埋め強制／C4 の L4 乱用／作る順番の割り付け・進み具合（完了・実装着手など。納品後に正しくなくなる→実装計画〔[§4](#4-工程をまたぐ受け皿-実装計画)〕／課題管理へ）。ただし設計の判断として分ける理由（移行の方針・依存）は含む | ≒ 基本設計の合意形成版。スプリントのインクリメントに合わせて living doc として更新 | 全セクション強制記入／L4（クラス図レベル）を最初から全描画（**design-doc スライス整備済み＝cycle-14・agile 3本目**: レシピ `agile/design-doc.md`・機械判定〔必須見出し `Context`/`Non-Goals`/`トレーサビリティ`＝**必須は絞る**〔全セクション強制が逸脱ゆえ・代替検討/横断懸念は推奨〕・`Non-Goals` を必須にしてスコープ否定側の欠落を機械検出・**vocab は当初空**〔Design Doc の逸脱は構造/量/文脈ゆえ・user-story と同型／AC とは非対称。**cycle-23 で進み具合の3語〔実装済み/実装中/実装着手〕だけ持たせた**＝実際の設計書で機械で拾えたため。**vocab の有無は逸脱が機械で綺麗に拾えるかで決まる・agile/WF の別でない**〕・ADR は `[ADR-NNNN]` リンク委譲 S5〕・rubric〔**agile は rubric 主導**・6観点〔cycle-23 でフェーズ分割の理由を追加〕・L4/gold plating の質的判定〕） |
| **PR-FAQ（Amazon）** | 顧客視点の未来 PR（1p）+ FAQ（5p）・未来に完成した製品の記者発表視点で記述 | スライド化／15p の機能リスト化 | ≒ 企画・要件の逆算版（Working Backwards）。要件定義の入口として使う | PR 部分が顧客視点でなく内部機能リストに変質している（**pr-faq スライス整備済み＝cycle-22・agile 6本目＝agile コア体系の締めくくり**: レシピ `agile/pr-faq.md`・機械判定〔必須見出し プレスリリース/想定問答/成功指標/トレーサビリティ＝**必須は絞る**・**`成功指標` を独立必須にして「測定可能な成功条件の欠落＝絵に描いた餅」を機械検出**〔最近縁は nonfunctional `測定方法`・test 系の `終了基準`/`網羅方針`/`前提・セットアップ` の **P6 系（測定可能/検証可能な条件の独立必須化）**・広くは ADR 却下案・design-doc Non-Goals・RFC 未解決の論点と同じ「核の欠落側を独立必須で機械検出」〕・`FAQ` は3文字で H1「PR-FAQ」に部分一致しデコイ化ゆえ required を複合語 `想定問答` に回避・vocab 空〔企画逆算で期待結果を書かず3語の主戦場が無い・6例目〕・**独立トレース有効**〕・rubric〔agile 主導・5観点〕。**トレース先は対応する顧客課題/事業目標**〔最上流ゆえ要求 ID 未確定・test-strategy が上位へ向けたのと同型〕＝顧客課題に紐付かない機能/主張＝Working Backwards 違反/プロダクトアウトの空セルを機械検出。PR の内部機能リスト化・楽観バイアス・スライド化・成功指標の曖昧表現〔「大幅に改善」等＝副詞ゆえ部分一致誤爆〕は rubric） |

## 3. 既存スキル委譲表

doc-standards の責任範囲は「**工程ドキュメントの粒度境界・工程間受け渡し**」に限定する。コード品質・設計判断記録・完成物レビューは下記スキルに委譲し、doc-standards との二重定義・責務重複を持ち込まない（[`granularity-axis.md`](./granularity-axis.md) の不変量に加え S2/S5 の設計判断による）。

> **制約 S2（限定スコープ・本節で定義）**: doc-standards の責任範囲は**ドキュメントの粒度境界と工程間の受け渡し**に限定する。コード品質・設計判断の記録・完成物レビューの所有は外部スキル（`coding-principles` / `architecture-decision-records` / `review-handoff`・`santa-method`）に委ね、本ライブラリはそれらを再定義しない。この限定スコープ宣言とそれを具体化した下表（委譲表）が S2 の実体であり、S2 の定義はここに一度だけ置く（定義の唯一性＝S3 と同じ運用）。S5（委譲先スキルとの境界の非二重定義）は S2 を ADR 採番・生成の所有という個別事例に適用したものである。

| 領域 | 所有スキル | doc-standard の関与 |
|---|---|---|
| コード品質（命名・コメント・構造・テスト） | `coding-principles` | 委譲（重複させない・粒度境界の観点で言及することはあるが、規約の source of truth は coding-principles） |
| 設計判断の記録（ADR の採番・生成） | `architecture-decision-records` | 参照・リンク・存在チェックのみ行う。採番・生成は行わない（S5） |
| 完成物の 2 観点レビュー | `review-handoff` / `santa-method` | 直交。doc-standard は「粒度境界」という単一観点の基準を提供するだけであり、レビュープロセス自体は担わない |
| 実装計画の作成（タスク分解・手順） | `writing-plans` など | 境界と最小レシピ（必須見出し3つ）だけ。計画スキルがあればそちらを優先 |
| 工程ドキュメントの粒度境界・工程間受け渡し | **doc-standard 本体** | 本表がその定義を担う |

## 4. 工程をまたぐ受け皿: 実装計画

設計書は納品物である。置いてよい記述の判定の問いは、**納品したあとも正しいままか**とする。作る順番（どの作業をいつ作るか）と進み具合（完了・着手中）は、納品したあとは正しくなくなる。そのため SRS や Design Doc には置かず、工程をまたぐ受け皿である実装計画（`implementation-plan`・手法に依存しないので `common/` に置く）が受ける。分け方の理由が設計の判断（移行の方針・依存）である場合は、設計書に残してよい。外すのは、どの要求を何番目に入れるかの割り付けと、進み具合である。

| 工程 | 含む | 含まない | 隣接へ渡す | 逸脱の判定基準 |
|---|---|---|---|---|
| **実装計画（共通）** | 作業の単位・作る順番・順番の理由（依存・リスク）・各作業が実現する設計要素 | 設計の決定（計画の中で初めて設計を決めない）・要件の再記述・進み具合の記録（計画は版を重ねてよいが、進み具合は課題管理へ） | 設計書 → 実装計画 → 実装 | 計画の中で設計を初めて決めている／順番に依存・リスクの理由がない／設計要素に戻れない作業（**implementation-plan スライス整備済み＝cycle-23**: レシピ `common/implementation-plan.md`・機械判定〔必須見出し 作業の順番/順番の理由/トレーサビリティ＝**3つ以内・範囲を広げない**・vocab は空・トレース表は ID 列ヘッダ「対応する設計」で孤立作業を検出〕・rubric〔2観点: 計画の中の設計の決定／順番の理由〕。実装計画の作成そのものは計画スキルに委譲し、本ライブラリは境界と最小の見出しだけを持つ） |

# 実装計画レシピ — 工程をまたぐ受け皿（implementation-plan）

> **レイヤー**: 第2層レシピ（手法に依存しない共通・実装計画）
> **原則参照**: [`../principles/granularity-axis.md`](../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義しない（制約 S3）。
> **責務対照**: [`../principles/responsibility-map.md`](../principles/responsibility-map.md) の「工程をまたぐ受け皿: 実装計画」を参照（含む＝作業の単位・作る順番・順番の理由〔依存・リスク〕・各作業が実現する設計要素／含まない＝設計の決定・要件の再記述・進み具合の記録／隣接＝設計書 → 実装計画 → 実装）。

---

## 位置づけ（なぜこの doc_type があるか）

設計書は納品物であり、**納品したあとも正しいままか**が置いてよい記述の判定の問いである。作る順番（どの作業を先にやるか）と進み具合（どこまで済んだか）は、納品したあとは正しくなくなる。そのため設計書（Design Doc・SRS など）には置かず、この文書が受ける。手法に依存しないので `waterfall/` にも `agile/` にも置かず `common/` に置く。

**計画スキルがあればそちらを優先する。** 実装計画の作成（タスク分解・手順の書き下ろし）は `writing-plans` などの計画スキルの領分であり（[委譲表](../principles/responsibility-map.md#3-既存スキル委譲表)・S2/S5）、本ライブラリは**境界と最小の見出し3つ**だけを持つ。計画スキルで書いた計画も、設計を初めて決めていないか・順番に理由があるか・設計書の要素へ戻れるかを、本レシピの観点で確かめられる。範囲は広げない。

- **必須節（3つ）**: `作業の順番`／`順番の理由`／`トレーサビリティ`。
- 体制・見積もり・スケジュールは必須にしない。必要なら足してよいが、本レシピは見ない。

---

## 作業の順番

**含む**: 作業の単位（1つずつ着手・確認できる大きさ）と、それを進める順番。各作業が何を作るか（実現する設計要素）が分かる書き方にする。

**含まない**: 設計の決定（計画の中で初めて設計を決めない。決める必要が出たら設計書へ戻す）・要件の再記述（設計書や SRS にある要件をここへ書き写さない）・進み具合の記録（完了・着手中などの状態）。

計画は版を重ねてよい。ただし**どこまで済んだかは課題管理へ**置く。計画に進み具合を書き込み始めると、納品後どころか次の版で正しくなくなる。

### 例（最小限・テンプレート用）

```
1. 注文テーブルの追加と移行
2. 一括登録のユースケース実装
3. 一括登録画面の追加
```

---

## 順番の理由

**含む**: なぜこの順番か。**依存**（先に出来ていないと次が作れない）と**リスク**（不確実なものを早く潰す、壊れると戻せないものを先に固める）で説明する。

**含まない**: 「やりやすいから」「なんとなく」だけの理由・設計の根拠そのもの（それは設計書に書く）。

理由が書けない順番は、順番に意味がないか、依存を見落としている。

### 例（最小限・テンプレート用）

```
1 → 2: 2 は注文テーブルの列を使うため、1 が先に必要（依存）。
2 → 3: 画面より先に在庫引当の整合を実機で確かめたい。ここが最も不確実で、後から変えると画面も作り直しになる（リスク）。
```

---

## トレーサビリティ

各作業が実現する設計書の要素へ紐付ける。設計のどの要素にも戻れない作業は、設計の裏付けがない作業（設計書に足りない記述か、不要な作業）である（P4）。

**表の書き方（作業 → 設計）**:
- ID 列のヘッダに「**対応**」を含める（`対応する設計`）。第1列は作業名であり、機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) は第1列を主語として除外し、「対応」を含む列を ID 列とみなす。
- 全セルを埋める。空欄やダッシュの作業は孤立作業として機械が検出する。

| 作業 | 対応する設計 | 備考 |
|---|---|---|
| 注文テーブルの追加と移行 | DD-01（注文テーブル） | 順番 1 |
| 一括登録のユースケース実装 | DD-02（一括登録ユースケース） | 順番 2 |
| 一括登録画面の追加 | DD-03（一括登録画面） | 順番 3 |

**逸脱の判定基準**:
- 「対応する設計」が空の作業が存在する → 孤立作業。対応を補うか、作業を削除する（空セルの検出は機械の担当）。
- 埋まっているが、その設計要素と作業の中身が合わない → 紐付けの質の問題であり、[`../rubric/implementation-plan.md`](../rubric/implementation-plan.md) で見る。

## 隣接との境界

| 隣接 | 渡すもの |
|---|---|
| 設計書（Design Doc・基本設計・詳細設計） → 本書 | 設計の要素（本書はそれを作る順番に並べる）。設計の決定は設計書に残る |
| 本書 → 実装 | 作業の単位と順番 |
| 本書 → 課題管理 | 進み具合（完了・着手中）。本書には書かない |

## vocab の説明（空）

本 doc_type の機械語彙チェックは空である（[`../scripts/vocab/implementation-plan.json`](../scripts/vocab/implementation-plan.json) の forbidden は `[]`）。計画の逸脱（計画の中で設計を初めて決める・順番に理由がない）は文脈の判定であり、特定の語の部分一致では拾えない。進み具合の語（`実装済み` など）は計画では書き方次第で正当に出る（版の履歴・前提の説明など）ため、禁止にしない。これらは [`../rubric/implementation-plan.md`](../rubric/implementation-plan.md) に委ねる。

## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**RFC（Request for Comments）**を対象とする。

agile は機械層が薄く **rubric が主判定**である（[`./user-story.md`](./user-story.md) / [`./design-doc.md`](./design-doc.md) / [`./adr.md`](./adr.md) と同じ非対称設計 S4）。RFC は design-doc / user-story / adr 同様 **vocab を空にした**——その逸脱（実装詳細の先取り・未決を装った既決・straw man 代替・提案/論点の質）は、いずれも**構造・文脈の判定**であって、特定の禁止トークンの部分一致では原理的に拾えない（RFC が将来の振る舞いを語る正当な未決表明「提案する仕組みが正しく動作するかは未解決の論点で検討する」で誤爆する）。これらが本ルーブリックの担当である。これは [`./acceptance-criteria.md`](./acceptance-criteria.md) が vocab を持つ（Then の曖昧期待結果3語が部分一致誤爆なく拾えた）のとは**非対称**である——vocab の有無は「その doc_type の逸脱が機械で綺麗に拾えるか」で決まり、agile/WF の別ではない。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`提案内容` / `代替案` / `未解決の論点` / `トレーサビリティ`）の欠落・**トレース表の空セル（対応要求列が空＝孤立提案）**の検出など、文字列・表構造で判定できる項目。とりわけ**`未解決の論点` 節の欠落（未決を装った既決の主因）の検出が機械層の主眼**（ADR の `却下案`・design-doc の `Non-Goals` と同型に、RFC 固有の核の否定側を独立必須化して機械検出する）。`代替案` 節の欠落も併せて検出するが、独立必須の主眼は `未解決の論点` 側にある（他3 doc_type との同型性の根拠はこちら）。**vocab は空（forbidden 無し）＝禁止語チェックは pass を返すだけで実質的な検出はしない。** |
| 質的（本ルーブリック・**主判定**） | LLM ＋人間 | 提案内容の質（具体性・実装可能性 vs 抽象すぎて議論できない）・代替案の質（straw man でないか・トレードオフが書けているか）・未解決の論点の質（本当に未決か・未決を装った既決／既決を装った未決でないか）・実装詳細の先取り混入（コード/詳細設計の先取り）・トレース紐付けの質——いずれも文脈・構造の判断が要る項目。**RFC はこの質的判定が主であり、機械層は薄い（必須見出し＋トレース空セルのみ）。** |

機械判定で済む項目（必須見出しの欠落、とりわけ `未解決の論点` / `代替案` 節の有無・**トレース表の空セルそのものの検出**）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。ここが見るのは「節はあるが提案が抽象すぎて議論できない」「代替が straw man」「論点はあるが実は既決（決まったことを未決のフリ）」「実装詳細を先取りしている」「対応要求が形式上は埋まっているが意味的に合っていない」類の、文字列照合・表構造では捕まえられない逸脱だけである。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「提案が議論できる具体性か抽象すぎるか」「代替が straw man か正直な比較か」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例で迷ったら逸脱と決めつけない。
- 「論点が本当に未決か・既決を未決に偽装しているか」「実装詳細の先取りか正当な方向提示か」の定量基準は無い（§4-D）。境界例は逸脱と断定せず pass に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P2/P4 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. 提案内容の質（具体性・実装可能性 vs 抽象すぎて議論できない）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（What/Why の記述・方向の提示）。

`提案内容` が、**コメントを募って議論できる程度に具体的**か。たたき台として方向が読み取れ、賛否を述べられるか。逆に、抽象的すぎて何に賛成/反対すればよいか分からない（「もっと良くする」程度の中身の無い提案）になっていないかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 提案内容がコメント/賛否を述べられる程度に具体的か。抽象的すぎて議論の対象にならない空虚な提案になっていないか | 提案が方向・たたき台として読み取れ、読み手が賛否やトレードオフを述べられる具体性を持つ | 抽象すぎて議論できない原文（中身の無い提案の該当行）を引く |

> 注（機械判定との分担）: 必須見出し `提案内容` の**有無それ自体**は機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが中身が議論できない抽象論**」ケースである。
>
> 注（境界は fail-open）: 「議論できる具体性か抽象すぎるか」を分ける一般ヒューリスティックは無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。

### 2. 代替案の質（straw man でないか・トレードオフが書かれているか）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠は必須・design rationale の記録）。

`代替案` が、**見せかけの弱い代替（straw man）**でなく、各案のトレードオフ（長所と短所）が書かれた正直な比較になっているか。採用本命を引き立てるために弱い代替をわざと並べていないか。代替が**まだ生きている選択肢**（採りうるもの）として書かれているか（「もう却下済み」のように書いていれば、それは観点3の未決を装った既決と重なる）。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 代替案が straw man（見せかけの弱い代替で本命を引き立てる事後正当化）でなく、各案のトレードオフ（長所と短所）が書かれた正直な比較になっているか。代替がまだ生きている選択肢として扱われているか | 各代替に正直なトレードオフ（採りうる長所も含む）が伴い、本命だけを良く書いていない。代替が「採りうる」前提で並ぶ | straw man に見える原文（弱い代替・短所だけ並べた代替・本命だけ良く書いた該当行）を引く |

> 注（内容の正否は評価しない・S5）: 代替が**技術的に妥当か**（どの案を採るべきか）は本ルーブリックの担当でない。それはレビュースキル（`review-handoff` / `santa-method`）および決定時の [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルの責務である。本観点は「straw man でないか・トレードオフが書かれているか」という**粒度・形式**だけを見る。
>
> 注（境界は fail-open）: 「straw man か正直な比較か」を分ける一般ヒューリスティックは無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。

### 3. 未解決の論点の質（本当に未決か・未決を装った既決／既決を装った未決でないか）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（What/Why の記述）。

`未解決の論点` が、**本当に未決の問い**を開いているか。RFC は決定前の文書であり、(a) 実は決まっていることを「論点」と偽装する（既決を装った未決＝形だけの論点）・(b) 逆に文書全体が実は決定済みで論点が形骸化している（未決を装った既決）——のいずれにもなっていないかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 未解決の論点が本当に未決の問いか。実は決まっていることを論点に偽装（既決を装った未決）していないか。逆に文書全体が実は決定済みで論点が形骸化（未決を装った既決＝決定の記録なら ADR の領分）していないか | 論点が実際に決着していない問いであり、コメントで決めたい対象が読み取れる。RFC が決定前の文書として成立している | 偽装の論点の原文（決まっているのに論点に見せた／形だけの論点の該当行）を引く。文書が実は既決である兆候（決定済みの断定）の原文を引く |

> 注（機械判定との分担）: 必須見出し `未解決の論点` の**有無それ自体**は機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）の担当であり、本観点に重複させない。論点節そのものが無い（未決を装った既決の最も明白な形）は機械が検出する。本観点が見るのは「**節はあるが中身が偽装の論点／形骸化**」ケースである。
>
> 注（境界は fail-open）: 「本当に未決か既決の偽装か」を分ける一般ヒューリスティックは無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。

### 4. 実装詳細の先取り混入（提案レベルを超えたコード/詳細設計）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（What/Why と How の分離・実装詳細は下流へ）。

RFC が**提案レベル**（方向への合意）にとどまり、コード・詳細設計レベルの作り込み（クラス構成・メソッドシグネチャ・ロック粒度の実装・SQL の具体）を**先取りしていない**か。RFC は決定前であり、実装詳細は決定後の詳細設計／コードの領域である。これは構造判定ゆえ機械でなく rubric が見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| RFC が提案レベル（方向）を超えてコード/詳細設計レベルの作り込み（クラス構成・シグネチャ・実装手順・具体 SQL 等）を先取りしていないか | 記述が方向・たたき台レベルにとどまり、実装詳細は決定後の詳細設計／コードへ委ねられている | 先取りされた実装詳細の原文（コード/詳細設計レベルの作り込みの該当行）を引く |

> 注（境界は fail-open）: 「提案レベルの正当な方向提示」と「実装詳細の先取り」を分ける一般ヒューリスティックは無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。
>
> 注（技術名の頻出は逸脱でない）: RFC は技術選定の探索で技術名・製品名が**正当に頻出**する（だから vocab で技術名を禁止しない）。技術名が出ること自体は先取りでない。先取りは「方向でなく実装の作り込みに踏み込んでいるか」で見る。

### 5. トレース紐付けの質（紐付けの妥当性・空セル検出は機械の担当）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能・孤立要素＝スコープクリープ検出点）。

各提案・論点が対応要求／user-story に**意味的に**紐付いているか（形式的な対応でなく）。その要求の価値と、提案が実現しようとする内容が一致しているか・粒度が見合っているかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各提案・論点の「対応要求／user-story」が形式的でなく意味的に妥当か（その価値と、提案が実現する内容が一致しているか）。粒度が見合っているか | 各提案・論点の対応要求が、その提案が何を実現するかを実際に説明している。紐付けが流用・コピペで実態とずれていない | 整合しない対応の原文（提案・論点と対応要求の行）を引き、何と何が食い違うかを示す |

> **注（過大主張の禁止・F5 の教訓）**: **対応要求列の空セルそのものの検出（孤立提案）は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当**であり、本観点に重複させない。本観点は ID が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた対応、形式上は埋まっているが意味的に無関係な対応）と、**紐付けの粒度**を見る。空セル検出を rubric の仕事として主張しない（cycle-12/F5 の教訓＝「rubric が機械の仕事を主張しない」）。RFC は独立トレース節を持つため、ADR（トレースが Context 内・空セル検出は発生しない）とは異なり、空セル検出が機械層で発生する点に注意する。
>
> 注（境界は fail-open）: 紐付けが妥当か流用かが紛らわしい境界例は逸脱と断定せず fail-open（pass）に倒す。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **「議論できる具体性 vs 抽象すぎ」「straw man vs 正直な比較」「本当に未決 vs 既決の偽装」「提案レベル vs 実装詳細の先取り」を分ける一般ヒューリスティックは存在しない。** いずれも文脈依存である。読み取れない境界例は逸脱と断定せず **fail-open（pass）**に倒して人間に委ねる。判断を盛らない。
- **「RFC を起こすべきか（trivial か非自明か）」の線引きそのものは裁定しない。** 「trivial な提案は RFC 化しない」「決定済みの記録は ADR の領分」という境界は責務対照表（RFC 行）が引いた合意事項であり、本ルーブリックはその確定境界を**前提として**判定する。境界の妥当性そのものは問わない。
- **RFC の内容評価・決定後の ADR 採番/生成は裁定対象でない（S5・二重定義回避）。** doc-standards は RFC の決定を下さず・ADR を生成・採番せず、**粒度境界のみ**を提供する。提案/代替/論点の内容の正否（どの案を採るべきか・提案が技術的に妥当か）は本ルーブリックの担当でない——それはレビュースキル（`review-handoff` / `santa-method`）および決定時の [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルが所有する。観点1〜4 は粒度・形式のみ、観点5 は紐付けの意味的妥当性のみを見る。RFC（決定前・本ルーブリックは粒度を定義）と ADR（決定後・別レシピ/別 rubric が粒度を定義）で時間軸を割って二重定義を避ける。
- **空セルの検出は機械の担当であり rubric は過大主張しない（F5）。** トレース表の空セル（孤立提案）は [`../scripts/check_traceability.py`](../scripts/check_traceability.py) が決定論で検出する。本ルーブリック（観点5）は埋まっているセルの**意味的妥当性と粒度**のみを見る（cycle-12/F5 の教訓）。RFC は独立トレース節を持つので空セル検出が機械層で発生する（ADR とは非対称）。

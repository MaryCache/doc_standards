## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**基本設計（非機能設計）**を対象とする。非機能設計の核心的な痛みは「具体グレード値はあるが**測定方法がない／測定不能**で verifiable を満たさない」ことと「禁止語に当たらない形で実現手段（アーキ実現詳細・性能の調整手順）が混入する」こと、そして「SRS の NFR を単純転記しただけで設計としての付加価値（測定方法・測定タイミング・合意済みターゲット）が無い」ことであり、その文字列照合では捕まえられない逸脱を見るのが主眼である。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`非機能要件` / `測定方法` / `トレーサビリティ`）の欠落・禁止語（`チューニング手順` / `計測スクリプト`）の出現・トレーサビリティ表の空セル〔孤立設計要素＝対応要件 ID 欠落〕（`check_traceability.py`）など、文字列で判定できる項目 |
| 質的（本ルーブリック） | LLM ＋人間 | 測定方法節はあるが中身が測定不能・禁止語に当たらない形の実現手段 leak・カテゴリ網羅と「該当なし＋理由」の妥当性・トレーサビリティの意味・SRS からの設計付加価値など、文脈判断が要る項目 |

機械判定で済む項目（必須見出しの欠落、禁止語の単純な出現、トレーサビリティ表の空セル＝孤立設計要素〔対応要件 ID 欠落・スコープクリープ候補・P4 違反〕＝[`../scripts/check_traceability.py`](../scripts/check_traceability.py) が決定論で検出）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。とりわけ「`測定方法` 節そのものの欠落」は機械の担当（見出し欠落＝verifiable 違反の機械検出）であり、本ルーブリックは「節はあるが中身が測定不能」を見る。

なお技術スタック名・製品名・プロトコル名（および **`SQL`**）と**定量化されていない曖昧表現**（「高速に」「安定して」「十分な」等）は、機械 vocab で弾かず本ルーブリックの文脈判断に委ねる（P2 訂正版・cycle-4 srs / cycle-7 external-design / cycle-8 architecture-design 踏襲）。技術名は測定対象環境・監視製品名として非機能設計でも正当に現れ、とりわけ `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり部分一致の語彙チェッカーが誤爆する（cycle-8 で実機検出）。曖昧表現も部分一致では正当な説明文・引用と区別できず誤爆する。よって**実際の実現手段（計測スクリプトのコード本体・チューニングパラメータの具体値）の侵入は機械でなく本ルーブリックの観点2が、曖昧表現による定量化不足は観点1が見る**（cycle-8 と同方針）。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「設計としての正当な測定方法・ターゲット」と「不当な実現手段の先取り」を分ける一般ヒューリスティックは存在しない。境界例で迷ったら逸脱と決めつけない。
- **技術スタック名・製品名・プロトコル名・`SQL` という語そのものは逸脱と決めつけない。** 測定対象環境・監視製品名として正当に現れることがある（P2 訂正版）。逸脱になるのはその先（実際の計測スクリプトのコード本体、チューニングパラメータの具体値）であり、測定対象の記述として必要か単なる実現手段の先取りかを読み取れないときは fail-open（pass）に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P1/P3 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. グレード値の定量化（verifiable）

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（検証可能性）・[P5](../principles/granularity-axis.md#p5-数値精度は工程マーカーである)（数値精度は工程マーカー）。

非機能設計の最重要観点。各 NFR が「高速に」「安定して」「十分な」等の**定量化されていない曖昧表現**でなく**具体グレード値**で書かれ、かつ「測定方法」節の記載がそのグレード値を実際に測れる形になっているかを見る。`測定方法` 節そのものの欠落は機械の担当であり、本観点は**節はあるが中身が測定不能**なケース（測定手段・条件・タイミングが曖昧でグレード値を判定できない）を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各 NFR が曖昧表現でなく具体グレード値で書かれ、対応する測定方法が実際に測れる形か（測定手段・測定条件・測定タイミングが揃い、そのグレード値を判定できるか） | すべての NFR が測定可能なグレード値を持ち、各グレード値に測れる測定方法（手段・条件・タイミング）が1対1で紐づいている。曖昧表現で書かれた品質目標が残っていない | 定量化されていない品質目標（例: 「レスポンスは高速に保つ」）や、グレード値はあるが測定手段・条件が曖昧で測れない測定方法の原文を該当節・該当行ごと引く |

### 2. アーキ実現方法／実装詳細の leak

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（非機能設計はターゲット値と測定方法までに限る・実現手段は下流へ）。

禁止語（`チューニング手順` / `計測スクリプト`）に当たらない形で「どう実現するか」が侵入していないかを見る。具体的には、**チューニングパラメータの具体値・計測スクリプトのコード本体・品質要求をアーキテクチャでどう実現するかのアルゴリズム**である。これらは外から見たターゲット・測定方針ではなく実現手段であり、詳細設計／運用設計の対象である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各節に、禁止語に当たらない形の実現手段（チューニングパラメータの具体値・計測スクリプトのコード本体・実現アルゴリズム）が侵入していないか | 非機能要件は定量グレード値に、測定方法は測定の方針（手段・条件・タイミング）に留まり、実現手段は詳細設計／運用設計へ委ねられている | 実現手段に当たる原文（例: 「接続プール上限を128に設定し…」のようなパラメータ具体値、計測を回すコード本体）を該当節・該当行ごと引く |

> 注（機械判定との分担）: 実現手段マーカーそのもの（`チューニング手順`・`計測スクリプト`）の単純な出現検出は機械判定（[`../scripts/`](../scripts/) の禁止語）の担当であり、本観点に重複させない。本観点が見るのは、禁止語に当たらない形（パラメータ具体値・コード本体・自然文のアルゴリズム）で侵入した実現手段である。
>
> 注（技術名・SQL は機械でなく本観点で見る理由）: `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出）。よって技術名・`SQL` は機械 vocab の禁止語に入れず本観点で見る。製品名としての `PostgreSQL` 等の出現（測定対象環境・監視製品名）は逸脱でなく、逸脱は実際の実現手段（計測スクリプトのコード本体・チューニングパラメータ具体値）である。境界例は fail-open（pass）。

### 3. カテゴリ網羅（IPA 6 カテゴリ）

参照原則: [P9](../principles/granularity-axis.md#p9-nfr-は要件段階で並行検討後回し禁止)（NFR は後回し禁止・網羅的に検討）・[P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)。

IPA 6 カテゴリ（可用性／性能・拡張性／運用・保守性／移行性／セキュリティ／システム環境）のうち**該当の薄いものが「該当なし＋理由」で埋まり、検討漏れと対象外が区別できるか**を見る。空節（カテゴリ見出しはあるが中身も理由も無い）は検討漏れの疑いがある。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| IPA 6 カテゴリが網羅され、該当の薄いカテゴリが「該当なし＋理由」で明示されているか（検討漏れ＝空節と対象外＝理由付き除外が区別できるか） | 6 カテゴリすべてに、定量グレード値か「該当なし＋理由」のいずれかが記載されている。理由なく空のカテゴリ（検討漏れの疑い）が無い | 中身も「該当なし＋理由」も無い空カテゴリ、または検討された形跡のないカテゴリの原文（節見出しと空の本文）を該当箇所ごと引く |

### 4. トレーサビリティの質（意味的妥当性）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）。

空セルの検出は機械判定（[`../scripts/check_traceability.py`](../scripts/check_traceability.py)＝孤立設計要素〔対応要件 ID 欠落〕の決定論検出）で済む。**本観点は埋まっているセルの妥当性**を見る — 各 NFR の対応 SRS NFR ID／要件 ID が形式上の対応ではなく、その NFR が表す品質目標と**意味的に**整合しているか（流用・コピペで実態とずれた ID でないか）。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各 NFR の対応 SRS NFR ID／要件 ID が形式的でなく意味的に妥当か（NFR が表す品質目標と、対応 ID が指す要件が一致しているか） | 対応 ID がその NFR の出どころを実際に説明している。性能 NFR にセキュリティ要件 ID が付くような意味的ミスマッチが無い | 整合しない対応の原文（NFR 名と対応 SRS NFR ID／要件 ID の行）を引き、何と何が食い違うかを示す |

> 注（機械判定との分担）: 「対応 SRS NFR ID／要件 ID」列が空の NFR の検出は機械判定の担当範囲（孤立 NFR＝スコープクリープ候補）。本観点は ID が**書かれているが内容が合っていない**ケースを見る。

### 5. 要件↔基本設計の NFR 粒度境界（cycle-4 srs との回収）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（工程ごとに付加すべき粒度がある）・[P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)。

**スタンスα（F4 決着・2026-06-05）**: 測定方法は工程で粒度分割する——**SRS（要件定義・cycle-4）が「測定方法の方向性/観点」を、基本設計の非機能設計が「測定方法の確定（測定手段・測定条件・測定タイミングの具体化）」を持つ**。本観点は、SRS の NFR（方向性/観点）を**単純転記しただけ（測定方法を確定させず＝設計の付加価値なし）**になっていないかを見る。要件↔基本設計の NFR 粒度境界の回収点である（responsibility-map 要件定義行＝方向性／非機能設計行＝確定）。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| SRS の NFR（測定方法の方向性/観点）からの単純転記でなく、基本設計として測定方法の確定（測定手段・条件・タイミングの具体化）・合意済みターゲットが設計として足されているか（SRS をコピペしただけになっていないか） | 各 NFR に、SRS の What＋測定方法の方向性に加えて、測定手段・測定条件・測定タイミングの確定ないし合意済みターゲットが設計として付加されている | SRS と同一の記述しか持たず付加価値の無い NFR（例: SRS の測定方向性そのままで測定手段・条件・タイミングの確定が無い箇所）の原文を該当節・該当行ごと引く |

## 境界注意（このルーブリックが裁定しないこと）

- **NFR 具体値の置き場（SRS か基本設計か）そのものは裁定しない。** NFR の具体グレード値を SRS（要件定義）に置くか基本設計（非機能設計）に置くかは規格・実務で割れる事項であり、[`../principles/responsibility-map.md`](../principles/responsibility-map.md)（要件定義行・非機能設計行）とプロジェクト方針が source of truth である。本ルーブリックはその確定境界を**前提として**、基本設計工程の文書に対し「設計としての付加価値（測定方法・測定タイミング・合意済みターゲット）があるか」（観点5）を見る（参照: [`../waterfall/requirements/srs.md`](../waterfall/requirements/srs.md) §非機能要件「具体値の置き場について」）。
- **NFR を実現するアーキテクチャ／実装の良し悪しは裁定しない。** どう実現するか（アーキ実現詳細・性能の調整手順・計測スクリプトのコード）は詳細設計／運用設計の対象であり、本ルーブリックは**それが非機能設計に混入していないか**（観点2）だけを見る。実現手段の設計品質は詳細設計のレビュー（`review-handoff` / `santa-method`）に委ねる。
- **「設計としての正当な測定方法・ターゲット vs 不当な実現手段の先取り」を分ける一般ヒューリスティックは存在しない。** どちらとも決めかねる境界例は、逸脱と断定せず fail-open（pass）に倒して人間に委ねる。判断を盛らない。
- **技術名・SQL・曖昧表現は機械で弾かず本ルーブリックで文脈判定する。** 非機能設計ではこれらが正当な記述になりうる（測定対象環境・監視製品名／説明文・引用）ため、機械 vocab で一律に弾くと誤爆する（P2 訂正版・cycle-4 srs / cycle-7 external-design / cycle-8 architecture-design と同方針）。本ルーブリックの観点1（曖昧表現による定量化不足）・観点2（実現手段＝計測スクリプトのコード本体・チューニングパラメータ具体値の踏み込み）で文脈判定し、読み取れない境界例は fail-open（pass）に倒す。

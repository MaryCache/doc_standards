## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**基本設計（論理）データ設計**を対象とする。物理（型/NULL/PK/FK/index）の厚みは詳細設計データ設計の対象であり、ここでは見ない（後述 note・観点2）。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出しの欠落（`check_headings.py`）・禁止語の出現（`check_vocabulary.py`）・トレーサビリティ表の空セル＝孤立設計要素〔対応要件 ID 欠落〕（`check_traceability.py`）など、文字列で判定できる項目 |
| 質的（本ルーブリック） | LLM ＋人間 | 抽象度の侵入・設計根拠・トレーサビリティの意味・可読性など、文脈判断が要る項目 |

機械判定で済む項目（必須見出し `論理ER` / `トレーサビリティ` の欠落、禁止語の出現、トレーサビリティ表の空セル＝対応要件 ID 欠落の孤立設計要素）は**本ルーブリックに重複させない**。とりわけ空セル＝孤立設計要素〔対応要件 ID 欠落・スコープクリープ候補・P4 違反〕の検出は [`../scripts/check_traceability.py`](../scripts/check_traceability.py) が決定論で担う（fail-open）。ここが見るのは「見出しはあるが中身の粒度がずれている」「セルは埋まっているが対応が意味的にずれている」類の、文字列照合では捕まえられない逸脱だけである。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「正当な設計制約」と「不当な設計先取り」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例で迷ったら逸脱と決めつけない。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P1/P3 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. 論理ER への物理先取り（leak 検出）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（What/Why と How の分離）・[P5](../principles/granularity-axis.md#p5-数値精度は工程マーカーである)（数値精度は工程マーカー）。

基本設計のデータ設計は**論理ERのみ**で、物理（型/index/NULL/物理名）は詳細設計レシピ [`../waterfall/detailed-design/data-design.md`](../waterfall/detailed-design/data-design.md) の対象である。スタンスA で最重要の leak 検出として、**論理ER に物理が先取りされていないか**を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 論理ER 節に物理制約（データ型・index 種別・NULL 可否・物理テーブル名/プレフィックス）が先取りされていないか | 論理ER は論理名・関連・正規化レベル・ビジネスルールに留まり、物理制約は詳細設計レシピへ委ねられている | 論理ER 節から、物理制約に当たる原文（例: `varchar(20)` `NOT NULL` `btree`）を該当行ごと引く |

> 注: 禁止語そのもの（`btree` など）の単純な出現検出は機械判定（[`../scripts/`](../scripts/)）の担当。本観点が見るのは、禁止語に当たらない形で侵入した物理制約（型の別表記、物理名のプレフィックスなど）である。

### 2. 物理の厚み（薄すぎ／厚すぎ）— 本ルーブリックの対象外

> 注: 物理ER・テーブル定義の厚み（薄すぎ＝実装不能／厚すぎ＝詳細先取り）は基本設計（論理）データ設計の対象外であり、本ルーブリックでは見ない。物理の厚みは**詳細設計データ設計の質的判定**で見る（レシピ本体 [`../waterfall/detailed-design/data-design.md`](../waterfall/detailed-design/data-design.md)・専用ルーブリックは将来整備）。

### 3. 設計根拠（Why・却下案・トレードオフ）の有無

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠は必須）。

ここでの Why は業務の Why ではなく、**設計判断の Why**である。基本設計（論理）では**論理レベルの根拠**（なぜこの正規化レベルか・非正規化したならその根拠）に焦点を当てる。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 正規化レベルの選定・理由のある非正規化など、論理レベルで判断の余地がある設計に根拠（業務要件・更新/参照特性・却下した代替）が添えられているか | 判断の余地がある論理設計に、選定根拠ないし却下案・トレードオフが明示されている | 根拠が必要なのに欠けている設計箇所の原文（例: 根拠記載のない非正規化エンティティ、選定理由のない正規化レベル宣言）を引く |

> 注: index 選定根拠（検索頻度・選択性・更新頻度）など**物理の設計根拠**は詳細設計データ設計の対象であり、本観点では見ない（レシピ本体 [`../waterfall/detailed-design/data-design.md`](../waterfall/detailed-design/data-design.md)）。

### 4. トレーサビリティの質（形式でなく意味を持つか）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）。

空セルの検出は機械判定（[`../scripts/check_traceability.py`](../scripts/check_traceability.py)＝孤立設計要素〔対応要件 ID 欠落〕の決定論検出）で済む。**本観点は埋まっているセルの妥当性**を見る — 対応要件 ID がそのエンティティ（論理名）と意味的に整合しているか。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各エンティティの対応要件 ID が形式的でなく意味的に妥当か（エンティティの役割と要件 ID の指す機能が一致しているか） | 対応要件 ID がそのエンティティの役割を実際に説明している。横断エンティティには対応する NFR ID が付く | 整合しない対応の原文（エンティティ名と対応要件 ID の行）を引き、何と何が食い違うかを示す |

> 注: 「対応要件 ID」列が空のエンティティの検出は機械判定（[`../scripts/check_traceability.py`](../scripts/check_traceability.py)）の担当範囲（孤立設計要素＝スコープクリープ候補・P4 違反）。本観点は ID が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた ID）を見る。

### 5. audience test（論理ER の可読性）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（抽象度の帰属）。

基本設計（論理）の読者は**非技術ステークホルダー**を含む。論理ER がその読者に読めるかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 非技術ステークホルダーが論理ER を理解できるか（できないなら抽象度が低すぎ＝物理が侵入している） | 論理ER がエンティティ・関連・業務ルールのレベルで、技術知識なしに読める | 非技術者が読めない原文（論理ER 節に紛れた物理表記）を引く（観点1と重なる場合は相互参照でよい） |

> 注: 「開発者が物理ER ＋テーブル定義だけで追加の設計判断なしに実装できるか」という実装可能性の観点は**詳細設計データ設計**の観点であり、本ルーブリックでは見ない（レシピ本体 [`../waterfall/detailed-design/data-design.md`](../waterfall/detailed-design/data-design.md)・専用ルーブリックは将来整備）。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **HLD/LLD（基本設計/詳細設計）の境界線そのものは裁定しない。** 「論理ER は基本設計・物理ER は詳細設計」という線引きは IEEE 1016 自身がスコープ外と明言する事項であり、**プロジェクト規約の合意事項**である。データ設計についてはこの境界が F1（スタンスA・2026-06-03）で**決着済み**（基本設計＝論理ER／物理＝詳細設計）であり、本ルーブリックはその確定境界を**前提として**判定する。境界の妥当性そのものは問わない（参照: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須) 注「アーキテクチャと詳細設計の境界はシステム依存でスコープ外」、決着記録: [CONTRIBUTING.md](../CONTRIBUTING.md) の F1）。
- **「正当な設計制約 vs 不当な設計先取り」を分ける一般ヒューリスティックは存在しない。** どちらとも決めかねる境界例は、逸脱と断定せず fail-open（pass）に倒して人間に委ねる。判断を盛らない。

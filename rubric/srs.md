# 要件定義（SRS）質的判定ルーブリック — ウォーターフォール要件定義

> **レイヤー**: 第2層レシピの質的判定（機械判定の補完）
> **原則参照**: [`../principles/granularity-axis.md`](../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義せず参照する（制約 S3）。
> **責務対照**: [`../principles/responsibility-map.md`](../principles/responsibility-map.md) の要件定義（SRS）行を参照（業務目的・スコープ・機能要件・NFR・トレーサビリティ）。
> **レシピ本体**: [`../waterfall/requirements/srs.md`](../waterfall/requirements/srs.md)。観点はこのレシピの節（機能要件 / 非機能要件 / トレーサビリティ・推奨のステークホルダー / ユースケース）に揃える。要件定義（SRS）は「何を（What）・なぜ（Why）」を確定する工程であり、「どう作るか（How）＝設計構造」は後続工程（基本設計・詳細設計）に委ねる。

## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**要件定義（SRS）**を対象とする。当初の痛み「要件で詰めすぎ／設計の先取り（痛み#1＝過剰仕様）」の、文字列照合では捕まえられない侵入を見るのが主眼である。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`機能要件` / `非機能要件` / `トレーサビリティ`）の欠落・禁止語（設計構造マーカー4語・進み具合3語）の出現など、文字列で判定できる項目 |
| 質的（本ルーブリック） | LLM ＋人間 | 言い換え・粒度で侵入した How／過剰詳細・検証可能性・NFR 中身の具体性・トレーサビリティの意味など、文脈判断が要る項目 |

機械判定で済む項目（必須見出しの欠落、設計構造マーカーの単純な出現）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。ここが見るのは「見出しはあるが中身の粒度がずれている」「禁止語に当たらない形で設計解が侵入している」類の、文字列照合では捕まえられない逸脱だけである。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「正当な制約（根拠付き）」と「不当な設計先取り（解空間を狭める How の侵入）」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例で迷ったら逸脱と決めつけない。
- **技術スタック名・製品名・プロトコル名そのものは逸脱と決めつけない。** 正当な制約（P2 訂正版）として根拠付きで現れることがあり、その場合は逸脱でない。根拠の有無・解の先取りか否かを読み取れないときは fail-open（pass）に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P1/P3/P10 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. 過剰仕様（詰めすぎ・設計の先取り＝痛み#1）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（要件は What/Why、How は原則排除・正当な制約は根拠付きで例外）・[P3](../principles/granularity-axis.md#p3-要件三層strssyrssrs検出補助)（要件三層・解を先取りすると解空間が狭まる）。検出補助: [P1](../principles/granularity-axis.md#p1-主語ヒューリスティック検出補助)（主語）・[P10](../principles/granularity-axis.md#p10-ireb-要件粒度フレーム検出補助)（IREB 粒度）。

当初の痛み#1。要件が設計解／How を先取りして、本来後続工程に委ねるべき解空間を不当に狭めていないかを見る。粒度が User Goal（開発フェーズの基準粒度）を超えて Sub-function／実装の手順に降りていないかを点検する。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 機能要件が What/Why に留まり、設計解／How（処理手順の分岐ロジック・内部構造への割り当て・解法の指定）を先取りして解空間を不当に狭めていないか。粒度が User Goal を超えて Sub-function／実装手順に降りていないか | 各機能要件が業務語彙の What（観測可能な振る舞い）と Why（業務目的）で書かれ、解の選定は後続工程に開かれている。粒度が User Goal レベル（スコープを曖昧なく定義できる粒度）に収まっている | 解を先取りして解空間を狭めている原文（例: 処理手順の if-then 分岐、内部構成要素への機能割り当て、特定解法の指定）を該当節・該当行ごと引く。粒度が Sub-function／実装に降りている原文を引く |

> 注（機械判定との分担）: 設計構造マーカー4語（`クラス図`・`テーブル定義`・`モジュール分割`・`インデックス`）と進み具合3語（`実装済み`・`実装中`・`実装着手`）の**単純な出現**は機械判定（[`../scripts/`](../scripts/) の禁止語）の担当であり、本観点に重複させない。本観点が見るのは、禁止語に当たらない形で**言い換え・粒度で侵入した How／過剰詳細**である。
>
> 注（主語ヒューリスティック・検出補助）: 主語が「利用者／業務」なら要件、「システム／コンポーネント」「部品／メソッド／物理データ」なら設計（P1）。要件節で主語が「システム／モジュール」へ落ちていたら粒度ズレを疑う手がかりになる。ただし P1 は検出補助であり、これ単独で fail に倒さない（fail-open）。
>
> 注（正当な制約は逸脱でない・重要）: 上位要求や外部条件に由来する**正当な制約**（セキュリティ・セーフティ要件、契約上指定されたプロトコル／ベンダー、上位から課された規格適合）は、**その根拠が明示されていれば逸脱ではない**（P2 訂正版）。技術手段の名称が現れても、それが「根拠ある制約」なら過剰仕様ではない。「根拠ある制約か／単なる解の先取りか」を読み取れない境界例は fail-open（pass）に倒す。

### 2. 検証可能性（verifiable か）

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（検証可能性は工程を貫く不変量）。

各要件が verifiable（検証可能）か。曖昧表現（「正しく動く」「使いやすい」「高速」など測定・確認の基準を持たない語）は検証不能であり弾く。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各機能要件が verifiable か。「正しく動く」「適切に処理する」「使いやすい」のような確認基準を持たない曖昧表現で逃げていないか | 各要件に、満たされたか否かを第三者が客観的に確認できる観測可能な振る舞い（受入の方向性）が示されている | 確認基準を持たない曖昧表現の原文（例: 「正しく動作する」「使いやすい画面」「適切にエラーを返す」）を該当節・該当行ごと引く |

> 注（NFR との切り分け）: 非機能要件側の曖昧表現（「速い」「安定」など測定値・測定方法の欠落）は観点3で扱う。本観点は主に機能要件の verifiable 性を見る。

### 3. NFR の具体性（グレード値＋測定方法の方向性があるか）

参照原則: [P9](../principles/granularity-axis.md#p9-nfr-は要件段階で並行検討後回し禁止)（NFR は要件段階で並行検討・後回し禁止）・[P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（検証可能）。

非機能要件に**グレード値（具体的な目標値）＋測定方法の方向性/観点**が揃っているか。概算値のみで測定方法の方向性が欠落していたら不足である。要件段階では概算粒度でよい（P5: 厳密値の確定は後続工程）が、「並行検討・後回し禁止」を満たすには検証可能な具体性（少なくとも測定の方向性/観点）が要る。**スタンスα（F4 決着・2026-06-05）**: SRS が持つのは「測定方法の方向性/観点」までであり、**測定方法の確定（測定手段・測定条件・測定タイミングの具体化）が SRS に書かれていたら基本設計（非機能設計）の先取り**として観点1（過剰仕様）側で見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各非機能要件にグレード値（測定可能な目標値）と測定方法の方向性/観点（どういう条件・観点で検証するか）の両方が示されているか。曖昧語（「速い」「安定」「十分な」）や、値はあるが測定の方向性すら無いもので逃げていないか | 各 NFR に測定可能なグレード値（概算粒度でよい）と測定方法の方向性/観点がセットで記されている。測定方法の確定（手段・条件・タイミングの具体化）まで踏み込んでいなくてよい（確定は基本設計の責務） | グレード値が無い／測定方法の方向性が欠落している NFR の原文（要求名＋該当行）を引く。曖昧語のみで具体値がない原文を引く |

> 注（機械判定との分担）: NFR 節（必須見出し `非機能要件`）の**有無それ自体**は機械判定（[`../scripts/`](../scripts/) の必須見出し欠落チェック）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが中身が verifiable でない**」（グレード値・測定方法の方向性の欠落）ケースである。
>
> 注（実現方法は対象外）: その NFR をアーキテクチャでどう実現するか・計測スクリプト・チューニング手順は基本設計／詳細設計の対象であり、要件には書かない。これらが NFR 節に混入していたら観点1（過剰仕様）側で見る。
>
> 注（測定方法の確定は基本設計の先取り・スタンスα）: 測定方法の**確定**（具体的な測定手段・測定条件・測定タイミングの具体化＝基本設計＝非機能設計の責務）が SRS の NFR に書き込まれていたら、それは要件での詰めすぎ＝設計の先取りであり観点1（過剰仕様）側で見る。本観点で見るのは「方向性/観点すら欠落して verifiable を満たさない」不足側であり、「方向性を超えて確定まで書いた」過剰側は観点1 が担う。境界例（方向性か確定かの判断が付かない）は fail-open（pass）に倒す。

### 4. トレーサビリティの質（形式でなく意味を持つか）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能・要件自身も上位要求へトレース可能であるべき）。

「上位要求 ID」列が空の検出は機械判定で済む。**本観点は埋まっているセルの妥当性**を見る — 各要件 ID が形式上の対応ではなく、上位（業務要求／StRS）の業務目的に**意味的に**紐付いているか。孤立要件・根拠なき要件（実態として上位に由来しない要件）を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各要件の「上位要求 ID」が形式的でなく意味的に妥当か（上位要求の指す業務目的と、その要件が実現する内容が一致しているか）。上位要求に由来しない孤立要件・根拠なき要件が紛れていないか | 各要件の上位要求 ID が、その要件の存在理由を実際に説明している。横断的な要件（監査・ログ等）には由来する方針 ID が付く | 整合しない対応の原文（要件 ID と上位要求 ID の行）を引き、何と何が食い違うかを示す。上位要求に由来しない実質孤立な要件の原文を引く |

> 注（機械判定との分担）: 「上位要求 ID」列が空の要件の検出は機械判定の担当範囲（孤立要件＝スコープクリープ候補）。本観点は ID が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた上位要求 ID、形式上は埋まっているが意味的に無関係な対応）を見る。

### 5. 優先度と作る順番の取り違え（優先度は残す・作る順番は外す）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（要件は What/Why・How は原則排除）。

SRS は納品物であり、置いてよい記述の判定の問いは**納品したあとも正しいままか**である。**優先度**（MoSCoW・高中低など）は要件の属性で、納品後も正しいので残す。**作る順番**（「段階1」「フェーズ2」「第2リリース」のようにどの機能をどの順で作るかの割り付け）と進み具合は納品後に正しくなくなるので外し、実装計画（[`../common/implementation-plan.md`](../common/implementation-plan.md)）や課題管理へ置く。両者は混同しやすく、優先度の列が実際には作る順番を表している（例: 「優先度」の値が `段階1`）ことがある。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 機能要件の「優先度」が要件の重要度・必須度（MoSCoW 等）を表しているか。「段階」「フェーズ」「リリース」への割り付けや進み具合を、優先度の名で書いていないか | 優先度は重要度や必須度の表明に留まる。作る順番の割り付けと進み具合が要件定義書に無い | 作る順番を表す原文（機能要件の該当行や、優先度列の値）を引く |

> 注（機械判定との分担）: 進み具合の記録を表す3語は機械の [`../scripts/check_vocabulary.py`](../scripts/check_vocabulary.py) が拾う。本観点は、語に当たらない形（「段階1」「第2リリース」など）と、優先度との取り違えを見る。
>
> 注（境界は fail-open）: 「段階」が作る順番か、業務上の段階（承認の段階など）かが読み取れない境界例は、逸脱と断定せず pass に倒す。リリースの区切りが契約上の要件（納期・段階納品の合意）に由来すると読める場合も、逸脱としない。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **要件と設計の境界線（Fuzzy Line）そのものは裁定しない。** 「どこまでが要件で、どこからが設計か」の線引きは規格上スコープ外（IEEE 1016 自身がアーキテクチャと詳細設計の境界をスコープ外と明記）であり、**プロジェクト規約の合意事項**である。本ルーブリックはレシピ本体が引いた境界を**前提として**判定する（参照: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須) 注「アーキテクチャと詳細設計の境界はシステム依存でスコープ外」）。
- **「正当な制約（根拠付き）vs 不当な設計先取り（解空間を狭める How）」を分ける一般ヒューリスティックは存在しない。** 技術スタック名・製品名・プロトコル名の出現も、それ単独では逸脱と決めつけない（P2 訂正版）。どちらとも決めかねる境界例は、逸脱と断定せず fail-open（pass）に倒して人間に委ねる。判断を盛らない。

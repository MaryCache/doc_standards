## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**PR-FAQ（Amazon Working Backwards）**を対象とする。

agile は機械層が薄く **rubric が主判定**である（[`./user-story.md`](./user-story.md) / [`./design-doc.md`](./design-doc.md) / [`./adr.md`](./adr.md) / [`./rfc.md`](./rfc.md) と同じ非対称設計 S4）。PR-FAQ は design-doc / user-story / adr / rfc 同様 **vocab を空にした**——その逸脱（PR の内部機能リスト化・楽観バイアス・成功指標の曖昧表現・スコープ肥大）は、いずれも**構造・量・文脈の判定**であって、特定の禁止トークンの部分一致では原理的に拾えない（成功指標の曖昧表現「大幅に改善」「高い満足度」は副詞・形容詞で、正当な記述と切り分けられず誤爆する）。これらが本ルーブリックの担当である。これは [`./acceptance-criteria.md`](./acceptance-criteria.md) が vocab を持つ（Then の曖昧期待結果3語が部分一致誤爆なく拾えた）のとは**非対称**である——vocab の有無は「その doc_type の逸脱が機械で綺麗に拾えるか」で決まり、agile/WF の別ではない。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`プレスリリース` / `想定問答` / `成功指標` / `トレーサビリティ`）の欠落・**トレース表の空セル（対応する顧客課題列が空＝顧客課題に紐付かない機能/主張）**の検出など、文字列・表構造で判定できる項目。とりわけ**`成功指標` 節の欠落（測定可能な成功条件の欠落＝絵に描いた餅の主因）の検出が機械層の主眼**（ADR の `却下案`・design-doc の `Non-Goals`・RFC の `未解決の論点` と同型に、PR-FAQ 固有の核の欠落側を独立必須化して機械検出する）。`プレスリリース` / `想定問答` 節の欠落も併せて検出するが、独立必須の主眼は `成功指標` 側にある（他 doc_type との同型性の根拠はこちら）。**vocab は空（forbidden 無し）＝禁止語チェックは pass を返すだけで実質的な検出はしない。** |
| 質的（本ルーブリック・**主判定**） | LLM ＋人間 | プレスリリースの顧客視点（顧客便益で書かれているか vs 内部機能リスト化）・FAQ の質（楽観バイアスでなく難所/コスト/リスクに正直か）・成功指標の測定可能性（曖昧表現でなく測定可能か）・スコープ肥大（機能リスト化/スライド化）・トレース紐付けの質——いずれも文脈・構造・量の判断が要る項目。**PR-FAQ はこの質的判定が主であり、機械層は薄い（必須見出し＋トレース空セルのみ）。** |

機械判定で済む項目（必須見出しの欠落、とりわけ `成功指標` / `プレスリリース` / `想定問答` 節の有無・**トレース表の空セルそのものの検出**）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。ここが見るのは「節はあるが PR が内部機能の羅列」「FAQ が楽観バイアスで難所を隠す」「成功指標はあるが『大幅に改善』等の曖昧表現で測定不能」「PR-FAQ が 15p の機能リストに肥大」「対応する顧客課題が形式上は埋まっているが意味的に合っていない」類の、文字列照合・表構造では捕まえられない逸脱だけである。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「PR が顧客便益で書かれているか内部機能リスト化か」「FAQ が楽観バイアスか正直か」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例で迷ったら逸脱と決めつけない。
- 「成功指標が測定可能か曖昧か」「スコープが肥大しているか適量か」の定量基準は無い（§4-D）。境界例は逸脱と断定せず pass に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P2/P4 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. プレスリリースの顧客視点（顧客便益 vs 内部機能リスト化）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（What/Why の記述・顧客便益の提示）。

`プレスリリース` が、**顧客にとって何が良くなるか（顧客便益）**で書かれているか。内部機能の羅列（PR の内部機能リスト化）になっていないか。これは PR-FAQ 最大の逸脱であり、Working Backwards（顧客便益から逆算）の体をなすかどうかの中核である（責務対照表「逸脱」line 67 相当）。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| プレスリリースが顧客便益（顧客にとって何が良くなるか）で書かれているか。内部機能の羅列（プロダクトアウト＝Working Backwards 違反）になっていないか | 顧客視点の便益・体験で書かれ、顧客が得る価値が読み取れる。機能の羅列に堕していない | 内部機能リスト化の原文（顧客便益でなく機能を並べた該当行）を引く |

> 注（機械判定との分担）: 必須見出し `プレスリリース` の**有無それ自体**は機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが中身が内部機能の羅列**」ケースである。
>
> 注（境界は fail-open）: 「顧客便益か内部機能リスト化か」を分ける一般ヒューリスティックは無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。

### 2. FAQ の質（楽観バイアスでないか・難所/コスト/リスクに正直か）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠は必須・両側の記録）。

`想定問答`（External FAQ）と推奨節 `社内向けの補足`（Internal FAQ）が、**楽観バイアス**（都合の悪い難所・コスト・リスクを隠す）でなく、不利な点にも正直に答えているか。とりわけ Internal FAQ で難所・コスト・リスクに正直か。便益だけを並べた都合のよい問答になっていないか。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| FAQ が楽観バイアス（難所・コスト・リスクを隠し便益だけ並べる）でなく、不利な点にも正直に答えているか。社内向けの補足（Internal FAQ）で難所・コスト・リスクに正直か | External/Internal を通じて、顧客が抱く不安や社内の難所・コスト・リスクに率直に答えている。便益だけの都合のよい問答になっていない | 楽観バイアスの原文（難所を隠した問答・リスクを軽視した該当行）を引く |

> 注（内容の正否は評価しない・S5）: FAQ の答えが**事業的に妥当か**（企画を採るべきか）は本ルーブリックの担当でない。それはレビュースキル（`review-handoff` / `santa-method`）の責務である。本観点は「楽観バイアスでないか・難所/コスト/リスクに正直か」という**粒度・形式**だけを見る。
>
> 注（境界は fail-open）: 「楽観バイアスか正直な問答か」を分ける一般ヒューリスティックは無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。

### 3. 成功指標の測定可能性（測定可能な数値 vs 曖昧表現）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（What/Why の記述・到達点の定量化）。

`成功指標` が、**測定可能な数値**で書かれているか。「大幅に改善」「高い満足度」のような測定不能な曖昧表現（形容詞・副詞）になっていないか。Working Backwards の到達点（プレスリリースで約束した便益）が、どうなれば実現したと言えるかが数値で判定できるか。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 成功指標が測定可能な数値（数値・期限つき）で書かれているか。「大幅に改善」「高い満足度」等の測定不能な曖昧表現になっていないか | 各指標が測定可能で、達成したか誰でも判定できる。曖昧な形容詞・副詞で逃げていない | 曖昧表現の原文（「大幅に改善」「高い満足度」等の該当行）を引く |

> **注（節の有無は機械・中身の測定可能性は rubric・P6）**: 成功指標**節の有無それ自体**は機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが中身が曖昧表現で測定不能**」ケースである。成功指標の曖昧表現（「大幅に」「高い」）は副詞・形容詞で、WF nonfunctional の「高速に」等と同じく**部分一致では正当な記述と切り分けられず誤爆**するため vocab で禁止せず本観点（rubric）が見る（P6＝節の有無は機械、中身の測定可能性が rubric）。
>
> 注（境界は fail-open）: 「測定可能な数値か曖昧表現か」を分ける一般ヒューリスティックは無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。

### 4. スコープ肥大（機能リスト化・スライド化＝量の逸脱）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（過剰文書化の回避・適切な粒度）。

PR-FAQ が **PR 1p＋FAQ 5p 程度の量**に収まっているか。15p の機能リスト化・スライド化（網羅的な機能の羅列へ肥大）していないか。書き切ろうとして機能を網羅し始めた PR-FAQ は、Working Backwards でなく機能リストへ堕している（量の逸脱・構造判定）。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| PR-FAQ が適量（PR 1p＋FAQ 5p 程度）に収まり、15p の機能リスト化・スライド化（網羅的な機能羅列への肥大）になっていないか | 顧客便益と核心的な問答に絞られ、網羅的な機能リストへ肥大していない | 肥大の原文（網羅的な機能羅列・スライド化した該当箇所）を引き、量の逸脱を示す |

> 注（境界は fail-open）: 「適量か肥大か」を分ける一般ヒューリスティックは無い（§4-D）。ページ数は目安であり厳密な閾値ではない。決めかねる境界例は逸脱と断定せず pass に倒す。

### 5. トレース紐付けの質（紐付けの妥当性・空セル検出は機械の担当）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能・孤立要素＝Working Backwards 違反の検出点）。

各主張・成功指標が、対応する**顧客課題／事業目標**に**意味的に**紐付いているか（形式的な対応でなく）。その顧客課題と、主張が実現しようとする内容が一致しているか・粒度が見合っているかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各主張・指標の「対応する顧客課題／事業目標」が形式的でなく意味的に妥当か（その顧客課題と、主張が実現する内容が一致しているか）。粒度が見合っているか | 各主張・指標の対応する顧客課題が、その主張が何を解決するかを実際に説明している。紐付けが流用・コピペで実態とずれていない | 整合しない対応の原文（主張・指標と対応する顧客課題の行）を引き、何と何が食い違うかを示す |

> **注（過大主張の禁止・F5 の教訓）**: **対応する顧客課題列の空セルそのものの検出（顧客課題に紐付かない機能/主張＝Working Backwards 違反）は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当**であり、本観点に重複させない。本観点は ID が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた対応、形式上は埋まっているが意味的に無関係な対応）と、**紐付けの粒度**を見る。空セル検出を rubric の仕事として主張しない（cycle-12/F5 の教訓＝「rubric が機械の仕事を主張しない」）。PR-FAQ は独立トレース節を持つため、ADR（トレースが Context 内・空セル検出は発生しない）とは異なり、空セル検出が機械層で発生する点に注意する。
>
> 注（境界は fail-open）: 紐付けが妥当か流用かが紛らわしい境界例は逸脱と断定せず fail-open（pass）に倒す。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **「顧客便益 vs 内部機能リスト化」「楽観バイアス vs 正直な問答」「測定可能な数値 vs 曖昧表現」「適量 vs スコープ肥大」を分ける一般ヒューリスティックは存在しない。** いずれも文脈依存である。読み取れない境界例は逸脱と断定せず **fail-open（pass）**に倒して人間に委ねる。判断を盛らない。
- **「PR-FAQ を起こすべきか（企画が PR-FAQ に値するか）」の線引きそのものは裁定しない。** 「内部機能リストの羅列・スライド化は含まない」「決まった設計判断は ADR の領分・観測可能な合否は acceptance-criteria の領分」という境界は責務対照表（PR-FAQ 行）が引いた合意事項であり、本ルーブリックはその確定境界を**前提として**判定する。境界の妥当性そのものは問わない。
- **PR-FAQ の内容評価・確定後の ADR 採番/生成は裁定対象でない（S5・二重定義回避）。** doc-standards は企画の是非を下さず・ADR を生成・採番せず、**粒度境界のみ**を提供する。主張/指標の内容の正否（企画が事業的に妥当か・指標が適切か）は本ルーブリックの担当でない——それはレビュースキル（`review-handoff` / `santa-method`）および確定時の [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルが所有する。観点1〜4 は粒度・形式・量のみ、観点5 は紐付けの意味的妥当性のみを見る。PR-FAQ（最上流・本ルーブリックは粒度を定義）と ADR（決定後）/ acceptance-criteria（合否の細目）で抽象度を割って二重定義を避ける。
- **空セルの検出は機械の担当であり rubric は過大主張しない（F5）。** トレース表の空セル（顧客課題に紐付かない機能/主張）は [`../scripts/check_traceability.py`](../scripts/check_traceability.py) が決定論で検出する。本ルーブリック（観点5）は埋まっているセルの**意味的妥当性と粒度**のみを見る（cycle-12/F5 の教訓）。PR-FAQ は独立トレース節を持つので空セル検出が機械層で発生する（ADR とは非対称）。

> **原則参照**: [`../principles/granularity-axis.md`](../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義せず参照する（制約 S3）。

## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**基本設計（外部設計）**を対象とする。外部設計の核心的な痛みは「外部から観測できない内部実装が、禁止語に当たらない形で画面・外部 IF に侵入する」ことであり、その文字列照合では捕まえられない侵入を見るのが主眼である。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`画面設計` / `外部インターフェース` / `トレーサビリティ`）の欠落・禁止語（`クラス図` / `シーケンス図` / `インデックス` / `テーブル定義`）の出現など、文字列で判定できる項目（`SQL` は製品名の部分文字列で誤爆するため機械禁止語から除外し、観点1の質的判断で見る） |
| 質的（本ルーブリック） | LLM ＋人間 | 禁止語に当たらない形で侵入した内部実装・外部仕様と内部仕様の混在・クライアント可読性・設計根拠・トレーサビリティの意味など、文脈判断が要る項目 |

機械判定で済む項目（必須見出しの欠落、禁止語の単純な出現）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。ここが見るのは「見出しはあるが中身の抽象度がずれている」「禁止語に当たらない形で内部実装が侵入している」類の、文字列照合では捕まえられない逸脱だけである。

なお API 語（REST/OpenAPI/endpoint/Swagger）・技術スタック名・ピクセル/hex カラーは、外部設計では正当な記述になりうる（外部公開 API 仕様・外部から観測する画面項目）ため**機械 vocab で弾かず本ルーブリックの文脈判断に委ねる**（P2 訂正版・cycle-4 srs 踏襲）。一律に弾くと正当な外部設計記述を誤爆するためである（観点1・観点3・§4-D 参照）。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「正当な外部仕様」と「不当な内部実装の先取り」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例で迷ったら逸脱と決めつけない。
- **技術スタック名・API 語・ピクセル/hex の厳密値そのものは逸脱と決めつけない。** 外部公開 API 仕様・外部から観測する画面項目として正当に現れることがあり、その場合は逸脱でない（P2 訂正版）。外部契約として必要か単なる内部詳細の先取りかを読み取れないときは fail-open（pass）に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P1/P3 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. 内部仕様の leak 検出（禁止語に当たらない形の侵入）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（外部設計は外部観測仕様に限る・内部実装は詳細設計へ）・[P5](../principles/granularity-axis.md#p5-数値精度は工程マーカーである)（数値精度・物理精度は詳細設計工程のマーカー）。

外部設計の最重要 leak 検出。画面設計節・外部インターフェース節に、**禁止語に当たらない形で内部実装が侵入していないか**を見る。具体的には、アルゴリズムの擬似コード・内部状態遷移・エラーハンドリングの実装方針・認証トークンの内部生成手順・**SQL クエリ/DB 操作文**など、外部から観測できない内部の作り込みである。SQL は機械 vocab では禁止語にしていない（製品名 PostgreSQL/NoSQL/MySQL 等の部分文字列で部分一致チェッカーが誤爆するため除外＝cycle-8 で横断検出・architecture-design と同方針）。そのため SQL クエリ/DB 操作文の混入は本観点の質的判断で見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 画面設計／外部 IF 節に、禁止語に当たらない形の内部実装（処理アルゴリズムの擬似コード・内部状態遷移・エラーハンドリングの実装方針・認証トークンの内部生成/署名手順・SQL クエリ/DB 操作文）が侵入していないか | 画面設計は外部から観測する「項目・遷移・契約」に留まり、外部 IF は入出力契約・エラーコード一覧・CRUD 図に留まる。内部の作り込み（SQL クエリ/DB 操作文を含む）は詳細設計レシピへ委ねられている | 内部実装に当たる原文（例: 「在庫数を for ループで減算し」「トークンは HMAC-SHA256 で署名」「`SELECT ... WHERE` で照会し」のような内部手順・擬似コード・DB 操作文）を該当節・該当行ごと引く |

> 注（機械判定との分担）: 禁止語そのもの（`クラス図`・`シーケンス図`・`インデックス`・`テーブル定義`）の単純な出現検出は機械判定（[`../scripts/`](../scripts/) の禁止語）の担当であり、本観点に重複させない。本観点が見るのは、禁止語に当たらない形（擬似コード・実装方針の自然文・トークン生成手順・SQL クエリ/DB 操作文など）で侵入した内部実装である。
>
> 注（`SQL` は機械でなく本観点で見る）: `SQL` は製品名 PostgreSQL・NoSQL・MySQL・SQLite 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出）。そのため `SQL` は機械 vocab の禁止語に入れず、SQL クエリ/DB 操作文の混入は本観点の質的判断で捕まえる（architecture-design と同方針）。製品名としての PostgreSQL 等の単なる言及は逸脱でなく、外部から観測できない DB 操作文・物理操作の先取りが逸脱である。
>
> 注（正当な記述は逸脱でない）: 「どのエンドポイントが認証を要するか」は外部契約であり逸脱でない。逸脱はその先（トークン検証ロジック・署名アルゴリズムなど詳細設計に属する内部手順）である。境界例は fail-open（pass）。

### 2. 外部仕様と内部仕様の同一節混在

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（外部観測仕様と内部実装の帰属分離）。

責務対照表（外部設計行）の逸脱判定基準そのもの。クライアントが承認すべき外部仕様（画面・IF 契約）と、開発者向けの内部仕様が**同一節に混ざっていないか**を見る。観点1が「内部実装が侵入したか」を見るのに対し、本観点は「外部仕様と内部仕様が**分離されず同じ節に同居している**」状態を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| クライアント承認すべき外部仕様（画面レイアウト・入出力項目・IF 契約）と、開発者向け内部仕様が同一節に混在していないか | 外部仕様の節は外部から観測できる内容だけで構成され、内部向けの記述が混在していない（混在するなら詳細設計へ分離されている） | 同一節に外部仕様と内部仕様が同居している原文（外部項目の記述に続けて内部実装の記述が現れる箇所）を、両者が分かるように該当行ごと引く |

### 3. audience test（非技術ステークホルダー／クライアント可読性）

参照原則: [P5](../principles/granularity-axis.md#p5-数値精度は工程マーカーである)（厳密値・物理精度は詳細設計工程のマーカー＝外部設計の読者には不要なノイズ）。

外部設計の読者は**クライアントを含む**。画面設計・外部 IF 仕様が**技術知識なしに読めるか**を見る。ピクセル/hex の厳密値や内部技術語が混じって読めなくなっていたら、抽象度が外部設計より下（詳細設計の UI コンポーネント仕様）へ降りている兆候である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| クライアント・非技術ステークホルダーが画面設計・IF 仕様を技術知識なしに読めるか。ピクセル/hex の厳密値（`16px`・`#3366FF` 等）や内部技術語が混じって読めなくなっていないか | 画面設計はレイアウト・項目・遷移のレベルで、IF 仕様は契約・エラーの意味のレベルで、技術知識なしに読める。厳密値が外部契約として必要な箇所（帳票の出力位置など）に限られている | 非技術者が読めない原文（画面設計節に紛れたピクセル/hex 厳密値・内部技術語）を該当行ごと引く |

> 注（機械でなく質的で見る理由）: ピクセル/hex 厳密値や技術語は外部設計でも正当になりうる（帳票の出力位置・外部公開 API のデータ型など）ため、機械 vocab で一律に弾くと誤爆する。よって機械では弾かず、本観点で「外部契約として必要か／単なる詳細先取りか」を文脈判定する（P2 訂正版・§4-D）。

### 4. 設計根拠（Why・却下案・トレードオフ）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠は必須）。

ここでの Why は業務の Why（要件で既出）ではなく、**外部設計判断の Why**である。画面遷移・外部 IF 設計のうち判断の余地がある箇所に、根拠（なぜこの画面分割か・なぜこの IF 粒度か・却下した代替）が添えられているかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 画面分割・画面遷移・外部 IF の粒度など判断の余地がある外部設計に、根拠（業務要件・利用シナリオとの対応・却下した代替・トレードオフ）が添えられているか | 判断の余地がある設計に、選定根拠ないし却下案・トレードオフが明示されている | 根拠が必要なのに欠けている設計箇所の原文（例: 根拠記載のない画面分割、選定理由のない IF 粒度）を該当節・該当行ごと引く |

### 5. トレーサビリティの質（意味的妥当性）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）。

空セルの検出は機械判定（[`../scripts/check_traceability.py`](../scripts/check_traceability.py)＝孤立設計要素〔対応要件 ID 欠落〕の決定論検出）で済む。**本観点は埋まっているセルの妥当性**を見る — 各画面/IF の対応要件 ID が形式上の対応ではなく、その画面/IF が実現する内容と**意味的に**整合しているか。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各画面/IF の対応要件 ID が形式的でなく意味的に妥当か（画面/IF の役割と、対応要件 ID が指す機能が一致しているか） | 対応要件 ID がその画面/IF の役割を実際に説明している。横断的な画面/IF（共通エラー画面・ヘルスチェック IF 等）には対応する NFR ID が付く | 整合しない対応の原文（画面名/IF 名と対応要件 ID の行）を引き、何と何が食い違うかを示す |

> 注（機械判定との分担）: 「対応要件 ID」列が空の画面/IF の検出は機械判定の担当範囲（孤立外部仕様＝スコープクリープ候補）。本観点は ID が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた要件 ID）を見る。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **HLD/LLD（基本設計/詳細設計）の境界線そのものは裁定しない。** 「外部観測仕様は外部設計・内部実装は詳細設計」という線引きは IEEE 1016 自身がスコープ外と明言する事項であり、**プロジェクト規約の合意事項**である。外部設計↔詳細設計の境界は [`../principles/responsibility-map.md`](../principles/responsibility-map.md)（外部設計行）で確定済み（外部から観測可能な仕様＝外部設計／内部実装＝詳細設計）であり、本ルーブリックはその確定境界を**前提として**判定する。これは**データ設計の論理/物理分割（F1）と同型の境界問題を一般化**したもの（F1 はデータ設計に閉じた決着、本件は外部設計全般へ拡張した同型問題）である（参照: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須) 注「アーキテクチャと詳細設計の境界はシステム依存でスコープ外」、決着記録: [CONTRIBUTING.md](../CONTRIBUTING.md) の F1）。
- **「正当な外部仕様 vs 不当な内部実装の先取り」を分ける一般ヒューリスティックは存在しない。** どちらとも決めかねる境界例は、逸脱と断定せず fail-open（pass）に倒して人間に委ねる。判断を盛らない。
- **技術スタック名・API 語・ピクセル/hex の厳密値は機械で弾かず本ルーブリックで文脈判定する。** 外部設計ではこれらが正当な記述になりうる（外部公開 API 仕様・外部から観測する画面項目・帳票の出力位置）ため、機械 vocab で一律に弾くと誤爆する（P2 訂正版・cycle-4 srs 踏襲）。本ルーブリックの観点1・観点3 で「外部契約として必要か／内部詳細の先取りか」を読み取り、読み取れない境界例は fail-open（pass）に倒す。

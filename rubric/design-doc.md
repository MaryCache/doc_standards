## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**Design Doc（設計合意文書）**を対象とする。

agile は機械層が薄く **rubric が主判定**である（[`./user-story.md`](./user-story.md) と同じ非対称設計 S4）。Design Doc は user-story 同様 **vocab を空にした**——その逸脱（全セクション強制記入・arc42 全12セクション埋め・C4 の L4 クラス図を最初から全描画・自明な実装やバグ修正の過剰文書化・gold plating・代替の事後正当化・トレース紐付けの質）は、いずれも**構造・量・文脈の判定**であって、特定の禁止トークンの部分一致では原理的に拾えない（「クラス図」を禁止語にすると C4／詳細設計への正当な委譲記述で誤爆する）。これらが本ルーブリックの担当である。これは [`./acceptance-criteria.md`](./acceptance-criteria.md) が vocab を持つ（Then の曖昧期待結果3語が部分一致誤爆なく拾えた）のとは**非対称**である——vocab の有無は「その doc_type の逸脱が機械で綺麗に拾えるか」で決まり、agile/WF の別ではない。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`Context` / `Non-Goals` / `トレーサビリティ`）の欠落・**トレース表の空セル（対応 user-story 列が空＝孤立した設計判断）**の検出など、文字列・表構造で判定できる項目。**vocab は空（forbidden 無し）＝禁止語チェックは pass を返すだけで実質的な検出はしない。** |
| 質的（本ルーブリック・**主判定**） | LLM ＋人間 | Goals/Non-Goals の質（Non-Goals が具体的にスコープを否定しているか）・抽象度と gold plating（L4 クラス図/コード詳細の全描画・arc42 全節埋めの過剰テンプレ化）・代替検討の質と ADR 委譲（事後正当化でないか・本文詳細展開でなく ADR リンク委譲か）・Context の質（なぜ作るかが書かれ自明な実装の過剰文書化でないか）・トレース紐付けの妥当性と粒度——いずれも文脈・量・構造の判断が要る項目。**Design Doc はこの質的判定が主であり、機械層は薄い（必須見出し＋トレース空セルのみ）。** |

機械判定で済む項目（必須見出しの欠落、**トレース表の空セルそのものの検出**）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。ここが見るのは「節はあるが Non-Goals が "特になし" で逃げている」「L4 クラス図を最初から全描画している」「代替が事後正当化」「Context が薄く自明な実装の過剰文書化」「対応 user-story が形式上は埋まっているが意味的に合っていない」類の、文字列照合・表構造では捕まえられない逸脱だけである。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「必要な抽象度に留まった設計」と「L4 の過剰描画・gold plating」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。どこまでが必要な詳細でどこからが過剰かの境界で迷ったら逸脱と決めつけない。
- 「Non-Goals が十分にスコープを否定しているか」「代替が事後正当化か実際の比較か」の定量基準は無い（§4-D）。境界例は逸脱と断定せず pass に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P2/P4 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. Goals/Non-Goals の質（Non-Goals が具体的にスコープを否定しているか）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計はスコープに紐付く・孤立要素＝スコープクリープ検出点）。

Non-Goals が**具体的に「今回やらないこと」を否定**しているか。Non-Goals は機械が見出しの有無を見るが、本観点は**中身**——"特になし" で逃げていないか・抽象的すぎてスコープを実質否定できていないか・Goals と Non-Goals の境界が読み手に伝わるかを見る。スコープ否定の放棄はスコープクリープの主因である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| Non-Goals が具体的に「今回やらないこと」を1つ以上否定しているか。"特になし"・空虚な一般論でスコープ否定を放棄していないか。Goals と Non-Goals の境界が読み手に伝わるか | Non-Goals が具体的な対象（やらない機能・対象外の範囲）を理由とともに挙げ、Goals との境界が明確である | "特になし" や空虚な Non-Goals の原文（節見出し＋該当行）を引く。Goals/Non-Goals の境界が曖昧な原文を引く |

> 注（機械判定との分担）: 必須見出し `Non-Goals` の**有無それ自体**は機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが中身がスコープを否定できていない**」ケースである。
>
> 注（境界は fail-open）: 「どこまで具体的なら十分か」の定量基準は無い（§4-D）。Non-Goals が十分にスコープを否定しているか決めかねる境界例は逸脱と断定せず pass に倒す。

### 2. 抽象度・gold plating（L4 クラス図/コード詳細の全描画・過剰テンプレ化）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（What/Why と How の分離・実装詳細は下流へ）。

Design Doc 固有の逸脱を見る。**C4 の L4（クラス図レベル）やコード詳細を最初から全描画していないか**、**arc42 全12セクションを必要性なくテンプレで埋めていないか**。責務対照表の「全セクション強制記入＝逸脱」「L4 を最初から全描画＝逸脱」を質的に判定する。Design Doc は L1-L2（システム文脈・コンテナ）優先・必要な節のみであり、L4 相当の内部の作り込みは詳細設計／コードに委ねる。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| C4 の L4（クラス図レベル）・コード詳細・コンポーネント内部の作り込みを最初から全描画していないか。arc42 全12セクションを必要性なくテンプレで埋める過剰テンプレ化（gold plating）になっていないか | 抽象度が L1-L2 優先・必要な節のみに留まり、L4 相当の内部設計・実装詳細は詳細設計／コードへ委ねられている。各節が本設計に必要だから書かれている（テンプレ消化でない） | 全描画された L4 クラス図/コード詳細の原文（該当節＋該当行）を引く。必要性なくテンプレ埋めされた空虚な節（中身が「該当なし」「未定」で機械的に並ぶ節）を引く |

> 注（境界は fail-open）: 「必要な抽象度」と「過剰な L4 描画・gold plating」を分ける一般ヒューリスティックは存在しない（§4-D）。どこまでが必要でどこからが過剰か決めかねる境界例は逸脱と断定せず pass に倒す。

### 3. 代替検討の質と ADR 委譲（事後正当化でないか・S5 二重定義回避）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠は必須・design rationale の記録）。

`検討した代替案`（推奨節）がある場合、それが**事後正当化**（採用案ありきで都合よく付けた却下理由）でなく実際の比較になっているか。かつ、**重要な設計判断が本文に詳細展開されず ADR にリンク委譲**されているか（S5・二重定義回避）。ADR の中身の良し悪し（却下案が妥当か等）は評価しない——それは ADR スキルおよびレビュースキル（`review-handoff` / `santa-method`）の責務である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 代替検討が事後正当化でなく実際のトレードオフ比較になっているか。重要な設計判断が本文に詳細展開されず `[ADR-0001](...)` 形式で ADR にリンク委譲されているか（本文と ADR の二重定義になっていないか）。あれば ADR リンクが採番され辿れるか | 代替が実際の比較・却下理由を伴い、重要判断は ADR に委譲され本文はリンク参照に留まる（本書に ADR 本体の全文を二重定義していない） | 事後正当化に見える代替の原文（採用案ありきで都合よい却下理由の該当行）を引く。本文に詳細展開された重要判断（ADR へ委譲すべきものが本文に二重定義されている箇所）を引く |

> 注（ADR リンクは必須でない・S5 委譲の境界）: ADR リンクの**存在**は機械強制しない（小さい設計では ADR 不要）。本観点は「重要判断が本文に詳細展開されていないか／あれば事後正当化でないか」を見るのであって、リンクが無いこと自体を逸脱とはしない。ADR の**採番・生成・内容評価**は [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルの責務であり、本観点はリンクの存在と委譲の妥当性のみ見る（doc-standards は ADR を生成しない・S5）。
>
> 注（境界は fail-open）: 「事後正当化か実際の比較か」を分ける一般ヒューリスティックは無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。

### 4. Context の質（なぜ作るかが書かれ、自明な実装の過剰文書化でないか）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（What/Why の記述）。

Context が「**なぜこの設計が必要か**」を書けているか。かつ、その Design Doc 自体が**自明な実装・バグ修正の過剰文書化**になっていないか（責務対照表「含まない＝自明な実装・バグ修正の Design Doc 化」）。Context が薄い（書くべき非自明な背景が無い）なら、その変更は Design Doc を要しない兆候である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| Context が「なぜこの設計が必要か」（課題・痛み・きっかけ）を書けているか。自明な実装・バグ修正にまで Design Doc を起こす過剰文書化になっていないか（Context が薄く非自明な背景が無いのに Design Doc 化していないか） | Context に非自明な背景・課題が書かれ、設計合意を要する変更であることが読み取れる | 「なぜ作るか」を欠いた／自明な実装の薄い Context の原文（節見出し＋該当行）を引き、Design Doc を要しない兆候（非自明な設計判断の不在）を示す |

> 注（境界は fail-open）: 「自明か非自明か」「Design Doc を要するか」を分ける一般ヒューリスティックは無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。Design Doc を起こすこと自体の可否を機械的に裁定しない。

### 5. トレーサビリティの質（紐付けの妥当性と粒度）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）。

各設計判断が対応 user-story／要求に**意味的に**紐付いているか（形式的な対応でなく）。その user-story の価値と、設計判断が実際に実現する内容が一致しているか・粒度が見合っているかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各設計判断の「対応 user-story／要求」が形式的でなく意味的に妥当か（その価値と、設計判断が実現する内容が一致しているか）。粒度が見合っているか（1 価値に対し過大／過小な判断になっていないか） | 各設計判断の対応 user-story／要求が、その判断が何を実現するかを実際に説明している。紐付けが流用・コピペで実態とずれていない | 整合しない対応の原文（設計判断と対応 user-story の行）を引き、何と何が食い違うかを示す |

> **注（過大主張の禁止・F5 の教訓）**: **対応 user-story 列の空セルそのものの検出（孤立した設計判断）は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当**であり、本観点に重複させない。本観点は ID が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた対応、形式上は埋まっているが意味的に無関係な対応）と、**紐付けの粒度**を見る。空セル検出を rubric の仕事として主張しない（cycle-12/F5 の教訓＝「rubric が機械の仕事を主張しない」）。
>
> 注（境界は fail-open）: 紐付けが妥当か流用かが紛らわしい境界例は逸脱と断定せず fail-open（pass）に倒す。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **「必要な抽象度の設計 vs L4 の過剰描画・gold plating」を分ける一般ヒューリスティックは存在しない。** どこまでが必要な詳細でどこからが過剰テンプレ化・L4 全描画かは文脈依存である。読み取れない境界例は逸脱と断定せず **fail-open（pass）**に倒して人間に委ねる。判断を盛らない。
- **「Design Doc を起こすべきか（自明な実装か非自明か）」の線引きそのものは裁定しない。** 「自明な実装・バグ修正は Design Doc 化しない」という境界は責務対照表（Design Doc 行）が引いた合意事項であり、本ルーブリックはその確定境界を**前提として**判定する。境界の妥当性そのものは問わない。
- **ADR との委譲境界は裁定対象でない。** doc-standards は ADR を生成せず、**粒度境界とリンク存在・委譲の妥当性のみ**を提供する（S5）。ADR の番号体系・記録フォーマット・内容評価（却下案が妥当か等）は [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルが所有・採番・生成する source of truth であり、本ルーブリックは ADR の**内容を評価しない**（観点3 はリンク存在と委譲の妥当性のみ）。
- **空セルの検出は機械の担当であり rubric は過大主張しない（F5）。** トレース表の空セル（孤立した設計判断）は [`../scripts/check_traceability.py`](../scripts/check_traceability.py) が決定論で検出する。本ルーブリック（観点5）は埋まっているセルの**意味的妥当性と粒度**のみを見る（cycle-12/F5 の教訓）。

## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**基本設計（運用・移行設計）**を対象とする。運用・移行設計の核心的な痛みは「方針レベルに留まるべき記述へ、禁止語に当たらない形で逐次手順・移行のデータ変換クエリ本文・インフラ構成の具体値が侵入する」ことと「監視・バックアップ・障害対応・移行・切替・ロールバックの検討漏れ」、そして「ロールバック条件・切替判定基準が『安定したら』のような曖昧表現で観測不能」であることであり、その文字列照合では捕まえられない逸脱を見るのが主眼である。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`運用方針` / `移行方針` / `トレーサビリティ`）の欠落・禁止語（`手順書` / `移行スクリプト`）の出現・トレーサビリティ表の空セル〔孤立設計要素＝対応要件 ID 欠落〕（`check_traceability.py`）など、文字列で判定できる項目 |
| 質的（本ルーブリック） | LLM ＋人間 | 禁止語に当たらない形で侵入した逐次手順・移行のクエリ本文・インフラ具体値・運用カテゴリの網羅と「該当なし＋理由」の妥当性・トレーサビリティの意味・ロールバック条件の検証可能性など、文脈判断が要る項目 |

機械判定で済む項目（必須見出しの欠落、禁止語の単純な出現、トレーサビリティ表の空セル＝孤立設計要素〔対応要件 ID 欠落・スコープクリープ候補・P4 違反〕＝[`../scripts/check_traceability.py`](../scripts/check_traceability.py) が決定論で検出）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。機械 vocab が禁止するのは「手順」単独・技術名と誤爆しない下流実行先取りマーカー2語（`手順書` / `移行スクリプト`）に**限る**。それ以外（禁止語に当たらない形の逐次手順・移行のデータ変換クエリ本文・インフラ構成の具体値・トレーサビリティの意味・ロールバック条件の曖昧さ）は機械では捕まえられないため、本ルーブリックが担う。

なお技術スタック名・製品名・プロトコル名（および **`SQL`**）と、**「手順」単独のような汎用語**は、運用・移行設計では正当な記述になりうる（監視対象製品名・移行元/先の環境記述／「運用手順の方針」等の方針記述）ため**機械 vocab で弾かず本ルーブリックの文脈判断に委ねる**（P2 訂正版・cycle-4 srs / cycle-7 external-design / cycle-8 architecture-design / cycle-9 nonfunctional-design 踏襲）。とりわけ `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出）。よって**実際の移行データ変換クエリ本文の侵入は機械でなく本ルーブリックの観点2が見る**（cycle-8 の設計判断）。一律に弾くと正当な運用・移行記述を誤爆するためである。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「方針レベルの正当な記述」と「不当な実行手段の先取り」を分ける一般ヒューリスティックは存在しない。境界例で迷ったら逸脱と決めつけない。
- **技術スタック名・製品名・プロトコル名・`SQL` という語そのもの、および「手順」単独は逸脱と決めつけない。** 監視対象製品名・移行元/先の環境記述・「運用手順の方針」等として正当に現れることがある（P2 訂正版）。逸脱になるのはその先（実際の移行データ変換クエリ本文、逐次手順の段取り、インフラ構成の具体値）であり、方針として必要か単なる実行手段の先取りかを読み取れないときは fail-open（pass）に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P1/P3 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. 方針 vs 手順の粒度

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（運用・移行設計は方針までに限る・実行手段は下流へ）。

運用・移行設計の最重要観点。運用方針・移行方針が「方針」レベル（何を・どの基準で行うか）に留まり、禁止語（`手順書` / `移行スクリプト`）に当たらない形で**逐次手順の粒度**（ステップ列・実行コマンド列・移行データ変換クエリの本文）が侵入していないかを見る。`手順書` という成果物名そのものの出現は機械の担当であり、本観点は**成果物名を使わずに逐次手順の粒度で書かれている**ケース（「まず A を停止し、次に B を流し、最後に C を確認する」のような段取り記述）を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 運用方針・移行方針が方針レベルに留まり、禁止語に当たらない形で逐次手順（ステップ列・コマンド列・移行クエリ本文）が侵入していないか | 各方針が「何を・どの基準で行うか」の方針として書かれ、逐次実行のための段取り（ステップ番号付き手順・コマンド列・クエリ本文）が混入していない | 方針でなく逐次手順の粒度で書かれた原文（例: 「①サービス停止 → ②データ投入 → ③再起動」のようなステップ列）を該当節・該当行ごと引く |

### 2. 移行 SQL／実装詳細の leak

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（運用・移行設計は方針・条件までに限る）・[P5](../principles/granularity-axis.md#p5-数値精度は工程マーカーである)（厳密値は工程マーカー）。

禁止語（`手順書` / `移行スクリプト`）に当たらない形で「どう実行するか」の実装詳細が侵入していないかを見る。具体的には、**移行のデータ変換クエリ本文（`SQL` を含む）・移行を回すコード本体・インフラ構成の具体値（サーバ台数・スペック・ネットワーク設定値）**である。これらは外から見た方針・条件ではなく実行手段であり、詳細設計／後続工程の対象である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各節に、禁止語に当たらない形の実装詳細（移行データ変換クエリ本文・コード本体・インフラ構成の具体値）が侵入していないか | 運用方針は運用の意思決定基準に、移行方針は移行の方針・条件に留まり、実装詳細は詳細設計／後続工程へ委ねられている | 実装詳細に当たる原文（例: `UPDATE orders SET ...` のようなクエリ本文、「Web サーバ4台・8 vCPU/16GB」のようなインフラ具体値）を該当節・該当行ごと引く |

> 注（機械判定との分担）: 実行手段マーカーそのもの（`手順書`・`移行スクリプト`）の単純な出現検出は機械判定（[`../scripts/`](../scripts/) の禁止語）の担当であり、本観点に重複させない。本観点が見るのは、禁止語に当たらない形（クエリ本文・コード本体・インフラ具体値）で侵入した実装詳細である。
>
> 注（技術名・SQL は機械でなく本観点で見る理由）: `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出）。よって技術名・`SQL` は機械 vocab の禁止語に入れず本観点で見る。製品名としての `PostgreSQL` 等の出現（監視対象製品名・移行元/先の環境記述）は逸脱でなく、逸脱は実際の移行データ変換クエリ本文・コード本体である。境界例は fail-open（pass）。

### 3. 運用カテゴリ網羅

参照原則: [P9](../principles/granularity-axis.md#p9-nfr-は要件段階で並行検討後回し禁止)（NFR は後回し禁止・網羅的に検討）・[P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)。

運用側（監視・バックアップ・障害対応）と移行側（移行・切替・ロールバック）の6項目が揃い、**該当の薄いものが「該当なし＋理由」で埋まり、検討漏れと対象外が区別できるか**を見る。空節（項目見出しはあるが中身も理由も無い）は検討漏れの疑いがある。とりわけ統合スライスでは片側（運用または移行）が手薄になりやすいため、双方の網羅を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 監視・バックアップ・障害対応・移行・切替・ロールバックが揃い、該当の薄いものが「該当なし＋理由」で明示されているか（検討漏れ＝空節と対象外＝理由付き除外が区別できるか） | 6項目すべてに、方針か「該当なし＋理由」のいずれかが記載されている。理由なく空の項目（検討漏れの疑い）が無い | 中身も「該当なし＋理由」も無い空項目、または検討された形跡のない項目の原文（節見出しと空の本文）を該当箇所ごと引く |

### 4. トレーサビリティの質（意味的妥当性）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）。

空セルの検出は機械判定（[`../scripts/check_traceability.py`](../scripts/check_traceability.py)＝孤立設計要素〔対応要件 ID 欠落〕の決定論検出）で済む。**本観点は埋まっているセルの妥当性**を見る — 各運用方針・移行方針の対応要件 ID／NFR ID が形式上の対応ではなく、その方針が表す内容と**意味的に**整合しているか（運用方針に運用保守性 NFR、移行方針に移行性 NFR 等が対応しているか）。性能 NFR が運用方針に、無関係な機能要件が移行方針に付くような意味的ミスマッチが無いかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各方針の対応要件 ID／NFR ID が形式的でなく意味的に妥当か（運用方針に運用保守性・可用性系、移行方針に移行性系の NFR が対応しているか） | 対応 ID がその方針の出どころを実際に説明している。運用方針に移行性 NFR が付くような意味的ミスマッチが無い | 整合しない対応の原文（方針名と対応要件 ID／NFR ID の行）を引き、何と何が食い違うかを示す |

> 注（機械判定との分担）: 「対応要件 ID／NFR ID」列が空の方針の検出は機械判定の担当範囲（孤立方針＝スコープクリープ候補）。本観点は ID が**書かれているが内容が合っていない**ケースを見る。

### 5. ロールバック条件の検証可能性

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（検証可能性は工程を貫く不変量）。

運用・移行の意思決定が verifiable かを見る本観点。ロールバック条件・切替判定基準・障害対応のエスカレーション基準が「安定したら」「問題なければ」「十分に検証できたら」のような**曖昧表現**でなく、**観測可能・判定可能な条件**（しきい値・件数・時間・率の比較）で書かれているかを見る。曖昧な判定基準は、運用・移行の意思決定の根拠にならない（誰が見ても同じ結論に至れない）。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| ロールバック条件・切替判定基準・エスカレーション基準が曖昧表現でなく観測可能・判定可能な条件で書かれているか | 各判定基準が観測可能な値・状態・しきい値比較（例: 「失敗率が5%を超えたら」「24時間以内に」）で書かれ、「安定したら」等の曖昧表現が残っていない | 曖昧な判定基準の原文（例: 「動作が安定したらカットオーバー」「問題なければ旧を停止」）を該当節・該当行ごと引く |

## 境界注意（このルーブリックが裁定しないこと）

- **運用・移行の具体手順の置き場（基本設計か詳細設計か）そのものは裁定しない。** 方針と手順の境界は実務で割れる事項であり、[`../principles/responsibility-map.md`](../principles/responsibility-map.md)（運用/移行設計行）とプロジェクト方針が source of truth である。本ルーブリックはその確定境界を**前提として**、基本設計工程の文書に対し「方針レベルに留まっているか」（観点1）「実装詳細が leak していないか」（観点2）を見る。
- **運用・移行を実現するインフラ／実装の良し悪しは裁定しない。** どう実行するか（作業の段取り・移行を回す実装・インフラ構成の詳細）は詳細設計／後続工程の対象であり、本ルーブリックは**それが運用・移行設計に混入していないか**（観点1・2）だけを見る。実装の設計品質は詳細設計のレビュー（`review-handoff` / `santa-method`）に委ねる。
- **「方針レベルの正当な記述 vs 不当な実行手段の先取り」を分ける一般ヒューリスティックは存在しない。** どちらとも決めかねる境界例は、逸脱と断定せず fail-open（pass）に倒して人間に委ねる。判断を盛らない。
- **技術名・SQL・「手順」単独は機械で弾かず本ルーブリックで文脈判定する。** 運用・移行設計ではこれらが正当な記述になりうる（監視対象製品名・移行元/先の環境記述／「運用手順の方針」等の方針記述）ため、機械 vocab で一律に弾くと誤爆する（P2 訂正版・cycle-4 srs / cycle-7 external-design / cycle-8 architecture-design / cycle-9 nonfunctional-design と同方針）。本ルーブリックの観点1（逐次手順の粒度での記述）・観点2（移行データ変換クエリ本文・インフラ具体値の踏み込み）で文脈判定し、読み取れない境界例は fail-open（pass）に倒す。

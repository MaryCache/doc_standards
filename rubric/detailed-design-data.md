## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**詳細設計（物理）データ設計**を対象とする。論理ER の質的判定（物理先取りの leak・論理ER の可読性など）は基本設計データ設計の対象であり、ここでは見ない（基本設計側のルーブリックは [`./data-design.md`](./data-design.md)）。本ルーブリックは対をなす相手の**逆側**＝物理が主役の工程を見る。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`物理ER` / `テーブル定義` / `制約とインデックス` / `トレーサビリティ`）の欠落・禁止語（`なぜなら業務`）の出現・**トレース表の空セル（孤立設計要素＝対応要件 ID 欠落・[`../scripts/check_traceability.py`](../scripts/check_traceability.py)）**など、文字列・表構造で判定できる項目 |
| 質的（本ルーブリック） | LLM ＋人間 | 物理設計の粒度逸脱（薄すぎ／厚すぎ）・物理の設計根拠・トレーサビリティの意味・実装可能性など、文脈判断が要る項目 |

機械判定で済む項目（必須見出しの欠落、禁止語 `なぜなら業務` の出現）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。ここが見るのは「見出しはあるが中身の粒度がずれている」類の、文字列照合では捕まえられない逸脱だけである。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「正当な物理設計」と「不当な詳細先取り（ghost document 化）」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例で迷ったら逸脱と決めつけない。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P1/P3 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

> 物理が主役の工程である。基本設計（論理）ルーブリックの観点1が「論理ER への物理先取り」を逸脱として挙げるのとは**逆**で、ここでは物理制約（データ型・NULL 可否・PK/FK・代表 index・`btree` 等の物理 index 種別）はむしろ正当な記述である。本ルーブリックが逸脱として見るのは、(a) 物理設計が薄すぎて実装判断ができない／厚すぎて実装コードを先取りしている（観点1）、(b) 物理の設計根拠が欠けている（観点2）、(c) トレースが形式的（観点3）、(d) 実装可能性が満たせない（観点4）であり、加えて (e) 業務上の Why の混入（P2）や基本設計で既出の論理の再記述といった「上流の越境」を物理 ER に持ち込んでいないかを横断的に見る。

### 1. 物理ER・テーブル定義の厚み（薄すぎ／厚すぎ）

参照原則: [P5](../principles/granularity-axis.md#p5-数値精度は工程マーカーである)（数値精度は工程マーカー）・[P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（How の帰属。厚すぎ＝実装コード逐語＝ghost document は How が下位工程へ越境した状態）。

薄すぎ＝型/NULL/PK/FK/代表 index が欠落し、開発者が実装判断できない。厚すぎ＝DML 全文・チューニング手順・実装コードの先取りで、レシピ本体が「逐語のコード」と化す（ghost document）。物理が主役の工程なので物理制約そのものは正当であり、見るのは**過不足**である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 物理ER・テーブル定義に、開発者が実装判断するための最小限（型・NULL 可否・PK・FK・代表的な index）が揃い、かつ実装コードの先取り（DML 全文・チューニング手順・boilerplate 逐語）に踏み込んでいないか | 各テーブルに型/NULL/PK/FK が記述され、主要アクセスパターンの代表 index が示される一方、SQL 全文やアプリ実装コードは制約とインデックス節の `sql` フェンス内の最小限に留まる | 薄すぎ: 型や NULL が欠けたカラム定義の原文（該当テーブル節・該当行）を引く／厚すぎ: コード同等の逐語（フェンス外に展開された DML 全文・チューニング手順・実装コード）の原文を引く |

> 注: `btree`/`hash` 等の**物理 index 種別の出現そのものは逸脱ではない**（詳細設計工程で確定するのが正当。P5）。本観点は種別の有無ではなく、定義の過不足を見る。

### 2. 設計根拠（物理）の有無

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠は必須）。

ここでの Why は業務の Why ではなく、**物理設計判断の Why**である。詳細設計（物理）では index 選定・非正規化・物理データ型選定など、判断の余地がある箇所に物理レベルの根拠を求める。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| index 選定（検索頻度・選択性・更新頻度）・非正規化の物理根拠・物理データ型/精度の選定など、判断の余地がある物理設計に根拠（および却下した代替）が添えられているか | 判断の余地がある物理設計に、選定根拠ないし却下案・トレードオフが明示されている（例: index に検索頻度・選択性・更新頻度の記載がある） | 根拠が必要なのに欠けている物理設計箇所の原文（例: 根拠記載のない index、根拠記載のない非正規化、選定理由のない型/精度）を引く |

> 注: 業務上の理由（要件で既出の Why）を物理 ER に書き足すのは逸脱（P2）。本観点が求めるのは**物理の設計根拠**であって業務 Why の転記ではない。なお禁止語 `なぜなら業務` の単純な出現検出は機械判定（[`../scripts/`](../scripts/)）の担当であり、本観点はそれに当たらない形で混入した業務 Why（言い換え・別表記）を見る。

### 3. トレーサビリティの質（形式でなく意味を持つか）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）。

空セルの検出は機械判定（[`../scripts/check_traceability.py`](../scripts/check_traceability.py)＝孤立設計要素〔対応要件 ID 欠落〕の決定論検出）で済む。**本観点は埋まっているセルの妥当性**を見る — 詳細設計（物理）では2方向の対応を見る：(a) 物理テーブル→要件 ID が意味的に整合しているか、(b) 論理エンティティ→物理テーブルの対応が妥当か。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各物理テーブルの対応要件 ID が形式的でなく意味的に妥当か、また論理エンティティ→物理テーブルの対応が（分割・統合・命名を含め）意味的に妥当か | 対応要件 ID がそのテーブルの役割を実際に説明している。論理→物理の対応が、論理エンティティの分割/統合の実態と一致している。横断テーブル（ログ・監査等）には対応する NFR ID が付く | 整合しない対応の原文（テーブル名と対応要件 ID の行、または論理名と物理名の対応行）を引き、何と何が食い違うかを示す |

> 注: 「対応要件 ID」列や「論理名」列が空のテーブルの検出は機械判定の担当範囲（孤立設計要素＝スコープクリープ候補）。本観点は ID/対応が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた ID、論理→物理の対応が崩れた行）を見る。

### 4. audience test（実装可能性）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能・設計根拠）。

詳細設計（物理）の読者は**実装する開発者**である。物理ER ＋テーブル定義から、追加の設計判断なしに実装（DDL 記述）できるかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 開発者が物理ER ＋テーブル定義だけで、追加の設計判断なしに実装（DDL 記述）に着手できるか（できないなら粒度が粗すぎ＝実装者に設計を押し戻している） | 物理名・型・NULL・PK・FK・代表 index・主要な制約が確定しており、DDL に落とすうえで残る判断が（命名規約への代入など）機械的なものに限られる | 実装に必要な決定が未確定で開発者が設計判断を迫られる原文（型未定・NULL 可否未定・FK 参照先未定・制約条件が曖昧な行）を引く（観点1の「薄すぎ」と重なる場合は相互参照でよい） |

> 注: 「非技術ステークホルダーが論理ER を理解できるか」という可読性の観点は**基本設計（論理）データ設計**の観点であり、本ルーブリックでは見ない（基本設計側ルーブリック [`./data-design.md`](./data-design.md) 観点5）。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **HLD/LLD（基本設計/詳細設計）の境界線そのものは裁定しない。** 「論理ER は基本設計・物理ER は詳細設計」という線引きは IEEE 1016 自身がスコープ外と明言する事項であり、**プロジェクト規約の合意事項**である。データ設計についてはこの境界が F1（スタンスA・2026-06-03）で**決着済み**（基本設計＝論理ER／物理＝詳細設計）であり、本ルーブリックはその確定境界を**前提として**、詳細（物理）側を判定する。境界の妥当性そのものは問わない（参照: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須) 注「アーキテクチャと詳細設計の境界はシステム依存でスコープ外」、決着記録: [CONTRIBUTING.md](../CONTRIBUTING.md) の F1）。
- **「正当な物理設計 vs 不当な詳細先取り（ghost document 化）」を分ける一般ヒューリスティックは存在しない。** どちらとも決めかねる境界例は、逸脱と断定せず fail-open（pass）に倒して人間に委ねる。判断を盛らない。

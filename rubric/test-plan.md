## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**テスト計画（Test Plan）**を対象とする。テスト計画の核心的な痛みは「**計画へテストケースの具体値が混入する**」（構造判定）・「**終了基準が測定不能**」（3語の定型句に当たらない言い換えで紛れる曖昧さ）・「**対象外がスコープを否定できていない**（"特になし" で逃げる）」であり、その文字列照合では捕まえられない逸脱を見るのが主眼である。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`スコープ` / `終了基準` / `トレーサビリティ`）の欠落・禁止語（終了基準の曖昧表現マーカー3語: `正しく表示` / `正しく動作` / `適切に処理`）の単純な出現・トレーサビリティ表の空セル〔孤立テスト項目＝対応要件/テストレベル欠落〕（[`../scripts/check_traceability.py`](../scripts/check_traceability.py)）など、文字列・表構造で判定できる項目 |
| 質的（本ルーブリック） | LLM ＋人間 | 計画へのテストケース具体値の混入・"特になし" で逃げた対象外・禁止語3語に当たらない言い換えで紛れた測定不能な終了基準・要件文の構造的転記・トレーサビリティの意味とカバレッジなど、文脈判断が要る項目 |

機械判定で済む項目（必須見出しの欠落、曖昧表現マーカー3語の単純な出現、トレーサビリティ表の空セル）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。ここが見るのは「節はあるが計画にケース具体値が紛れている」「対象外が空虚でスコープを否定できていない」「禁止語3語に当たらない言い換えで終了基準が測定不能」「特定語ではなく構造として要件が転記されている」類の、文字列照合・表構造では捕まえられない逸脱だけである。

なお技術スタック名・製品名・`SQL`・ツール名（JUnit 等）は、テスト計画では正当な記述になりうる（`リソース・環境` の記述）ため**機械 vocab で弾かず本ルーブリックの文脈判断に委ねる**（cycle-8 以降の WF スライス踏襲）。とりわけ `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「計画にふさわしい方針レベルの記述」と「ケース具体値の混入」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例（計画の例示が具体的すぎるか・ケース具体値の先取りか紛らわしいもの）で迷ったら逸脱と決めつけない。
- 「対象外が十分にスコープを否定しているか」「終了基準が測定可能か」の定量基準は無い（§4-D）。境界例は逸脱と断定せず pass に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P6/P7 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. スコープの質（対象外＝やらないテスト範囲が具体的か）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（スコープに紐付く・孤立要素＝スコープクリープ検出点）。

`スコープ` 節の**対象外（やらないテスト範囲）が具体的にスコープを否定**しているか。対象外は機械が見出しの有無を見るのでなく**中身**——"特になし" で逃げていないか・抽象的すぎてテスト範囲を実質否定できていないか・対象と対象外の境界が読み手に伝わるかを見る。スコープ否定の放棄はテストのスコープクリープの主因である（Design Doc の Non-Goals と同型）。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 対象外が具体的に「今回テストしないこと」を理由とともに1つ以上否定しているか。"特になし"・空虚な一般論でスコープ否定を放棄していないか。対象と対象外の境界が読み手に伝わるか | 対象外が具体的なフィーチャ／機能と理由を挙げ、対象との境界が明確である | "特になし" や理由を欠く空虚な対象外の原文（節見出し＋該当行）を引く。対象/対象外の境界が曖昧な原文を引く |

> 注（機械判定との分担）: 必須見出し `スコープ` の**有無それ自体**は機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが対象外がスコープを否定できていない**」ケースである。

### 2. 終了基準の測定可能性（P6・3語に当たらない曖昧表現）

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（検証可能性は工程を貫く不変量）。

`終了基準` が、第三者が同じ完了判定に到達できる**測定可能・判定可能**な条件で書かれているか。曖昧表現マーカー3語の語そのものではなく、**言い換えで紛れた曖昧さ**（「十分にテストできたら」「網羅的に確認できたら」「品質が安定したら」「適切にカバーできたら」など測定基準を持たない完了条件）で逃げていないかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 終了基準が測定可能・判定可能か。禁止語3語に当たらない言い換えの曖昧表現（「十分に」「網羅的に」「安定したら」「適切にカバー」等）や、しきい値・件数を欠いて合否が一意に決まらない完了条件で逃げていないか | 各終了基準が観測できる値・件数・率・しきい値比較（例: 「カバレッジ 95% 以上」「重大バグ 0 件」「全 P1 ケース pass」「p95 ≤ 3000ms」）で書かれ、第三者が同じ完了判定に到達できる | 測定不能な終了基準の原文（節見出し＋該当行。例: 「十分にテストできたら完了」「品質が安定したらリリース」）を引く |

> 注（機械判定との分担）: 曖昧表現マーカー3語（`正しく表示`・`正しく動作`・`適切に処理`）の**単純な出現**は機械判定（[`../scripts/`](../scripts/) の禁止語 vocab）の担当であり、本観点に重複させない。本観点が見るのは、**禁止語に当たらない言い換え**（「十分に」「網羅的に」「安定したら」など別語に化けた測定不能な完了条件）や、語は具体的でも合否が主観／前提不足で一意に決まらない書き方である（nonfunctional-design が曖昧表現を rubric にした前例と同型）。

### 3. ケース具体値の混入（計画 vs ケース仕様の境界・F1 同型）

参照原則: [P7](../principles/granularity-axis.md#p7--p8-テスト文書の階層と戦略計画の分離検出補助)（テスト文書の階層＝計画 → 設計仕様 → ケース仕様 → 手順仕様の4層。テスト戦略は組織横断の方針層として計画の直上に分離する〔戦略/計画の二分は厳密な規格境界ではない＝P7 注〕。階層を飛び越えない）。

計画に**個々のテストケースの具体的入力値・期待結果**が書かれていないか（それはケース仕様＝[`../waterfall/test/test-case-spec.md`](../waterfall/test/test-case-spec.md) の担当）。計画は「何を・どこまでテストするか／いつ完了とするか」の方針までであり、1ケースの事前条件・入力値・操作・具体的期待結果はケース仕様へ降ろす。これは F1（論理/物理）と同型の隣接境界（計画 vs ケース仕様）である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 計画に個々のテストケースの具体的入力値・期待結果（1ケースの事前条件・入力・操作・観測値）が混入していないか | スコープ・終了基準・トレーサビリティが計画レベル（方針・条件・対象範囲）に留まり、ケースの具体値はケース仕様へ委ねられている | ケース具体値に当たる原文（例: 「数量=11 を入力すると E-STOCK が返る」のような1ケースの入力値・期待結果）を該当節・該当行ごと引く |

> 注（境界は fail-open）: 計画の例示（テストレベルの枠組みを伝える最小限の例）と、ケース仕様の具体値の先取りとを分ける一般ヒューリスティックは無い（§4-D）。どちらとも決めかねる境界例は逸脱と断定せず pass に倒す。

### 4. 要件転記アンチパターン（転記か・ID 参照か）

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（テスト文書は要件を ID 参照する・要件文を転記しない）。

スコープやトレーサビリティに要件文（What の文言・Why の説明）が**構造として転記**されていないか。要件は ID で参照されているかを見る。転記は二重管理と矛盾の温床になる（同期負債）。これは test-case-spec の要件転記観点と同型である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| スコープ／トレーサビリティに要件文が**構造として転記**されていないか（特定語ではなく、要件をそのまま写した内容になっていないか）。要件は ID で参照されているか | テスト対象・トレーサビリティが要件を「対応要件 ID」で参照し、要件の文言・理由は写されていない | 要件文が逐語転記された原文（節見出しまたは表行＋該当箇所）を引き、対応する要件 ID を示す |

> 注（機械判定との分担）: 要件転記は**特定の禁止語では弾けない構造の問題**であり、機械語彙（[`../scripts/`](../scripts/) の vocab）の対象外である（レシピ本体の越境 note も「転記は機械語彙では弾かず質的判定に委ねる」と明記）。本観点が転記の検出を専任で担う。曖昧表現マーカーの出現検出（観点2の機械側）とは別物として扱う。
>
> 注（正当な引用との区別）: 計画を読むのに最小限必要な文脈（テスト対象の主題を一言添える等）と、要件文をまるごと写した二重管理とは別である。どちらとも決めかねる境界例は逸脱と断定せず fail-open（pass）に倒す。

### 5. トレーサビリティの質（意味的な紐付けとカバレッジの穴）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）・[P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（要件は ID 参照）。

各テスト項目が対応要件 ID／テストレベルに**意味的に**紐付いているか（形式的な対応でなく）。あわせて要件側のカバレッジ（スコープ対象の要件にテスト項目の穴が無いか）を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各テスト項目の「対応要件/テストレベル」が形式的でなく意味的に妥当か（その要件/レベルが検証する内容と、テスト項目が実際にカバーする内容が一致しているか）。スコープ対象の要件に、紐付くテスト項目が無い穴（テスト漏れ）が見落とされていないか | 各テスト項目の対応要件/テストレベルが、その項目が何を検証するかを実際に説明している。スコープ対象の要件がテスト項目でカバーされ、漏れは明示されている | 整合しない対応の原文（テスト項目と対応要件/テストレベルの行）を引き、何と何が食い違うかを示す。スコープ対象なのにテスト項目が無い要件 ID を示す |

> **注（過大主張の禁止・F5 の教訓）**: **対応要件/テストレベル列の空セルそのものの検出（孤立テスト項目）は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当**であり、本観点に重複させない。本観点は ID が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた対応、形式上は埋まっているが意味的に無関係な対応）と、**スコープ対象の要件側から見たカバレッジの穴**（要件一覧との突き合わせを要する文脈判断）を見る。空セル検出を rubric の仕事として主張しない（cycle-12/F5 の教訓＝「rubric が機械の仕事を主張しない」）。
>
> 注（境界は fail-open）: 紐付けが妥当か流用かが紛らわしい境界例は逸脱と断定せず fail-open（pass）に倒す。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **「計画レベルの正当な記述 vs ケース具体値の先取り」を分ける一般ヒューリスティックは存在しない。** 計画の例示がどこまで具体的なら「計画として十分」で、どこからが「ケース仕様の先取り」かを分ける一般閾値は無い。境界例（具体的すぎる例示・ケース具体値の混入のどちらとも決めかねるもの）は、逸脱と断定せず **fail-open（pass）**に倒して人間に委ねる。判断を盛らない。
- **「対象外が十分にスコープを否定しているか」「終了基準が測定可能か」の定量基準は無い。** どこまで具体的なら十分かは文脈依存である。読み取れない境界例は逸脱と断定せず pass に倒す。
- **テスト文書の階層境界（戦略／計画／設計仕様／ケース仕様／手順仕様）そのものは裁定しない。** この階層は P7／P8（検出補助・機械強制しない）由来であり、各層の責務割当ては規格（IEEE 829／ISO/IEC/IEEE 29119-3／ISTQB v4）に由来する。「どこまでが計画で、どこからがケース仕様／設計仕様か」の線引きはレシピ本体（[`../waterfall/test/test-plan.md`](../waterfall/test/test-plan.md)）が引いた境界を**前提として**判定する。境界の妥当性そのものは問わない（参照: [P7](../principles/granularity-axis.md#p7--p8-テスト文書の階層と戦略計画の分離検出補助)）。
- **空セルの検出は機械の担当であり rubric は過大主張しない（F5）。** トレース表の空セル（孤立テスト項目）は [`../scripts/check_traceability.py`](../scripts/check_traceability.py) が決定論で検出する。本ルーブリック（観点5）は埋まっているセルの**意味的妥当性とカバレッジの穴**のみを見る（cycle-12/F5 の教訓）。

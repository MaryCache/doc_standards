> **原則参照**: [`../principles/granularity-axis.md`](../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義せず参照する（制約 S3）。
> **責務対照**: [`../principles/responsibility-map.md`](../principles/responsibility-map.md) の「工程をまたぐ受け皿: 実装計画」を参照（含む＝作業の単位・作る順番・順番の理由・各作業が実現する設計要素／含まない＝設計の決定・要件の再記述・進み具合の記録／隣接＝設計書 → 実装計画 → 実装）。

## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**実装計画**を対象とする。

実装計画は design-doc / rfc と同じく **vocab を空にした**。計画の逸脱（計画の中で設計を初めて決める・順番に理由がない）は文脈の判定であり、特定の禁止トークンの部分一致では拾えない。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`作業の順番` / `順番の理由` / `トレーサビリティ`）の欠落・**トレース表の空セル（対応する設計列が空＝孤立作業）**の検出。vocab は空で、禁止語チェックは pass を返すだけ。 |
| 質的（本ルーブリック・**主判定**） | LLM ＋人間 | 計画が設計を初めて決めていないか・順番の理由が依存とリスクで説明されているか。 |

機械判定で済む項目（必須見出しの欠落・トレース表の空セルそのものの検出）は**本ルーブリックに重複させない**。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「作業の説明として必要な記述」と「設計の決定」を分ける一般ヒューリスティックは無い（§4-D）。迷ったら逸脱と決めつけない。
- 「順番の理由として十分か」の定量基準は無い。境界例は逸脱と断定せず pass に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. 計画の中で設計を初めて決めていないか（設計の決定は設計書へ戻す）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（What/Why と How の分離）・[P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計は根拠に紐付く）。

実装計画は設計書にある要素を作る順番に並べる文書である。**計画の中で初めて設計の中身（データ構造・方式・振る舞いの選択）が決まっていたら**、その決定は設計書に書かれていない。決定を納品物である設計書へ戻す。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 作業の説明に、設計書に無い設計の決定（構造・方式・振る舞いの選択とその理由）が初めて書かれていないか | 作業の内容が設計書の要素（トレーサビリティの「対応する設計」）を指すだけで、計画を読まないと設計が分からない状態になっていない | 設計を決めている原文（作業の節見出し＋該当行）を引き、設計書のどこにも無いことを示す |

> 注（機械判定との分担）: 「対応する設計」が空の作業（孤立作業）は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当であり、本観点に重複させない。本観点は**設計への対応が書かれていても、計画の本文が設計を新たに決めている**ケースを見る。
>
> 注（境界は fail-open）: 作業を説明するための記述と設計の決定の境界は文脈依存（§4-D）。決めかねる境界例は pass に倒す。

### 2. 順番の理由が依存・リスクで説明されているか

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（根拠は必須）。

`順番の理由` が、**依存**（先に出来ていないと次が作れない）か**リスク**（不確実なものを早く潰す、壊れると戻せないものを先に固める）で説明されているか。「やりやすいから」「なんとなく」だけの理由、または作業の並びをただ繰り返した文は、理由になっていない。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 順番の理由が依存かリスクで説明されているか。「やりやすい順」「作業の再掲」で済ませていないか | 隣り合う作業の順番について、何がどの作業に依存するか、またはどのリスクを先に潰すのかが書かれている | 理由になっていない原文（`順番の理由` の該当行）を引く |

> 注（機械判定との分担）: 節 `順番の理由` の**有無それ自体**は機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）の担当であり、本観点に重複させない。本観点は節はあるが中身が理由になっていないケースを見る。
>
> 注（境界は fail-open）: 作業が1つだけなど、順番の理由が本質的に要らない計画もある。決めかねる境界例は pass に倒す。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **「作業の説明として必要な記述」と「設計の決定」を分ける一般ヒューリスティックは存在しない。** 読み取れない境界例は逸脱と断定せず **fail-open（pass）**に倒して人間に委ねる。
- **作業の分け方や順番の妥当性そのもの（本当にその順が最善か）は裁定しない。** 本ルーブリックは理由が依存・リスクで書かれているかだけを見る。
- **進み具合の記録（完了・着手中）は機械でも rubric でも裁定しない。** 責務対照表が「含まない（課題管理へ）」と定める境界であり、計画の版の履歴や前提の説明として正当に書かれうる。
- **空セルの検出は機械の担当であり rubric は過大主張しない（F5）。** トレース表の空セル（孤立作業）は [`../scripts/check_traceability.py`](../scripts/check_traceability.py) が決定論で検出する。

## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**テスト手順仕様（Test Procedure Specification）**を対象とする。テスト手順仕様の核心的な痛みは「**手順に期待結果の合否判定（What to expect）が混入する**」（実行↔判定の隣接境界・構造判定）・「**前提・セットアップが再現不能なほど曖昧**」・「**実行手順の粒度がずれている／ステップ順で再現できない**」であり、その文字列照合では捕まえられない逸脱を見るのが主眼である。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`前提` / `実行手順` / `トレーサビリティ`）の欠落・禁止語（判定基準混入マーカー3語: `正しく表示` / `正しく動作` / `適切に処理`）の単純な出現・トレーサビリティ表の空セル〔孤立手順＝対応ケース ID 欠落〕（[`../scripts/check_traceability.py`](../scripts/check_traceability.py)）など、文字列・表構造で判定できる項目 |
| 質的（本ルーブリック） | LLM ＋人間 | 前提の再現可能性（具体性）・実行手順の粒度とステップ順の再現性・禁止語3語に当たらない言い換えで紛れた判定基準の混入・設計意図/テスト条件の逆流・ケース内容の逐語転記・トレーサビリティの意味的妥当性とカバレッジなど、文脈判断が要る項目 |

機械判定で済む項目（必須見出しの欠落、判定基準マーカー3語の単純な出現、トレーサビリティ表の空セル）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。ここが見るのは「節はあるが前提が再現不能なほど曖昧」「ステップ順で再現できない／粒度がずれている」「3語に当たらない言い換えで判定基準が手順に紛れている」「特定語ではなく構造としてケース内容が転記されている」類の、文字列照合・表構造では捕まえられない逸脱だけである。

なお技術スタック名・製品名・`SQL`・ツール名（JUnit 等）は、テスト手順仕様では正当な記述になりうる（前提・セットアップ／実行環境の記述）ため**機械 vocab で弾かず本ルーブリックの文脈判断に委ねる**（cycle-8 以降の WF スライス踏襲）。とりわけ `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「手順仕様にふさわしい操作記述」と「期待結果の判定基準の混入」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例（操作に付随する観測の言及か・合否判定の混入か紛らわしいもの）で迷ったら逸脱と決めつけない。
- 「前提が再現可能なほど具体的か」「実行手順の粒度が適切か」の定量基準は無い（§4-D）。境界例は逸脱と断定せず pass に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P6/P7 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行、またはステップ番号＋該当操作）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. 前提・セットアップの質（開始状態・環境が再現可能に具体的か）

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（検証可能性は工程を貫く不変量）。

`前提・セットアップ` 節が、誰が実行しても同じ初期条件から始められる**再現可能な具体性**を持つか。開始状態（初期データ・初期値・認証状態・対象バージョン）が、第三者が再現できる形で書かれているかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 前提・セットアップが再現可能な具体性を持つか。開始状態・環境が "特になし" や曖昧な表現（「環境を整える」「データを準備する」など何をどの値にするか不明）で逃げていないか | 前提が初期データ・初期値・認証状態・対象バージョン等を具体値で示し、第三者が同じ初期条件を再現できる | 再現不能な前提の原文（節見出し＋該当行。例: 「環境を整える」「適宜データを準備する」など具体性を欠く記述）を引く |

> 注（機械判定との分担）: 必須見出し `前提` の**有無それ自体**は機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが中身が再現不能なほど曖昧**」（"特になし"・具体値を欠く前提）ケースである。これは test-plan の `スコープ`（"特になし" で逃げない）を rubric で見るのと同型。

### 2. 実行手順の質（ステップ順で再現可能か・粒度が適切か）

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（検証可能性）。検出補助: [P5](../principles/granularity-axis.md#p5-数値精度は工程マーカーである)（数値精度は工程マーカー）。

`実行手順` が、第三者が同じ順序で再現できる**ステップ順の操作**になっているか。1ステップの粒度が抽象的すぎる（操作が一意に再現できない）／具体的すぎる（自明な所作まで刻む）でないか・複数の独立操作を1ステップに詰めて順序が曖昧になっていないかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各ステップが一意に再現できる単一の働きかけになっているか。抽象的すぎて操作が再現できない（「適宜操作する」「必要な処理を行う」）／複数の独立操作を1ステップに詰めて順序が曖昧／自明な所作まで刻みすぎ、になっていないか。順序依存があるとき順序が明示されているか | 各ステップが再現可能な単一の操作（働きかけ）に絞られ、順序が一意に決まる。粒度が再現に必要十分（抽象すぎず具体すぎず） | 再現不能な手順の原文（ステップ番号＋該当操作。例: 「適宜操作する」、複数操作を詰めた1ステップ）を引く |

> 注（機械判定との分担）: 必須見出し `実行手順` の**有無それ自体**は機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが中身の粒度がずれている／ステップ順で再現できない**」ケースである。
>
> 注（粒度の境界例は fail-open）: 「1ステップが過大か」「どこまで刻めば十分か」の定量基準は無い（§4-D）。境界例は逸脱と断定せず pass に倒す。

### 3. 判定基準の混入（実行 ↔ 判定の隣接境界・このスライスの肝）

参照原則: [P7](../principles/granularity-axis.md#p7--p8-テスト文書の階層と戦略計画の分離検出補助)（テスト文書の階層＝計画→設計仕様→ケース仕様→手順仕様。階層を飛び越えない）。

手順仕様に**各操作の期待結果の合否判定（What to expect）**が書かれていないか（それはケース仕様＝[`../waterfall/test/test-case-spec.md`](../waterfall/test/test-case-spec.md) の担当）。手順仕様は「どう実行するか＝操作・ステップ順」と「その前提」までであり、観測結果の合否判定はケース仕様へ ID 参照する。あわせて、設計意図・テスト条件（抽象・どう網羅するか＝設計仕様）の逆流も上流越境として見る。これは **手順仕様（実行＝How to run）↔ ケース仕様（判定＝What to expect）の隣接境界**である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 手順に各操作の期待結果の合否判定（「…されることを確認」型の判定基準・観測値の合否＝What to expect）が混入していないか。禁止語3語に当たらない言い換え（「正常に登録される」「期待どおり遷移する」等の合否判定）で判定基準が紛れていないか。設計意図・テスト条件（抽象・どう網羅するか＝設計仕様）が逆流していないか | 手順が操作（実行）と前提に留まり、期待結果の合否判定はケース仕様へ委ねられ（ケース ID 参照）、設計意図・テスト条件は設計仕様に留まっている | 判定基準が手順に混入した原文（ステップ番号＋「…されることを確認」型の合否判定）、または設計意図/テスト条件が逆流した原文を引く |

> 注（機械判定との分担）: 判定基準混入マーカー3語（`正しく表示`・`正しく動作`・`適切に処理`）の**単純な出現**は機械判定（[`../scripts/`](../scripts/) の禁止語 vocab）の担当であり、本観点に重複させない。本観点が見るのは、**3語に当たらない言い換え**（「正常に登録される」「期待どおり遷移する」など別語に化けた合否判定）で紛れた判定基準の混入、および**設計意図・テスト条件の逆流**（構造判定）である。
>
> 注（境界は fail-open）: 操作に付随する観測の言及（「画面が遷移する」を操作の到達点として書く）と、期待結果の合否判定（What to expect＝そこで合否を下す）とを分ける一般ヒューリスティックは無い（§4-D）。どちらとも決めかねる境界例は逸脱と断定せず pass に倒す。線引き自体はレシピ本体（[`../waterfall/test/test-procedure-spec.md`](../waterfall/test/test-procedure-spec.md)）が引いた境界を前提とする。

### 4. ケース転記アンチパターン（転記か・ID 参照か）

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（テスト文書は ID 参照する・文言を転記しない）。

手順やトレーサビリティに**ケース内容（期待結果の文言・入力値）が構造として転記**されていないか。ケースは ID で参照されているかを見る。転記は二重管理と矛盾の温床になる（同期負債）。これは test-case-spec／test-design-spec の要件転記観点と同型である（参照先がケース仕様である点が異なる）。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 手順／トレーサビリティにケース内容（期待結果の文言・具体的入力値）が**構造として転記**されていないか（特定語ではなく、ケースをそのまま写した内容になっていないか）。ケースは ID で参照されているか | 手順・トレーサビリティがケースを「対応ケース ID」で参照し、期待結果の文言・入力値は写されていない | ケース内容が逐語転記された原文（ステップ番号または表行＋該当箇所）を引き、対応するケース ID を示す |

> 注（機械判定との分担）: 転記は**特定の禁止語では弾けない構造の問題**であり、機械語彙（[`../scripts/`](../scripts/) の vocab）の対象外である（レシピ本体の越境 note も「転記は機械語彙では弾かず質的判定に委ねる」と明記）。本観点が転記の検出を専任で担う。判定基準マーカーの出現検出（観点3の機械側）とは別物として扱う。
>
> 注（正当な引用との区別）: 手順を読むのに最小限必要な文脈（操作の主題を一言添える等）と、ケースをまるごと写した二重管理とは別である。どちらとも決めかねる境界例は逸脱と断定せず fail-open（pass）に倒す。

### 5. トレーサビリティの質（意味的な紐付けとカバレッジの穴）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）・[P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（ID 参照）。

各実行手順が対応ケース ID に**意味的に**紐付いているか（形式的な対応でなく）。あわせてケース側のカバレッジ（実行すべきケースに、対応手順の穴が無いか）を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各手順の「対応ケース ID」が形式的でなく意味的に妥当か（その手順が実際に実行する操作と、対応ケースが定める内容が一致しているか）。実行すべきケースに、紐付く手順が無い穴（実行漏れ）が見落とされていないか | 各手順の対応ケース ID が、その手順が何を実行するかを実際に説明している。実行対象のケースが手順でカバーされ、漏れは明示されている | 整合しない対応の原文（手順と対応ケース ID の行）を引き、何と何が食い違うかを示す。実行対象なのに手順が無いケース ID を示す |

> **注（過大主張の禁止・F5 の教訓）**: **対応ケース ID 列の空セルそのものの検出（孤立手順）は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当**であり、本観点に重複させない。本観点は ID が**書かれているが内容が合っていない**手順（流用・コピペで実態とずれた対応ケース ID、形式上は埋まっているが意味的に無関係な対応）と、**実行すべきケース側から見たカバレッジの穴**（ケース一覧との突き合わせを要する文脈判断）を見る。空セル検出を rubric の仕事として主張しない（cycle-12/F5 の教訓＝「rubric が機械の仕事を主張しない」）。
>
> 注（境界は fail-open）: 紐付けが妥当か流用かが紛らわしい境界例は逸脱と断定せず fail-open（pass）に倒す。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **「手順仕様レベルの正当な操作記述 vs 期待結果の判定基準の混入」を分ける一般ヒューリスティックは存在しない。** 操作に付随する観測の言及がどこまでなら「実行（How to run）」で、どこからが「合否判定（What to expect＝ケース仕様）」かを分ける一般閾値は無い。境界例（観測の言及・合否判定の混入のどちらとも決めかねるもの）は、逸脱と断定せず **fail-open（pass）**に倒して人間に委ねる。判断を盛らない。線引き自体はレシピ本体が引いた境界を前提とする。
- **「前提が再現可能なほど具体的か」「実行手順の粒度が適切か」の定量基準は無い。** どこまで具体的なら十分かは文脈依存である。読み取れない境界例は逸脱と断定せず pass に倒す。
- **テスト文書の階層境界（戦略／計画／設計仕様／ケース仕様／手順仕様）そのものは裁定しない。** この階層は P7／P8（検出補助・機械強制しない）由来であり、各層の責務割当ては規格（IEEE 829／ISO/IEC/IEEE 29119-3／ISTQB v4）に由来する。「どこまでが手順仕様で、どこからがケース仕様／設計仕様か」の線引きはレシピ本体（[`../waterfall/test/test-procedure-spec.md`](../waterfall/test/test-procedure-spec.md)）が引いた境界を**前提として**判定する。境界の妥当性そのものは問わない（参照: [P7](../principles/granularity-axis.md#p7--p8-テスト文書の階層と戦略計画の分離検出補助)）。
- **空セルの検出は機械の担当であり rubric は過大主張しない（F5）。** トレース表の空セル（孤立手順）は [`../scripts/check_traceability.py`](../scripts/check_traceability.py) が決定論で検出する。本ルーブリック（観点5）は埋まっているセルの**意味的妥当性とカバレッジの穴**のみを見る（cycle-12/F5 の教訓）。

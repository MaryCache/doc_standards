# テストケース仕様 質的判定ルーブリック — ウォーターフォール テスト（ケース仕様）

> **レイヤー**: 第2層レシピの質的判定（機械判定の補完）
> **原則参照**: [`../principles/granularity-axis.md`](../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義せず参照する（制約 S3）。
> **責務対照**: [`../principles/responsibility-map.md`](../principles/responsibility-map.md) のテスト仕様行を参照（テスト戦略・計画・設計仕様・ケース仕様・手順仕様のうち、本レシピは**ケース仕様**＝テスト条件＋具体値を担う）。
> **レシピ本体**: [`../waterfall/test/test-case-spec.md`](../waterfall/test/test-case-spec.md)。観点はこのレシピの節（テスト観点 / テストケース / トレーサビリティ）に揃える。本レシピが担うのは**ケース仕様レベル**——テスト条件に対して具体値（事前条件・入力・操作・期待結果）を確定した層——に限り、計画レベル（戦略・体制・スケジュール）・設計仕様レベルの高レベルテスト条件のみの記述・手順仕様レベルの実行順の詳細は対象外である。

## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**テストケース仕様（ケース仕様）**を対象とする。テストケースの粒度逸脱——とりわけ**要件転記アンチパターン**と**期待結果の検証可能性**——のうち、文字列照合では捕まえられない侵入を見るのが主眼である。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`テストケース` / `トレーサビリティ`）の欠落・禁止語（曖昧表現マーカー3語）の単純な出現など、文字列で判定できる項目 |
| 質的（本ルーブリック） | LLM ＋人間 | 言い換えで紛れた検証不能な期待結果・要件文の構造的な転記・1ケースの過大な粒度・トレーサビリティの意味とカバレッジの穴など、文脈判断が要る項目 |

機械判定で済む項目（必須見出しの欠落、曖昧表現マーカーの単純な出現）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。ここが見るのは「見出しはあるが中身の粒度がずれている」「禁止語に当たらない言い換えで検証不能な期待結果が紛れている」「特定語ではなく構造として要件が転記されている」類の、文字列照合では捕まえられない逸脱だけである。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「ケース仕様にふさわしい具体値」と「過大な粒度／高レベル条件の混入」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例（1ケースが過大かどうか・Just Barely Good Enough の十分性）で迷ったら逸脱と決めつけない。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P1/P7/P10 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どのケース ID の・どの要素か」が分かる単位で引く（ケース ID ＋該当行／該当要素）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. 期待結果の検証可能性（測定可能／観測可能か）

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（検証可能性は工程を貫く不変量）。

各ケースの期待結果が、合否を一意に決められる測定可能／観測可能な記述になっているか。観測できる値・状態・コード・件数・しきい値との比較で書かれているかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各ケースの期待結果が測定可能／観測可能か。曖昧表現マーカーの語そのものではなく、**言い換えで紛れた曖昧さ**や**主観的合否**（「使いやすい」「十分速い」「自然な挙動」など測定基準を持たない期待結果）で逃げていないか | 各ケースの期待結果が、観測できる値・状態・コード・件数・しきい値比較で書かれ、第三者が同じ判定に到達できる（判定者の主観に依存しない） | 検証不能な期待結果の原文（ケース ID ＋期待結果の該当行。例: 「使いやすく表示される」「十分速く応答する」「自然に遷移する」）を引く |

> 注（機械判定との分担）: 曖昧表現マーカー3語（`正しく表示`・`正しく動作`・`適切に処理`）の**単純な出現**は機械判定（[`../scripts/`](../scripts/) の禁止語 vocab）の担当であり、本観点に重複させない。本観点が見るのは、**禁止語に当たらない言い換え**（「使いやすい」「十分速い」「自然な」など別語に化けた測定不能な期待結果）や、語は具体的でも合否が主観に依存する書き方である。
>
> 注（NFR ケース）: 性能・可用性などの NFR ケースでも期待結果は観測値で書く（例: しきい値との比較が示されている）。値はあるが測定の前提（分位点・負荷条件など）を欠いて合否が一意に決まらない期待結果も、検証不能側として本観点で見る。ただし「どこまで前提を書けば十分か」の定量基準は無いため、境界例は fail-open（§4-D）。

### 2. 要件転記アンチパターン（転記か・変換か）

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（テスト文書は要件を「何をすべきか」から「どう確認するか」へ変換し、要件文を転記しない・要件は ID 参照）。

要件文を逐語コピーせず、「どう確認するか」（事前条件・入力・操作・期待結果）へ**変換**できているか。要件は ID 参照になっているかを見る。転記は二重管理と矛盾の温床になる（同期負債）。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| ケースやトレーサビリティに要件文（What の文言・Why の説明）が**構造として転記**されていないか（特定語ではなく、要件をそのまま写した内容になっていないか）。要件は ID で参照され、ケースは「どう確認するか」へ変換されているか | 各ケースが事前条件・入力・操作・期待結果という確認手段へ変換され、要件は「対応要件 ID」で参照される。要件の文言・理由はケース／トレーサビリティに写されていない | 要件文が逐語転記された原文（ケース ID または表行＋該当箇所）を引き、対応する要件 ID を示す。要件の Why（理由）がケースに写り込んでいる原文を引く |

> 注（機械判定との分担）: 要件転記は**特定の禁止語では弾けない構造の問題**であり、機械語彙（[`../scripts/`](../scripts/) の vocab）の対象外である（レシピ本体の越境 note も「転記は機械語彙では弾かず質的判定に委ねる」と明記）。本観点が転記の検出を専任で担う。曖昧表現マーカーの出現検出（観点1の機械側）とは別物として扱う。
>
> 注（正当な引用との区別）: ケースを読むのに最小限必要な文脈（要件の主題を一言添える等）と、要件文をまるごと写した二重管理とは別である。どちらとも決めかねる境界例（要件の言い換えが「変換」か「転記」か紛らわしいもの）は逸脱と断定せず fail-open（pass）に倒す。

### 3. 粒度（過大なケース・階層の混同）

参照原則: [P7](../principles/granularity-axis.md#p7--p8-テスト文書の階層と戦略計画の分離検出補助)（テスト文書の階層＝計画→設計仕様→ケース仕様→手順仕様。設計仕様＝テスト条件＋高レベルケース／具体値なし、ケース仕様＝具体値）。検出補助: [P5](../principles/granularity-axis.md#p5-数値精度は工程マーカーである)（数値精度は工程マーカー）。

1ケースが過大（複数の検証を1ケースに詰める／実行に過大な時間がかかり1件として観測しきれない）でないか。テスト条件（高レベル＝設計仕様レベル）と具体値ケース（ケース仕様レベル）を混同していないかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 1ケースが「1件として観測可能」な粒度に収まっているか（複数の独立した検証を1ケースに詰めていないか・実行に過大な時間がかかる肥大シナリオになっていないか）。具体値を欠いた高レベルのテスト条件のみがテストケース節に置かれていないか（設計仕様レベルの混入）。逆に、ケース具体値が計画・戦略の宣言と混在していないか | 各ケースが単一の観測単位（1つの確認点）に絞られ、事前条件・入力・操作・期待結果が具体値で確定している。高レベルのテスト条件はテスト観点節に置かれ、テストケース節には具体値がある | 過大粒度の原文（ケース ID ＋複数検証を詰めた箇所、または肥大シナリオの該当行）を引く。具体値を欠いた高レベル条件のみがテストケース節にある原文を引く |

> 注（機械判定との分担）: 必須見出し `テストケース` の**有無それ自体**は機械判定（[`../scripts/`](../scripts/) の必須見出し欠落チェック）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが中身の粒度がずれている**」（1ケース過大・高レベル条件の混入）ケースである。
>
> 注（粒度の境界例は fail-open）: 「1ケースが過大か」「具体値が十分か（Just Barely Good Enough）」の定量基準は無い（§4-D）。責務対照表は「粒度過大（1ケース 3 日超）」を逸脱マーカーの一例として挙げるが、これは目安であって厳密な閾値ではない。境界例は逸脱と断定せず pass に倒す。
>
> 注（計画・手順との分離）: 計画事項（戦略・体制・スケジュール・スコープ宣言）や実行の逐次手順（環境構築の手順・反復順序）がケースに混入していたら、本観点の「階層の混同」として見る（移送先はそれぞれ計画仕様・手順仕様）。

### 4. トレーサビリティの質（意味的な紐付けとカバレッジの穴）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）・[P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（要件は ID 参照）。

各ケースが要件 ID に**意味的に**紐付いているか（形式的な対応でなく）。あわせて要件側のカバレッジ（要件 → ケースの逆引き）に穴がないか——テスト漏れ——を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各ケースの「対応要件 ID」が形式的でなく意味的に妥当か（その要件が検証する内容と、ケースが実際に確認する内容が一致しているか）。要件 → ケースの逆引きで、ケース0件の要件（テスト漏れ）が見落とされていないか | 各ケースの対応要件 ID が、そのケースが何を検証しているかを実際に説明している。逆引き表で各要件が最低1ケースでカバーされ、未充足の要件は明示されている | 整合しない対応の原文（ケース ID と対応要件 ID の行）を引き、何と何が食い違うかを示す。逆引きで穴になっている要件 ID（カバーするケースが実質ない要件）を示す |

> 注（機械判定との分担）: 「対応要件 ID」列が空のケースの検出（孤立ケース＝根拠のないテスト）は機械判定の担当範囲。本観点は ID が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた対応要件 ID、形式上は埋まっているが意味的に無関係な対応）と、**逆引きの穴**（要件側から見たカバレッジ欠落）を見る。
>
> 注（カバレッジの穴）: 逆引き表で「ケース0件」と明示された要件の単純な検出は記述の有無の問題に近いが、**逆引き表に現れていない要件**（そもそも逆引きの対象から漏れた要件）の発見は要件一覧との突き合わせを要する文脈判断であり、本観点で見る。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **「Just Barely Good Enough（十分性）」の定量基準は無い。** 1ケースがどこまで具体値を持てば「ケース仕様として十分」か、どこからが「過大」かを分ける一般閾値は存在しない。責務対照表の「1ケース 3 日超」等は目安であり、厳密な境界線ではない。粒度の境界例（過大／不足のどちらとも決めかねるもの）は、逸脱と断定せず **fail-open（pass）**に倒して人間に委ねる。判断を盛らない。
- **テスト文書の階層境界（計画／設計仕様／ケース仕様／手順仕様）そのものは裁定しない。** この階層は P7／P8（検出補助・機械強制しない）由来であり、各層の責務割当ては規格（IEEE 829／ISO/IEC/IEEE 29119-3）に由来する。「どこまでがケース仕様で、どこからが手順仕様／設計仕様か」の線引きはレシピ本体（[`../waterfall/test/test-case-spec.md`](../waterfall/test/test-case-spec.md)）が引いた境界を**前提として**判定する。境界の妥当性そのものは問わない（参照: [P7](../principles/granularity-axis.md#p7--p8-テスト文書の階層と戦略計画の分離検出補助)）。

## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**詳細設計（処理）**を対象とする。処理詳細の核心的な痛みは、詳細設計に特有の**両端の逸脱**——①コード逐語まで降りる ghost document（厚すぎ）と②分岐・エラー条件・性能制約が抜けた実質空（薄すぎ）——であり、いずれも**特定の禁止語では弾けない構造・量の問題**である。その文字列照合では捕まえられない逸脱を見るのが主眼である。対をなすデータ詳細ルーブリック（[`./detailed-design-data.md`](./detailed-design-data.md)）が物理データの過不足を見るのに対し、本ルーブリックは**処理の過不足**を見る。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`モジュール構造` / `処理仕様` / `トレーサビリティ`）の欠落・禁止語（業務理由転記マーカー）の出現・トレース表の空セル（孤立設計要素）など、文字列・表構造で判定できる項目 |
| 質的（本ルーブリック） | LLM ＋人間 | 処理設計の粒度逸脱（薄すぎ＝実質空／厚すぎ＝ghost document）・クラス構造とメソッド仕様の設計レベルの妥当性・トレーサビリティの意味・実装可能性など、文脈・量の判断が要る項目 |

機械判定で済む項目（必須見出しの欠落、業務理由転記マーカーの出現、トレース表の空セル）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。とりわけ **`SQL`** は製品名 PostgreSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出）。よって SQL 全文の混入（ghost document）は機械 vocab でなく**本ルーブリックの観点3**が見る。技術名・製品名・言語名・メソッド名の出現自体は処理仕様で正当であり弾かない。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「正当な処理設計」と「不当なコード逐語（ghost document 化）」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。同様に「設計レベルに足る粒度」と「実質空（薄すぎ）」の境界も一意でない。境界例で迷ったら逸脱と決めつけない。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P1/P3 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

> 処理が主役の工程である。本ルーブリックが逸脱として見るのは、(a) クラス・モジュールの静的構造が設計レベルで書けているか・コード逐語でないか（観点1）、(b) メソッド仕様（引数/戻り値/エラー処理）・処理ロジック・IPO が設計レベルで書けているか（観点2）、(c) **コード逐語まで降りた ghost document＝厚すぎ**（観点3＝詳細設計特有の両端の一端）、(d) **分岐・エラー条件・性能制約が未記述の実質空＝薄すぎ**（観点4＝両端の他端）、(e) トレースが形式的でなく意味を持つか（観点5）であり、加えて業務上の Why の混入（P2）や基本設計で既出の機能スコープ・UI レイアウトの再記述といった「上流の越境」を持ち込んでいないかを横断的に見る。
>
> 注（業務 Why の機械/rubric 分担）: 禁止語 `なぜなら業務`（上位 Why の定型字面）の**単純な出現**は機械判定（[`../scripts/`](../scripts/)）の担当であり本ルーブリックに重複させない。本ルーブリックが横断的に見るのは、**その定型字面に当たらない形で言い換え・別表記で混入した業務 Why**（P2 違反）である（対をなすデータ詳細 [`./detailed-design-data.md`](./detailed-design-data.md) の同分担と対称）。

### 1. クラス・モジュール構造の質（静的構造が設計レベルか・コード逐語でないか）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（How の帰属。コード逐語は実装への越境）・[P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠）。

クラス・モジュールの静的構造（責務分割・依存方向・抽象境界）が、開発者が実装に着手できる設計レベルで書けているかを見る。コード逐語（変数宣言・boilerplate）に降りておらず、かつ責務分割が曖昧でないかの**両面**を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| クラス・モジュールの責務分割と依存方向が設計レベルで明示され、コード逐語（変数宣言・boilerplate）に降りていないか。循環依存・責務の混在が放置されていないか | 各クラス/モジュールに責務（1〜2行）と依存方向が示され、抽象境界（ポート/IF）が必要箇所で示される。変数宣言・boilerplate の逐語は無い | 責務が曖昧/依存方向が不明な構造の原文、またはコード逐語に降りた構造記述の原文（該当節・該当行）を引く |

### 2. 処理仕様の質（メソッド仕様＝引数/戻り値/エラー処理・ロジック/IPO が設計レベルか）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠）・[P5](../principles/granularity-axis.md#p5-数値精度は工程マーカーである)（数値精度は工程マーカー＝性能制約の厳密値は詳細設計で正当）。

メソッド仕様（引数・戻り値・例外/エラー処理）と処理ロジック・IPO が、追加の設計判断なしに実装できる設計レベルで書けているかを見る。厳密数値（p95 800ms 等）の出現そのものは詳細設計工程のマーカーとして正当（P5）であり、本観点は厚薄ではなく**設計レベルの妥当性**（入出力・エラー処理・ロジックが揃い意味を持つか）を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各メソッドに引数・戻り値・エラー処理が示され、処理ロジック・IPO が設計レベルで書けているか（実装者が追加の設計判断なしに着手できるか） | 主要メソッドに引数・戻り値・例外/エラー処理が記述され、処理（Input→Process→Output）が追える。性能制約は厳密数値で示してよい（P5） | 引数/戻り値/エラー処理が欠けたメソッド仕様の原文、または処理ロジックが意味をなさない記述の原文（該当節・該当行）を引く（薄すぎは観点4と相互参照でよい） |

> 注: `p95 800ms`・`3600ms@p99` 等の厳密数値の**出現そのものは逸脱でない**（詳細設計工程で確定するのが正当・P5）。本観点は数値の有無ではなく、メソッド仕様・ロジックの設計レベルの妥当性を見る。

### 3. ghost document（厚すぎ）＝コード逐語混入

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（How の帰属。厚すぎ＝実装コード逐語＝ghost document は How が下位工程〔実装〕へ越境した状態）。

詳細設計特有の**両端の一端**。処理仕様・クラス構造が**コード逐語**（SQL 全文〔`SELECT ... FROM ...` の本文〕・変数宣言・boilerplate の逐語・単純 CRUD の全ステップ）にまで降り、設計書が「逐語のコード」と化していないかを見る。これは**機械では厚みを測れない構造判定**であり（とりわけ `SQL` は製品名 PostgreSQL・MySQL の部分文字列で機械が誤爆する）、本観点が担う。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 処理仕様・クラス構造に、コード逐語（SQL 全文・変数宣言・boilerplate・単純 CRUD の全ステップ）が混入し ghost document 化していないか | メソッド仕様・処理ロジックは設計レベル（入出力・分岐・エラー条件・性能制約）に留まり、SQL 全文・変数宣言・boilerplate の逐語は無い。DB アクセスはデータ詳細のテーブル定義を ID 参照する | コード同等の逐語（フェンス外に展開された SQL 全文・変数宣言・boilerplate・CRUD 全ステップ）の原文（該当節・該当行）を引く |

> 注（SQL は機械でなく本観点で見る理由）: `SQL` は製品名 PostgreSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出）。よって SQL 全文の混入は機械 vocab に入れず本観点で見る。製品名としての `PostgreSQL` 等の出現は逸脱でなく、逸脱は実際の SQL クエリ本文（`SELECT ... FROM ...`）の逐語展開である。境界例は fail-open（pass）。

### 4. 実質空（薄すぎ）＝分岐・エラー条件・性能制約が未記述

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠・実装に必要な決定の確定）。

詳細設計特有の**両端の他端**。処理仕様が**薄すぎ**て、メソッド名と一行説明だけで分岐条件・エラー条件・性能制約が書かれておらず、開発者が実装判断できない状態になっていないかを見る。これも**機械では量を測れない構造判定**であり本観点が担う。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 処理仕様に、判断の余地がある箇所の分岐条件・エラー条件・性能制約が記述され、開発者が実装判断できるか（実質空＝メソッド名と一行説明だけで判断材料が無い状態になっていないか） | 分岐（条件と各経路）・エラー条件（例外/失敗時の挙動）・必要な性能制約が記述され、実装者に設計判断を押し戻していない | 分岐・エラー条件・性能制約が未記述で実装判断ができない処理仕様の原文（メソッド名と一行説明だけの箇所等）を引く（観点2の設計レベル妥当性と重なる場合は相互参照でよい） |

> 注（両端の関係）: 観点3（厚すぎ＝ghost document）と観点4（薄すぎ＝実質空）は詳細設計特有の**両端**であり、どちらも構造・量の判定で機械では測れない。一つの文書が観点3と観点4を同時に犯すこともある（ある節はコード逐語・別の節は実質空）。各々を独立に見る。

### 5. トレーサビリティの質（形式でなく意味を持つか）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）。

**空セルそのものの検出は機械 [`../scripts/check_traceability.py`](../scripts/check_traceability.py)（孤立設計要素〔対応 ID 欠落〕の決定論検出）の担当**であり、本観点はそれに重複させない（cycle-12/F5 の教訓＝過大主張しない）。**本観点は埋まっているセルの妥当性**を見る — 各クラス/処理の対応 基本設計/要件 ID が形式的でなく意味的に整合しているか、また基本設計のコンポーネント→詳細設計のクラス/処理の対応（分割・統合を含め）が妥当か。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各クラス/処理の対応 基本設計/要件 ID が形式的でなく意味的に妥当か、また基本設計コンポーネント→詳細設計クラス/処理の対応（分割・統合・命名を含め）が妥当か | 対応 ID がそのクラス/処理の役割を実際に説明している。基本設計→詳細設計の対応が、コンポーネントの分割/統合の実態と一致している。横断的処理（ログ・監査等）には対応する NFR ID が付く | 整合しない対応の原文（クラス/処理名と対応 ID の行、または基本設計コンポーネントと詳細設計クラスの対応行）を引き、何と何が食い違うかを示す |

> 注（機械判定との分担）: 「対応 基本設計/要件 ID」列が空のクラス/処理の検出は機械判定の担当範囲（孤立設計要素＝スコープクリープ候補・[`../scripts/check_traceability.py`](../scripts/check_traceability.py)）。本観点は ID が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた ID、基本設計→詳細設計の対応が崩れた行）を見る。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **HLD/LLD（基本設計/詳細設計）の境界線そのものは裁定しない。** 「外から観測できるアーキ方式・コンポーネント構成は基本設計／クラス・メソッド・シーケンス等の内部の作り込みは詳細設計」という線引きは IEEE 1016 自身がスコープ外と明言する事項であり、**プロジェクト規約の合意事項**である。方式設計↔詳細設計の境界は [`../principles/responsibility-map.md`](../principles/responsibility-map.md)（方式設計行・詳細設計行）で確定済みであり、これは**データ設計の論理/物理分割（F1）と同型の境界問題を一般化**したものである。本ルーブリックはその確定境界を**前提として**、詳細（処理）側を判定する。境界の妥当性そのものは問わない（参照: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須) 注「アーキテクチャと詳細設計の境界はシステム依存でスコープ外」、決着記録: [CONTRIBUTING.md](../CONTRIBUTING.md) の F1）。
- **「正当な処理設計 vs 不当なコード逐語（ghost document 化）」を分ける一般ヒューリスティックは存在しない。** 同様に「設計レベルに足る粒度 vs 実質空（薄すぎ）」の境界も一意でない。どちらとも決めかねる境界例は、逸脱と断定せず fail-open（pass）に倒して人間に委ねる。判断を盛らない。
- **技術名・SQL は機械で弾かず本ルーブリックで文脈判定する。** 処理仕様ではこれらが正当な記述になりうる（メソッド仕様・性能制約の対象環境・製品名 PostgreSQL/MySQL 等）ため、機械 vocab で一律に弾くと誤爆する（cycle-8 と同方針）。本ルーブリックの観点3 で「SQL 全文の逐語展開（ghost document）か、正当な技術名・設計レベルの記述か」を文脈判定し、読み取れない境界例は fail-open（pass）に倒す。

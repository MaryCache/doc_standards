## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**基本設計（方式設計）**を対象とする。方式設計の核心的な痛みは「外から観測できる方式に留まるべき記述へ、禁止語に当たらない形でコンポーネント内部の作り込み・DB 操作文が侵入する」ことと「技術名が**根拠なく**列挙され解の先取りになる」ことであり、その文字列照合では捕まえられない逸脱を見るのが主眼である。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`アーキテクチャ方式` / `技術選定` / `横断懸念` / `トレーサビリティ`）の欠落・禁止語（`クラス図` / `メソッド仕様` / `シーケンス図`）の出現など、文字列で判定できる項目 |
| 質的（本ルーブリック） | LLM ＋人間 | 禁止語に当たらない形で侵入した内部実装・DB 操作文・根拠なき技術名の列挙・横断懸念の網羅と粒度・トレーサビリティの意味など、文脈判断が要る項目 |

機械判定で済む項目（必須見出しの欠落、禁止語の単純な出現）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。機械 vocab が禁止するのは技術名と誤爆しない内部実装マーカー3語（`クラス図` / `メソッド仕様` / `シーケンス図`）に**限る**。それ以外（禁止語に当たらない形の内部実装・SQL クエリ／DB 操作文・技術名の根拠の有無・横断懸念の粒度）は機械では捕まえられないため、本ルーブリックが担う。

なお技術スタック名・製品名・プロトコル名（および **`SQL`**）は、方式設計では正当な記述になりうる（技術選定は方式設計の核）ため**機械 vocab で弾かず本ルーブリックの文脈判断に委ねる**（P2 訂正版・cycle-4 srs / cycle-7 external-design 踏襲）。とりわけ `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出）。よって**実際の SQL クエリ／DB 操作文の侵入は機械でなく本ルーブリックの観点2が見る**（cycle-8 の設計判断）。一律に弾くと正当な技術選定記述を誤爆するためである（観点2・観点3・§4-D 参照）。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「正当な技術選定・アーキ方式」と「不当な内部実装・解の先取り」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例で迷ったら逸脱と決めつけない。
- **技術スタック名・製品名・プロトコル名・`SQL` という語そのものは逸脱と決めつけない。** 技術選定の核として正当に現れることがあり、その場合は逸脱でない（P2 訂正版）。逸脱になるのはその先（根拠なき列挙、実際の `SELECT ... FROM ...` のような DB 操作文、コンポーネント内部の作り込み）であり、外部契約／方針として必要か単なる内部詳細の先取りかを読み取れないときは fail-open（pass）に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P1/P3 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. ADR リンクの有無・妥当性（S5 委譲の確認）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠は必須・design rationale の記録）。

方式設計で最重要のアーキ判断・技術選定について、その決定根拠が ADR にリンク／採番されているかを見る。ADR リンクなしの重要判断は決定根拠不明であり、responsibility-map（方式設計行）の逸脱判定基準「ADR リンクなし（決定根拠が不明）」に該当する。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 重要なアーキ判断・技術選定の決定根拠が ADR にリンク／採番されているか（`[ADR-0001](...)` 形式で参照され、リンク切れ・番号欠落がないか） | 比較・却下を伴う重要な技術選定・アーキ判断には採番された ADR への参照リンクが付き、本文（技術選定節・トレーサビリティ節備考）から辿れる | ADR リンクが必要なのに欠けている重要判断の原文（例: 却下案つきで比較したのに ADR 参照のない技術選定）を該当節・該当行ごと引く |

> 注（S5 委譲の境界）: ADR の**採番・生成・内容の良し悪し**（却下案が妥当か等）は [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルの責務であり、**本観点はリンクの存在と参照の妥当性のみ**を見る（doc-standards は ADR を生成しない・S5）。ADR の中身評価は ADR スキルおよびレビュースキル（`review-handoff` / `santa-method`）に委ねる。

### 2. 内部実装の leak 検出（SQL クエリ含む）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（方式設計は外から観測できるアーキ方式に限る・内部実装は詳細設計へ）・[P5](../principles/granularity-axis.md#p5-数値精度は工程マーカーである)（厳密値・物理精度は下流工程のマーカー）。

方式設計の最重要 leak 検出。アーキテクチャ方式節・技術選定節・横断懸念節に、**禁止語に当たらない形でコンポーネント内部の作り込み・DB 操作文が侵入していないか**を見る。具体的には、クラス階層・loop・変数名・メソッド単位の処理など外から観測できない内部の作り込み、**および実際の SQL クエリ／DB 操作文（`SELECT ... FROM ...` 等）**である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各節に、禁止語に当たらない形の内部実装（クラス階層・loop・変数名・メソッド単位の処理）や、実際の SQL クエリ／DB 操作文（`SELECT ... FROM ...`・`INSERT ... INTO ...` 等）が侵入していないか | アーキ方式は外から見た責務分割・依存方向・デプロイトポロジに、技術選定は採用技術と根拠に、横断懸念は方針の粒度に留まり、内部の作り込み・DB 操作文は詳細設計／データ設計レシピへ委ねられている | 内部実装・DB 操作文に当たる原文（例: 「在庫数を for ループで減算し」「`SELECT * FROM orders WHERE ...`」のような内部手順・クエリ）を該当節・該当行ごと引く |

> 注（機械判定との分担）: 内部実装マーカーそのもの（`クラス図`・`メソッド仕様`・`シーケンス図`）の単純な出現検出は機械判定（[`../scripts/`](../scripts/) の禁止語）の担当であり、本観点に重複させない。本観点が見るのは、禁止語に当たらない形（クラス階層の自然文・loop・変数名・SQL クエリ）で侵入した内部実装である。
>
> 注（SQL は機械でなく本観点で見る理由）: `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する（cycle-8 で実機検出）。よって `SQL`（DB 操作文／クエリ）は機械 vocab の禁止語に入れず本観点で見る（cycle-8 の設計判断）。製品名としての `PostgreSQL` 等の出現は逸脱でなく、逸脱は実際の DB 操作文（クエリ本文）である。境界例は fail-open（pass）。

### 3. 技術選定根拠（なぜこの技術か・却下案・トレードオフ）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠は必須）。

技術選定節で、技術名が**選定根拠なしに列挙**されていないかを見る。技術名の出現自体は方式設計で正当（技術選定の核）であり機械では弾かない。本観点が見るのは「技術名だけで Why がない」状態 — なぜその技術か・比較した却下案・トレードオフが欠けていれば、根拠なき解の先取りであり逸脱である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 採用技術が選定根拠（なぜそれか・比較した却下案・トレードオフ）なしに列挙されていないか。技術名だけで Why が欠けていないか | 判断の余地がある技術選定に、選定根拠ないし却下案・トレードオフが明示されている（既定指定の技術は「選定の余地なし＋既定の根拠」が明記されている） | 根拠が必要なのに欠けている技術選定の原文（例: 「メッセージング基盤に Kafka」とだけあり選定根拠・却下案の記載がない箇所）を該当節・該当行ごと引く |

> 注（正当な記述は逸脱でない）: 技術名・製品名・プロトコル名の**出現自体は正当**であり機械でも本観点でも弾かない。本観点が問うのは「根拠・却下案の有無」だけである。根拠付きで比較・決定された技術選定は逸脱でない。

### 4. 横断懸念の網羅

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（方式設計は方針レベルの How に限り、実装の How は下流へ）。

横断懸念節で、複数コンポーネントを横断する設計方針（ログ・認証/認可・エラー処理・トランザクション方針など）が**揃っているか**、かつ**方針の粒度に留まり実装詳細に踏み込みすぎていないか**を見る。網羅の欠落と粒度の逸脱の両面を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| ログ・認証/認可・エラー処理・トランザクションなど横断的な設計方針が揃っているか（該当の薄い項目は「該当なし＋理由」が明示され、検討漏れと対象外が区別できるか）。かつ各方針が「方針」の粒度に留まり、実装コード・詳細手順・ライブラリ固有の設定値へ踏み込みすぎていないか | 横断方針が網羅され（薄い項目も「該当なし＋理由」で埋まっている）、各方針が方針レベル（どの境界で・どの方式で・どう正規化するか）に留まり、実装の How は下流へ委ねられている | 欠落／逸脱の原文を引く。欠落なら検討漏れの懸念名（空節）を、粒度逸脱なら方針節に紛れた実装詳細（ライブラリ固有設定値・詳細手順）を該当節・該当行ごと引く |

### 5. トレーサビリティの質（意味的妥当性）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）。

空セルの検出は機械判定（[`../scripts/check_traceability.py`](../scripts/check_traceability.py)＝孤立設計要素〔対応要件 ID 欠落〕の決定論検出）で済む。**本観点は埋まっているセルの妥当性**を見る — 各アーキ判断・技術選定・横断方針の対応要件 ID／NFR ID が形式上の対応ではなく、その判断が実現する内容と**意味的に**整合しているか。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各アーキ判断・技術選定・横断方針の対応要件・NFR ID が形式的でなく意味的に妥当か（判断が実現する内容と、対応 ID が指す機能/品質が一致しているか） | 対応要件・NFR ID がそのアーキ判断/技術選定/横断方針の役割を実際に説明している。機能要件に直接紐付かない横断方針（ログ・監査等）には対応する NFR ID が付く | 整合しない対応の原文（アーキ判断/技術選定名と対応要件・NFR ID の行）を引き、何と何が食い違うかを示す |

> 注（機械判定との分担）: 「対応要件・NFR ID」列が空のアーキ判断/技術選定の検出は機械判定の担当範囲（孤立設計要素＝スコープクリープ候補）。本観点は ID が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた要件/NFR ID）を見る。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **HLD/LLD（方式設計/詳細設計）の境界線そのものは裁定しない。** 「外から観測できるアーキ方式は方式設計・コンポーネント内部の作り込みは詳細設計」という線引きは IEEE 1016 自身がスコープ外と明言する事項であり、**プロジェクト規約の合意事項**である。方式設計↔詳細設計の境界（アーキ方式・コンポーネント構成＝方式設計／クラス・メソッド・シーケンス＝詳細設計）は [`../principles/responsibility-map.md`](../principles/responsibility-map.md)（方式設計行）で確定済みであり、本ルーブリックはその確定境界を**前提として**判定する。これは**データ設計の論理/物理分割（F1）と同型の境界問題を一般化**したもの（F1 はデータ設計に閉じた決着、本件は方式設計全般へ拡張した同型問題）である（参照: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須) 注「アーキテクチャと詳細設計の境界はシステム依存でスコープ外」、決着記録: [CONTRIBUTING.md](../CONTRIBUTING.md) の F1）。
- **ADR との委譲境界は裁定対象でない。** doc-standards は ADR を生成せず、**粒度境界とリンク存在のみ**を提供する（S5）。ADR の番号体系・記録フォーマット・内容評価（却下案が妥当か等）は [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルが所有・採番・生成する source of truth であり、本ルーブリックは ADR の**内容を評価しない**（観点1 はリンク存在と参照妥当性のみ）。
- **「正当な技術選定・アーキ方式 vs 不当な内部実装・解の先取り」を分ける一般ヒューリスティックは存在しない。** どちらとも決めかねる境界例は、逸脱と断定せず fail-open（pass）に倒して人間に委ねる。判断を盛らない。
- **技術名・SQL は機械で弾かず本ルーブリックで文脈判定する。** 方式設計ではこれらが正当な記述になりうる（技術選定の核・製品名 PostgreSQL/NoSQL/MySQL 等）ため、機械 vocab で一律に弾くと誤爆する（P2 訂正版・cycle-4 srs / cycle-7 external-design と同方針）。本ルーブリックの観点2・観点3 で「根拠ある正当な選定か／根拠なき解の先取りか・実装詳細（DB 操作文）への踏み込みか」を文脈判定し、読み取れない境界例は fail-open（pass）に倒す。

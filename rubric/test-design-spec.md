## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**テスト設計仕様（Test Design Specification）**を対象とする。テスト設計仕様の核心的な痛みは「**設計仕様に低レベルケース（具体値）が混入する**」（F1 同型・構造判定）・「**テスト条件が具体値に降りている／抽象として導出されていない**」・「**網羅方針のテスト技法・カバレッジが条件に対し妥当でない／測定不能**」であり、その文字列照合では捕まえられない逸脱を見るのが主眼である。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`テスト条件` / `網羅方針` / `トレーサビリティ`）の欠落・禁止語（テスト条件の非観測マーカー3語: `正しく表示` / `正しく動作` / `適切に処理`）の単純な出現・トレーサビリティ表の空セル〔孤立テスト条件＝対応要件/設計 ID 欠落〕（[`../scripts/check_traceability.py`](../scripts/check_traceability.py)）など、文字列・表構造で判定できる項目 |
| 質的（本ルーブリック） | LLM ＋人間 | 設計仕様への低レベルケース（具体値）の混入・テスト条件が抽象として導出されているか・網羅方針の技法/カバレッジの妥当性・禁止語3語に当たらない言い換えで紛れた測定不能な網羅方針・要件文の構造的転記・トレーサビリティの意味とカバレッジなど、文脈判断が要る項目 |

機械判定で済む項目（必須見出しの欠落、非観測マーカー3語の単純な出現、トレーサビリティ表の空セル）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。ここが見るのは「節はあるが設計仕様に具体値が紛れている」「テスト条件が抽象でなく具体値に降りている」「網羅方針の技法がテスト条件に対し妥当でない／カバレッジが測定不能」「特定語ではなく構造として要件が転記されている」類の、文字列照合・表構造では捕まえられない逸脱だけである。

なお技術スタック名・製品名・`SQL`・ツール名（JUnit 等）は、テスト設計仕様では正当な記述になりうる（テスト条件の対象環境・網羅方針の技法記述）ため**機械 vocab で弾かず本ルーブリックの文脈判断に委ねる**（cycle-8 以降の WF スライス踏襲）。とりわけ `SQL` は製品名 PostgreSQL・NoSQL・MySQL 等の部分文字列であり、部分一致の語彙チェッカーでは技術名を `SQL` ヒットとして誤爆する。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「設計仕様にふさわしい抽象的なテスト条件」と「具体値（低レベルケース）の先取り」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例（テスト条件の例示が具体的すぎるか・ケース具体値の先取りか紛らわしいもの）で迷ったら逸脱と決めつけない。
- 「網羅方針のテスト技法が条件に対し妥当か」「カバレッジが測定可能か」の定量基準は無い（§4-D）。境界例は逸脱と断定せず pass に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P6/P7 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行、またはテスト条件 ID ＋該当要素）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. テスト条件の質（SRS／設計から導出された抽象的テスト項目か）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（要件へトレース可能）・[P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（検証可能性は工程を貫く不変量）。

`テスト条件` 節の各条件が、SRS／設計から導出された**抽象的なテスト項目（高レベルケース）**になっているか。条件が具体値（個々の入力値・期待結果）に降りていないか・抽象のままでも観測へ降ろせる方向で書かれているかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各テスト条件が SRS／設計から導かれた抽象的なテスト項目（高レベルケース）か。具体値（個々の入力値・期待結果）にまで降りていないか。抽象でも「何を確認するか」が観測へ降ろせる方向になっているか（禁止語3語に当たらない言い換えで非観測のまま逃げていないか） | 各テスト条件が抽象的なテスト項目として導出され、対応要件/設計を持ち、観測へ降ろせる方向で書かれている（具体値はケース仕様へ委ねられている） | 具体値に降りているテスト条件の原文（条件 ID ＋該当行）、または非観測で逃げた条件の原文を引く |

> 注（機械判定との分担）: 必須見出し `テスト条件` の**有無それ自体**・非観測マーカー3語の**単純な出現**は機械判定（[`../scripts/`](../scripts/)）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが中身が抽象として導出されていない／具体値に降りている**」「**3語に当たらない言い換え**で非観測のまま逃げている」ケースである。
>
> 注（観点3との分担）: テスト条件が「具体値に降りている」ことは本観点と観点3（F1 同型境界）の双方に関わるが、本観点は**テスト条件節の質**（抽象として導出されているか）を、観点3は**設計仕様全体への低レベルケースの混入**（構造境界）を主眼に見る。重複したら観点3を優先し二重 fail を避ける。

### 2. 網羅方針の質（テスト技法の妥当性・カバレッジの測定可能性）

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（検証可能性は工程を貫く不変量）。

`網羅方針` が、テスト条件をどう網羅するかを**妥当なテスト技法**（同値分割・境界値分析等）と**測定可能なカバレッジ方針**で示しているか。技法が条件に対し妥当か・カバレッジが第三者に同じ達成判定を許す測定可能な目標かを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 網羅方針のテスト技法（同値分割/境界値分析/デシジョンテーブル等）が、対応するテスト条件に対し妥当に選ばれているか。カバレッジ方針が測定可能か——禁止語3語に当たらない言い換え（「網羅的に」「十分にカバー」「ひと通り」等）や、しきい値・率を欠いて達成判定が一意に決まらない方針で逃げていないか | テスト技法が各テスト条件に対し妥当に対応し、カバレッジ方針が観測できる目標（例: 機能カバレッジ 95% 以上・分岐網羅 C1 100%・有効/無効同値類の全網羅）で書かれ、第三者が同じ達成判定に到達できる | 条件に対し技法が不適合な原文（節見出し＋該当行）、または測定不能なカバレッジ方針の原文（例: 「網羅的に確認する」「十分にカバーする」）を引く |

> 注（機械判定との分担）: 必須見出し `網羅方針` の**有無それ自体**は機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが技法が条件に対し妥当でない／カバレッジが測定不能**」ケースである。3語の単純な出現は機械側、3語に当たらない言い換えの曖昧さは本観点（nonfunctional-design が曖昧表現を rubric にした前例と同型）。

### 3. 低レベルケース（具体値）の混入（設計仕様 vs ケース仕様の境界・F1 同型）

参照原則: [P7](../principles/granularity-axis.md#p7--p8-テスト文書の階層と戦略計画の分離検出補助)（テスト文書の階層＝計画→設計仕様→ケース仕様→手順仕様。階層を飛び越えない）。

設計仕様に**個々のテストケースの具体的入力値・期待結果（低レベルケース）**が書かれていないか（それはケース仕様＝[`../waterfall/test/test-case-spec.md`](../waterfall/test/test-case-spec.md) の担当）。設計仕様は「テスト条件＝抽象・どう網羅するか」までであり、1ケースの事前条件・入力値・操作・具体的期待結果・SQL 等はケース仕様へ降ろす。これは **F1（論理/物理）と同型の隣接境界（設計仕様＝抽象 ↔ ケース仕様＝具体値）**である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 設計仕様に個々のテストケースの具体的入力値・期待結果（1ケースの事前条件・入力・操作・観測値・具体的 SQL 等）が混入していないか | テスト条件・網羅方針・トレーサビリティが設計仕様レベル（抽象・技法・カバレッジ・対応関係）に留まり、ケースの具体値はケース仕様へ委ねられている | 低レベルケース（具体値）に当たる原文（例: 「在庫 10 に対し数量 11 を入力したら E-STOCK が返る」のような1ケースの入力値・期待結果・具体的 SQL）を該当節・該当行ごと引く |

> 注（境界は fail-open）: 設計仕様の例示（テスト条件の抽象を伝える最小限の例）と、ケース仕様の具体値の先取りとを分ける一般ヒューリスティックは無い（§4-D）。どちらとも決めかねる境界例は逸脱と断定せず pass に倒す。F1（論理 ER ↔ 物理 ER）が抽象/具体を工程で割るのと同型であり、線引き自体はレシピ本体が引いた境界を前提とする。

### 4. 要件転記アンチパターン（転記か・ID 参照か）

参照原則: [P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（テスト文書は要件を ID 参照する・要件文を転記しない）。

テスト条件やトレーサビリティに要件文（What の文言・Why の説明）が**構造として転記**されていないか。要件は ID で参照されているかを見る。転記は二重管理と矛盾の温床になる（同期負債）。これは test-case-spec／test-plan の要件転記観点と同型である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| テスト条件／トレーサビリティに要件文が**構造として転記**されていないか（特定語ではなく、要件をそのまま写した内容になっていないか）。要件は ID で参照されているか | テスト条件・トレーサビリティが要件を「対応要件/設計 ID」で参照し、要件の文言・理由は写されていない | 要件文が逐語転記された原文（節見出しまたは表行＋該当箇所）を引き、対応する要件 ID を示す |

> 注（機械判定との分担）: 要件転記は**特定の禁止語では弾けない構造の問題**であり、機械語彙（[`../scripts/`](../scripts/) の vocab）の対象外である（レシピ本体の越境 note も「転記は機械語彙では弾かず質的判定に委ねる」と明記）。本観点が転記の検出を専任で担う。非観測マーカーの出現検出（観点1の機械側）とは別物として扱う。
>
> 注（正当な引用との区別）: 設計仕様を読むのに最小限必要な文脈（テスト条件の主題を一言添える等）と、要件文をまるごと写した二重管理とは別である。どちらとも決めかねる境界例は逸脱と断定せず fail-open（pass）に倒す。

### 5. トレーサビリティの質（意味的な紐付けとカバレッジの穴）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（全要素トレース可能）・[P6](../principles/granularity-axis.md#p6-検証可能性は工程を貫く不変量テスト文書は要件を-id-参照する)（要件は ID 参照）。

各テスト条件が対応要件 ID／設計要素に**意味的に**紐付いているか（形式的な対応でなく）。あわせて要件側のカバレッジ（対象要件にテスト条件の穴が無いか）を見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 各テスト条件の「対応要件/設計 ID」が形式的でなく意味的に妥当か（その要件/設計が検証する内容と、テスト条件が実際に確認する内容が一致しているか）。対象要件に、紐付くテスト条件が無い穴（テスト漏れ）が見落とされていないか | 各テスト条件の対応要件/設計 ID が、その条件が何を検証するかを実際に説明している。対象要件がテスト条件でカバーされ、漏れは明示されている | 整合しない対応の原文（テスト条件と対応 ID の行）を引き、何と何が食い違うかを示す。対象なのにテスト条件が無い要件 ID を示す |

> **注（過大主張の禁止・F5 の教訓）**: **対応要件/設計 ID 列の空セルそのものの検出（孤立テスト条件）は機械の [`../scripts/check_traceability.py`](../scripts/check_traceability.py) の担当**であり、本観点に重複させない。本観点は ID が**書かれているが内容が合っていない**ケース（流用・コピペで実態とずれた対応、形式上は埋まっているが意味的に無関係な対応）と、**対象要件側から見たカバレッジの穴**（要件一覧との突き合わせを要する文脈判断）を見る。空セル検出を rubric の仕事として主張しない（cycle-12/F5 の教訓＝「rubric が機械の仕事を主張しない」）。
>
> 注（境界は fail-open）: 紐付けが妥当か流用かが紛らわしい境界例は逸脱と断定せず fail-open（pass）に倒す。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **「設計仕様レベルの正当な記述 vs ケース具体値の先取り」を分ける一般ヒューリスティックは存在しない。** テスト条件の例示がどこまで具体的なら「設計仕様として十分」で、どこからが「ケース仕様の先取り（低レベルケース）」かを分ける一般閾値は無い。境界例（具体的すぎる例示・ケース具体値の混入のどちらとも決めかねるもの）は、逸脱と断定せず **fail-open（pass）**に倒して人間に委ねる。判断を盛らない。これは F1（論理 ER ↔ 物理 ER）が抽象/具体を割るのと同型であり、線引き自体はレシピ本体が引いた境界を前提とする。
- **「網羅方針のテスト技法が条件に対し妥当か」「カバレッジが測定可能か」の定量基準は無い。** どこまで具体的なら十分かは文脈依存である。読み取れない境界例は逸脱と断定せず pass に倒す。
- **テスト文書の階層境界（戦略／計画／設計仕様／ケース仕様／手順仕様）そのものは裁定しない。** この階層は P7／P8（検出補助・機械強制しない）由来であり、各層の責務割当ては規格（IEEE 829／ISO/IEC/IEEE 29119-3／ISTQB v4）に由来する。「どこまでが設計仕様で、どこからがケース仕様／計画か」の線引きはレシピ本体（[`../waterfall/test/test-design-spec.md`](../waterfall/test/test-design-spec.md)）が引いた境界を**前提として**判定する。境界の妥当性そのものは問わない（参照: [P7](../principles/granularity-axis.md#p7--p8-テスト文書の階層と戦略計画の分離検出補助)）。
- **空セルの検出は機械の担当であり rubric は過大主張しない（F5）。** トレース表の空セル（孤立テスト条件）は [`../scripts/check_traceability.py`](../scripts/check_traceability.py) が決定論で検出する。本ルーブリック（観点5）は埋まっているセルの**意味的妥当性とカバレッジの穴**のみを見る（cycle-12/F5 の教訓）。

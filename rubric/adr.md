# ADR 質的判定ルーブリック — アジャイル ADR

> **レイヤー**: 第2層レシピの質的判定（機械判定の補完／本 doc_type では**主判定**）
> **原則参照**: [`../principles/granularity-axis.md`](../principles/granularity-axis.md) が唯一の真実。本ファイルは原則を再定義せず参照する（制約 S3）。
> **責務対照**: [`../principles/responsibility-map.md`](../principles/responsibility-map.md) の**アジャイル責務対照表の ADR 行**を参照（含む＝1 判断につき 1 ADR・Context/Decision/Status/Consequences・却下案の明示／含まない＝trivial な決定〔Prettier 等・可逆で影響小〕・決定済みの再宣言／隣接＝SAD の意思決定層・採番生成は architecture-decision-records スキルに委譲／逸脱＝事後正当化〔承認なし accepted〕・trivial な決定の ADR 化・Why の記述なし）。
> **レシピ本体**: [`../agile/adr.md`](../agile/adr.md)。観点はこのレシピの節（Context / Decision / Status / 却下案 / Consequences / 委譲境界）に揃える。ADR は1つの設計判断を Nygard 形式で永続記録し、**採番・生成・内容評価は [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルに委ねる**。本ルーブリックは ADR の**粒度**（必須節・却下案明示・trivial でない・事後正当化でない）のみを見る。

## このルーブリックの位置づけ

二層チェック（M5）のうち、**機械で判定できないものだけ**を LLM＋人間に回すための雛形である。このルーブリックは**ADR（Architecture Decision Record）**を対象とする。

agile は機械層が薄く **rubric が主判定**である（[`./user-story.md`](./user-story.md) / [`./design-doc.md`](./design-doc.md) と同じ非対称設計 S4）。ADR は design-doc / user-story 同様 **vocab を空にした**——その逸脱（事後正当化〔承認なし accepted〕・trivial な決定の ADR 化・Why の記述なし・Consequences/Context の質）は、いずれも**構造・文脈の判定**であって、特定の禁止トークンの部分一致では原理的に拾えない（`accepted` を禁止語にすると正当な承認状態宣言で誤爆する）。これらが本ルーブリックの担当である。これは [`./acceptance-criteria.md`](./acceptance-criteria.md) が vocab を持つ（Then の曖昧期待結果3語が部分一致誤爆なく拾えた）のとは**非対称**である——vocab の有無は「その doc_type の逸脱が機械で綺麗に拾えるか」で決まり、agile/WF の別ではない。

| 判定方式 | 担い手 | 対象 |
|---|---|---|
| 決定論的（機械） | [`../scripts/`](../scripts/) | 必須見出し（`Context` / `Decision` / `Status` / `却下案` / `Consequences`）の欠落など、文字列で判定できる項目。とりわけ**`却下案` 節の欠落（Why の片側欠落）の検出**が機械層の主仕事。**vocab は空（forbidden 無し）＝禁止語チェックは pass を返すだけで実質的な検出はしない。** ADR は**トレース節を持たない**（トレースは Context 内）ため [`../scripts/check_traceability.py`](../scripts/check_traceability.py) は **skipped**（空セル検出は ADR では発生しない）。 |
| 質的（本ルーブリック・**主判定**） | LLM ＋人間 | 却下案の質（Why の両側が実際の比較か・事後正当化でないか）・trivial な決定の ADR 化（可逆で影響小を ADR 化していないか）・Consequences の質（帰結・トレードオフ・影響範囲が書けているか）・Context の質と Status（なぜこの判断が必要か・driven by トレースが Context 内にあるか・承認なし accepted でないか）・委譲境界（S5）——いずれも文脈・構造の判断が要る項目。**ADR はこの質的判定が主であり、機械層は薄い（必須見出し、とりわけ却下案欠落のみ）。** |

機械判定で済む項目（必須見出しの欠落、とりわけ `却下案` 節の有無）は**本ルーブリックに重複させない**。決定論的な判定は [`../scripts/`](../scripts/) が担い、質的な判定は本ルーブリックが担う。ここが見るのは「却下案の節はあるが採用案ありきの事後正当化」「trivial な決定を ADR 化している」「Consequences が薄くトレードオフが書けていない」「Context に driven by が無く承認も得ていない accepted」類の、文字列照合では捕まえられない逸脱だけである。

> **空セル検出は無関係（ADR 固有・F5 と同方針）**: ADR は**トレース表を持たない**（トレースは Context 内・[`../agile/adr.md`](../agile/adr.md) の「トレースは Context 内に書く」節）。よってトレース表の空セル（孤立要素）検出は ADR では**発生しない**（check_traceability は skipped）。本ルーブリックも空セル検出を主張しない（acceptance-criteria / design-doc の rubric が空セル検出を機械の担当として重複させないのと同方針＝cycle-12/F5 の教訓「rubric が機械の仕事を主張しない」を、トレース節そのものが無い ADR では「空セルは検出対象外」として徹底する）。本ルーブリックが Context 内のトレースで見るのは driven by が**書かれているか・意味的に妥当か**（観点4）であって、表の空セルではない。

## 運用規則（全観点に共通・例外なし）

### fail-open（判断不能は pass に倒す）

LLM が逸脱か否かを判断できない場合は、**逸脱と断定せず pass 扱いにして人間に委ねる**。安全側に倒す。

- 「却下案が実際の比較か事後正当化か」を分ける一般ヒューリスティックは存在しない（§4-D 参照）。境界例で迷ったら逸脱と決めつけない。
- 「ADR 化すべき判断か（trivial か非自明か）」「Consequences が十分にトレードオフを書けているか」の定量基準は無い（§4-D）。境界例は逸脱と断定せず pass に倒す。
- pass に倒すときは「判断不能のため人間判断へ」と理由を残し、握りつぶさない。
- このルーブリックは検出**補助**である。原則層の検出補助（P2/P4 等）と同じく、機械強制の自動拒否には使わない。

### 根拠抜粋必須（抜粋なき判定は無効）

逸脱（fail）と判定する場合は、**該当箇所の原文抜粋（引用）を必ず添える**。抜粋のない判定は無効とし、採用しない。

- 抜粋は「どの節の・どの行か」が分かる単位で引く（節見出し＋該当文／該当行）。
- 抜粋が原文と一致しない（要約・言い換え）判定も無効。原文をそのまま引く。
- pass の場合は抜粋不要だが、判断不能で pass に倒したときはその旨を記す。

## 観点

各観点は [判定問い / 合格基準 / 根拠抜粋の出し方] の3列で示す。合格基準を満たさず、かつ判断可能なときだけ fail とし、根拠抜粋を添える。判断不能は fail-open（pass）。

### 1. 却下案の質（Why の両側か・事後正当化でないか）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠は必須・design rationale の記録）。

`却下案` 節がある場合（節の有無それ自体は機械判定の担当）、それが**事後正当化**（採用案ありきで都合よく付けた却下理由）でなく、**Why の両側**（採用理由と却下理由が実際の比較）になっているか。採用案の利点だけが並び、却下案の却下理由が「採用案を引き立てるための後付け」になっていれば逸脱である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 却下案が事後正当化でなく実際のトレードオフ比較になっているか（採用理由と却下理由の両側が、実際に比較した内容として書かれているか）。採用案ありきで都合よい却下理由を後付けしていないか | 各代替案に、実際に比較した却下理由が伴い、採用案にも採用理由が書かれている（Why の両側が成立し、却下理由が後付けの空虚な一般論でない） | 事後正当化に見える原文（採用案ありきで都合よい却下理由・空虚な却下理由の該当行）を引く。Why の片側しか書かれていない（却下理由が実質無い）原文を引く |

> 注（機械判定との分担）: `却下案` 節の**有無それ自体**は機械判定（[`../scripts/check_headings.py`](../scripts/check_headings.py)）の担当であり、本観点に重複させない。本観点が見るのは「**節はあるが中身が事後正当化／Why の片側**」ケースである。
>
> 注（内容の正否は評価しない・S5）: 却下案が**技術的に妥当か**（その代替を却下した判断が正しいか）は本ルーブリックの担当でない。それは [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルおよびレビュースキル（`review-handoff` / `santa-method`）の責務である。本観点は「Why の両側が実際の比較として書かれているか」という**粒度・形式**だけを見る。
>
> 注（境界は fail-open）: 「事後正当化か実際の比較か」を分ける一般ヒューリスティックは無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。

### 2. trivial な決定の ADR 化（可逆で影響小を ADR にしていないか）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠の記録は非自明な判断に対して行う）。

ADR が **trivial な決定**（Prettier 等・可逆で影響小・決定済みの再宣言）を記録していないか。責務対照表の「含まない＝trivial な決定」「逸脱＝trivial な決定の ADR 化」を質的に判定する。ADR は1判断1記録で、影響範囲・不可逆性のある非自明な判断に限る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| この ADR が trivial な決定（可逆で影響小・整形ルール等）や決定済みの再宣言を記録していないか。Context が薄く（非自明な背景が無く）ADR を要しない判断を ADR 化していないか | 記録された判断が非自明（影響範囲があり・容易に巻き戻せない）であり、Context にその非自明性が読み取れる。決定済み方針の焼き直しでない | trivial さが読み取れる原文（可逆で影響小・整形ルール等の該当行）を引く。Context が薄く ADR を要しない兆候（非自明な背景の不在）を示す |

> 注（境界は fail-open）: 「trivial か非自明か」「ADR を要するか」を分ける一般ヒューリスティックは無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。ADR を起こすこと自体の可否を機械的に裁定しない。

### 3. Consequences の質（帰結・トレードオフ・影響範囲）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠＝判断の帰結まで含めて記録する）。

`Consequences` 節が、判断の**帰結とトレードオフ**を書けているか。良い帰結だけでなく悪い帰結（トレードオフ）・この判断が及ぼす影響範囲（後続判断・呼び出し側に移る責務等）が書かれているかを見る。Consequences が「良い帰結だけ」「該当なし」で埋まっていれば、判断の代償を直視していない逸脱である。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| Consequences が良い帰結だけでなくトレードオフ（悪い帰結・代償）と影響範囲（後続判断・移る責務）を書けているか。"特になし"・良い帰結のみで判断の代償を直視していないことはないか | Consequences に良い帰結とトレードオフ（代償）の両面が書かれ、判断の影響範囲（後続・呼び出し側）が読み取れる | トレードオフを欠いた（良い帰結のみ・"特になし"の）Consequences の原文（節見出し＋該当行）を引く |

> 注（境界は fail-open）: 「トレードオフが十分に書けているか」の定量基準は無い（§4-D）。決めかねる境界例は逸脱と断定せず pass に倒す。

### 4. Context の質と Status（driven by トレース・承認なし accepted でないか）

参照原則: [P2](../principles/granularity-axis.md#p2-要件は-whatwhyhow-は原則排除正当な制約は例外)（What/Why の記述）・[P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（トレース可能）。

`Context` が「**なぜこの判断が必要か**」を書け、**この判断が driven された要求/設計（対応 ID・user-story・Design Doc）が Context 内に書かれている**か（ADR はトレース表を持たず、トレースは Context 内＝[`../agile/adr.md`](../agile/adr.md)）。あわせて Status が**事後正当化（承認なしの accepted）**になっていないか——承認を得ずに決定済み（accepted）として記録していないかを見る。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| Context が「なぜこの判断が必要か」を書け、driven 元（対応する要求/user-story/Design Doc）が Context 内に書かれているか。Status が承認なしの accepted（事後正当化）になっていないか（承認プロセスを経ずに決定済みとして記録していないか） | Context に非自明な背景と driven 元（トレース）が書かれ、Status が実際の承認状態を正直に表している（承認なしの accepted でない） | driven 元（トレース）を欠いた Context の原文（節見出し＋該当行）を引く。承認を経ていないのに accepted とした Status の原文を引く |

> 注（トレースは Context 内・空セル検出は無関係）: ADR は**トレース表を持たない**（独立トレース節を設けない）。本観点が見るのは Context 内に driven 元が**書かれているか・意味的に妥当か**であって、**表の空セルではない**（空セル検出は ADR では発生しない＝check_traceability は skipped。§4-D 参照）。
>
> 注（境界は fail-open）: 「driven 元が十分に書かれているか」「承認を経たか」を読み取れない境界例は逸脱と断定せず pass に倒す。

### 5. 委譲境界（S5・採番/生成/内容評価はスキルの責務）

参照原則: [P4](../principles/granularity-axis.md#p4-設計は要件へ全要素トレース可能設計根拠は必須)（設計根拠の記録は委譲先が所有）。

本ルーブリックが ADR の**粒度**（必須節・却下案明示・trivial でない・事後正当化でない）のみを見ており、**ADR の採番・生成・内容評価（却下案が技術的に妥当か・決定が正しいか）に踏み込んでいない**ことを、判定者自身が守るための観点である。本スライス最大の肝（二重定義回避）を rubric 運用に焼き込む。

| 判定問い | 合格基準 | 根拠抜粋の出し方 |
|---|---|---|
| 判定者が ADR の**内容の正否**（却下案が技術的に妥当か・決定が正しいか・採番が正しいか）を評価しようとしていないか。本ルーブリックの判定が**粒度境界**（必須5節・却下案の明示・trivial でない・事後正当化でない）に留まっているか | 判定が粒度境界のみに限られ、ADR の採番（ADR-NNNN）・記録の生成・内容の技術的妥当性には踏み込まない（それらは architecture-decision-records スキル／レビュースキルの責務） | （これは判定者の自己点検観点であり、ADR 本文の逸脱抜粋ではなく、判定が内容評価へ越境していないかを確認する。越境した判定はその判定文ごと無効とする） |

> 注（委譲分担・二重定義回避）: doc-standards は ADR の**粒度境界**を定義し、`architecture-decision-records` スキルは**採番・生成・内容評価**を所有する（S5）。Design Doc / 方式設計が ADR を**リンク委譲する側**（リンク存在のみ確認）であったのと対をなし、ADR スライスは ADR の**粒度を定義する側**である。両者で役割を割って二重定義を避ける。ADR の内容の良し悪し（却下案が妥当か等）は本ルーブリックの担当でない。

## §4-D の境界注意（このルーブリックが裁定しないこと）

- **「実際の比較 vs 事後正当化」「trivial vs 非自明」を分ける一般ヒューリスティックは存在しない。** 却下案が実際に比較したトレードオフか採用案ありきの後付けか、判断が ADR を要する非自明さか trivial かは文脈依存である。読み取れない境界例は逸脱と断定せず **fail-open（pass）**に倒して人間に委ねる。判断を盛らない。
- **「ADR を起こすべきか（trivial か非自明か）」の線引きそのものは裁定しない。** 「trivial な決定は ADR 化しない」という境界は責務対照表（ADR 行）が引いた合意事項であり、本ルーブリックはその確定境界を**前提として**判定する。境界の妥当性そのものは問わない。
- **ADR の内容評価・採番・生成は裁定対象でない（S5・二重定義回避・本スライス最大の肝）。** doc-standards は ADR を生成・採番せず、**粒度境界のみ**を提供する。ADR の番号体系（ADR-NNNN）・記録フォーマット・内容評価（却下案が技術的に妥当か・決定が正しいか）は [`architecture-decision-records`](../principles/responsibility-map.md#3-既存スキル委譲表) スキルが所有・採番・生成する source of truth であり、本ルーブリックは ADR の**内容を評価しない**（観点1〜4 は粒度・形式のみ、観点5 は判定者が内容評価へ越境しないことの自己点検）。Design Doc / 方式設計の ADR リンク委譲（リンク存在のみ確認する側）と対をなす（こちらは ADR の粒度を定義する側）。
- **空セルの検出は ADR では発生しない（トレース節が無い・F5 の徹底）。** ADR はトレース表を持たず（トレースは Context 内）、[`../scripts/check_traceability.py`](../scripts/check_traceability.py) は skipped を返す。本ルーブリックは空セル検出を主張しない（cycle-12/F5「rubric が機械の仕事を主張しない」を、トレース節そのものが無い ADR では「空セルは検出対象外」として徹底する）。観点4 は Context 内の driven by トレースの**意味的妥当性**を見るのであって、表の空セルではない。
